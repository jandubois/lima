## Executive Summary

This PR adds `networks[].guestToGuest`. With it set, a boot script reads the vzNAT subnet and gateway from the guest's lease and hands a route via the host to systemd-networkd, NetworkManager or Alpine's dhcpcd. The Go wiring, validation and docs are right. Two things in the script need fixing. It removes networkd drop-ins only when the option is off everywhere, so a rename or partial disable leaves a stale route. And its timeout warning blames DHCP when wicked is the cause.

## Important Issues

I1. **Stale networkd drop-ins stay after an interface rename or a partial disable** — `pkg/cidata/cidata.TEMPLATE.d/boot.essential.Linux/30-guest-to-guest-route.sh:18-33` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```sh

		if [ -e "${f}" ]; then

```

The script removes its drop-ins only when the option is off everywhere. The drop-in directory follows the network file, and netplan names that file after the interface. So two config changes leave a stale route until someone deletes the file:

- A network inserted ahead of vzNAT renames vzNAT's interface from lima0 to lima1. networkd then applies lima0's old drop-in, an onlink route to the vzNAT subnet at metric 99, to the new lima0.
- With the option on lima0 and lima1, turning it off for lima1 keeps lima1's route.

NetworkManager and Alpine are unaffected, because cloud-init and the script rewrite their config on every boot.

S1. **`retry` ignores the line-count assertion on every attempt but the last** — `hack/bats/extras/vz-guest-to-guest.bats:60` [Claude Opus 5.5]

```bash
    run -0 grep 'proto static' <<<"${output}"
```

`retry` calls the function as `if "$@"` (`hack/bats/helpers/load.bash:90`), and bash turns errexit off inside a function that runs in a condition. The first test calls the function directly, so it is unaffected.

## Design Observations

### Concerns

- **(in-scope)** Failures show up only in the guest's boot log. That covers the script's two warnings (lines 83 and 114) and a `set -e` exit on `networkctl reload` or `nmcli device reapply`. `boot.sh` turns a failing script into a warning and still writes `lima-boot-done`, so the host doesn't tell a user on an unsupported guest that the option did nothing. Every other boot script behaves the same way, and the docs name the unsupported case. [Claude Opus 5.5]

**Outcome:** Declined. Every boot script reports this way, `limactl start --progress` shows the warning, and the docs name the unsupported guest.

### Strengths

- The script hands the route to the guest's own network service, so the service restores it after a reconfigure, a renewal or a link bounce, without a watcher. [Codex GPT 6 Astra, Gemini 3.5 Flash]
- The script reads the subnet in the guest, so it works whichever /24 macOS picks. [Codex GPT 6 Astra, Gemini 3.5 Flash]
- The script rewrites the networkd drop-in, and reloads networkd, only when the content changes, so an ordinary boot doesn't reconfigure lima0. [Claude Opus 5.5]
- `networkctl status` finds the network file instead of assuming netplan's name, and the script falls through to NetworkManager when networkd reports `n/a`. [Claude Opus 5.5]
- Both `networks[]` merge paths copy the new field, and the qemu driver resets a `false` value to nil on a copy of each network entry, so an instance doesn't warn about the field. [Claude Opus 5.5, Codex GPT 6 Astra]

## Acknowledged Limitations

- **One guest in the BATS extra (from the #5826 review).** GitHub's macOS runners lose contact when two hardware-accelerated guests run at once. Do not re-suggest a test that starts two vz guests.
- **openSUSE Leap 15.6 (wicked) is unsupported**; the PR body, the docs and the default template say so.
- **Alpine with the option turned off.** A lease that arrives before the script runs lets the old hook re-add the route for that boot. The author measured the script running before the lease in 7 of 7 boots.
- **Checked and not defects; do not re-suggest:**
  - A QEMU or krunkit guest never boots with a vzNAT entry. Both drivers reject it at start with "invalid network spec", so the script never waits there for a missing vzNAT interface.
  - cloud-init re-renders the network config on every boot, plain mode included, because Lima writes a new instance-id per start (`pkg/cidata/cidata.go:210`). So a NetworkManager route doesn't outlast a boot that turns the option off.
  - Lima's `network-config` doesn't set any route, so `ipv4.routes` doesn't replace any route that a user configured through cloud-init.
  - Every boot script reads `LIMA_CIDATA_*` bare under `set -eu`, and the `lima.env` in the same cidata always defines the variable.
  - The subnet arithmetic runs in 64 bits in every `/bin/sh` on a supported guest, so the first octet doesn't need a mask.

###### Design Observations

###### Concerns

- **Dynamic lease polling delay during guest boot** `(in-scope)`: In `30-guest-to-guest-route.sh:72-81`, the script polls up to 60 seconds (600 iterations at 0.1s sleep) waiting for `CIDR` and `GATEWAY` on `${INTERFACE}` before checking whether systemd-networkd or NetworkManager manages the link. On systems with alternative or slow-to-configure network stack managers (such as openSUSE Leap 15.6 with wicked), the script blocks for a full 60 seconds during boot before warning that the manager is unsupported. Checking for manager support (`systemctl is-active systemd-networkd || systemctl is-active NetworkManager`) before entering the sleep loop would fail fast and eliminate the 60-second boot stall on unsupported network stacks.

###### Strengths

- **Dynamic subnet and gateway discovery**: Abandoning hardcoded `192.168.64.0/24` in favour of querying DHCP leases accommodates host-dependent subnets assigned by macOS Virtualization framework (such as `192.168.65.0/24` on GitHub Actions runners).
- **Service-native route persistence**: Writing drop-in files for systemd-networkd, connection routes for NetworkManager, and hooks for dhcpcd ensures routes survive interface reconfigurations and DHCP renewals without requiring a long-running guest-agent watcher.
- **Metric ordering**: Automatically computing metric as `network.Metric - 1` guarantees that the host-routed subnet route wins over the kernel's connected link route.
