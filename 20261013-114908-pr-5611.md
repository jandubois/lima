## Executive Summary

The PR routes the omap and filesystem B-tree walks in `pkg/apfs` through a validated node view, so crafted key and value offsets now return errors where they used to panic. One case in that class still panics: an internal node with zero keys, because every walk reads entry 0's child pointer when no key precedes the target. A short check in `parseBTreeNode` closes it. The suggestions cover a misnamed test case, comments about removed code, and untested filesystem-walk guards.

## Important Issues

I1. **An internal node with zero keys still panics in all three walks** — `pkg/apfs/chown.go:441-443` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	if n.keyAreaStart > n.valueAreaEnd || n.nkeys > tspLen/entrySize {
		return nil, errors.New("b-tree node table space is out of range")
	}
```

This check accepts `nkeys == 0` with any table-space length. Each walk's internal-node branch starts from `childIdx := 0` and calls `node.tocEntry(childIdx)` even when its key loop never ran (`omapLookup` line 379, `lookupDirEntry` 674, `chownInode` 812). With no keys and an empty table near the end of the block, that read indexes past the block. A corrupted volume omap in a real image reaches the same panic through `Chown`.

The merge-base panics here too, so this is a gap. But the PR exists to close this panic class, and its new `btreeNode` and `tocEntry` docs (lines 393-397 and 448) promise what this node breaks.

## Suggestions

S1. **Test case `root-smaller-than-info` tests an ordinary root leaf** — `pkg/apfs/chown_test.go:155` [Claude Opus 5.5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
		{"root-smaller-than-info", btnodeRoot | btnodeLeaf | btnodeFixedKVSize, 0, 0, 0, true},
```

The case runs on the shared 4096-byte container and expects success, so it never reaches the `valueAreaEnd < btreeInfoSize` guard at `chown.go:425`. No real container reaches that guard either, because `openContainer` rejects block sizes below 4096 (line 100). A reader of the test list will think the guard is tested.

The fixture comment at `chown_test.go:202` has a related slip. It calls `objectTypeBTreeNode` (0x02) a "non-root B-tree node", while `verifyBTreeNodeType`'s doc (`chown.go:486-488`) names 0x02 the root type, `OBJECT_TYPE_BTREE`. The constant's misleading name predates the PR (`types.go:21`).

Fix: rename the case `empty-root-leaf`, and describe the line-202 node as one without `BTNODE_ROOT`, or store type `0x03` there.

S2. **Comments describe the code that this PR removed** — `pkg/apfs/chown.go:767-770` [Claude Opus 5.5]

```go
				// Found the inode. Validate before writing. valueOffset also
				// rejects a vOff that would underflow valueAreaEnd-vOff, which
				// the old c.blockSize check (computed in wrapping uint32
				// arithmetic) could let through.
```

"The old c.blockSize check" names code that is gone from the merged tree, so a later reader has nothing to compare it with. The test comment at `chown_test.go:168-171` ("the old chownInode guard") does the same.

Fix: state only the current property, for example "valueOffset rejects a vOff past the value area, so the subtraction cannot wrap", and put the history in the commit body.

S3. **No test trips the filesystem walks' new guards** — `pkg/apfs/chown.go:771-774` [Claude Opus 5.5]

```go
				valStart, ok := node.valueOffset(vOff, inodeGroupOff+4)
				if !ok {
					return fmt.Errorf("inode %d value exceeds block boundary", inodeNum)
				}
```

The PR names this guard as its motivating case, yet only `omapLookup` gets a crafted-node test. I disabled this check and the `lookupDirEntry` leaf value check at line 646, and `go test -skip TestChownIntegration ./pkg/apfs/` still passed. A regression here would surface as a loud panic on a crafted image, so the test is optional.

Fix: add a `chownInode` test built like `TestOmapLookupRejectsCraftedNode`, with a leaf whose inode key matches and whose `v_off` is 60000, and assert the error "value exceeds block boundary".

S4. **The omap test accepts any of the walk's range errors** — `pkg/apfs/chown_test.go:224` [Claude Opus 5.5]

```go
	assert.ErrorContains(t, err, "out of range")
```

Five errors that `omapLookup` can now return contain "out of range". They come from the leaf key, leaf value, internal key and child pointer checks, and from `parseBTreeNode`'s table-space check. `TestOmapLookupRejectsCraftedNode` means to pin the value-offset underflow, but a fixture that tripped the header or key check first would pass it too.

Fix: assert `"omap leaf value out of range"`.

S5. **One new test uses `t.Error` in a file that uses `assert`** — `pkg/apfs/chown_test.go:175-177` [Gemini 3.5 Flash]

```go
	if _, ok := n.keyOffset(10, 8); !ok {
		t.Error("keyOffset rejected an in-range key")
	}
```

`TestBTreeNodeOffsetsRejectOutOfRange` checks each result with `if ... { t.Error(...) }`, while every other test in `chown_test.go` uses `gotest.tools/v3/assert`.

Fix: use `assert.Assert(t, ok, ...)` for the booleans and `assert.Equal` for the offset.

## Design Observations

### Concerns

- **(future) A B-tree cycle hangs every walk** [Claude Opus 5.5]. `omapLookup`, `lookupDirEntry` and `chownInode` loop with `for {}` over child pointers read from the image, as they did at the merge-base, and nothing bounds the depth. An internal omap node whose one child pointer names its own block kept `omapLookup` running past a 3-second timeout in a probe against the reviewed code. The vz driver's `CreateDisk` (`pkg/driver/vz/vz_driver_darwin.go:411`) reaches these walks through `macos.Patch` and `Chown`, so it would stall with no error. Requiring each child's `btn_level` (`btnLevelOff`, already in `types.go`) to be one below its parent's, and level 0 exactly at the leaves, bounds the walk. This belongs in its own issue.
- **(in-scope) `parseBTreeNode` sizes the node from `c.blockSize` instead of `len(blk)`** [Claude Opus 5.5]. The view's bounds guarantee holds only because `readBlock` allocates exactly `c.blockSize` bytes. Deriving `valueAreaEnd` from `len(blk)` would make the guarantee local to the type and drop the `container` receiver.
- **(future) The accessors ignore the stored key and value lengths** [Gemini 3.5 Flash]. `tocEntry` drops `k.len` and `v.len` from `kvloc_t`, so the accessors check only the fixed sizes that each walk reads. That suffices to prevent panics; checking the stored lengths would also catch inconsistent records.

### Strengths

- One parse step now feeds all three walks, so the header decoding exists once, and every later read goes through an accessor that returns `ok`. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]
- `valueOffset` checks `vOff > valueAreaEnd` before it subtracts, which removes the wrapping arithmetic from the former `chownInode` guard. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

## Acknowledged Limitations

- `compareDrecKey` requires 12 bytes before it compares the 8-byte key header (`chown.go:557`). Do not re-suggest narrowing that to 8 bytes. Each key in an internal node has an 8-byte child value in the value area at the block's tail, so a valid key ends at least 8 bytes before `valueAreaEnd`, and the 12-byte bound never rejects one.
- `drecName` returns `""` when a name field runs past the node, so a malformed name reads as a non-match instead of an error. Its doc comment (`chown.go:691-694`) states this; do not re-suggest a distinct error.

I1. **Internal node with zero keys still panics in `tocEntry(childIdx)`**: `pkg/apfs/chown.go:379` (important, gap)

```go
		// Read child pointer (physical address, 8 bytes).
		_, vOff := node.tocEntry(childIdx)
```

Each internal-node path starts with `childIdx := 0` (lines 360, 659, 796) and calls `tocEntry(childIdx)` even when `nkeys == 0` (lines 379, 674, 812). The merge-base panicked here too, so this is a gap rather than a regression. It is still part of the panic class the PR says it closes.
