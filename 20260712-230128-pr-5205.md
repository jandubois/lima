## Executive Summary

The PR detects whether the selected `ssh.exe` is Cygwin-based by looking for a
sibling `cygpath.exe`, converts paths to that toolchain's form, and adds an
in-process drive-letter fallback so a missing `cygpath` no longer hard-fails
`limactl create`. The detection is the right design. The pairing is incomplete:
`SSHOpts` still converts `ControlPath` through PATH-global `cygpath`,
`ssh-keygen` still resolves off bare `PATH`, and the new fallback fires on every
`cygpath` error rather than on a missing binary alone.

All three reviewers examined all five changed files. Findings cluster in two
themes: incomplete toolchain pairing (I1, I2) and a fallback that degrades
silently (I3). Gemini's sole Critical was a fabrication and is dropped.

## Important Issues

I1. **`SSHOpts` converts `ControlPath` with PATH-global `cygpath`** — `pkg/sshutil/sshutil.go:555` [Codex GPT 5.5, Claude Opus 4.8]

```go
	if runtime.GOOS == "windows" {
		controlSock, err = ioutilx.WindowsSubsystemPath(ctx, controlSock)
		if err != nil {
			return nil, err
		}
		controlPath = fmt.Sprintf(`ControlPath='%s'`, controlSock)
	}
```

`SSHOpts` receives `sshExe` (line 544) and forwards it to `CommonOpts` (line
549), whose `identityFileEntry` now converts through `PathForSSH`. Line 555 was
left on the PATH-global converter, so the identity file and the control socket
can be formatted for two different toolchains. On a native-OpenSSH host with no
`cygpath`, the new fallback (I3) turns this into `/c/Users/.../ssh.sock` — a
Cygwin-form path handed to a native `ssh` that reads it as a drive-relative
path.

Lima's own bookkeeping compounds it: `IsControlMasterExisting`
(`sshutil.go:502`), `IsControlMasterRunning` (`sshutil.go:514`), and
`RemoveStaleControlMaster` (`sshutil.go:536`) all stat the *native*
`filepath.Join(instDir, filenames.SSHSock)`, so Lima and `ssh` would never agree
on the socket.

Fix:

```diff
 	if runtime.GOOS == "windows" {
-		controlSock, err = ioutilx.WindowsSubsystemPath(ctx, controlSock)
+		controlSock, err = PathForSSH(ctx, sshExe, controlSock)
 		if err != nil {
 			return nil, err
 		}
```

I2. **Key path is converted for the selected toolchain, then handed to a PATH-resolved `ssh-keygen`** — `pkg/sshutil/sshutil.go:290` [Codex GPT 5.5, Claude Opus 4.8]

```go
			keygenCmd := exec.CommandContext(ctx, "ssh-keygen", "-t", "ed25519", "-q", "-N", "",
				"-C", "lima", "-f", privPath)
```

Line 285 formats `privPath` for the `sshExe` that `NewSSHExe` selected; line 290
executes whichever `ssh-keygen` PATH resolves first. The two diverge on the very
paths this PR adds. `NewSSHExe` returns early for the `SSH` env var (line 60)
and can fall back to `%SystemRoot%\System32\OpenSSH\ssh.exe` (line 103), a
directory that need not sit on PATH at all. So `SSH=C:\Program
Files\Git\usr\bin\ssh.exe` on a host whose PATH carries native OpenSSH yields
`/c/Users/...` from `PathForSSH`, which native `ssh-keygen` then writes to the
wrong location.

The commit subject promises exactly this ("pair its companion tools"), and
`pkg/copytool/scp.go:24` repeats the shape with `exec.LookPath("scp")`.

Fix: resolve the companion from the directory of the selected `ssh`, falling
back to PATH only when the sibling is absent. Shape the helper so the `scp` call
site can adopt it when `limactl copy` lands.

I3. **The native fallback fires on every `cygpath` error, not on a missing binary** — `pkg/ioutilx/ioutilx.go:68` [Claude Opus 4.8, Codex GPT 5.5]

```go
	out, err := exec.CommandContext(ctx, cygpathExe, filepath.ToSlash(orig)).CombinedOutput()
	if err == nil {
		return strings.TrimSpace(string(out)), nil
	}

	logrus.WithError(err).Debugf("cygpath unavailable for %#q (output: %#q), attempting native conversion", orig, strings.TrimSpace(string(out)))
```

Every failure now degrades to the hand-rolled conversion: a non-zero exit, a
broken Cygwin install, or a cancelled context. A cancelled context therefore
yields a successful conversion rather than an error. Worse, the fallback's
`/c/...` formula is the MSYS2 and Git-for-Windows convention, while stock Cygwin
maps `C:\` to `/cygdrive/c/` and any `fstab` can remap it — so on a host that
*has* an authoritative `cygpath`, a transient failure silently substitutes a
path that resolves elsewhere. The Debug-level message also claims "cygpath
unavailable" for a `cygpath` that ran and failed.

Codex rated this a Suggestion and Claude an Important; the silent substitution of
a wrong path on Cygwin hosts settles it as Important.

Fix: fall back only when the binary is genuinely absent, and return the error
otherwise.

```diff
 	if err == nil {
 		return strings.TrimSpace(string(out)), nil
 	}
+	if !errors.Is(err, exec.ErrNotFound) && !errors.Is(err, fs.ErrNotExist) {
+		return "", fmt.Errorf("failed to run %#q on %#q: %#q: %w", cygpathExe, orig, strings.TrimSpace(string(out)), err)
+	}
```

I4. **`SftpServerForSSH` and `IsSSHCygwin` are exported with no caller** — `pkg/sshutil/sshutil.go:205` [Claude Opus 4.8, Codex GPT 5.5]

```go
func SftpServerForSSH(ctx context.Context, sshExe SSHExe) string {
	if runtime.GOOS != "windows" || sshExe.Exe == "" {
		return ""
	}
	if cygpathExe, ok := cygpathForSSH(sshExe); ok {
		out, err := exec.CommandContext(ctx, cygpathExe, "-w", "/usr/lib/ssh/sftp-server").Output()
```

Neither symbol has a call site anywhere in the tree. `SftpServerForSSH` spans
~35 lines and shells out to `cygpath -w`; its contract ("Returns `""` … leaving
the caller to fall back to its library's auto-detection") cannot be exercised
without the reverse-sshfs consumer, which the PR description defers to a

setting `OpensshSftpServerBinary`. `IsSSHCygwin` (line 138) is a one-line
wrapper over `cygpathForSSH`.

Fix: land both in the follow-up that consumes them. If they must ship now, add
Windows unit tests and fold the duplicated resolution into one helper (S3).

## Suggestions

S1. **`"input is UNC path"` mislabels most inputs that reach it** — `pkg/ioutilx/ioutilx.go:95` [Claude Opus 4.8]

```go
	return "", fmt.Errorf("cannot convert %#q to a Cygwin-style path: input is UNC path", orig)
```

The branch catches every absolute path whose `VolumeName` is not exactly `X:` —
a UNC path, but also an extended-length path (`\\?\C:\foo`, whose `VolumeName`
is `\\?\C:`). The test at `pkg/ioutilx/ioutilx_windows_test.go:33` asserts only
the shared `"cannot convert"` prefix, so the mislabel stays invisible.

Fix: name what the input lacks — `"input has no drive letter"` — and merge the
two error returns into one message.

S2. **The native-install fallback skips the completeness check** — `pkg/sshutil/sshutil.go:102` [Claude Opus 4.8]

```go
	nativeSSH := filepath.Join(systemRoot(), "System32", "OpenSSH", "ssh.exe")
	if _, err := os.Stat(nativeSSH); err == nil {
		return nativeSSH
	}
```

The PATH walk rejects any directory whose `ssh.exe` lacks `scp.exe` or
`ssh-keygen.exe` (line 95), but the native fallback returns `ssh.exe` unchecked.
Reusing `missingSiblings` here costs one line and matters more once I2 reads the
companion tools from that same directory.

Fix: guard the return with `len(missingSiblings(filepath.Dir(nativeSSH), "scp.exe", "ssh-keygen.exe")) == 0`.

S3. **`SftpServerForSSH` duplicates the resolution logic in `cygpathForSSH`** — `pkg/sshutil/sshutil.go:222-229` [Gemini 3.1 Pro, Claude Opus 4.8]

```go
	path := sshExe.Exe
	if !filepath.IsAbs(path) {
		resolved, err := exec.LookPath(path)
		if err != nil {
			return ""
		}
		path = resolved
	}
```

The same abs-check and `LookPath` sequence, followed by the `EvalSymlinks` call
at lines 230-232, appears verbatim at lines 152-165 in `cygpathForSSH`. A future
change to how Lima resolves the ssh binary must land in both places.

Fix: extract `resolvedSSHPath(sshExe SSHExe) (string, bool)` and call it from
both.

S4. **The cache comment buries the lock protocol in a 190-column run-on** — `pkg/sshutil/sshutil.go:130` [Claude Opus 4.8]

```go
	// cygwinDetectCache maps a resolved ssh path to its sibling cygpath.exe,
	// or "" when that ssh is not Cygwin-based. Each path is probed once. Before using it, we should call cygwinDetectCacheRW's RLock/Lock to protect from concurrent access.
	cygwinDetectCache   = map[string]string{}
```

The third sentence reads as a note-to-self and runs past 190 columns.

Fix: put `// Guarded by cygwinDetectCacheRW.` on its own line and rewrap.

S5. **`TestDefaultPubKeys_WithoutExistingKey` asserts only the key count** — `pkg/sshutil/sshutil_test.go:32` [Claude Opus 4.8]

```go
	keys, err := DefaultPubKeys(t.Context(), false)
	assert.NilError(t, err)
	assert.Equal(t, 1, len(keys))
```

The test proves a key gets created under the isolated `LIMA_HOME` but never
checks where or whether it parses. Asserting the filename would make it a canary
for the Windows path-form bugs this PR exists to fix.

Fix: assert `keys[0].Filename` against the expected path under `tmpDir`, and
check `detectValidPublicKey(keys[0].Content)`.

S6. **Doc wording: "fails back", "besides", and "Cygwin-style"** — `pkg/ioutilx/ioutilx.go:63` [Claude Opus 4.8]

`ioutilx.go:63` says the conversion "fails back to a native conversion" where it
means "falls back"; `sshutil.go:145` says "the cygpath.exe besides sshExe" for
"beside". More substantively, the `/c/...` formula and the phrase "Cygwin-style
path" (lines 82 and 95) name the wrong toolchain — `/c/...` is the MSYS2 and
Git-for-Windows form, while stock Cygwin defaults to `/cygdrive`.

Fix: say "MSYS-style" in the fallback's doc and errors, and note that the
fallback models no `fstab`.

## Design Observations

### Concerns

**Two conversion policies now answer one question (in-scope)** [Claude Opus 4.8, Codex GPT 5.5]. The tree
carries `sshutil.PathForSSH` (toolchain-aware) alongside `ioutilx.WindowsSubsystemPath`
(PATH-global `cygpath`, else the MSYS fallback). Four call sites still use the
latter: `pkg/hostagent/mount.go:58`, `pkg/copytool/copytool.go:127`,
`cmd/limactl/shell.go:789`, and `pkg/limayaml/defaults.go:717` — plus `SSHOpts`
(I1). Two are the acknowledged follow-ups, but the intent differs per site:
`defaults.go` wants a POSIX guest mount point, while the ssh call sites want the
client's path form. Splitting the API by consumer intent (`PathForSSH` for ssh
arguments, a separate helper for Linux-guest paths) would stop the next reader
from "fixing" `defaults.go` into emitting `C:/Users/...` as a mount point. Codex
sketches the same fix as a single Windows toolchain struct holding `ssh`, `scp`,
`ssh-keygen`, and an optional `cygpath`.

**`pickCompleteSSHOnWindows` silently overrides PATH order (in-scope)** [Claude Opus 4.8]. `exec.LookPath`
honours `PATHEXT`, so an `ssh.cmd` or `ssh.bat` wrapper placed first on PATH used
to win. The new walk stats only `ssh.exe` and moves on, so a user's deliberate
wrapper loses without a word. The `SSH` env var remains the escape hatch, which
makes this acceptable — but the `Debugf` at line 96 fires only for incomplete
installs, never for a skipped wrapper. Logging the chosen `ssh.exe` in
`NewSSHExe` would make the selection diagnosable from a bug report.

### Strengths

- Detecting the toolchain from a sibling `cygpath.exe` rather than sniffing
  version strings is cheap and correct for all three Cygwin-family installs, and
  caching by the symlink-resolved path is the right key. [Claude Opus 4.8]
- `PathForSSH` stays a no-op on non-Windows, so call sites can shed their
  `runtime.GOOS` guards over time without behavior change. [Claude Opus 4.8, Codex GPT 5.5]

## Testing Assessment

`go test ./pkg/sshutil ./pkg/ioutilx` passes on darwin. Windows CI runs
`go test ./...`, so both new `_windows_test.go` files execute there. Gating the
`ioutilx` fallback test by filename is correct, not a gap: `filepath.IsAbs` and
`filepath.VolumeName` are OS-dependent, so the drive-letter cases only hold on
Windows.

Untested scenarios, highest risk first:

1. **`WindowsSubsystemPathWithCygpath` with `cygpath` present** — the success
   path and the new error branching (I3) have no coverage. A stub `cygpath` in a
   temp directory that echoes a canned answer, exits non-zero, or is absent
   covers all three branches. The author's objection — that real Cygwin and
   native toolchains produce different results — does not apply to a stub.
2. **`PathForSSH` on the native branch** — nothing asserts `C:\Users\x` becomes
   `C:/Users/x` for a non-Cygwin `sshExe`.
3. **`cygpathForSSH` detection and caching** — a temp directory holding
   `ssh.exe` and `cygpath.exe` would cover the positive branch and the cache.
4. **`SftpServerForSSH`** — no coverage at all (I4).
5. **`DefaultPubKeys` where the selected toolchain's `ssh-keygen` is off PATH** —
   the I2 failure mode.

  PATH-global converter. Note the failure mode there changed from loud to silent

## Review Process Notes

### Skill improvements

- When a finding's quoted snippet does not appear verbatim in the cited file,
  drop the finding rather than repair it. A reviewer who reconstructs a snippet
  from a mental model of the diff will also reconstruct the bug; the mismatch
  between quote and file is the signal, and no amount of surrounding plausibility
  redeems it. This matters most when the fabricated finding happens to match a
  known anti-pattern for the codebase, because the pattern match supplies the
  confidence the evidence lacks.

- When a change introduces a fallback that replaces a hard error, ask what the
  fallback returns on inputs the original path would have rejected, and whether
  any caller can now proceed on a plausible-but-wrong value. A fallback keyed on
  a broad error check (`if err != nil`) rather than a specific cause converts
  every failure mode of the primary path — including cancellation — into a
  success. Flag the breadth of the error check, not just the fallback's own
  logic.

The change detects whether the selected `ssh.exe` is Cygwin-based (by the presence of a sibling `cygpath.exe`) and converts paths accordingly, plus adds an in-process drive-letter fallback so `cygpath`'s absence no longer hard-fails. The detection design is good, but the pairing is incomplete: `ssh-keygen` is still resolved off bare `PATH` (`sshutil.go:290`), `SSHOpts` still converts `ControlPath` with the PATH-based `cygpath` (`sshutil.go:555`), and the new fallback fires on *any* `cygpath` error — not just "binary absent" — so a real Cygwin failure now silently yields a wrong path instead of an error.

## Design Observations

**Concerns**

1. *Two conversion policies for one question* (in-scope). After this PR the tree has two entry points with different toolchain semantics: `sshutil.PathForSSH` (toolchain-aware; native → `C:/…`, Cygwin → sibling `cygpath`) and `ioutilx.WindowsSubsystemPath` (bare `cygpath` on PATH, else the MSYS-form fallback). Four call sites still use the latter — `pkg/hostagent/mount.go:58`, `pkg/copytool/copytool.go:127`, `cmd/limactl/shell.go:789`, `pkg/limayaml/defaults.go:717` — plus `SSHOpts` (I3). Two of those are the acknowledged follow-ups, but `defaults.go` genuinely wants the POSIX form (it is a *guest* mount point, not an ssh argument), while `mount.go` wants whatever the local sftp-server understands. Making that intent explicit in the API — e.g. `PathForSSH` for ssh-client arguments vs. a separate `PathForLinuxGuest` for mount points — would prevent the next reader from "fixing" `defaults.go` to use `PathForSSH` and silently emitting `C:/Users/...` as a Linux mount point.

2. *`pickCompleteSSHOnWindows` overrides PATH ordering, and can bypass a user's wrapper* (in-scope). `exec.LookPath("ssh")` honours `PATHEXT`, so a `ssh.cmd`/`ssh.bat` shim placed first on PATH used to win; the new walk only stats `ssh.exe` and, finding none in that directory, moves on. A user who deliberately front-loads a wrapper now gets a different binary with no warning. The `SSH` env var is the documented escape hatch, so this is acceptable — but the `Debugf` at line 96 only fires for *incomplete* installs, never for "your `ssh.cmd` was ignored." Consider logging the chosen `ssh.exe` at Debug in `NewSSHExe` so the selection is diagnosable from a bug report.

**Strengths**

- Detecting the toolchain from a sibling `cygpath.exe` rather than sniffing versions or output formats is simple, cheap, and correct for all three Cygwin-family installs; caching by *resolved* (symlink-expanded) path is the right key.
- Keeping `PathForSSH` a no-op on non-Windows lets the call sites drop their `runtime.GOOS` guards over time without behavior change.

### Executive Summary

This PR enables Lima to work with native Windows OpenSSH by detecting the toolchain and formatting paths appropriately. However, it preserves a critical gap where converted Cygwin paths are passed directly to Go's native filesystem functions (`os.Stat` and `os.ReadFile`), which completely breaks SSH key generation and initialization for users running Git for Windows.

### Findings

#### Critical Issues

C1. **Converted path passed to native Go filesystem calls** — `pkg/sshutil/sshutil.go:278-285`

```go

				if err != nil {
					return nil, err
				}

```

When Git for Windows is used, `PathForSSH` returns a Cygwin-style path (e.g., `/c/Users/...`). Overwriting `privPath` with this value breaks the subsequent `os.Stat(privPath)` and `os.ReadFile(pubPath)` calls (line 304), because Go's native Windows standard library cannot resolve `/c/...`. `os.Stat` will always return `os.ErrNotExist` causing `ssh-keygen` to run even if the key exists, and `os.ReadFile` will then fail, entirely breaking SSH initialization. The path conversion should only apply to the `-f` argument passed to `ssh-keygen`.

Fix: Keep `privPath` as a native Windows path. Convert it to a separate variable solely for the `ssh-keygen` arguments.
