S1. **The cleanup deletes the drop-in of a listed interface that networkd can't name yet** — `pkg/cidata/cidata.TEMPLATE.d/boot.essential.Linux/30-guest-to-guest-route.sh:26-27` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro]

```sh
	for ROUTE in ${LIMA_CIDATA_GUEST_TO_GUEST_ROUTES}; do
		FILE=$(networkctl status "${ROUTE%,*}" 2>/dev/null | sed -n 's/^ *Network File: //p')
		KEEP="${KEEP} /etc/systemd/network/${FILE##*/}.d/${DROPIN}"
	done
```

When `networkctl status` reports `n/a` for a listed interface, or fails because networkd doesn't know the link yet, the keep list misses that interface's drop-in. The loop at lines 31-41 then deletes it and reloads networkd. If the lease arrives within 60 seconds and networkd names the file by then, the script writes the drop-in again and reloads a second time. If networkd doesn't, as in the probe below, the script only warns. If the lease arrives later, the drop-in is already gone, so networkd has no route to add until a later boot. Round 1's code kept the drop-in in all three cases.

That needs a link that networkd hasn't processed when cloud-final runs the boot scripts. How often a real guest gets there is untested.

```sh

```

When the cleanup removes a drop-in, it reloads networkd whether networkd runs or not. On a NetworkManager guest that still has a drop-in from an earlier boot under networkd, and whose networkd is now disabled or missing, `networkctl reload` fails, and `set -e` ends the script before line 134 sets the NetworkManager route. The code relies on a guest with networkd inactive never having a Lima drop-in, which holds unless the guest's network service changed between boots.

S1. **Cleanup deletes the drop-in of a listed interface that networkd cannot name yet** — `pkg/cidata/cidata.TEMPLATE.d/boot.essential.Linux/30-guest-to-guest-route.sh:25-28` (suggestion, regression)

```sh
	for ROUTE in ${LIMA_CIDATA_GUEST_TO_GUEST_ROUTES}; do
		FILE=$(networkctl status "${ROUTE%,*}" 2>/dev/null | sed -n 's/^ *Network File: //p')
		KEEP="${KEEP} /etc/systemd/network/${FILE##*/}.d/${DROPIN}"
	done
```

Two cases break the keep list:
- `networkctl status` fails because the link doesn't exist yet. `FILE` is empty and `KEEP` gets `/etc/systemd/network/.d/…`.
- networkd reports `n/a` because the link is still pending. `KEEP` gets `…/n/a.d/…`.

In both cases the loop at lines 31-41 removes the listed interface's own drop-in and runs `networkctl reload` (line 43).
- **If the lease arrives within 60 s:** lines 127-130 write the drop-in again and reload a second time. A boot with an unchanged config then reloads twice instead of zero times.
- **If the lease arrives later:** line 107 gives up and the drop-in stays deleted. networkd has nothing to add when the lease finally comes. Round 1 would have kept the drop-in in this case.

Likelihood is low. Boot scripts run from cloud-final after `network-online.target`. Lima's netplan config marks lima0 required-for-online unless `internal_netplanOptional` is set, so networkd normally knows the link by then.

Fix: only remove drop-ins when every lookup produced a real file name.

```diff
 		FILE=$(networkctl status "${ROUTE%,*}" 2>/dev/null | sed -n 's/^ *Network File: //p')
+		case "${FILE}" in "" | n/a) KEEP=SKIP && break ;; esac
 		KEEP="${KEEP} /etc/systemd/network/${FILE##*/}.d/${DROPIN}"
```

The removal loop then runs only when `[ "${KEEP}" != SKIP ]`. A stale drop-in would then survive one more boot, which is the trade-off.

If an interface is listed but `systemd-networkd` has not yet matched it to a network file, `networkctl status` reports `Network File: n/a`. `FILE` becomes `n/a`, and `KEEP` records the malformed path `/etc/systemd/network/n/a.d/...`. The script then deletes the interface's valid drop-in from the previous boot. If the lease subsequently takes longer than the 60-second timeout, the script abandons recreation (`continue` at line 108). `systemd-networkd` never receives the drop-in, and the route is permanently lost. The script accounts for this at line 115 (`[ "${FILE}" != n/a ]`), but omits the check here.
