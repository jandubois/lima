## Important Issues

I1. **The native-generator test passes code that reads `cygpath` from PATH** — `pkg/iso9660util/joliet_windows_test.go:43` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	t.Setenv("PATH", binDir)
```

The fix converts each path with the `cygpath` in the generator's directory. This test puts only `mkisofs.exe` on PATH, so it can't tell the fix from a PATH lookup of `cygpath`. Code that reads `cygpath` from PATH and falls back to `filepath.ToSlash` passes it, and that's the obvious fix for round 1's first symptom. Where Git for Windows or MSYS2 puts `cygpath` on PATH, such code hands a native generator `/c/...`, and the error names the path but not the cause. An opaque failure on an uncommon host makes the test required.

On Windows the empty decoy should fail to start with `ERROR_BAD_EXE_FORMAT`. Go's `Errno.Is` maps only not-found codes to `fs.ErrNotExist`, so `WindowsSubsystemPathWithCygpath` returns that error, and the mutant fails.

func WindowsSubsystemPathWithCygpath(ctx context.Context, cygpathExe, orig string) (string, error) {
	out, err := exec.CommandContext(ctx, cygpathExe, filepath.ToSlash(orig)).CombinedOutput()

## Suggestions

S1. **The conversion lost round 1's comment on why an ISO helper calls `sshutil`** — `pkg/iso9660util/joliet.go:71` [Claude Opus 5.5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
		isoPathForTool, err := sshutil.PathForTool(ctx, cmdAbs, isoPath)
```

Round 1's patch had a two-line comment above this call, and the revision dropped it. Without the comment, nothing tells a reader why an ISO helper calls an `sshutil` function, or that MSYS2 `xorrisofs` reads `C:\...` as a relative path, as #5704's log shows. A reader who doesn't know that might take the conversion out.

Fix: restore the comment above line 71.

```go

		// give each generator the path form of its own toolchain.
```

S2. **The new Prerequisites list repeats QEMU and doesn't say where a Windows host gets a generator** — `website/content/en/docs/usage/guests/windows.md:24-26` [Claude Opus 5.5]

```markdown
Prerequisites:
- QEMU
- A Joliet ISO generator on the host: `hdiutil` on macOS, or `xorrisofs` (from xorriso), `genisoimage`, or `mkisofs` on other hosts.
```

The list is accurate, and it names the generators in the order `joliet.go:64` tries them. But the requirement table at line 6 already names QEMU, and so does the Caveats list at line 40. `hdiutil` comes with macOS, so a Mac user has nothing to install. Fix: drop `- QEMU`, and name the package for Windows hosts, for example "on Windows, MSYS2's `xorriso` package".

"fix Windows Joliet ISO generation" could mean Windows guests or Windows hosts. The change is host-side, and it also helps FreeBSD guests on a Windows host, since `pkg/cidata/cidata.go:535-539` asks for Joliet for FreeBSD too.

Fix: a title such as `iso9660util: convert Joliet generator paths on Windows hosts`.

## Design Observations

### Concerns

- **`pkg/downloader` now reaches `pkg/sshutil`** (future) [Claude Opus 5.5]: `downloader` imports `iso9660util`, so `go list -deps ./pkg/downloader` grows by 15 packages, among them `sshutil`, `limatype` and `osutil`. ### Strengths

- **Round 1's three strengths still hold** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]: `writeJoliet` keeps the native paths for its file operations, `TestWriteJolietWindows` runs a real generator and reads the image back, and `windows_msys2_prep` fails the job when `xorrisofs.exe` or `cygpath.exe` is missing.
- **`PathForTool` fits a generator** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]: a generator can be native, MSYS2 or Cygwin, and the helper's per-binary fallback covers all three.
