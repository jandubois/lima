Executive Summary ¶

One defect dominates. install_provision.ps1 enumerates four provision.<mode> directories that exist on the ISO only when that mode is configured, under $ErrorActionPreference = "Stop". Any config not using all four modes aborts the installer before it registers the scheduled tasks, silently, because no caller checks the exit code.

All four reviewers found that independently. The remaining important findings cluster into three themes: the guest copy of the payload freezes at first logon and never refreshes; the port drops several cross-platform contracts documented in templates/default.yaml (env/PARAM_ delivery, unprivileged user mode, continue-on-failure, readiness gating); and unsupported modes are accepted in silence.

Design Observations ¶

Concerns ¶

  • Two security contexts for the same script (in-scope) Claude Opus 5 Gemini 3.1 Pro. At first logon, -Mode system runs inside FirstLogonCommands, as the elevated lima administrator; from the next boot on, the same script runs as SYSTEM. $env:USERPROFILE, HKCU, and mapped drives all differ between the two, so a script that looks idempotent on the first boot can diverge afterwards. Running the first-boot pass through the registered tasks would give one context for both.
  • ISO-as-source versus copy-as-source (future) Codex GPT 5.6 Sol Claude Opus 5. The design copies provisioning into C:\ProgramData once and treats that copy as the source of truth, which is what produces I3's stale scripts and much of C1's per-mode branching. Re-syncing from a per-start volume, then running the modes in order, would collapse C1, I3, and S3 into one path that mirrors Linux's boot.sh.
  • ValidateTemplateArgs now runs twice per call (in-scope) Claude Opus 5. executeTemplateWalkDir validates at template.go:212 while both callers already validate (cidata.go:404, cidata.go:605). Harmless, but it is why five test cases needed new UID/Home/Shell/SSHPubKeys fields. Worth deciding which layer owns the check.

Strengths ¶

  • Replacing the hand-listed two-file Windows layout with the WalkDir helper the Linux path already uses means new files under wincidata.TEMPLATE.d ship automatically and get template expansion for free. That is what lets install_provision.ps1 use {{.User}} with no extra wiring. (in-scope) [all four reviewers]
  • %08d naming in appendProvisionEntries plus Sort-Object Name in startup_runner.ps1:14 preserves the declared script order, matching Linux's glob order. (in-scope) Codex GPT 5.6 Sol Gemini 3.1 Pro Claude Opus 5
  • Provisioning runs before the boot-done marker (first_logon.ps1:93), so first-boot provisioning is covered by limactl start's wait. (in-scope) Claude Opus 5

Review Process Notes ¶

Skill improvements ¶

  • When a change adds a second platform's implementation of a feature that already exists on another platform, locate the feature's normative documentation (spec file, template comments, user-facing docs) and check the new implementation against each promise it makes, one promise at a time. Ports reproduce the happy path and quietly drop the guards, environment plumbing, ordering guarantees, and error-continuation semantics that the documentation states as cross-platform contracts. Report each unmet promise as a finding, and say whether documenting the divergence would be an acceptable resolution.
  • When a change makes new work run during an existing lifecycle phase (boot, startup, first login, shutdown), check whether that phase's completion signal still covers the new work. A readiness marker, probe, or wait condition written before the new work existed will report done while the new work is still running, and the failure is silent because the caller sees a successful start.

Repo context updates ¶

  • The PowerShell scripts under pkg/cidata/wincidata.TEMPLATE.d/ ship to the Windows guest, and no CI job lints, parses, or executes them. No CI job boots a Windows guest at all: windows-2025 in .github/workflows/test.yml is a runner label, so those jobs run lima on a Windows host with Linux guests. Treat any behavior claim about these scripts as unverified and reason from documented PowerShell semantics.
  • templates/default.yaml is the normative spec for provision semantics. It documents the per-boot execution order (data → yq → system → user), that user scripts run without root privileges, and that param values reach provisioning scripts as PARAM_<key> environment variables. Check any platform-specific provisioning implementation against each of those promises.
  • The Windows guest's cidata ISO is attached only until the guest is installed (pkg/driver/qemu/qemu.go, gated on isWindowsBootDone), while the hostagent regenerates that ISO on every start. Anything the guest needs after installation must be copied into the guest or delivered on a separate volume, so host-side config edits never reach an existing Windows instance.
