## Executive Summary

The PR pins each guest's SSH host key and makes `ssh` verify it. The design holds up: default guests pass CI, and all five Copilot comments are fixed at this head. But a plain-mode `alpine-iso` instance now fails its second start, and a guest without an ed25519 key never starts. The `Copy-Provision` fix still stops at the second script, and one comment blames the wrong Lima. Each has a patch below.

I1. **A plain-mode `alpine-iso` instance cannot start twice** — `pkg/hostagent/requirements.go:72-75` [Codex GPT 6 Astra, Claude Opus 5.5]

```go
			err := a.pinSSHHostKey(ctx)
			if err == nil {
				err = fn(req)
			}
```

`alpine-iso` runs from a RAM disk, so `/etc/ssh` keeps its contents across a reboot only on the data volume. `boot.sh:73-77` skips `boot.Linux/` in plain mode, and `04-persistent-data-volume.sh` is in that directory. alpine-lima's `lima-init.sh` ignores `write_files`, so the new `ssh_deletekeys` file does not help either. The guest therefore presents a new key on every boot. The merge-base tolerated that. With this PR the second start hits `ErrHostKeyMismatch` and retries until `limactl start` gives up, after 10 minutes by default. Removing the file, as the error suggests, only pins the next boot's key.

I2. **A guest without an ed25519 host key can no longer start** — `pkg/sshutil/hostkey.go:144` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
		HostKeyAlgorithms: []string{ssh.KeyAlgoED25519},
```

`ScanHostKey` offers only `ssh-ed25519`, and `waitForRequirements` does not run any requirement until the pin succeeds, so a guest without that key fails its first start. The merge-base connects to such a guest. cloud-init skips ed25519 in FIPS mode (`FIPS_UNSUPPORTED_KEY_NAMES` in `cc_ssh.py`), and a guest's `sshd_config` can leave it out. No template in the tree does either, so few users will meet this, but no setting turns the check off.

See also `pkg/sshutil/hostkey.go:203`, which restricts `ssh` the same way.

I3. **`Copy-Provision` still fails on the second script** — `pkg/cidata/wincidata.TEMPLATE.d/install_provision.ps1:20-25` [Codex GPT 6 Astra]

```powershell
        $dst = $Dst
        if ($Extension) {
            # `.ps1` extension is necessary for script otherwise Powershell returns an error.
            $dst = Join-Path $Dst ("{0}.ps1" -f $item.BaseName)
        }

```

PowerShell variable names are case-insensitive, so the local `$dst` is the `$Dst` parameter. The first pass through the loop overwrites the parameter with the first script's path, and the second joins its file name under that file. `Copy-Item` then fails and `$ErrorActionPreference = "Stop"` ends the script, the failure that `715206e4` says it fixes. Every `-Extension` call failed before that commit, so this is a gap in the fix and the `[switch]` change is still needed.

`appendProvisionEntries` (`pkg/cidata/cidata.go:599`) writes one file per `provision` entry, so two entries of one script mode (`system`, `user` or `dependency`) trigger it.

I4. **Two comments misstate when an unpinned file matters** — `pkg/sshutil/hostkey.go:90-91` [Claude Opus 5.5]

```go
// RemoveKnownHostsFileUnlessPinned removes the known_hosts file of the instance when it pins no key,
// so that an older version of Lima that starts the instance next does not fail to verify the host key.
```

An older Lima never reads this file, because v2.2.1 hard-codes `StrictHostKeyChecking=no` and `UserKnownHostsFile=/dev/null`. The client that fails is this version's `limactl`, which refuses an instance whose file is empty, and an older host agent never fills that file.

`pkg/sshutil/hostkey.go:161` and the head commit's body make a related error. Both equate a missing file with an instance this version has never started, but `Run` removes the file after a start that never pinned, as the probe's second line shows.

## Design Observations

### Concerns

- **The stated motivation covers one configuration** (in-scope) [Claude Opus 5.5]: the PR comment names a guest user process impersonating `sshd` after a crash. With the default passwordless sudo that process can read the private key, and the threat model treats guest root as the attacker, so pinning stops it only under `user.passwordlessSudo: false`. The threat model does list that as a boundary, which is why the verdict is **Merge with fixes**. For that vector alone, `boot.Linux/20-rootless-base.sh:64` could keep port 22 privileged with `ip_unprivileged_port_start=23`, one line against this PR's 742 added lines, tests and CI included, and a new rule for every guest. Pinning may also stop another local user who binds the host's SSH port, but nobody has claimed or measured that.
- **A guest that breaks the new rule cannot opt out** (in-scope) [Claude Opus 5.5]: I1 and I2 fix the two known cases one at a time. No workflow boots a macOS or Windows guest and this review did not either, so their restart behavior is unmeasured. An `ssh` config field that skips the pin and takes `HostKeyOpts`'s unpinned branch would give users a way out of the next case.

### Strengths

- **Mixed copies stay verified** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]: `accept-new` with `/dev/null` first works as its comment says. Real `ssh`, rerun for this report, accepted the legacy host, refused a wrong key for the pinned host, and left the pin file's key unchanged.
- **The pin does not depend on the port** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]: `HostKeyAlias` keeps a single-instance connection working when an older host agent picks a new port.
- **The scan proves possession of the key** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]: x/crypto v0.58.0 verifies the signature before it calls `HostKeyCallback` (`ssh/handshake.go:837-841`), so the comment on `ScanHostKey` is accurate.
- **A failed write cannot unpin the instance** (in-scope) [Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]: `fsutil.WriteFileAtomic` keeps the old file until the new one is complete.

## Review Process Notes

### Skill improvements

- A sandboxed CLI can refuse a Go module cache outside its worktree, so an agent there cannot build or test, and it reports that only in its Testing Assessment. For a Go repo, stage the module cache as well as the sources named in the prompt, and give the agents the `GOMODCACHE` value to use, because a review whose agents can run tests finds defects that a read does not.

### Repo context updates

- `boot.Linux/` runs only outside plain mode, and alpine-lima's `lima-init.sh` handles only the user-data keys that it parses by hand. So on an `alpine-iso` guest, no cloud-init setting applies, and a change that needs guest state to persist across a restart must check which boot script keeps that state in plain mode.
- `hack/test-templates.sh` restarts Linux guests in non-plain mode only, `freebsd.bats` stops without restarting, and no workflow boots a macOS or Windows guest. CI does not cover a restart on those paths, so ask for a probe when a change depends on one.

###### Design Observations

###### Concerns

- **`writeSSHConfigFile` receives `AdditionalArgs` on dynamic SSH address changes** `(in-scope)`: In `pkg/hostagent/hostagent.go:466`, when dynamic SSH address changes on WSL2/HCS, `writeSSHConfigFile` is invoked with `a.sshConfig.AdditionalArgs`. `writeSSHConfigFile` forwards options to `sshutil.Format(..., FormatConfig, ...)`, which expects `key=value` pairs. Because `a.sshConfig.AdditionalArgs` contains CLI flags (`"-F"`, `"/dev/null"`), `FormatConfig` will return `unexpected option "-F"`. While pre-existing from commit `9ed9bbc1`, passing `sshOpts` rather than `AdditionalArgs` avoids this failure when dynamic addresses shift.
- **Hardcoded `ssh-ed25519` key algorithm assumption** `(future)`: `ScanHostKey`, `PinHostKey`, and `HostKeyOpts` hardcode `ssh-ed25519`. While ED25519 is standard across modern distributions, environments enforcing FIPS 140 disallow ED25519 host keys. In a FIPS-configured guest image, OpenSSH only enables RSA and ECDSA, which causes `ScanHostKey` to fail negotiation and stalls `waitForRequirements` for 10 minutes. Supporting ECDSA fallback when ED25519 is unavailable would accommodate FIPS guests.

###### Strengths

- **Atomic pinning and crash safety**: Using `fsutil.WriteFileAtomic` ensures that `ssh.known_hosts` is never partially written or corrupted during abrupt shutdown. Writing a 0-byte file in `hostagent.New()` safely enforces `StrictHostKeyChecking=yes` during boot so that unverified connections fail until `PinHostKey` scans and commits the key.
- **In-guest key generation with cloud-init persistence**: Generating the host key pair inside the guest avoids exposing private keys on the cidata ISO or host filesystem. Writing `ssh_deletekeys: false` via cloud-init `write_files` ensures static keys from pristine images are refreshed on first boot while remaining pinned across subsequent reboots and Lima version downgrades.

###### Testing Assessment

- **I1 (Alpine ISO host key mismatch on reboot)**: Required test under check #3 (How would a user see it?). On reboot of an Alpine ISO instance, host key verification fails repeatedly until the 10-minute timeout expires with no clear remediation other than manual file removal. An integration test covering stop/start cycles for `templates/alpine-iso.yaml` would have surfaced the missing `sshd` restart in `04-persistent-data-volume.sh`.
- Existing test suites `hack/test-downgrade.sh` and `hack/test-upgrade.sh` provide coverage for Ubuntu/QEMU, and unit tests in `pkg/sshutil/hostkey_test.go` and `pkg/cidata/template_test.go` cover parsing, multi-instance known_hosts generation, and cloud-init template rendering.

- **Host key verification for localhost**: In PR discussion, the author clarified that verifying host keys for localhost is intentional to prevent an unprivileged guest user process from impersonating `sshd` on port 22 (`net.ipv4.ip_unprivileged_port_start=0`).

The implementation was intentionally revised to generate keys inside the guest and trust the public key on first boot.
