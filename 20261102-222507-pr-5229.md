## Executive Summary

The PR resumes interrupted cache downloads from a stable `data.part` with `Range` and `If-Range`, and the design holds: the existing lock gives each URL one writer, and resume needs a digest and a cached validator. One branch breaks the digest's guarantee. A 206 that answers a request without `Range` appends to the stale partial, but the digest covers only the new bytes, so a hostile server or an on-path attacker gets its bytes cached as verified.

## Critical Issues

C1. **A 206 to a request without `Range` bypasses the digest check** — `pkg/downloader/downloader.go:1118-1120` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]

```go
	case resp.StatusCode == http.StatusPartialContent:
		logrus.Debugf("server returned 206 Partial Content; resuming %#q from offset %d", url, offset)
		resuming = true
```

When `resumeOffset` declines a leftover partial (no cached validator), the request carries no `Range` and `offset` stays 0. A 206 still sets `resuming`, so `openPartialFile` appends to the old bytes (line 984), but `resumeDigester` hashes only the new body (line 1012). The digest matches, and `fetch` records it (line 423) for `getCached` to trust on later runs (lines 373-379).

A hostile server needs two responses. It cuts the first short without `ETag` or `Last-Modified` and answers the retry with 206. Lima v2.0.0's and v2.1.0's default Ubuntu images now redirect to plain `http://cloud-images-archive.ubuntu.com`, and the `freebsd` and `freebsd-15` templates use `http://`, so an on-path attacker can. The merge-base writes a fresh temp file and passes the same test.

## Suggestions

S1. **Response metadata is written at the wrong moment for both 200 and 206** — `pkg/downloader/downloader.go:1134-1138` [Codex GPT 6 Astra, Gemini 3.5 Flash, Claude Opus 5.5]

```go
	if err := writeResponseMetadata(t, resp); err != nil {
		return err
	}

	fileWriter, err := openPartialFile(partial, resuming)
```

RFC 9110 §15.3.7 lets a server that matched `If-Range` leave `Last-Modified` and `Content-Type` out of the 206, and `writeResponseMetadata` then empties `time` and `type`. If that resumed transfer is cut off as well, `resumeOffset` finds no validator and the next attempt starts from zero. The five hosts I probed (Ubuntu, Debian, Fedora, openSUSE and GitHub releases) all repeat `Last-Modified` in a 206, so this needs a stricter server.

On a 200, the new validator is written before `O_TRUNC` empties the old bytes, so a kill between the two calls pairs old bytes with a new validator. The digest catches that, but the retry then fails with a digest error, as S3 describes, and only the run after it succeeds.

Fix: skip `writeResponseMetadata` on a 206, since the matched `If-Range` already vouches for the cached files, and call it after `openPartialFile` on a 200.

S2. **A weak `ETag` goes out as `If-Range`, which never matches** — `pkg/downloader/downloader.go:910-915` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]

```go
func ifRangeValidator(etagPath, timePath string) string {
	if etag := readFile(etagPath); etag != "" {
		return etag
	}
	return readFile(timePath)
}
```

RFC 9110 §13.1.5 forbids a weak entity tag in `If-Range`, and servers compare strongly, so a `W/"..."` tag always draws a 200 and a full download, even when the cached `Last-Modified` would have allowed a resume. The cost is a full download, which is the merge-base's behavior, and none of the image hosts I probed sends a weak tag.

Fix: skip an `ETag` that starts with `W/` and fall back to `time`.

S3. **A failed resume ends the command with a digest error** — `pkg/downloader/downloader.go:1036-1039` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	if resume {
		_ = os.Remove(partial)
	}
	return fmt.Errorf("expected digest %#q, got %#q", expectedDigest, actualDigest)
```

When a resumed transfer stitches the wrong bytes together, the digest check deletes the partial and fails the command, and the user has to run it again; the merge-base would have downloaded the whole file and succeeded. That happens when a server honors `Range` but ignores `If-Range`. GitHub's release-asset host answered a bogus `If-Range` with 206 in my probe, so the first download after a release asset is replaced and the template is updated to its new digest fails. The 206 branch also never compares the `Content-Range` start with `offset`.

Fix: when the digest fails after a resume (`offset > 0`), discard the partial and restart once from scratch, as `finalizeOrRestartPartial` already does for a 416. Rejecting a 206 whose `Content-Range` start differs from `offset` would catch the same case before the transfer.

S4. **`newDownloadRequest` re-checks a validator that `resumeOffset` already required** — `pkg/downloader/downloader.go:952-956` [Claude Opus 5.5]


Fix: have `resumeOffset` return the validator with the offset and pass it to `newDownloadRequest`.

### Skill improvements

- When a finding needs a peer to break the protocol (a 206 nobody asked for, a malformed header, an out-of-range length), rate it by what a hostile peer gains whenever the threat model treats that peer as untrusted, such as a download server, a mirror, a guest or the network. "No honest server does this" lowers the likelihood only for honest peers, and an integrity check that a hostile peer can step around is the bug that the check exists to stop.

### Repo context updates

- [repo] Several bundled image URLs reach plain HTTP or third-party hosts. Archived Ubuntu releases redirect to `http://cloud-images-archive.ubuntu.com`, which covers the default templates of Lima v2.0.0 and v2.1.0 and, I expect, of each later release once its pinned image ages out; the `freebsd` and `freebsd-15` templates use `http://` directly; Fedora, openSUSE and Debian URLs redirect to third-party mirrors.
