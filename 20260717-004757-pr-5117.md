## Executive Summary

The privilege boundary holds: no agent found a path from the sudo helper to an arbitrary root-readable file, and the layered defenses around the open are sound. The blocking problem sits outside that boundary. Making VZ file-descriptor retention per-VM dropped retention for the exported `PassFDToUnix`, whose only caller is krunkit — reintroducing the garbage-collector-closes-live-fd bug the deleted package global existed to prevent. Seven integration gaps follow, none of them challenging the design.

This round supersedes `20260716-213905-pr-5117`, which is kept for comparison. In that round the Gemini reviewer received the diff as prompt text, answered in a single turn without opening a file, and reported nothing. Re-running both Gemini models with the diff delivered as a file instead produced 117 and 97 turns of tool use, and three findings this report adds: I8, S8, and S9. Nothing else changed — same commits, same review SHA.

Findings group into four themes: the fd-retention regression (C1, S8), sudoers verification and setup (I2, I3, I4, S1, S9), helper-path hardening (I8), and configuration reach — which builds, install locations, and YAML layers the feature actually works from (I1, I5, I6). Every finding was verified against the worktree at the review SHA before it was kept, including all three added this round; two agent claims survived with their reasoning corrected, recorded inline.

## Critical Issues

C1. **`PassFDToUnix` passes a `nil` retainer, so krunkit's network fd can be closed by GC** — `pkg/driver/vz/network_darwin.go:27-29` [Claude Opus 4.8]

```go
func PassFDToUnix(unixSock string) (*os.File, error) {
	return passFDToUnix(unixSock, nil)
}
```

At the merge-base, `createSockPair` appended every socketpair file to the package global `vmNetworkFiles` unconditionally, under a comment warning that `f.FD()` becomes invalid once `f` is garbage collected. This PR made that append conditional on `retainedFDs != nil`, then deleted the global and the comment. The exported wrapper passes `nil`, so nothing retains.

The only non-test caller is `pkg/driver/krunkit/krunkit_darwin_arm64.go:125`, which uses the returned file solely for its raw number and drops the reference when `buildNetworkArgs` returns. `os.NewFile` installs a finalizer that closes the fd, so any GC cycle before krunkit execs hands it a closed — or recycled — descriptor. That file is untouched by this PR, so the diff alone cannot reveal the break. `DialQemu` at `network_darwin.go:55-57` has the same shape.

Fix: give the exported wrappers a package-level retainer instead of `nil`.

```diff
+var processRetainedFDs = newRetainedFileDescriptors()
+
 func PassFDToUnix(unixSock string) (*os.File, error) {
-	return passFDToUnix(unixSock, nil)
+	return passFDToUnix(unixSock, processRetainedFDs)
 }
```

## Important Issues

I1. **`blockDevices` is dropped from override and default YAML layers** — `pkg/limatype/lima_yaml.go:30` [Codex GPT 5.5]

```go
	BlockDevices          []string      `yaml:"blockDevices,omitempty" json:"blockDevices,omitempty" jsonschema:"nullable"`
```

`FillDefault` never merges this field. Every comparable list field is concatenated across the three layers — see `y.AdditionalDisks = slices.Concat(o.AdditionalDisks, y.AdditionalDisks, d.AdditionalDisks)` at `pkg/limayaml/defaults.go:304` — and the documented contract says override, user YAML, and defaults all contribute. `BlockDevices` appears nowhere in `defaults.go`; it turns up only in `validate.go` and tests. A `blockDevices` list in `$LIMA_HOME/_config/override.yaml` or a base template is silently discarded, so the field works only when set directly on the instance YAML or through `--block-device`.

Fix: add `y.BlockDevices = slices.Concat(o.BlockDevices, y.BlockDevices, d.BlockDevices)` to `FillDefault`, and cover override inheritance in tests.

I2. **`sudoers --check` reports a correct file as out of sync, and its hint destroys the grant** — `cmd/limactl/sudoers_darwin.go:112-114` [Claude Opus 4.8]

```go
	if string(b) != content {
		return fmt.Errorf("sudoers file %q is out of sync and must be regenerated (Hint: %s)", file, hint)
	}
```

`renderSudoers` builds `content` from the `--block-device` flag of this invocation (line 36). A user who installed with `limactl sudoers --block-device=/dev/disk4` and later runs the documented `limactl sudoers --check /etc/sudoers.d/lima` hits this mismatch, because `content` then carries only the network fragment. `sudoersCheckHint` (lines 118-125) reads the same flag, so it tells them to run plain `limactl sudoers` — whose output drops the block-device entry. Following the hint breaks a working setup.

Fix: verify the network fragment and each block-device entry separately, ignoring well-formed helper entries the current flags do not name.

I3. **`limactl sudoers --block-device` requires socket_vmnet to be installed** — `cmd/limactl/sudoers_darwin.go:28-31` [Codex GPT 5.5]

```go
	if err := nwCfg.Validate(); err != nil {
		logrus.Infof("Please check %s for more information.", socketVMNetURL)
		return err
	}
```

`sudoersAction` validates the network configuration before it reads the `--block-device` flag at line 36. `networks.Validate` returns "`paths.socketVMNet` has to be installed" when socket_vmnet is absent, so a VZ-only user who wants block devices and no shared network cannot generate the fragment at all. CI installs socket_vmnet first, so no lane exercises this.

Reconciliation: Codex labeled this a regression. The merge-base `sudoersAction` already called `nwCfg.Validate()` first, so the gate is pre-existing and the new flag merely inherits it. Relabeled a gap.

Fix: render the block-device fragment without requiring network validation when no network entries are requested.

I4. **`VerifySudoAccess` loosened from exact match to substring containment** — `pkg/networks/sudoers.go:112` [Claude Opus 4.8]

```go
	if !strings.Contains(string(b), sudoers) {
```

The merge-base required `string(b) != sudoers`, so the installed file had to be byte-identical to Lima's own output. Containment is genuinely needed now that the file also carries block-device entries, but it is broader than composition requires: any file embedding the fragment anywhere passes, including one where the fragment appears only inside a comment. Meanwhile `limactl sudoers --check` still compares exactly (I2), so the two paths disagree about what a valid file is.

Reconciliation: Claude attributed the exact-match check to PR #2734. That PR is "networks.Validate() requires that socket_vmnet is owned by root" and never touched this check, which came from `4558b5a2`. Because the file is root-owned, no privilege boundary is crossed — this is drift detection, not escalation.

Fix: compare against the composed content that `cmd/limactl` already renders.

I5. **`external_vz` builds neither support `blockDevices` nor reject them** — `pkg/blockdevice/block_device_darwin.go:200-207` [Codex GPT 5.5]

```go
	exe, err := os.Executable()
	if err != nil {
		return nil, err
	}
	if err := validateSecureHelperPath(exe); err != nil {
		return nil, err
	}
	return []string{exe, SudoOpenBlockDeviceCommand, devicePath}, nil
```

The helper path comes from whichever process performs the attach. Under `external_vz` (`Makefile:294`, enabled by `ADDITIONAL_DRIVERS=vz`), VZ runs inside `lima-driver-vz`, so `os.Executable()` resolves there while the sudoers entry names `limactl`. qemu, krunkit, and wsl2 each received an explicit rejection stub in this PR; external VZ received none, so the config is accepted and then fails at VM start.

Reconciliation: Codex claimed sudo would run `lima-driver-vz sudo-open-block-device`, "starting the driver server instead of the helper". `sudoers.Args` passes `--non-interactive` (`pkg/sudoers/sudoers.go:20`), so sudo cannot authorize a command absent from the NOPASSWD entry and rejects it outright. The gap is real; that outcome is unreachable.

Fix: reject `blockDevices` under `external_vz`, or register the helper in the driver and pin sudoers to its path.

I6. **Homebrew-installed `limactl` cannot use the feature, and the docs bury it** — `website/content/en/docs/config/disk.md:136-137` [Claude Opus 4.8]

```md
The block-device entry is scoped to the current user and is only generated when the `limactl`
executable is installed in a root-owned path that cannot be modified by regular users.
```

`sudoOpenBlockDeviceHelperArgs` feeds `os.Executable()` to `validateSecurePath`, which rejects any symlink and any non-root-owned ancestor up to `/` (`pkg/blockdevice/block_device_darwin.go:379-392`). Homebrew's `limactl` is a symlink under a prefix Homebrew chowns to the invoking user, so it fails both tests. This PR's own CI creates a root-owned `/opt/lima` and installs there (`.github/workflows/test.yml:606-608`) for exactly that reason. The restriction is correct; the docs present it as a footnote rather than "this does not work with `brew install lima`".

This host has no Homebrew-installed `limactl`, so the layout claim rests on Homebrew's documented prefix ownership plus the CI's explicit root-owned PREFIX, not on direct observation.

Fix: name Homebrew as incompatible and show the `sudo make PREFIX=/opt/lima install` escape hatch.

I7. **Additional-disk locks are stranded when block-device attach fails** — `pkg/driver/vz/vm_darwin.go:636-638` [Codex GPT 5.5]

```go
	configurations, err := attachHostBlockDevices(ctx, inst, configurations, retainedFDs)
	if err != nil {
		return err
	}
```

`attachDisks` locks each additional disk with `disk.LockForInstance` at line 615 and never unlocks on a later error. The hostagent registers its unlock hook inside `startHostAgentRoutines` (`pkg/hostagent/hostagent.go:645`), which runs at line 520 — after `a.driver.Start(ctx)` at line 437. A failure inside `Start` therefore skips registration and leaves the `in_use_by` symlink behind, forcing a manual `limactl disk unlock`.

Reconciliation: Codex labeled this a regression. The merge-base already had failure points after the lock — `Convert`, the attachment constructors, `validateDiskFormat` — so stranded locks are pre-existing. Relabeled a gap. The PR still matters here: a missing sudoers entry is a far likelier first-run failure than any of those.

Fix: unlock the disks this call locked on the error path.

I8. **`validateSecurePath` accepts sudoers command delimiters in the helper path** — `pkg/blockdevice/block_device_darwin.go:369` [Gemini 3.1 Pro] (re-run)

```go
	if strings.ContainsAny(path, " \t\r\n") {
```

The same file rejects `,`, `:`, `=`, and `\` in a sudoers user name 155 lines earlier (`validateSudoersUserName`, line 214), because those characters carry meaning in sudoers grammar. The helper-path check rejects whitespace alone. `NOPASSWD` joins commands with a comma (`pkg/sudoers/sudoers.go:53`), so a comma in the executable path splits one granted command into two: a `limactl` installed at `/opt/lima,bin/limactl` would also grant passwordless root to `/opt/lima` as a command in its own right.

Reaching this needs an admin to install `limactl` at a root-owned path carrying one of those characters, so exploitability is negligible. It remains an incomplete implementation of the PR's own hardening — `validateSecurePath` exists to make the helper path untamperable, and the correct character class already sits in the same file.

Fix: use the character class `validateSudoersUserName` already uses.

```diff
-	if strings.ContainsAny(path, " \t\r\n") {
-		return fmt.Errorf("path %q contains whitespace", path)
+	if strings.ContainsAny(path, " \t\r\n,:=\\") {
+		return fmt.Errorf("path %q contains whitespace or sudoers delimiters", path)
 	}
```

## Suggestions

S1. **Sudoers-setup failure surfaces as a raw `sudo` error with no hint** — `pkg/blockdevice/block_device_darwin.go:561` [Claude Opus 4.8]

```go
		return nil, fmt.Errorf("failed to run %v: stdout=%q, stderr=%q: %w", cmd.Args, stdout.String(), stderr.String(), err)
```

The commonest first-run failure — no sudoers entry for this user and device — reaches the user as `sudo: a password is required` wrapped in a command dump, raised from inside VM startup in the background hostagent. `networks.VerifySudoAccess` carries an explicit `Hint:` for the same class of problem. Downgraded from Claude's Important: this improves diagnostics rather than fixing a defect.

Fix: wrap the failure with a hint naming `limactl sudoers --block-device=<devicePath>`.

S2. **Nonce read has no deadline** — `pkg/blockdevice/block_device_darwin.go:517` [Claude Opus 4.8]

```go
			if _, err := io.ReadFull(conn, nonce); err != nil {
```

The deferred `listener.Close()` at line 486 unblocks `AcceptUnix` but not an already-accepted `conn`. A root peer that connects and stalls leaks the goroutine and the connection for the process lifetime; `waitForReceivedFD` honours the context but the goroutine does not. Only root can reach this path, so impact is low.

Fix: set a read deadline before `io.ReadFull`, and close `conn` on cancellation.

S3. **Received fd is stranded in the channel on context cancellation** — `pkg/blockdevice/block_device_darwin.go:564-567` [Claude Opus 4.8]

```go
	receivedFile, err := waitForReceivedFD(ctx, fdCh)
	if err != nil {
		return nil, fmt.Errorf("failed to receive file descriptor for %q: %w", devicePath, err)
	}
```

When the context fires while the goroutine is mid-handoff, the goroutine pushes an open `*os.File` into the buffered channel and nobody drains it. The finalizer eventually closes it, so this self-heals, but a root-opened device fd stays open meanwhile. `drainReceivedFD` already serves the sibling path at line 558.

Fix: drain and close on the `waitForReceivedFD` error path.

S4. **Device path is validated three times per helper request** — `pkg/blockdevice/block_device_darwin.go:58` [Claude Opus 4.8]

```go
	if err := validateDiskDeviceNode(req.DevicePath); err != nil {
```

`validateForAllowedDevice` reaches `validateDiskDevicePath` through `validate`; `validateDiskDeviceNode` calls it again; `validateDiskDeviceMode` at line 78 calls it a third time. Defense in depth inside a privileged helper is defensible, but the repetition hides which check is load-bearing.

Fix: keep the redundancy and add one line saying it is deliberate, so a later reader does not simplify away the wrong call.

S5. **CI socket_vmnet install is duplicated and pinned to a mutable tag** — `.github/workflows/test.yml:600-602` [Claude Opus 4.8]

```yaml
          git clone https://github.com/lima-vm/socket_vmnet
          cd socket_vmnet
```

Lines 594-604 are byte-identical to lines 499-509 — `diff` reports no difference. `v1.2.2` is a movable tag rather than a commit SHA, and `/Users/runner/socket_vmnet` hardcodes the runner's home. The pre-existing block has the same shape, so this PR replicates the pattern rather than introducing it.

S6. **The shared template's `blockDevices` comment leads with the wrong scope** — `templates/default.yaml:134-135` [Claude Opus 4.8]

```yaml

# Each entry is a host device path whose exact format is backend-specific.
```

S8. **`retainedFDs` is never closed when `startVM` fails** — `pkg/driver/vz/vm_darwin.go:88-92` [Gemini 3.1 Pro] (re-run)

```go
	retainedFDs := newRetainedFileDescriptors()
	machine, err := createVM(ctx, inst, retainedFDs)
	if err != nil {
		return nil, nil, nil, err
	}
```

The only `CloseAll()` sits at line 106, inside the goroutine that starts after `machine.Start()` succeeds. A failure in `createVM` or in `Start` returns before that goroutine exists, so every descriptor the VM configuration retained — network socketpairs, and any block device the privileged helper opened — stays open. The hostagent exits on this path today, so the OS reclaims them; the leak would start to matter the moment VM start becomes retryable in-process.

This pairs with C1: both are gaps in the same retention refactor, and whoever fixes one should fix the other.

Fix: close the retainer on the error branches.

```diff

 	if err != nil {
+		retainedFDs.CloseAll()
 		return nil, nil, nil, err
 	}
```

S9. **The network sudoers hint renders an unbalanced parenthesis** — `pkg/networks/sudoers.go:89` [Gemini 3.5 Flash] (re-run)

```go
	hint := fmt.Sprintf("run `%s sudoers >etc_sudoers.d_lima && sudo install -o root etc_sudoers.d_lima %q`)",
```

The format string closes a parenthesis it never opens. Both call sites wrap it as `(Hint: %s)` (lines 103 and 114), so the user reads `(Hint: run ... /etc/sudoers.d/lima))`. `git blame` dates the line to `9d822a29`, 2022-12-01, so it predates this PR.

One of the two hints is now tested for balanced parentheses; the other still renders wrong.

Fix: drop the trailing `)` from the format string.

## Design Observations

### Concerns

**Device-number grants are neither stable nor time-bounded** *(future)* [Claude Opus 4.8]

`macOSDiskDevicePathRE` pins the sudoers grant to a path like `/dev/disk4`, and `openDiskDeviceNoFollow` opens it `O_RDWR`. macOS assigns `diskN` by attach order, so a grant issued for a USB stick becomes a standing root read-write grant for whatever device lands on that slot after the next reboot or replug. Nothing in the sudoers file, the docs, or the code re-confirms the binding. The grant names a slot, not a device.

Worth evaluating: record the disk's UUID at grant time and have the helper verify it after opening, rejecting a mismatch. That also forecloses a `--block-device=/dev/disk0` grant surviving as a permanent boot-disk handle. Relatedly, the helper always opens `O_RDWR`, so a read-only attachment cannot be expressed even though the VZ attachment constructor takes a `readOnly` argument.

**Verification is split across two packages that each own half the file** *(in-scope)* [Claude Opus 4.8]

I2 and I4 are one problem seen from two sides: `pkg/networks` verifies its fragment, `pkg/blockdevice` renders another, and neither checks the whole. The composition already lives in `cmd/limactl` via `renderSudoers`. Moving verification there — one function that renders the expected file and compares it exactly, called by both `--check` and network startup — collapses both findings.

### Strengths

- **Argv pinning is the right primitive** *(in-scope)* [Claude Opus 4.8, Codex GPT 5.5]. The allowed device arrives as argv, so sudo's own command matching becomes the allowlist and the policy lives in the file the admin reviewed. `validateForAllowedDevice` is a second check, not the gate.
- **The open path closes its TOCTOU window rather than papering over it** *(in-scope)* [Claude Opus 4.8, Gemini 3.1 Pro]. `Lstat` and symlink rejection, then `O_NOFOLLOW`, then a post-open `Stat`, then a block/char cross-check — each layer is independently justified.
- **`F_DUPFD_CLOEXEC` on the root-opened fd** *(in-scope)* [Claude Opus 4.8] keeps the descriptor out of later child processes. Most implementations miss this.
- **Requiring `SUDO_UID` and validating the socket directory against it** *(in-scope)* [Claude Opus 4.8, Gemini 3.1 Pro] means the helper cannot be coaxed into delivering the fd into a directory the sudo-invoking user does not own.
- **Per-VM fd retention removes a real cross-VM hazard** *(in-scope)* [Codex GPT 5.5, Gemini 3.1 Pro]. The direction is right; C1 is a gap in its execution, not an argument against it.

## Testing Assessment

Coverage is unusually strong for a security change: 23 new Go tests plus a real end-to-end BATS roundtrip. `hack/bats/extras/vz-block-device.bats` is the highlight — a real ramdisk, real GPT/exFAT, and a real guest-to-host-to-guest write across a stop/start, with no mocks anywhere in the suite. The regression tests the author added in response to earlier review (real yq evaluation for missing/null `blockDevices`, the sudoers hint parenthesis assertion, context-cancellation, close-on-exec) each pin a bug that previously escaped.

The gaps cluster where the tests assert the new property but not the one it replaced:

1. **Exported-wrapper fd retention (C1).** `TestRetainedFileDescriptorsArePerVM` proves the new per-VM property; nothing asserts that `PassFDToUnix` still retains, which is exactly what regressed. A test that calls the exported wrapper, forces a GC, and checks the fd is still valid would have caught it.
2. **`validateSecurePath` recursion (I6).** The element check is tested in isolation; the recursion refusing a user-owned ancestor or a symlinked exe is not — the two cases every Homebrew user hits.
3. **`blockDevices` layer merging (I1).** No test covers override or default inheritance, which is why the missing `FillDefault` line went unnoticed.
4. **`sudoers --check` against a file installed with `--block-device` (I2).** The hint's formatting is asserted; that following the hint preserves the grant is not.
5. **`VerifySudoAccess` containment (I4).** A test asserts the new permissiveness; nothing pins what it must still reject.
6. **Full `Open()` handoff.** Request rejection and peer checks are covered separately, but no test drives listener to dial to nonce to SCM_RIGHTS to `validateDiskDeviceFile` as one unit.

## Documentation Assessment

`disk.md` is accurate for the happy path and explains the sudoers opt-in clearly. Three gaps: it advertises the wrong version (S7), it presents the root-owned-install requirement as a footnote when it disqualifies Homebrew outright (I6), and it never mentions that the grant is `O_RDWR` or that `/dev/diskN` numbering shifts across reboots. Every new exported symbol carries a godoc comment in the correct declarative form except `SudoersForUser`.

## Commit Structure

The two-commit split is defensible for review, and the author offered to squash. But `5564e6bf` bundles four concerns under a "Secure macOS VZ block-device helper" subject: security hardening, rebase conflict resolution, the fd-retention refactor, and reviewer cleanup. The fd-retention change is not hardening, and it is the one change here that breaks a shipping driver — folding it under that subject is plausibly how C1 escaped notice through several review rounds. Splitting it into its own commit would help whatever happens to the rest.

## Acknowledged Limitations

- **Documented data-corruption risk.** `disk.md:144` warns that mounting a shared block-device filesystem on host and guest simultaneously can corrupt data, and the BATS test encodes the stop/remount handoff it requires. The feature exposes this by design; the limitation is documented and tested.
- **Deliberate non-blocking drain.** The comment at `pkg/blockdevice/block_device_darwin.go:556-557` explains why the code does not wait for a helper response after sudo fails. The handling is correct, though S1 makes this path the common one.
- **Guest device naming.** The comment at `pkg/driver/vz/block_device_darwin.go:69-71` correctly notes the identifier does not pin a guest `/dev` node; the 20-character truncation is a VZ API limit.

## Review Process Notes

### Skill improvements

- **Treat a deleted comment as a claim.** When a diff removes a comment documenting a non-obvious invariant — why a reference is held, why an order is fixed, why a check exists — treat the deletion as an implicit assertion that the invariant no longer applies, and verify that assertion against the code the comment guarded. Comments of this kind are often the only record of a constraint the type system does not encode, so their removal alongside a refactor signals that the refactor may have dropped the constraint rather than obviated it.

- **Check what each call site passes when a behavior becomes conditional.** When a change converts an unconditional behavior into a conditional one — adding a nil guard, an opt-in parameter, or a feature flag — enumerate every call site and confirm what each one now supplies. Refactors commonly thread the new parameter through the call sites inside the diff while leaving exported wrappers passing a zero value, which silently removes the behavior for every caller outside it. The wrapper looks innocuous in review because its body is one line; the behavior change lives in the argument.

### Repo context updates

- **[repo] The vz driver exports helpers that krunkit calls.** `pkg/driver/vz` exports `PassFDToUnix` and `DialQemu`, which `pkg/driver/krunkit` calls. A change to vz internals can therefore break krunkit without any krunkit file appearing in the diff. When reviewing changes to exported functions in `pkg/driver/vz`, enumerate callers under `pkg/driver/krunkit` and confirm each still receives the prior behavior.

- **[repo] The vz driver has an external-binary build mode.** `ADDITIONAL_DRIVERS=vz` sets the `external_vz` build tag, which excludes `pkg/driver/vz/register.go` from limactl and runs the driver inside `lima-driver-vz` instead. Any vz code that depends on `os.Executable()`, or on a command registered only under `cmd/limactl`, behaves differently in that build. Features added to the vz driver should state whether they support it, and the other backends' explicit rejection stubs are the convention to follow when they do not.

- **[repo] Instance directories are created with mode 0700.** `pkg/instance/create.go` creates `inst.Dir` with `0o700`. Code requiring a private directory beneath `inst.Dir` — for example a Unix socket whose parent must not be group- or world-accessible — is satisfied by construction. Do not flag such a requirement as a setup step the user must perform.

## Critical Issues

**C1. `PassFDToUnix` no longer retains socketpair descriptors, so krunkit's network fd can be closed by GC — `pkg/driver/vz/vm_darwin.go:991-993`** *(critical, regression)*

```go
	if retainedFDs != nil {
		retainedFDs.Append(server, client)
	}
	return server, client, nil
```

At the merge base, `createSockPair` unconditionally appended to the package global `vmNetworkFiles`, whose comment read: *"Hold all `*os.File` created via `socketpair()` so that they won't get garbage collected. `f.FD()` gets invalid if f gets garbage collected."* That comment was deleted along with the global.

The exported `PassFDToUnix` now calls `passFDToUnix(unixSock, nil)` (`pkg/driver/vz/network_darwin.go:27-29`), so `createSockPair` skips the `Append` entirely. Its only non-test caller is `pkg/driver/krunkit/krunkit_darwin_arm64.go:125`, which uses the returned file purely for its raw number at line 130 (`fmt.Sprintf("virtio-net,type=unixgram,fd=%d,...", client.Fd(), ...)`) and then drops the reference when `buildNetworkArgs` returns. `os.NewFile` installs `runtime.SetFinalizer(f.file, (*file).close)` (Go 1.26.4, `os/file_unix.go:225`), so once `client` is unreachable any GC cycle before `cmd.Start()` closes the fd — krunkit then inherits a closed or, worse, recycled descriptor. `DialQemu` (`network_darwin.go:55-57`) has the same nil-retention shape for any future external caller.

Fix: give the exported wrappers a retainer rather than `nil`.

```diff
-func PassFDToUnix(unixSock string) (*os.File, error) {
-	return passFDToUnix(unixSock, nil)
-}
+// processRetainedFDs holds descriptors for callers outside the VZ VM lifecycle
+// (krunkit), which have no per-VM retainer to hand in.
+var processRetainedFDs = newRetainedFileDescriptors()
+
+func PassFDToUnix(unixSock string) (*os.File, error) {
+	return passFDToUnix(unixSock, processRetainedFDs)
+}
```

Apply the same to `DialQemu`. `TestRetainedFileDescriptorsArePerVM` (`pkg/driver/vz/block_device_darwin_test.go:22`) covers the per-VM property but not the "exported wrapper still retains" property that krunkit depends on — add that assertion.

## Important Issues

**I1. `VerifySudoAccess` downgraded from exact match to substring containment — `pkg/networks/sudoers.go:105-113`** *(important, regression)*

```go

	// non-network entries. Network startup only needs its own generated
	// fragment to be present verbatim.
	if !strings.Contains(string(b), sudoers) {
```

`/etc/sudoers.d/lima` was previously required to be byte-identical to Lima's own output, which is the property PR #2734 was defending: Lima refuses to proceed against a sudoers file it did not fully generate. With `Contains`, any file that embeds the network fragment anywhere passes — including one carrying stale or hand-edited privileged rules Lima would previously have flagged. The loosening is needed for composition, but it is broader than composition requires.

Fix: keep an exact check against the composed content. Either have `VerifySudoAccess` accept the full expected content from the caller (`cmd/limactl` already composes it via `sudoers.AssembleSudoersFragments`), or verify the file equals `networkFragment + optionalBlockDeviceFragment` rather than merely containing the first. At minimum, anchor the containment so the fragment must start at a line boundary and the remainder must parse as known Lima fragments.

**I2. `limactl sudoers --check` silently reports a correct file as out of sync, and its hint destroys the block-device grant — `cmd/limactl/sudoers_darwin.go:108-114`** *(important, regression)*

```go
	content, err := renderSudoers(nwCfg, blockDevices)

		return err
```

`blockDevices` comes from the `--block-device` flag on *this* invocation (line 36). **S1. Accept goroutine reads the nonce with no deadline — `pkg/blockdevice/block_device_darwin.go:516-521`** *(suggestion, regression)*

```go
			nonce := make([]byte, len(req.Nonce))
			if _, err := io.ReadFull(conn, nonce); err != nil {
				_ = conn.Close()
				fdCh <- receivedFD{err: fmt.Errorf("failed to read authentication nonce: %w", err)}
```

The deferred `listener.Close()` (line 486) unblocks `AcceptUnix` but not an already-accepted `conn`. A root peer that connects and stalls leaks the goroutine and the conn for the process lifetime; `waitForReceivedFD` returns on ctx but the goroutine does not. Only root can trigger it, so the practical impact is low.

**S2. Received fd is stranded in the channel on context cancellation — `pkg/blockdevice/block_device_darwin.go:564-567`** *(suggestion, regression)*


If ctx fires while the goroutine is mid-handoff, the goroutine pushes an open `*os.File` into the buffered channel that nobody drains. Fix: on the `waitForReceivedFD` error path, `if f := drainReceivedFD(fdCh); f != nil { _ = f.Close() }` before returning.

Defense in depth in a privileged helper is defensible, but the repetition obscures which check is load-bearing.

## Design Observations

### Concerns

**Device-number grants are neither stable nor time-bounded** *(future)*

`macOSDiskDevicePathRE` (`pkg/blockdevice/block_device_darwin.go:41`) pins the sudoers grant to a path like `/dev/disk4`, and `openDiskDeviceNoFollow` opens it `O_RDWR` (line 346). macOS assigns `diskN` by attach order, so a grant issued for a USB stick at `/dev/disk4` becomes a standing root read/write grant for whatever device lands on slot 4 after the next reboot or replug — a different user's external drive, a disk image, or a partition of a data volume. Nothing in `/etc/sudoers.d/lima`, the docs, or the code expires or re-confirms the binding.

Two directions worth evaluating: (a) record the device's disk UUID / `IORegistry` identity at grant time and have the helper re-verify it after opening, rejecting a mismatch — this makes the grant name the *device*, not the slot; (b) failing that, document the volatility prominently and recommend regenerating the sudoers file per session. Option (a) also closes the door on a future `--block-device=/dev/disk0` grant surviving as a permanent boot-disk handle. Related: the helper always opens `O_RDWR`, so there is no way to express a read-only attachment even though `NewDiskBlockDeviceStorageDeviceAttachment` takes a `readOnly` argument (`pkg/driver/vz/block_device_darwin.go:36` passes `false`).

**Layering forces `--check` and `VerifySudoAccess` apart** *(in-scope)*

I1 and I2 are the same problem seen from two sides: `pkg/networks` owns half the file and `pkg/blockdevice` owns the other half, so neither can verify the whole. The composition already lives in `cmd/limactl` (`renderSudoers`, `sudoers_darwin.go:59-72`). Moving verification there too — one function that renders the expected file and compares exactly, called by both `--check` and network startup — collapses both findings and restores the exact-match property from #2734.

### Strengths

- Pinning the allowed device as **argv** (`cmd/limactl/sudo_open_block_device_command_darwin.go:25`) rather than trusting stdin is the right primitive: sudo's own command matching becomes the allowlist, so the policy lives in the file the admin reviewed. `validateForAllowedDevice` (`block_device_darwin.go:183-194`) is a belt-and-braces re-check, not the gate.
- The defense stack around the open is genuinely layered and each layer is independently justified: `Lstat`+symlink reject → `O_NOFOLLOW` → post-open `Stat` → `validateDiskDeviceMode` block/char cross-check. This closes the TOCTOU window rather than papering over it.
- `duplicateFileCloseOnExec` (`block_device_darwin.go:603-609`) using `F_DUPFD_CLOEXEC` on the root-opened fd is a detail most implementations miss.
- Requiring `SUDO_UID` (`block_device_darwin.go:279-289`) and validating the socket directory against it means the helper cannot be coaxed into delivering the fd to a directory the sudo-invoking user does not own.

### Design Observations

#### Concerns

- **Structured blockDevices Schema**: Currently, `blockDevices` is a flat slice of string paths. This is simple, but limits future extensions like read-only configuration, caching, or sync options. Transitioning to a union-type schema (supporting both string paths and objects) would maintain backward compatibility while allowing advanced tuning. `(future)`
- **Symmetric Hint Formatting**: Defining the surrounding parentheses in error formatting (`(Hint: %s)`) while defining the closing parenthesis inside the helper `hint` string (`run ... %q)`) is asymmetric and leads to rendering bugs. Defining all decoration at the print/error formatting site is a cleaner pattern. `(in-scope)`

#### Strengths

- **Comprehensive Defense-in-Depth**: The privileged helper implementation is exemplary in its security posture, using `O_NOFOLLOW` on open, double-checking the `fstat` of the resolved fd to prevent TOCTOU symlink races, restricting socket folder permissions to `0700` owned by `SUDO_UID`, and utilizing peer UID credentials checking alongside a random 64-character nonce handshake.
- **Isolating VZ File Descriptors**: Storing and managing Virtualization-framework file descriptors inside a per-VM struct `retainedFileDescriptors` instead of a package-global map prevents VM lifecycles from leaking or closing descriptors that belong to another VM running concurrently.

### Testing Assessment

The test coverage in `pkg/blockdevice/block_device_darwin_test.go` and `pkg/driver/vz/block_device_darwin_test.go` is extensive and extremely high quality. It directly tests the nonce challenge, peer-UID verification, socket path ownership, and `retainedFileDescriptors` segregation.

Potential scenarios to watch:
1. **Concurrent VM Start Race**: Multiple VMs starting concurrently requesting different block devices. (Successfully covered by unit tests proving `retainedFileDescriptors` are strictly per-VM).
2. **Helper Process Crash During Open**: What happens if the `sudo-open-block-device` helper crashes or hangs after opening the device but before connecting to the Unix socket. (Properly handled by the context-aware `waitForReceivedFD` select block).
3. **Malicious Peer Connection Attempt**: An unprivileged user trying to write to the temporary Unix socket directory or connect to the socket during the handshake. (Checked and prevented by `validatePrivateSocketPath` checking that parent is owned by `SUDO_UID` with `0700` mode, and the socket peer UID being checked via `LOCAL_PEERCRED`).

### Acknowledged Limitations

- **Host-Guest Concurrency Danger**: "Avoid mounting filesystems on shared block devices on both host and guest at the same time, it will cause corruption..." (documented in `website/content/en/docs/config/disk.md:144-147`).
- **VZ-Only Support**: Support for `blockDevices` is explicitly limited to the `vz` driver on macOS (enforced in `pkg/driver/qemu/qemu_driver.go:121-123` and `pkg/driver/krunkit/krunkit_driver_darwin_arm64.go:193-195`).
