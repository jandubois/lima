## Executive Summary

The change pins both halves of a Windows reverse-sshfs mount (the host path form and the local sftp-server) to the one `ssh.exe` Lima resolved at startup. This gives `sshutil.SftpServerForSSH` its first caller. The mechanism is sound. But two log lines misreport ordinary setups, the pairing this PR exists to establish has no test, and the ssh transport itself stays unpinned.

Four reviewers ran the same prompt. Gemini 3.1 Pro reported nothing; Gemini 3.5 Flash reported one finding that verification rejected. Claude and Codex agreed on the substance.

## Suggestions

S1. **The lookup and warning also run when `sftpDriver: builtin`, where both are inert** — `pkg/hostagent/mount.go:65` [Codex GPT 5.6 Sol, Claude Opus 5]

```go
		sftpServerBinary = sshutil.SftpServerForSSH(ctx, a.sshExe)
```

`Driver` comes from `*m.SSHFS.SFTPDriver`, which users may set to `builtin` (`pkg/limatype/lima_yaml.go:179`). sshocker v0.3.9 documents `OpensshSftpServerBinary` as "used only when Driver == DriverOpensshSftpServer", and its `Start()` takes the NOP branch for `DriverBuiltin`. So sshocker ignores the field, performs no auto-detection, and the warning describes a fallback that cannot happen. The Cygwin branch also spends a `cygpath -w` subprocess per mount for a value nobody reads. The default is `""`, which does route through detection, so only the explicit opt-out suffers.

Fix: guard the whole block on `*m.SSHFS.SFTPDriver != limatype.SFTPDriverBuiltin`.

**Resolved: fixed.** `mountPathAndSftpServer` returns early for `limatype.SFTPDriverBuiltin`, skipping both the lookup and the log.

S2. **The warning fires on an ordinary client-only OpenSSH install, and the next line contradicts it** — `pkg/hostagent/mount.go:66-69` [Claude Opus 5]

```go
		if sftpServerBinary == "" {
			logrus.Warnf("reverse-sshfs: no sftp-server found alongside %#q; falling back to auto-detection, which may pick one that cannot resolve %#q", a.sshExe.Exe, resolvedLocation)
		}
		logrus.Debugf("reverse-sshfs: host path %#q resolved to %#q for sftp-server %#q", m.Location, resolvedLocation, sftpServerBinary)
```

`pickCompleteSSHOnWindows` accepts a toolchain on `scp.exe` and `ssh-keygen.exe` alone, so a selected `ssh.exe` with no sibling `sftp-server.exe` is a supported configuration; Windows ships `sftp-server.exe` with the OpenSSH Server feature, not the client (reasoned, no Windows host was available). The builtin driver then serves the mount fine. Warning once per mount on a working setup trains operators to ignore warnings, and the `Debugf` prints `for sftp-server ""` right after announcing that none was found.

Fix: demote the warning to `Infof`, and make the `Debugf` an `else` branch so the two cannot both fire.

**Resolved: fixed.** The warning is now `Infof` and the `Debugf` sits in an `else`, so only one fires per mount. The message also names the toolchain instead of `ssh.exe`'s directory, which was wrong for the Cygwin branch: that branch asks cygpath for `/usr/lib/ssh/sftp-server` rather than looking beside `ssh.exe`.

S3. **`SftpServerForSSH` can return a candidate sshocker rejects, and that rejection is fatal** — `pkg/sshutil/sshutil.go:256-259` [Claude Opus 5]

```go
		for _, p := range []string{candidate, candidate + ".exe"} {
			if _, err := os.Stat(p); err == nil {
				return p
			}
		}
```

With the default driver `""`, sshocker routes to `DetectDriver(explicit)`, which runs `exec.LookPath(explicit)` and on failure returns an error that `Start()` wraps as `failed to choose driver automatically`. Both `Start()` attempts then fail, so the mount errors out where an empty field would have degraded to auto-detect or builtin. Go 1.26's `findExecutable` skips the direct stat for an extension-less path and tries only `file+ext`, so it rejects a candidate that `os.Stat` here accepts. Cygwin's magic-`.exe` handling means the real file is `sftp-server.exe` today, so the filesystem layout guards this, not the code.

Fix: validate the candidate with `exec.LookPath` before returning it, so a non-executable match yields `""` and preserves the fallback.

**Resolved: fixed.** Both branches of `SftpServerForSSH` now resolve through `exec.LookPath`, and the Cygwin branch logs the rejected candidate at Debug. The accompanying comment is scoped to the default driver, since sshocker skips `DetectDriver` entirely when `sftpDriver` is set to `openssh-sftp-server`.

S4. **The native branch drops the input rejection the replaced helper performed** — `pkg/hostagent/mount.go:61` [Claude Opus 5]

```go
		resolvedLocation, err = sshutil.PathForSSH(ctx, a.sshExe, m.Location)
```

Without `cygpath`, the old `fsutil.WindowsSubsystemPath` fell through to `windowsSubsystemPathWithoutCygpath`, which rejects UNC and drive-relative inputs with an explicit error (`pkg/fsutil/fsutil_windows.go:52-66`). `PathForSSH`'s native branch is a bare `filepath.ToSlash`, so a UNC location becomes `//server/share/dir` and flows on. `pkg/limayaml/validate.go:124-127` accepts UNC because `filepath.IsAbs` does, and sshocker's own relative-path check passes it too, so the mount fails later with a vaguer error. Niche, and plain-Windows reverse-sshfs did not work at all before this PR.

Fix: reject a `filepath.VolumeName` that is not a two-character drive letter in `PathForSSH`'s native branch, matching the Cygwin-less fallback's contract.

**Resolved: declined.** This finding is wrong. A UNC location mounts under the builtin driver: `filepath.ToSlash` yields `//server/share/dir`, sshfs 3.7.3 prefixes that verbatim, and `pkg/sftp` v1.13.11's `toLocalPath` maps it back to `\\server\share\dir`. The old helper rejected UNC only when cygpath was absent, so this PR enabled such mounts rather than losing a guard, and the proposed rejection would remove them. A rejection was implemented, verified against that chain, then reverted.

## Design Observations

### Concerns

1. **The converted path also becomes the guest's sshfs base path** *(in-scope)* [Claude Opus 5]. sshocker uses `LocalPath` twice: as the `-d` root of the local sftp-server, which this PR pairs, and as the guest's `sshfs ':'+LocalPath` argument, which it does not. On the native branch the guest now receives `:C:/Users/jan` where every earlier form began with `/`. Reading sshfs 3.7.3 settles most of it: `find_base_path` scans forward to the first colon, so the base path is `C:/Users/jan`, and `buf_add_path` prepends it verbatim with no realpath expansion. Two residual questions remain for the deferred plain-Windows run. Win32 OpenSSH's sftp-server must resolve a drive-letter path in `SSH_FXP_LSTAT`, since `sftp_check_root` requires it to stat as a directory. And `transform_symlink` returns early unless the base path starts with `/`, so absolute symlinks inside the mount stop being rewritten.

2. **The "single ssh.exe" invariant stops short of the transport** *(in-scope)* [Codex GPT 5.6 Sol, Claude Opus 5]. sshocker's `SSHConfig.Binary()` is a hardcoded `return "ssh"` in both v0.3.9 (pinned at `go.mod:10`) and v0.3.11, so PATH picks the ssh that carries the mount, not `a.sshExe`. Every other ssh invocation in Lima execs `sshExe.Exe` (`pkg/copytool/rsync.go:74`, `pkg/mcp/toolset/toolset.go:48`, `cmd/limactl/shell.go:464`, `cmd/limactl/tunnel.go:114`); reverse-sshfs is the exception. `pickCompleteSSHOnWindows` can select an ssh that `exec.LookPath("ssh")` would not, because it skips a PATH directory missing `scp.exe` and falls back to `%SystemRoot%\System32\OpenSSH`, which need not be on PATH. In that last case the mount fails outright. Any `sshExe.Args` from `$SSH` are dropped too. Closing this needs a `Binary` field upstream in sshocker, and nothing here makes it worse.

### Strengths

- `m.Location` stays native for `os.MkdirAll` while the converted value lives in `resolvedLocation`, so no single variable carries both forms *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash]
- Caching `sshExe` on the `HostAgent` (`hostagent.go:62`, `:271`) keeps every mount on one toolchain decision and makes it available to later hostagent call sites *(in-scope)* [all four reviewers]
- Returning `""` from `SftpServerForSSH` leaves sshocker's own detection in place, so a host Lima cannot pair degrades instead of failing *(in-scope)* [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]

## Review Process Notes

### Skill improvements

- When a change alters the *format* of a value that is handed to a third-party library (a path, a URL, an identifier), read the library's source and enumerate every place it forwards that value, not only the consumer the change targets. A library's field documentation names its primary use and stays silent about the rest, so a format that satisfies one consumer can break a second one in the same call. Flag any such value whose other consumers the change does not account for.
- Verify a finding's supporting citations, not only its own `file:line`. When a finding argues from precedent elsewhere in the project (a named test, helper, or convention "already used" in a sibling area), confirm that reference exists at the review SHA. An agent working from a series of related branches will cite work that has not merged, and the citation reads as established practice.

With the default driver `""`, sshocker's `Start()` routes to `DetectDriver(explicit)`, which runs `exec.LookPath(explicit)` and, on failure, returns an error that `Start()` wraps as `failed to choose driver automatically`. Both `Start()` attempts (`mount.go:101` and `:105`) then fail, so the mount errors out — where before this PR the empty field always degraded to auto-detect or builtin. Go's Windows `findExecutable` will not match an extension-less path, but `os.Stat` at line 257 accepts one. Cygwin's magic-`.exe` handling means the real on-disk file is `sftp-server.exe`, so the first loop element does not currently match; the guard is the filesystem layout, not the code.

Fix: validate the candidate with `exec.LookPath` before returning it, so a non-executable match yields `""` and preserves the fallback.

**S4. The native branch drops the input rejection the replaced helper performed — `pkg/hostagent/mount.go:61` (suggestion, regression)**

```go

```

On a Windows host with no `cygpath`, the old `fsutil.WindowsSubsystemPath` fell through to `windowsSubsystemPathWithoutCygpath`, which rejects UNC and drive-relative inputs with an explicit error (`fsutil_windows.go:53-67`). `PathForSSH`'s native branch is a bare `filepath.ToSlash` (`sshutil.go:238`) with no validation, so a UNC location becomes `//server/share/dir` and flows on. `limayaml/validate.go:125` accepts UNC because `filepath.IsAbs` does, and sshocker's own relative-path check passes it too. The mount then fails later with a less informative error. Niche, and plain-Windows reverse-sshfs did not work at all before this PR, so it is not a practical regression.

Fix: reject a `filepath.VolumeName` that is not a two-character drive letter in `PathForSSH`'s native branch, matching the Cygwin-less fallback's contract.
