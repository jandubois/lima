## Important Issues

I1. **Doc comments and the commit message state that scp parses `IdentityFile`** — `pkg/sshutil/sshutil.go:411` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
// CommonOptsForTool is CommonOpts for a caller that hands the options to a
// binary other than sshExe, such as scp, which parses IdentityFile itself
// rather than passing it to a separately named ssh. Path options take
```

scp forwards `-o` options verbatim to an ssh subprocess. I captured the child argv with `scp -S <script> -o "IdentityFile='/tmp/keyfile'"` on OpenSSH 10.2p1: `[-o] [IdentityFile='/tmp/keyfile'] [-o] [IdentitiesOnly=yes]`. The ssh it spawns is its own (`strings /usr/bin/scp` gives the compile-time `/usr/bin/ssh`; Win32-OpenSSH resolves it beside the running binary), so keying the form to `t.toolPath` stays correct for a different reason: scp's sibling ssh shares scp's path conventions, and `t.sshExe` need not.

The same mechanism appears at `pkg/copytool/copytool.go:124`, at `pkg/copytool/copytool_test.go:157`, and in the commit body ("because scp parses its own options"). The commit message becomes permanent history, and a reader who checks the claim may conclude the `toolPath` threading is unnecessary.

Fix: say that scp forwards these options to the ssh from its own install, so the form must match that toolchain.

I2. **No Windows CI job runs the rsync backend, so the new test hunk never executes** — `hack/test-templates.sh:306` [orchestrator]

```bash
	testdir_host=$testdir
```

## Design Observations

### Concerns

- **`limactl shell --sync` still mixes two toolchains' path forms in one rsync argv** *(future)* [Claude Opus 5]. `mountDirFromWindowsDir` converts `hostCurrentDir` through the PATH-global `fsutil.WindowsSubsystemPath`, and the result reaches `copytool` as a rooted non-`IsAbs` path that `pathForRsync` passes through untouched, while `hostTmpDest` from `askUserForRsyncBack` arrives native and is converted by rsync's own sibling cygpath. Both forms agree under this repo's CI, where Git for Windows and MSYS2 both map `C:\` to `/c/`; a stock Cygwin install or a custom fstab would not. This PR narrows the gap, leaving `mountDirFromWindowsDir` as the last PATH-global converter feeding a toolchain-pinned consumer.

- **`CommonOptsForTool`'s promise about version detection holds only for the first caller** *(in-scope)* [Claude Opus 5]. The doc says version detection still runs against `sshExe`, but that probe sits inside `sshInfo.Do` (`pkg/sshutil/sshutil.go:479`), a process-wide `sync.Once`, so after any earlier call the argument is inert. The `sync.Once` predates this PR; the new doc is the first place that promises anything about it.

### Strengths

- Converting local operands before the trailing-slash pass at `pkg/copytool/rsync.go:114` *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol]. It preserves directory-versus-contents semantics that cygpath output would otherwise scramble, and the comment says why.
- Keying each path to the binary that consumes it *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]. All four reviewers named this as the right split, and it removes `pkg/copytool` from the PATH-global converter's callers.
- Resolving symlinks inside `pathForRsync` rather than in `newRsyncTool` *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol]. It keeps `exec`'s target and `argv[0]` untouched on every platform, and the comment records that constraint.
- One shared `sshOptsForInstance` for the availability probe and the transfer *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol]. It forecloses a probe rejecting an rsync the command would have driven.
- Classifying Windows absolute paths before the `":"` split *(in-scope)* [Gemini 3.5 Flash, Claude Opus 5]. Single-letter instance names keep working, and `TestParseCopyPathsWindowsDriveLetter` pins both halves.

## Review Process Notes

### Skill improvements

- When a change adds a test or a CI step, confirm the job that would run it actually reaches it. Read the workflow's setup steps for the tools the test's guard requires, and read the most recent job log for a skip message. A guarded block (`if command -v X`, a platform conditional, a matrix filter) reports success whether it ran or was skipped, so a reviewer who reads only the diff records new coverage where none exists, and a later round inherits that belief as established.

- When a comment or commit message explains *why* a change is correct by naming a mechanism in an external tool, verify the mechanism before accepting the conclusion. Run the tool and observe what it does with the input in question. A correct conclusion resting on a wrong mechanism reads as fully verified, and the next reader who checks the mechanism has grounds to revert the change.

- When a prior round's fix replaced a comment that was wrong, check whether the replacement errs in the opposite direction. A correction written to escape one over-claim commonly lands on its mirror image, and the round that requested the fix is the least likely to re-examine it.

### Repo context updates

- [repo] Neither Windows CI job installs rsync. `.github/workflows/test.yml` prepends `C:\msys64\usr\bin` to PATH and runs `pacman -Sy --noconfirm openbsd-netcat diffutils socat w3m`, which omits rsync, so `hack/test-templates.sh` logs `Skipping rsync backend test (rsync not available on host or guest)` on both the QEMU and WSL2 Windows jobs. Any claim that Windows CI exercises the rsync backend, its path conversion, or its `-r` trailing-slash handling is false. The Linux and macOS jobs do run that block, so a guest-side explanation for the skip is wrong.

- [repo] Windows unit tests do run: the WSL2 Windows job has a `go test -v ./...` step on `windows-2025` before its integration step. A Windows-only branch guarded by `runtime.GOOS == "windows"` in a Go test therefore executes in CI, unlike a Windows-only branch reachable only through `hack/test-templates.sh`.

- [repo] scp does not interpret the `-o` options Lima passes it. It forwards them to an ssh subprocess resolved from its own install directory (`/usr/bin/ssh` compiled in on Unix; beside the running binary under Win32-OpenSSH). Path-valued options must therefore take the form scp's *toolchain* reads, which is why keying them to the scp binary is right, and any comment saying scp parses them itself is wrong.

- [repo] `pkg/hostagent/requirements.go` and `pkg/hostagent/mount.go` rebuild the hostagent's `sshConfig` with `DisableControlMasterOptsFromSSHArgs` on Windows. Combined with the hostagent's own `sshConfig` keeping the mux options, this means some hostagent invocations multiplex on Windows and some do not. Reject both blanket claims: that Lima strips multiplexing everywhere on Windows, and that every command the hostagent runs multiplexes.

## Design Observations

### Concerns

**`limactl shell --sync` still mixes two toolchains' path forms in one rsync argv (future).** `mountDirFromWindowsDir` (`cmd/limactl/shell.go:783-789`) converts `hostCurrentDir` through `fsutil.WindowsSubsystemPath`, which shells out to the PATH-global `cygpath`. That already-converted value reaches `copytool` as a rooted, non-`IsAbs` path, so `pathForRsync` passes it through untouched (`pkg/copytool/rsync.go:95-97`), while `hostTmpDest` from `askUserForRsyncBack` (`cmd/limactl/shell.go:581`) arrives native and *is* converted by rsync's own sibling `cygpath`. Under this repo's own CI both forms happen to agree, because `_LIMA_WINDOWS_EXTRA_PATH` puts Git for Windows first while rsync comes from MSYS2 and both map `C:\` to `/c/`; a stock Cygwin install (`/cygdrive/c/`) or a non-default `fstab` would not. This PR narrows the gap rather than widening it, so it is not a regression — but it leaves `mountDirFromWindowsDir` as the last PATH-global converter feeding a toolchain-pinned consumer. Routing it through the same helper `pathForRsync` uses would close the class.

**Two binaries in one signature (in-scope, low cost).** `CommonOptsForTool(ctx, sshExe, toolPath, useDotSSH)` and `SSHOptsWithoutMultiplexing(ctx, sshExe, toolPath, username, useDotSSH)` take two executables where `sshExe` now serves only the version probe. That probe runs under `sshInfo.Do` (`pkg/sshutil/sshutil.go:479-482`), a process-wide `sync.Once` — so after the first call anywhere in the process, the `sshExe` argument is inert. The doc's "version detection still runs against sshExe" is therefore true only of the first caller. The `sync.Once` predates this PR, but the new doc is the first place that makes a promise about it. Either drop the caveat or note that the first caller wins.

### Strengths

- Converting local operands **before** the trailing-slash pass (`pkg/copytool/rsync.go:114-123`) preserves the directory-vs-contents semantics that `cygpath` output would otherwise scramble, and the comment says exactly why.
- Resolving symlinks for the `cygpath` sibling lookup *inside* `pathForRsync` rather than in `newRsyncTool` (`pkg/copytool/rsync.go:98-99`) keeps `exec`'s `argv[0]` untouched — a non-obvious constraint that the comment records.

### Design Observations

#### Concerns

None.

#### Strengths

- **Dynamic, Toolchain-Aware Path Formatting**: Moving away from the PATH-global `ioutilx.WindowsSubsystemPath` in `copytool` and using `PathForTool` guarantees that paths are converted precisely based on the target binary's toolchain (Cygwin-based vs. native Windows OpenSSH).
- **Separation of Absolute and Drive-Relative Paths**: Pre-classifying absolute drive-letter paths before performing the colon split in `parseCopyPaths` on Windows beautifully preserves the local status of full paths while keeping single-letter instance support intact.

---

### Testing Assessment

#### Untested Scenarios

1. **Host-to-Host (Multi-Instance) Transfer using scp on Windows**: While `TestSCPCommandLocalPathForm` and `TestSSHOptsForInstanceMultiplexing` verify local and single-instance behavior, copying files between multiple running Windows instances is not fully simulated in the unit tests.
2. **Cygwin-based `rsync` Resolution fallback on Windows**: When `cygpath.exe` is missing from the directory of `rsync`, the native MSYS-style fallback in `WindowsSubsystemPathWithCygpath` is used. This path is tested via integration tests but lacks a standalone mocked unit test.

### Documentation Assessment

All newly exported symbols (`PathForTool`, `CommonOptsForTool`, `CompanionForSSH`, `SSHOptsWithoutMultiplexing`) have extremely precise, informative, and grammatically standard docstrings explaining their underlying architectural intent.

### Acknowledged Limitations

- **Unit test for pathForRsync's real cygpath branch** (`pkg/copytool/rsync.go:88`): The author declined a mock unit test as it is covered end-to-end by the MSYS2 integration test runner, and a local unit test would require a live Cygwin setup.
- **Native Windows OpenSSH end-to-end validation**: The author noted that validation on plain Windows hosts is deferred to a later PR (#5342) containing the Windows plain-CI jobs.
- **Multi-instance scp on Windows (no User=)**: The branch is pre-existing and requires multiple concurrent instances on Windows.
- **The hostagent running guest commands with multiplexing on Windows**: The limitation is pre-existing and outside the scope of `copytool`.
- **Tests for UNC and extended-length (`\\?\`) paths**: The path-parsing rules correctly classify them and do not misread them as remote hostspecs.
- **`cmd/limactl/shell.go` building then stripping ssh options**: Deemed behavior-neutral.
- **`srcWdDepth` calculation on pre-converted path**: This remains an acknowledged pre-existing bug.
- **Error classification inside `pkg/copytool/copytool.go`**: Handled via a separate unmerged branch.
