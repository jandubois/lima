## Suggestions

S1. **`prune --keep-referred` fails when another prune removes an entry it waits on** — `pkg/downloader/downloader.go:1364` [Gemini 3.5 Flash]

```go
func removeStaleTempFilesInDir(dir string) error {
	return lockutil.WithDirLock(dir, func() error {
```

`WithDirLock` now returns `ErrDirRemoved` when the directory disappears while the caller waits for its lock. `RemoveCacheEntry` treats that as success (line 1332), but the stale-partial sweep passes it up. So `limactl prune --keep-referred` exits with "directory was removed while waiting for its lock", although the entry it wanted to clean is gone. A probe that holds an entry's lock, starts `RemoveStaleTempFiles`, and then removes the entry fails 5 of 5 runs at the review SHA and passes 5 of 5 with the merge-base's `downloader.go` and `lockutil`.

It takes a plain `limactl prune` deleting a kept entry while a `--keep-referred` prune waits on it. The merge-base already failed the same way when the entry vanished before `WithDirLock` opened it (`os.Open` at `lockutil_unix.go:34-37` there), and a rerun succeeds.

Fix: ignore `ErrDirRemoved` and `os.ErrNotExist` in `removeStaleTempFilesInDir`, as `RemoveCacheEntry` does.

S2. **Prune waits silently for a download, and the commit message leaves out its narrower scope** — `pkg/downloader/downloader.go:1329-1331` [Claude Opus 5.5]

```go
	err = lockutil.WithDirLock(dir, func() error {
		return os.RemoveAll(dir)
	})
```

At the merge-base, plain `limactl prune` deleted the cache at once. Now it blocks on each entry until the download holding that entry finishes. The only message before the wait is `Pruning …` (line 1299), and `--keep-referred` doesn't log anything above debug level, so against a slow server prune looks hung.

The commit message says prune removes entries under the download lock. It doesn't say that plain prune now keeps the cache root, `download/by-url-sha256`, and anything else under the cache directory. Apart from `pkg/downloader`, only the `limactl-url-fedora-rawhide` plugin writes there, and it rewrites its file on every run, so keeping that file doesn't hurt.

Fix: log a line when the lock wait passes a second or so, and mention the narrower scope in the commit message.

S3. **The Windows `ErrDirRemoved` check has no test that runs on Windows** — `pkg/downloader/downloader_test.go:296-298` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	if runtime.GOOS == "windows" {
		t.Skip("on Windows the lock file held open by the waiting download cannot be removed")
	}
```

`TestDownloadStartsOverWhenPrunedWhileWaiting` is the only test that removes an entry while a download waits for it, and the Windows CI job skipped it. `TestCheckLockedDir` is Unix-only, so the existence check at `lockutil_windows.go:71-74` never runs in a test. Without that check, a waiting download would fail loudly when `fetch` writes into the missing directory, instead of starting over. The race is rare and the failure visible, so the test is optional. The Unix guards are pinned. With `withCacheEntryLock` limited to one attempt, this test fails 40 of 40 runs on macOS.

Fix: hold the entry's lock in the test, start `Download`, remove only the entry directory, and release the lock. That works on Windows because the waiting download holds `<key>.lock` open, not the directory. The 3-attempt limit needs fault injection and can stay unpinned.

S4. **A restart-loop regression shows up as a test timeout, not a failure** — `pkg/downloader/downloader_test.go:745-748` [Claude Opus 5.5]

```go
		ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			requests.Add(1)
			http.ServeContent(w, r, "data", modtime, bytes.NewReader(content))
		}))
```

With `offset > 0` removed from the restart condition at `downloader.go:1219`, each failed verification restarts again, and `restarts at most once after a failed resume` never returns. Under `-timeout 20s` it ends in `panic: test timed out after 20s`. With the default timeout that becomes ten minutes and a goroutine dump that doesn't name the guard. The 416 subtest already cancels its download after three requests (lines 612-618).

Fix: give this subtest a cancellable context and cancel it in the handler once `requests.Add(1) > 3`, so the mutant fails on the request count.

S5. **The tests don't pin the truncation that comes before the metadata write on a 200** — `pkg/downloader/downloader.go:1189-1193` [Codex GPT 6 Astra]

```go
	if !resuming {
		if err := writeResponseMetadata(t, resp); err != nil {
			return err
		}
	}
```

Round 1's S1 moved this block below `openPartialFile` (line 1176), so a new validator is never paired with the old bytes. Moving it back above that line leaves the whole `pkg/downloader` suite green. A kill between the two writes would then pair old bytes with a new `time` or `etag`. The digest still catches the stitched result and the restart begins from scratch, so the gap costs one wasted transfer.

Fix: add a subtest with an existing partial, a 200 response, and a metadata path that can't be written, and assert that the partial is already empty when `Download` returns the error.

S6. **The Windows lock ignores `Stat` errors other than not-exist** — `pkg/lockutil/lockutil_windows.go:72-74` [Gemini 3.5 Flash]

```go
	if _, err := os.Stat(dir); errors.Is(err, os.ErrNotExist) {
		return fmt.Errorf("%w: %#q", ErrDirRemoved, dir)
	}
```

`checkLockedDir` on Unix returns any other `Stat` error (`lockutil_unix.go:66-68`). The Windows check calls `fn` after, say, a permission error, and `fn` then fails at its first file operation, so the caller still gets an error, just from a later point.

Fix: return the error when it is not `os.ErrNotExist`.

S7. **On Windows, `prune --keep-referred` can leave a `<key>.lock` behind for an entry it deleted** — `cmd/limactl/prune.go:58` [Gemini 3.5 Flash]

```go
	for cacheKey, cachePath := range cacheEntries {
```

`CacheEntries` lists the Windows `<key>.lock` files beside the entry directories, and this loop deletes every unreferenced key in map order. When `<key>.lock` goes first, `RemoveCacheEntry(<key>)` recreates it by locking the entry, and the file stays until the next prune. `RemoveAllCacheDir` sorts its keys to avoid exactly this (`downloader.go:1304-1305`). Deleting the lock files of kept entries here predates the PR. I reasoned this from the code, and the reviewers didn't run it on Windows either.

Fix: iterate over the keys in sorted order here too.

## Acknowledged Limitations

- **Declined in prior rounds:** none. Round 1 has no Resolution table, and the maintainer's review of 2026-11-05 asked the author to fix every round-1 finding.
- **Resume needs a digest** (`downloader.go:959-965`). Downloads without one restart from scratch. Do not re-suggest resuming them.
- **Resume needs a cached validator.** Without one `resumeOffset` returns 0, so `offset > 0` still means that a `Range` request went out, and the 206 and 416 guards rely on that.
- **`time` has two jobs** (issue #5724). The stale-`data` bug it causes predates the PR.
- **Round 1's S5**, the Windows defer order on the uncached path, predates the PR; round 1 asked for it in a separate change.
- **On Windows, a plain prune fails when a second download of the same URL waits on the entry.** The waiting download holds `<key>.lock` open, and Go opens files without `FILE_SHARE_DELETE` (`syscall_windows.go:395` in go1.27.4), so deleting the lock file fails. That is the reason for the skip in S3. Because the open lock file can't be deleted, two processes also can't end up locking different `<key>.lock` files. The merge-base's `os.RemoveAll(cacheDir)` failed the same way against open handles. Do not re-suggest running that test on Windows unchanged.

##### Design Observations

**Verdict on the delta (since round 1).** Clean.

- **Prune race fixed.** I ran the maintainer's reproducer, changed to run prune in a goroutine (the author is right that the synchronous version blocks with this fix). At head, 3 of 3 runs passed: download A got the full content, B started over (`requests=2`) and got the full content, and the next download got the full content as `used-cache`. With `RemoveCacheEntry` changed back to a plain `os.RemoveAll`, 3 of 3 failed with `rename …/data.part …/data: no such file or directory`.
- **Lock timing on Unix.** I traced every point where a prune can remove the entry against a download (`withCacheEntryLock` lines 271-293, `checkLockedDir`):
  - between `MkdirAll` and `Open`: `ErrNotExist`, retried;
  - while waiting for the lock: the inode is gone or replaced, so `ErrDirRemoved`, retried;
  - while the download holds the lock: prune waits.

  The `locked` flag keeps a `not-exist` error returned by `fn` itself from being retried.
- **Windows.** The lock lives on the separate `<entry>.lock` file, so a recreated directory is still guarded and the existence check is enough. The sorted removal order puts `<key>.lock` right after `<key>`, because `.` sorts below every hex digit. That makes the comment at line 1304 true.
- **Commit message and PR body.** They describe the delta accurately except for the two omissions in S1.

**Effects of each fix:**
- **Prune under the lock.** This makes prune wait (S1). It also changes what plain prune deletes: only entries now, where it used to delete the whole cache directory. `pkg/downloader` is the only package that writes there (grep for `WithCache`/`UserCacheDir`), so nothing outside the entries is lost.
- **`checkLockedDir`.** This now applies to the other two `WithDirLock` callers, `pkg/sshutil/sshutil.go:320` and `pkg/networks/usernet/recoincile.go:72`. Neither removes its own locked directory, so nothing changes for them.
- **`Accept-Encoding: identity`.** The staged `net/http` source (`transport.go:3021-3039`) confirms that Go adds gzip, and transparently decompresses, only when the request has no `Accept-Encoding` header. So cached requests now store the bytes exactly as served. That also helps with servers that tag `.gz` files with `Content-Encoding: gzip`: Go used to decompress those, which broke the digest.

**PR #5751 interaction.** The finding still holds after #5751. `copyLocal` now writes `perProcessTempfile(dstPath)` next to the caller's local path, never inside a cache entry. So it does not collide with `data.part` or with the `data.tmp.*` cleanup. The orchestrator's merged-tree run supports this.

**Concerns:**
- **(future)** `Cached()` at `downloader.go:611-619` runs the digest check backwards. When the digest file exists, it hashes the whole `data` file; when it is missing, it reads the missing file and fails. Callers fall back to `Download`, so the only cost is time. This predates the PR (blame `5071535b`, 2024).
- **(in-scope, open question)** `Fixes #5171` versus `Refs #5171`. Resume works only with a digest and a cached validator, and the cleanup half of the issue comes from the existing `RemoveStaleTempFiles` sweep. I lean toward `Fixes`, but no maintainer has ruled.

**Strengths:**
- Prune now uses the same per-entry lock as downloads, so round 1's first strength (a stable `data.part` safe under the per-URL lock) holds again, and the retry is contained in one function (`withCacheEntryLock`).
- The restart-at-most-once rule now rests on the partial actually being gone (lines 1218-1225), not on a comment.

##### Design Observations

###### Concerns

- **Issue linking keyword (`Fixes #5171` vs `Refs #5171`)** `(in-scope)`: Issue #5171 requested partial resume for `limactl (create|start)` across concurrent sessions. The PR successfully implements resume for cached downloads (which `create` and `start` use for template images), but uncached direct downloads continue using per-PID temporary files and restart from scratch. If maintainers consider uncached resume part of #5171, changing the keyword to `Refs #5171` keeps the issue open for tracking; otherwise `Fixes #5171` is appropriate.

###### Strengths

- **Robust lock synchronization**: Synchronizing cache downloads and pruning under `WithDirLock` and verifying directory identity via `checkLockedDir` (`os.SameFile`) eliminates directory inode replacement races during pruning.
- **Strict digest verification**: `resumeDigester` reads pre-existing on-disk bytes into the digester before appending incoming HTTP 206 bytes, ensuring corrupt partials never pass validation, with automatic single-restart recovery.
- **Protocol conformance**: Gating 206 on `offset > 0`, enforcing `Accept-Encoding: identity`, and skipping weak ETags aligns the resume logic strictly with RFC 9110 §13.1.5 and §15.3.7.
