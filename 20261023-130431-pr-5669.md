## Executive Summary

The PR moves sudoers digest pinning into `sudoers.NOPASSWD`, so every helper under `lima/privileged` is pinned, the macOS block-device helper included, and it adds `--digest=false` to opt out. The approach is sound and the unit suite passes. The headline finding is I1. The rewritten comment promises a race-free check, but macOS lacks `fexecve(2)`, so sudo there hashes and runs the helper by path. Another comment is now stale, and no test reaches the opt-out in `VerifyFragment`.

## Important Issues

I1. **The digest comment promises a race-free check that macOS cannot give** — `pkg/sudoers/digest.go:28-30` [Claude Opus 5.5]

```go
// replace a helper cannot get the replacement executed as root. Unlike the
// install-path ownership checks, this one runs inside sudo and is therefore
// free of a time-of-check/time-of-use race.
```

At the merge-base this comment sat on `Pin`, which only `lima-privileged-net` used, and that helper runs only on Linux. The PR moves the claim to `pinPrivilegedHelpers`, which now also pins `lima-privileged-block-device`, a macOS-only helper. sudo's default `fdexec=digest_only` runs a digest-checked command through `fexecve(2)`, so it executes the file it hashed, and the sudoers manual (sudo.ws) says the setting "has no effect" without `fexecve`. It adds: "A similar race condition exists on systems that lack the fexecve(2) system call when the directory in which the command is located is writable by the user." The macOS SDK does not declare `fexecve`, while the `execve` control compiles.

The sentence in `website/content/en/docs/config/disk.md:139-140`, "sudo refuses to run a modified helper", still holds for a helper changed before sudo runs, so it can stay.

## Suggestions

S1. **`--digest=false` still reads and hashes every helper** — `cmd/limactl/sudoers_action.go:68-74` [Codex GPT 6 Astra, Gemini 3.5 Flash]

```go
	content, err := renderSudoers(nwCfg, blockDevices, includeNetwork)
	if err != nil {
		return err
	}
	if !pinDigest {
		content = sudoers.Unpin(content)
	}
```

`NOPASSWD` hashes each helper (`pkg/sudoers/sudoers.go:47`) before line 73 strips the digests. So `--digest=false` fails with "permission denied" on a root-owned helper that the user cannot read. `validateSecureHelperFile` accepts such a helper, and its unpinned grant rendered at the merge-base. Codex's probe reproduced this with mode 0111 and passed with 0755. No Lima install produces an unreadable helper (`go build` writes 0755), and the error names the file, so this stays a suggestion. `verifySudoersFile` hashes the same way before it compares.

Fix: pass the pinning choice into the renderers and skip `fileDigest` when pinning is off.

S2. **`--check` accepts either form, ignores `--digest`, and never says which form matched** — `cmd/limactl/sudoers_action.go:142-143` [Gemini 3.1 Pro, Gemini 3.5 Flash, Claude Opus 5.5]

```go
	// Files generated with --digest=false are accepted too.
	if b == content || b == sudoers.Unpin(content) {
```

Accepting an unpinned file is deliberate, as line 142 says, and `VerifySudoAccess` does the same at network start. But `sudoersAction` reads `--digest` and never passes it to `verifySudoAccess`, so `--check --digest=true` passes an unpinned file, and neither check tells the user that pinning is off. Making `--check` strict, as two reviews proposed, would reject a `--digest=false` file under a plain `--check`. That breaks the `sudo cat … | limactl sudoers --check /dev/stdin` advice, which does not pass the flag, and it would disagree with the network-start check.

Fix: say in the `--digest` help that `--check` accepts either form, and log at info level when only the unpinned form matched.

S3. **The regenerate hints leave out `--digest=false`** — `pkg/sudoers/verify.go:80-81` [Consolidator]

```go
	return fmt.Sprintf("run `%s %s >etc_sudoers.d_lima && %s etc_sudoers.d_lima %q`; %s",
		exe, args, install, file, RegenerateGrantWarning)
```

`RegenerateHint` and the block-device failure hint (`pkg/blockdevice/block_device_darwin.go:684`) both print `limactl sudoers` without `--digest=false`. A user who opted out and follows either hint installs a pinned file without noticing. Their next Lima upgrade then breaks the grant they had chosen to keep unpinned.

Fix: mention the flag in both hints, for example "add --digest=false if you generated the file that way".

S4. **`pkg/sudoers` hashes with go-digest but relies on its callers to link `crypto/sha256`** — `pkg/sudoers/digest.go:13` [Gemini 3.5 Flash]

go-digest panics with "sha256 not available (make sure it is imported)" unless the binary links `crypto/sha256`. Flash's standalone program that calls `NOPASSWD` on a privileged helper panics, and the same program exits 0 with `_ "crypto/sha256"` added. This is latent and older than the PR. The merge-base `Pin` had the same imports, and `go list -deps` shows `crypto/sha256` in `limactl` and in the Linux `lima-privileged-net`. `lima-privileged-block-device` imports `pkg/sudoers` without it, but it never renders a grant.

Fix: add `_ "crypto/sha256"` to `digest.go`, the file that hashes.

## Design Observations

### Concerns

- **The digest is defense in depth, and on macOS it is weaker than the prose says** (in-scope) [Claude Opus 5.5]. `.oss-scanner/threat_model.md:54-56` already requires that only root may modify a helper or its parent directories, and Lima checks that before each use. If that invariant later breaks, someone who runs the grant through sudo directly bypasses Lima's checks, and the digest still stops a replaced helper from running as root. On macOS that same broken invariant opens the race in I1. The cost is a regenerated sudoers file after every upgrade unless the user passes `--digest=false`. Master already chose this trade for `lima-privileged-net`, and this PR extends it to the other helper in the same directory, so the change is worth its diff.

### Strengths

- **Pinning follows the install location** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]. The next helper installed under `privileged/` is pinned with no per-helper code, and `pinPrivilegedHelpers` hashes each helper once per `NOPASSWD` call.
- **The checks unpin the expected text, never the installed file** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]. A stale digest is still rejected (`pkg/sudoers/digest_test.go:60-62`), so the opt-out does not weaken the stale-file check.

## Acknowledged Limitations

- **Accepting the unpinned form in `--check` and at network start is deliberate.** The comment at `cmd/limactl/sudoers_action.go:142` says so, and it implements the maintainer's request for an opt-out. Do not re-suggest making `--check` enforce one form unless the network-start check and the `sudo cat … --check /dev/stdin` advice also get a way to pass the user's choice.
- **`Unpin`'s regular expression is unanchored, and no input reaches that.** Every value interpolated into a rendered grant is validated. Helper paths reject whitespace, network names are identifiers, and device paths must be macOS disk nodes. So no input can put `sha256:<64 hex> ` anywhere but a `Digest_Spec`. Do not re-suggest anchoring it.

## Review Process Notes

### Skill improvements

- When a change extends a security mechanism to a helper or code path on another operating system, check every guarantee that the mechanism's comments and docs state against that platform. A guarantee written for the platforms that the mechanism first covered often rests on a system call or kernel feature that the new platform lacks.
- A reproducer must show that its input reaches the branch under test, for example by printing the intermediate value that the branch reads. On a host where the feature is inactive, the before and after runs produce identical output, and the run proves nothing.

### Repo context updates

- [repo] sudo's digest check (`Digest_Spec`) is free of a time-of-check/time-of-use race only where sudo can `fexecve(2)` the file it hashed. macOS lacks `fexecve`, so there a pinned helper is protected from replacement before sudo runs, but a writer of the helper's directory can still race the check. Flag prose that calls a digest-pinned grant race-free on macOS.
- [repo] On a macOS host without socket_vmnet, the network sudoers fragment holds only the `mkdir` grant and no privileged helper, so it does not have a digest. Pinned grants appear in `cmd/limactl` output only through `--block-device` on macOS, or through `lima-privileged-net` on Linux. A probe of digest handling must use one of those, or its pinned and unpinned outputs are identical.
- [repo] `limactl sudoers --check` on a file that does not exist falls back to `VerifyPasswordLess`. That runs `sudo -k`, which drops the user's cached sudo credentials, and then `sudo --non-interactive` probes. Read that path in the code instead of running `--check` against a missing file.

The change moves sudoers digest pinning into `sudoers.NOPASSWD`. Any command under `*/lima/privileged/` is now pinned to its sha256 digest, so the macOS block-device helper is pinned as well. The force-push added a `--digest=false` opt-out, and the checks now accept unpinned grants. The headline finding is I1: the comment says the digest check is free of a time-of-check/time-of-use race, and that is false for the macOS helper this PR newly pins. macOS has no `fexecve`, so sudo cannot run a digest-checked command by file descriptor there.

###### Findings

###### Critical Issues

None.

###### Important Issues

I1. **Digest comment claims no TOCTOU race, which is false on macOS** — `pkg/sudoers/digest.go:26-30` (important, regression)

```go
// sudo (>= 1.8.7) hashes the file immediately before executing it and refuses
// to run it when the digest no longer matches, so an attacker who manages to
// replace a helper cannot get the replacement executed as root. Unlike the
// install-path ownership checks, this one runs inside sudo and is therefore
// free of a time-of-check/time-of-use race.
```

This PR rewrote the comment and extended it to `lima-privileged-block-device`, a helper that runs only on macOS. The sudoers(5) manual (sudo.ws) says:
- `fdexec=digest_only` "avoids a time of check versus time of use race condition when the command is located in a directory writable by the invoking user".
- "If the operating system does not support the fexecve(2) system call, this setting has no effect."
- Even with `fexecve`, a user with write access to the command itself "may be able to replace it after the digest check".

The macOS SDK does not declare `fexecve` (probe below). The attacker this comment describes, someone who can replace a helper, is exactly the one who can race sudo. They can also retry for free under `NOPASSWD`. `website/content/en/docs/config/disk.md:139-140` ("sudo refuses to run a modified helper") overstates the protection in the same way.

```c repro
// save as fx.c; run: cc -Werror=implicit-function-declaration -o fx fx.c

int main(void){char *a[]={0};return fexecve(3,a,a);}

```

###### Design Observations

###### Concerns

1. **Regex post-processing (`Unpin`) instead of conditional rendering** `(in-scope)`: Rather than generating unpinned sudoers entries directly when `--digest=false` is requested, `NOPASSWD` unconditionally reads and hashes helper binaries from disk, formats them with digests, and then strips them back out using `Unpin`'s regular expression replacement (`ReplaceAllString`). Passing a boolean or option to `NOPASSWD` avoids unnecessary disk I/O, prevents failures when binaries cannot be read, and avoids fragile regex post-processing.
2. **Divergence between `--digest` CLI flag and `--check` mode** `(in-scope)`: `--digest` is defined as a general flag on `limactl sudoers` defaulting to `true`. In `--check` mode, however, passing `--digest=true` or `--digest=false` has no effect because `verifySudoersFile` hardcodes acceptance of both pinned and unpinned files. If `--digest` is only intended for generation, documenting it as such or honoring it during verification would prevent confusion.

###### Strengths

1. **Automatic pinning without per-helper boilerplates**: Consolidating pinning in `sudoers.NOPASSWD` based on directory location (`libexec/lima/privileged/` and `lib/lima/privileged/`) ensures that all current and future privileged helpers are pinned without requiring custom `sudoers.Pin` calls at each call site.
2. **Safe backward compatibility for unpinned grants**: `ContainsFragment` and `verifySudoersFile` allow hosts generated with `--digest=false` (or existing unpinned installations) to survive upgrades without false-positive verification errors, while still strictly rejecting stale digests.
