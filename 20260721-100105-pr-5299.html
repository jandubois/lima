Executive Summary ¶

Routing host paths through the ssh that consumes them is the right fix for scp, and the classification restructure in parseCopyPaths is correct and well-commented. But parseCopyPaths feeds both backends, so rsync now receives the native form C:/foo and parses the drive letter as a hostspec. All four reviewers found it independently, and it reproduces.

Two further gaps: scp is still resolved from PATH independent of that ssh, and the new diagnostic Warn cannot fire on the default backend.

Design Observations ¶

Concerns ¶

  • Path formatting is keyed on the wrong binary (in-scope) Claude Opus 4.8 Codex GPT 5.6 Sol Gemini 3.1 Pro. Path.Path now holds a value pre-formatted for one toolchain, so neither backend can recover the native host path. Keeping it native and formatting at each argv site would make I1 and I2 structurally impossible, let scp and rsync diverge correctly, and remove parseCopyPaths's dependency on sshutil, which is what forced the lazy-resolution machinery in S5.
  • Mux stripping spreads by copy-paste (future) Claude Opus 4.8. Four sites now pair runtime.GOOS == "windows" with SSHOptsRemovingControlPath under three separately worded justifications. A sshutil wrapper would hold the policy and its rationale once. The strip is also broader than needed: cygpathForSSH already distinguishes native OpenSSH (no multiplexing at all) from Cygwin ssh (works well enough that the port-forwarder relies on it), so it could be gated on the native case.

Strengths ¶

  • The continue short-circuit at copytool.go:152-155 is the right call Claude Opus 4.8 Gemini 3.1 Pro Codex GPT 5.6 Sol. Once PathForSSH can return a colon-bearing C:/foo, letting it fall through to strings.SplitN(path, ":", 2) would re-misclassify it as instance C. The comment explains why drive-relative C:foo deliberately stays on the instance path.
  • Applying the same strip to the probe (rsync.go:74-78) as to the command it predicts is a correctness fix, not just symmetry Claude Opus 4.8 Codex GPT 5.6 Sol. A probe with different options answers a different question.

Testing Assessment ¶

go test ./pkg/copytool/... passes and GOOS=windows go vet ./pkg/copytool/... is clean on the review host. TestParseCopyPathsWindowsDriveLetter skips on non-Windows by design.

Untested scenarios, highest risk first:

  1. rsync receiving a native-form local path (I1). No test builds an rsync argv from a native-formatted path and checks it is not a hostspec. This is reachable without a Windows host.
  2. The converted path value itself (S1). Neither backend has a test asserting the Cygwin and native forms.
  3. ControlMaster stripping. Nothing asserts that Command emits no -o ControlMaster=… on Windows, nor that checkRsyncOnGuest and Command agree — the invariant rsync.go:75-76 declares.
  4. Test failure modes (S2). The err != nil branch at copytool_test.go:43-48 asserts only a negative, so a PathForSSH regression that returns an error passes silently.
  5. UNC and extended-length paths. filepath.IsAbs accepts \\server\share\f and \\?\C:\f; the native branch yields //server/share/f and //?/C:/f, untested. Both begin with a slash, so neither is misread as a hostspec — low risk, but unexercised.

Review Process Notes ¶

Skill improvements ¶

  • When a change converts a value into a tool-specific format, identify every binary that consumes that value, not only the one the change names. A conversion helper named for one tool (ssh, git, docker) is often called from a shared parsing path that feeds several tools, and the mismatch surfaces only for the consumers the author was not thinking about. Trace the converted value to each exec.Command argv that receives it, and confirm the format matches that binary's expectations.
  • When a change adds a log line, an error message, or any other diagnostic, verify the control-flow path that reaches it under the code's default configuration. Check whether an earlier caller swallows the same error, returns a default that skips the branch, or short-circuits before the diagnostic runs. A diagnostic that only fires on a non-default flag is a gap worth reporting even though the added code reads correctly in isolation.

Repo context updates ¶

  • [repo] On Windows, exec.LookPath for a copy or transfer tool (scp, rsync, cygpath) and sshutil.NewSSHExe can resolve binaries from different toolchains. NewSSHExe honours $SSH with no sibling check and falls back to %SystemRoot%\System32\OpenSSH, which is off PATH, while pickCompleteSSHOnWindows selects only a directory holding ssh.exe, scp.exe, and ssh-keygen.exe together. When reviewing Windows path handling, check whether the code assumes one toolchain for both the ssh transport and the tool consuming local paths.
  • [repo] Windows has no native rsync build, so any rsync on a Windows host is Cygwin or MSYS based and applies Cygwin path semantics, including reading a colon before the first slash as host:path. Native Windows path forms such as C:/foo reach rsync as a hostspec. Flag any code path that hands a drive-letter path to rsync.
  • [repo] limactl shell --sync calls copytool.New with BackendRsync explicitly (cmd/limactl/shell.go), so it bypasses the auto backend's rsync-to-scp fallback. A defect that only affects the rsync backend still reaches users through this path even when limactl copy would have fallen back to scp.
