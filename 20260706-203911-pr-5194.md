## Executive Summary

PR #5194 adds a first-class `user.shell` field and `--user-shell` flag: it defaults the shell per guest OS, auto-installs it on Linux and FreeBSD guests at boot, and generalizes `limactl shell` on Windows to `cmd.exe`, `powershell.exe`, and `pwsh.exe`. Validation and tests are strong. Two Important guest-boot problems block the documented custom-shell workflow: the shell installer runs after rootless-containerd setup, and the Linux installer applies the configured path without confirming a binary landed there.

All three reviewers converged on the missing path check (I2). Codex alone traced the boot-ordering failure (I1) — the standout catch of this round — and I verified its full chain against the code. Gemini rated the path check Critical and the Windows argument quoting Important; I downgraded both after checking the default path stays unaffected and the quoting predates this PR. The remaining four suggestions and the `$SHELL` design shift all came from Claude.

## Important Issues

I1. **Shell installer runs after rootless-containerd setup, so a custom shell breaks containerd on first boot** — `pkg/cidata/cidata.TEMPLATE.d/boot.Linux/40-install-shell.sh` [Codex GPT 5.5]

```sh
# 40-install-containerd.sh (set -eux) sorts BEFORE 40-install-shell.sh:
sudo -iu "${LIMA_CIDATA_USER}" ... containerd-rootless-setuptool.sh install
```

`40-install-shell.sh` sorts alphabetically after `40-install-containerd.sh`, so the shell installs second. cloud-init has already set the lima user's login shell from `user.shell` (`user-data:50`), and `containerd.user` defaults to true on Linux amd64/arm64 (`defaults.go:536-539`). Rootless-containerd setup runs `sudo -iu`, which execs that login shell; when the shell is not yet installed, `set -eux` aborts the script. Boot continues (per-script failures only warn), so `limactl create --user-shell=/bin/zsh template:default` — the documented example — returns success with containerd silently broken until a restart installs the shell. The new bats test misses this because it never exercises containerd.

Fix: rename the installer to run before any step that enters the user login environment — after `04-persistent-data-volume.sh` (which must precede `/etc` writes) but before `20-rootless-base.sh`, e.g. `11-install-shell.sh`.

I2. **Linux installer never verifies the shell exists at the configured path** — `pkg/cidata/cidata.TEMPLATE.d/boot.Linux/40-install-shell.sh:16-53` [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

```sh
if ! command -v "${SHELL_NAME}" >/dev/null 2>&1; then   # basename lookup on PATH
    ...                                                  # e.g. ksh -> mksh on Alpine
echo "${SHELL_PATH}" >>/etc/shells                       # registers the full path
chsh -s "${SHELL_PATH}" "${LIMA_CIDATA_USER}"            # may point at nothing
```

The installer decides "already present?" with a basename lookup on `PATH`, then registers and `chsh`-es the full configured `SHELL_PATH` without checking a binary lives there. When the package lands off the requested path — Alpine maps `ksh`→`mksh`, and non-usrmerge distros split `/bin` from `/usr/bin` — the account points at a missing shell, breaking login and `limactl shell` (which now execs `SHELL_PATH`), and reinstalls every boot. The FreeBSD sibling gates on `[ ! -x "${SHELL_PATH}" ]` and re-verifies after install; Linux does neither. Line 48 also drops the `[ -n "${current_shell}" ]` guard FreeBSD keeps, so an empty `getent` runs `chsh` and aborts under `set -e`.

Fix: mirror the FreeBSD structure —

```sh
if [ ! -x "${SHELL_PATH}" ]; then
    # install by ${SHELL_NAME}...
    if [ ! -x "${SHELL_PATH}" ]; then
        echo "ERROR: '${SHELL_PATH}' not found after installing '${SHELL_NAME}'." >&2
        exit 1
    fi
fi
```

Gemini rated this Critical; I downgraded it to Important because the default `/bin/bash` path stays unaffected and the break requires an opt-in custom shell whose install path differs from the requested one.

## Suggestions

S1. **Dead nil-checks on `inst.Config.User.Shell`** — `cmd/limactl/shell.go:295-308` [Claude Opus 4.8]

```go
} else {
    shell = `"$SHELL"`   // unreachable: User.Shell is always set post-load
}
```

`FillDefault` populates `User.Shell` for every OS (`defaults.go:201-212`), and `inst.Config` loads through `limayaml.Load`, which runs it. So the `inst.Config.User.Shell != nil` checks are always true and the `else` fallbacks (`cmd.exe` at line 298, `"$SHELL"` at line 308) never run. The dead branches imply reachable states that do not exist.

Fix: assign from `*inst.Config.User.Shell` directly, or add a comment that the pointer is guaranteed non-nil after load.

S2. **`--user-shell` completion duplicates `SupportedWindowsShells`** — `cmd/limactl/editflags/editflags.go:97-100` [Claude Opus 4.8]

The completion list hardcodes `cmd.exe`, `powershell.exe`, and `pwsh.exe` — a third copy of `limayaml.SupportedWindowsShells` (`validate.go:449`); a shell added there never reaches this list. The POSIX entries (`/bin/ksh`, `/bin/tcsh`) also hardcode paths that may not match a distro's package layout, so completing a value that then fails to install (see I1, I2) is a poor hint. Reference `SupportedWindowsShells` for the Windows portion.

S3. **Help text calls the Windows value a "login shell"** — `cmd/limactl/editflags/editflags.go:97` [Claude Opus 4.8]

`"User login shell in the guest (e.g. /bin/bash, /bin/zsh)"` fits POSIX but not Windows, where `user.shell` is the command interpreter `limactl shell` launches, not a login shell. Append a Windows note such as "(command interpreter on Windows)".

S4. **Windows command args are POSIX-escaped, then wrapped for cmd/powershell** — `cmd/limactl/shell.go:339-352` [Claude Opus 4.8, Gemini 3.1 Pro]

```go
quotedArgs[i] = shellescape.Quote(arg)   // POSIX single-quotes
script += fmt.Sprintf(` %s "%s"`, flag, strings.Join(quotedArgs, " "))
```

`shellescape.Quote` produces POSIX single-quoted tokens, which neither `cmd.exe /c` nor `powershell -Command` parse as intended — `limactl shell win -- echo "a b"` sends `echo 'a b'` and prints the quotes. This predates the PR for cmd.exe, but the PR now routes powershell and pwsh through the same path, where quoting differs again. Windows-guest support is experimental and this path is untested, so a suggestion — worth a follow-up before Windows `shell -- args` is relied on.

Gemini rated this Important and proposed naive double-quoting (`"`+arg+`"`), which itself breaks on args containing `"`; I downgraded it to Suggestion because the cmd.exe behavior predates this PR and correct cmd/powershell quoting is a larger, untested change.

## Design Observations

### Concerns

**`limactl shell` default shifts from `$SHELL` to the configured `user.shell`** — (future) [Claude Opus 4.8]

An empty `--shell` previously ran `exec "$SHELL" -l`, honoring the guest's actual login shell — including a manual in-guest `chsh`. It now runs `exec <user.shell> -l` (`shell.go:304-306`), and because `FillDefault` always sets `User.Shell`, the shift applies to every existing and new instance. The config value therefore overrides an in-guest shell change, and `limactl shell` now depends on a successful install: it breaks where `$SHELL` would have worked when the boot install fails (I1) or no installer exists (macOS guests). The PR intends this behavior, but the docs should call out the lost `$SHELL` fidelity.

### Strengths

**Validation centralized with a shared shell enum** — (in-scope) [Claude Opus 4.8, Codex GPT 5.5, Gemini 3.1 Pro]

`validate.go` holds the new check (the single source of cross-field validation), `SupportedWindowsShells` is shared between `validate.go` and `shell.go`, and `path.IsAbs` — the always-POSIX predicate — validates guest paths correctly even from a Windows host.

**FreeBSD installer re-verifies after install** — (in-scope) [Claude Opus 4.8]

The FreeBSD script gates on `[ ! -x "${SHELL_PATH}" ]` and, on a post-install path mismatch, prints an actionable error pointing at `/usr/local/bin`. This is the pattern I2 asks the Linux script to adopt.

**`windowsQuoteShell` skips already-quoted input** — (in-scope) [Gemini 3.1 Pro]

The helper returns a pre-quoted path unchanged, avoiding double-wrapping.

## Review Process Notes

### Skill improvements

- When a change installs or sets a per-user login resource during guest boot — login shell, home directory, group membership, dotfiles — trace every earlier boot step that assumes that resource is already valid, especially steps that enter the user's login environment (`sudo -i`, `su -`, `systemctl --user`, or a login-shell exec). A new step ordered after such a consumer, but whose resource the consumer needs, silently breaks the consumer. Where boot steps run in numeric-prefix order, confirm the new step's prefix sorts before every consumer of what it provides. This class of bug hides because the ordering is implicit in filenames and the failing consumer is a sibling file, not the changed one.

### Repo context updates

- [repo] Guest boot scripts under `pkg/cidata/cidata.TEMPLATE.d/boot.<OS>/` run in numeric-prefix (lexical) order via `boot.sh`, which catches each script's failure as a warning, sets `CODE=1`, and continues — and writes `lima-boot-done` regardless. A failing boot script therefore does not abort `limactl start`; it degrades silently. Two constraints for any new or reordered boot script: (1) changes to `/etc` or `/var/lib` must run after `04-persistent-data-volume.sh`, which may relocate those directories on first boot; (2) several scripts (e.g. `40-install-containerd.sh`, `set -eux`) enter the user's login environment via `sudo -iu "${LIMA_CIDATA_USER}"`, which execs the login shell recorded in `/etc/passwd`. The lima user's login shell is set at cloud-init time from `user.shell` (`user-data`: `shell: {{.Shell}}`) before any `boot.<OS>` script runs, so a script that provisions or changes that shell must run before every `sudo -iu` consumer, or the consumer fails to exec a not-yet-installed shell.

### Executive Summary

This PR introduces the `--user-shell` flag and `.user.shell` configuration to support custom login shells across operating systems. The implementation effectively handles Windows-specific shells (`cmd.exe`, `pwsh.exe`) and fallback defaults. However, a critical bug in the Linux shell installation script allows a path mismatch to permanently lock users out of their instance when the package manager installs the requested shell to a different path (e.g., `/usr/bin/fish` instead of `/bin/fish`).

### Findings

#### Critical Issues

**C1. Linux shell installation sets non-existent shell on path mismatch** — `pkg/cidata/cidata.TEMPLATE.d/boot.Linux/40-install-shell.sh:15-54` (critical, regression)

```sh
# Install the shell if not already present.
if ! command -v "${SHELL_NAME}" >/dev/null 2>&1; then
	pkg="${SHELL_NAME}"
```

The Linux boot script does not verify that the requested `SHELL_PATH` actually exists before setting it as the login shell via `chsh`. When a user configures a shell like `user.shell: /bin/fish` on a distribution that places it at `/usr/bin/fish` (e.g., Alpine or older non-usrmerge distros), `command -v fish` succeeds or the package manager installs it successfully to `/usr/bin`. However, the script then blindly forces `/etc/shells` and `chsh` to use `/bin/fish`. Because `/bin/fish` does not exist, the user is permanently locked out of SSH and `limactl shell` sessions.

Fix: Mirror the safety logic from the FreeBSD script. Check for the existence of `SHELL_PATH` directly, and fail cloud-init with an error instead of applying a broken configuration:

```diff
-if ! command -v "${SHELL_NAME}" >/dev/null 2>&1; then
+if [ ! -x "${SHELL_PATH}" ]; then
+	if ! command -v "${SHELL_NAME}" >/dev/null 2>&1; then
 		pkg="${SHELL_NAME}"
 
 		if command -v apt-get >/dev/null 2>&1; then
@@ -38,6 +39,15 @@
 			echo "ERROR: no supported package manager found; cannot install '${SHELL_NAME}'." >&2
 			exit 1
 		fi
+	fi
+
+	if [ ! -x "${SHELL_PATH}" ]; then
+		alt="$(command -v "${SHELL_NAME}" || true)"
+		if [ -n "${alt}" ] && [ -x "${alt}" ]; then
+			echo "ERROR: shell installed at '${alt}' but user.shell is '${SHELL_PATH}'. Please update user.shell." >&2
+		else
+			echo "ERROR: shell '${SHELL_PATH}' not found after install." >&2
+		fi
+		exit 1
+	fi
 fi
```

#### Important Issues

**I1. Windows `cmd.exe` argument quoting uses POSIX shell rules** — `cmd/limactl/shell.go:343-344` (important, gap)

```go
				} else {
					parsingEnv = false
					quotedArgs[i] = shellescape.Quote(arg)
				}
```

The CLI uses `shellescape.Quote`, which applies POSIX single-quote rules (e.g. `'my argument'`). When passing arguments to a Windows guest configured with `cmd.exe` (`limactl shell default cat "my file"`), `cmd.exe /c` does not strip single quotes. The remote program receives the single quotes as a literal part of the argument, which breaks any payload requiring spaces or escapes. While this PR safely redirects `-Command` for PowerShell (which natively understands single quotes), it preserves this pre-existing gap for `cmd.exe`.

Fix: Apply correct double-quoting rules dynamically when passing arguments to `cmd.exe`:

```go
					parsingEnv = false
					if *inst.Config.OS == limatype.WINDOWS && windowsShellCommandFlag(shell) == "/c" {
						// Implement cmd.exe double-quoting
						quotedArgs[i] = `"` + arg + `"`
					} else {
						quotedArgs[i] = shellescape.Quote(arg)
					}
```
