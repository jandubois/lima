## Executive Summary

This head meets the three requests of the earlier review. On a btrfs loop mount, clones and renames of instances made by master share every block, `LIMA_BTRFS_NOCOW=false` keeps copy-on-write, and the FAQ makes the requested corrections. Two gaps remain. `limactl disk import` and images with a local `location` now make full copies where master made reflinks, and neither the FAQ nor any log message mentions them. `MatchCopyOnWrite` also clears No_COW when its source is off btrfs, contrary to its doc comment.

I1. **`limactl disk import` and local images now make full copies** — `cmd/limactl/disk.go:483-487` [Claude Opus 5.5]


`limactl disk import` now copies the user's file, normally copy-on-write, into a No_COW directory. btrfs can't reflink between the two modes, so `contfs.CopyFile` falls back to a full copy where master made a reflink. Images whose `location` is a local file take the same route, through `copyLocal` and `fs.CopyFile` (`pkg/downloader/downloader.go:685`), into the instance directory that `create.go` flagged. Nothing warns, and the FAQ names this cost only for old cache entries.

Fix: name both paths in the FAQ's list of costs, as the patch does, and warn when Lima makes such a copy.

The full copy is the better default for both paths. Each copy becomes a disk that the guest writes. `disk import` copies to `datadisk`, and QEMU renames a copied local image to `disk` (`pkg/driver/qemu/qemu.go:143`), so after a full copy, each of these disks is No_COW for good. `MatchCopyOnWrite(diskDir, fName)` would keep the reflink for an import, the way clone does. But a clone's copy-on-write sources are the instances made before this PR, and those go away over time. An import's source is a user file outside `LIMA_HOME`, and it stays copy-on-write, so imported disks would never get No_COW. The PR's default also leaves the user a choice. Under it, `LIMA_BTRFS_NOCOW=false limactl disk import` gets the reflink back for one command. With matching, a user who wants a No_COW disk would first have to make the full copy into a `+C` directory.

A user sees the full copy only in the time and space it takes, so Lima should say when it makes one. Before the `CopyFile` calls at `cmd/limactl/disk.go:487` and `pkg/downloader/downloader.go:685`, compare the No_COW attribute of the source with that of the destination's directory when both are on btrfs. When they differ, log a warning such as `Copying %#q in full, because btrfs cannot share blocks between files with and without copy-on-write`. The second site also copies cached images into instances, so the warning covers both old cache entries and the No_COW cache entries that S3 describes. The check has to predict the full copy from the two attributes, because continuity's `CopyFile` doesn't report whether the kernel made a reflink. For the mismatch that this PR creates, that prediction is exact. Clone does not need the check and can keep calling continuity directly, because only a user's `chattr +C` makes its source and destination disagree (S1).

I2. **`MatchCopyOnWrite` clears No_COW when its source is off btrfs** — `pkg/fsutil/fsutil_linux.go:58-66` [Claude Opus 5.5]

```go
// MatchCopyOnWrite gives dst the No_COW attribute of src, or takes it away when src has none,
// if both are on btrfs. btrfs cannot reflink between files with and without the attribute, so the
// directory for a copy of an instance must follow the original, whatever LIMA_BTRFS_NOCOW says.
func MatchCopyOnWrite(dst, src string) error {
	noCOW, err := hasNoCOW(src)
	if err != nil {
		return err
	}
	return setNoCOW(dst, noCOW)
```

The doc comment says that the function acts "if both are on btrfs". But when `src` is on another filesystem, `hasNoCOW` returns `false, nil`, and `setNoCOW(dst, false)` clears No_COW on a btrfs `dst`, including one that inherited `+C` from `LIMA_HOME`. `CloneOrRename` gets there when an instance directory is a symlink to another filesystem or a mount point of one. No reflink is possible then, so the clone is a full copy either way, and the new instance ends up copy-on-write although the user never opted out.

## Suggestions

S1. **Clone takes the mode from the old directory, not from its disk** — `pkg/instance/clone.go:63` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	if err := fsutil.MatchCopyOnWrite(newInstDir, oldInst.Dir); err != nil {
```

Lima never makes a directory and its disk disagree, but a user can, by running `chattr +C` on an existing instance directory. The disk keeps copy-on-write, because btrfs ignores `+C` on a file that already has data (`chattr` exits 0 and `lsattr` does not show `C`). Cloning that instance gives the new directory `+C`, so its disk is a full copy where master shared it (row S4 of the probe output below). That same behavior is the only way to move an old instance to No_COW (`chattr +C ~/.lima/old && limactl clone old new`), so I'd keep it. Matching the first disk file instead (`filenames.Disk`, then the legacy names) keeps the reflink and loses that migration path.

S2. **"Do not fragment over time" overstates what No_COW does** — `pkg/fsutil/fsutil_linux.go:42-43` [Codex GPT 6 Astra]

The doc comment and the FAQ's opening (`website/content/en/docs/faq/_index.md:190`) promise disk images that "do not fragment over time", and a few lines later the FAQ says that clones and snapshots bring the fragmentation back. The earlier review's measurements show that the gain comes from in-place random writes.

S3. **The opt-out docs don't say when the variable has to be set** — `website/content/en/docs/config/environment-variables.md:118` [Claude Opus 5.5, Gemini 3.5 Flash]

```text
  Set it to `false` to keep copy-on-write and the btrfs checksums, at the price of disk images that fragment over time.
```

The variable matters in every process that creates one of these directories, which includes the command that creates the instance, `limactl disk create`, and whichever command first downloads an image into the cache, usually the first `limactl start`. When it is set in one shell only, a command run from another shell creates No_COW cache entries. A copy-on-write instance made later from such an entry is a full copy until `limactl prune`, the cost that the FAQ names for old cache entries. The usage example shows `limactl start` alone.

Fix: say to set it for every `limactl` command, for example in the shell profile, and that setting it later changes nothing already created.

S4. **A compression flag makes `DisableCopyOnWrite` fail with EINVAL** — `pkg/fsutil/fsutil_linux.go:114` [Gemini 3.5 Flash, Claude Opus 5.5]

```go
	return unix.IoctlSetPointerInt(int(f.Fd()), unix.FS_IOC_SETFLAGS, int(newFlags))
```

btrfs refuses `FS_NOCOW_FL` on an inode that has `FS_COMPR_FL` or `FS_NOCOMP_FL`, and a directory inherits those from a parent marked with `chattr +c` or a `btrfs property set ... compression`. On the test VM, `DisableCopyOnWrite` on a child of a `+c` directory returned `invalid argument` and left No_COW off. Under such a tree, every instance create, disk create and download through the cache logs "Failed to disable copy-on-write", while the behavior stays master's.

Fix: when the directory has a compression flag, skip it with a debug message, since the user chose compression for that tree.

## Design Observations

### Concerns

- **The opt-out has to be in each command's environment** (future) [Claude Opus 5.5]: a `limactl start` from another shell or an autostart unit creates No_COW cache entries, and S3's full copies follow. A persistent switch would avoid that, either a host-level setting under `_config`, or flagging only the roots (`LIMA_HOME`, `_disks`, the cache) so `chattr -C` on them opts out. The earlier review asked for an environment variable, so this belongs to a later change.

### Strengths

- **`setNoCOW` changes only the No_COW bit** (in-scope) [Claude Opus 5.5]: it keeps every other flag and skips the ioctl when nothing changes, so the call on an existing cache entry costs one `statfs` and one `FS_IOC_GETFLAGS`.
- **Every call site treats a failure as a warning** (in-scope) [Claude Opus 5.5, Gemini 3.5 Flash]: the worst outcome is master's behavior.
- **Clone and rename follow the old instance** (in-scope) [Claude Opus 5.5, Gemini 3.5 Flash]: S1's probe shows instances made by master cloning and renaming with every block shared, the case that the earlier review measured at 0.93 s and 901 MiB unshared.

## Review Process Notes

### Skill improvements

- When a change alters state that later operations pick up without a call (an attribute, ACL or mode that new files inherit from their directory, a umask, a process-wide setting), list every operation that creates or copies a file under that state, including ones outside the diff, and check each against the change's stated goal. Reviewers otherwise check only the paths that the PR or its earlier review names, and the unchanged writers inherit the new behavior unseen.

### Repo context updates

- [repo] On a btrfs host, a file gets its No_COW attribute from its directory when it is created, and btrfs refuses a reflink between a No_COW file and a copy-on-write one; `continuity`'s `CopyFile` then makes a full copy without an error. `chattr +C` on a file that already has data exits 0 and sets nothing. So any change to the attributes of instance, `_disks` or download-cache directories changes the cost of every copy into them. Those copies are `limactl clone`, `limactl disk import`, a local image `location`, and the copy from the cache into an instance.
