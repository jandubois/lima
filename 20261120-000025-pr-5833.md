## Executive Summary

The PR replaces four accept loops that retried every failed `Accept` with `acceptloop.Serve`, which closes the listener and returns on any error except running out of descriptors. That stops the EBADF log flood, and `AcceptQemu` no longer gets a nil connection. Two fixes remain. A one-off ENOMEM or ENOBUFS now ends a forwarder for good where the old loops recovered (I1). And the tests still pass when `Serve` skips its close, its wait, its 1s maximum or its reset (I2).

## Important Issues

I1. **One ENOMEM or ENOBUFS from `accept` now ends the listener for good** — `pkg/acceptloop/acceptloop_others.go:12` [Claude Opus 5.5, Gemini 3.1 Pro]

```go
var outOfDescriptorErrnos = []syscall.Errno{syscall.EMFILE, syscall.ENFILE}
```

`Serve` retries only the errnos in this list and returns on any other. The macOS `accept(2)` man page lists ENOMEM, Linux's lists ENOBUFS and ENOMEM, and Go 1.27.4's poller retries neither. At the merge-base, the vz, krunkit and FD loops logged such an error and kept accepting. Now `Serve` returns it, the caller logs "Stopped …", and the callers don't restart the listener. So the guest loses SSH over vsock, or usernet stops taking QEMU or FD connections, until a restart. These errors clear the way EMFILE does, so the same backoff fits them.

## Suggestions

S1. **The `Serve` doc comment and the commit message don't say that the retries go on until `Accept` succeeds** — `pkg/acceptloop/acceptloop.go:26`

```go
// descriptors, Serve waits and tries again, because the error clears once
// other connections close. The wait starts at 5ms and doubles up to 1s.
```

"Doubles up to 1s" leaves open whether `Serve` keeps trying once the wait reaches 1s, or gives up. It keeps trying, once a second, until `Accept` succeeds or `ctx` is done (lines 54-59). The commit message's "starting at 5ms and doubling up to 1s" has the same gap. Jan raised this during the review; the agents missed it.

Fix: I1's patch rewrites the comment to "Serve waits and tries again until Accept succeeds or ctx is done … The wait starts at 5ms, doubles after each failure, and stays at 1s." Without that patch, use the same two sentences. Say the same in the commit message.

**Outcome:** fixed in `7eb366a6`: the doc comment and the commit message say that `Serve` keeps trying until `Accept` succeeds or the context is done.

S2. **The tests never cancel the context during the backoff wait** — `pkg/acceptloop/acceptloop.go:55` [Gemini 3.5 Flash]

```go
			select {
			case <-ctx.Done():
				return nil
```

`TestServeStopsWhenContextIsDone` cancels while `Serve` blocks in `Accept`. Deleting the `ctx.Done()` case at line 55 still passes every test, the I2 patch's tests included. With a real listener, the watcher goroutine closes `l`, so `Accept` returns `net.ErrClosed` after the current wait and a stop takes up to 1s longer. The test is optional, and under `synctest` it doesn't need real waits.

Fix: in a `synctest` bubble, give `Serve` out-of-descriptor errors forever, cancel the context once the first wait starts, and assert that `Serve` returns nil without another `Accept` call.

**Outcome:** declined: without the `ctx.Done()` case a stop still ends at the next `Accept`, at most 1s later, when the watcher closes the listener.

## Design Observations

### Concerns

- **(future) The usernet daemon keeps running after its QEMU or FD listener stops.** [Claude Opus 5.5] At the merge-base, a failed QEMU `Accept` handed a nil conn to `AcceptQemu`. `AcceptQemu` passes it to `Switch.Accept`, which calls `conn.RemoteAddr()` on it (gvisor-tap-vsock v0.9.0 `pkg/tap/switch.go:87`), so the daemon crashed. Claude infers that the next `usernet.Start` then relaunched it, because `recoincile.go:46` starts the daemon when `ReadPIDFile` returns 0 for the dead PID. Now `Serve` returns and closes the listener, which removes its socket file. The daemon keeps serving the running guests, but a new QEMU guest can't connect. Running `Serve` under the daemon's errgroup would trade the running guests' network for a relaunch. Both outcomes beat the merge-base. **Outcome:** declined for this PR; tracked as follow-up work.
- **(future) Closing the listener after EBADF can close a descriptor that has since been reused.** [Claude Opus 5.5] EBADF means `l`'s descriptor number no longer belongs to `l`, so the deferred `l.Close()` (`acceptloop.go:32`) closes whatever took that number in between, which is the hazard that the commit message blames on Code-Hex/vz. The merge-base closed it only at instance stop, a much wider window, so this PR shrinks the window. **Outcome:** declined for this PR; tracked with the Code-Hex/vz v4 bump.

### Strengths

- **(in-scope)** `Serve` hands its handler only connections that `Accept` returned, so the QEMU listener stops passing a nil conn to `AcceptQemu`. [Codex GPT 6 Astra, Gemini 3.5 Flash]
- **(in-scope)** `listenFD`'s `fd.Get` handshake now runs in the per-connection goroutine, so a stalled client no longer blocks later accepts. [Claude Opus 5.5]
- **(in-scope)** The Windows file matches `WSAEMFILE`, because Go's `syscall.EMFILE` on Windows is an invented value that `Accept` never returns. [Claude Opus 5.5, Gemini 3.5 Flash]

## Acknowledged Limitations

- The callers don't restart a listener after `Serve` returns, so the guest loses SSH over vsock until it restarts. The PR body says so. It names the double close in Code-Hex/vz v3.8.0 as the likely but unproven reason that `Accept` fails.
- `listenFD` still indexes `files[0]` after a failed `fd.Get` and never closes the accepted `*net.UnixConn`. The PR moves that body into the handler unchanged, and the bug is tracked separately.
- Do not re-suggest a timeout that makes `Serve` give up on out-of-descriptor errors. The callers don't restart the listener, so giving up turns a stall that would clear into a dead forwarder, and the retries already end when `ctx` is done.
- Do not re-suggest logging the out-of-descriptor retries less often. The warning appears at most once a second, and each line shows that the listener is still waiting.
- Do not re-suggest returning on every `Accept` error, retrying every error, or fixing the four loops in place.
