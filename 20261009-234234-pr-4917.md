## Executive Summary

The PR adds a repeatable `--sync-exclude` flag and a top-level `.limasyncignore` file to `limactl shell --sync`. The maintainer's amendment fixes all three round-1 Important findings. One new defect needs fixing before merge. The dry run behind the sync-back prompt starts its transfer one directory above the synced one, so anchored patterns report phantom changes, and a pattern matching the synced directory's name makes the prompt delete the guest's work without syncing it back.

## Critical Issues

C1. **The sync-back prompt's dry run starts one directory above the synced one** — `cmd/limactl/shell.go:594` [Claude Opus 5.5] [Codex GPT 6 Astra] [Gemini 3.5 Flash]

```go
	rawOutput, stats, err := getRsyncStats(ctx, remoteSource, filepath.Dir(hostCurrentDir), excludeArgs)
```

Every other rsync call in `--sync`, `rsyncBack` included (lines 567-570), passes the directory with a trailing slash, so the transfer starts inside it. The stats dry run copies the directory itself into its parent instead. rsync matches excludes against paths from where the transfer starts, so one pattern means two different things.

An anchored pattern such as `/.env`, the usual `.gitignore` idiom, then shows a deletion that the sync-back never makes. A pattern matching the synced directory's own name (`app` while syncing `.../app`) excludes the whole dry run. The stats come back empty, the prompt prints "No changes detected" (line 599), and the cleanup deletes the guest workdir without syncing anything back. The PR introduced both by first passing excludes to this call. GNU rsync 3.4.1 behaves like the openrsync that the probe ran on.

S3. **An unreadable `.limasyncignore` is skipped silently** — `cmd/limactl/shell.go:991` [Claude Opus 5.5] [Codex GPT 6 Astra] [Gemini 3.1 Pro] [Gemini 3.5 Flash] round 1 S2 unaddressed; raised in round 1 by Claude Opus 4.7

```go
	if _, err := os.Stat(filepath.Join(nativeDir, ".limasyncignore")); err == nil {
```

Any `os.Stat` error counts as "no file", so the excludes fail open and the files that the user listed sync into the guest. The fix that the reviewers proposed, ignoring only `fs.ErrNotExist`, still misses the likeliest case. A dangling symlink, such as one pointing at a moved shared ignore file, also reports `ErrNotExist`. A probe showed `buildSyncExcludeArgs` returning no arguments for a dangling and for a self-referencing symlink, while `os.Lstat` succeeded on both.

Fix: decide presence with `os.Lstat`. rsync then fails to open a file it cannot read and stops before copying anything (GNU rsync 3.4.1 exits 11, openrsync exits 1). A directory named `.limasyncignore` fails the same way.

S4. **The docs describe the excludes inaccurately** — `website/content/en/docs/examples/ai.md:193-194` [Claude Opus 5.5] [Codex GPT 6 Astra] [Gemini 3.1 Pro] [Gemini 3.5 Flash] round 1 S4 unaddressed; raised in round 1 by Claude Opus 4.7

In addition to the `--sync` flag, a `--sync-exclude` flag is available, which allows you to configure directories that will not be synced to the VM. This is useful to exclude large generated directories (like `node_modules`, or `vendor`),

The section says the flag excludes "directories", yet it takes rsync patterns, and the page's own example lists `*.o`. It also omits four facts a user needs to predict the result.

- The file must sit at the top of the synced host directory, which line 202 calls "the target directory".
- A leading `/` anchors a pattern to that directory.
- Excluded host files survive the sync-back, because rsync's `--delete` spares them.

Fix: rewrite the section around those points.

## Design Observations

### Concerns

- **`.limasyncignore` round-trips through the guest it restricts** (in-scope) [Claude Opus 5.5]. Nothing excludes the file itself, so the guest gets a copy and `rsyncBack` writes the guest's edits back to the host, without a prompt under `--yes` (line 591). The current session stays protected, but a guest that deletes or trims the file receives the excluded files next session. Adding `--exclude /.limasyncignore` whenever the file exists (safe once C1 is fixed) keeps the guest from seeing it. The author's `--sync-exclude-from FILE` proposal, reading a file outside the synced tree, does the same.
- **"View the changed contents" copies the whole host tree when excludes are set** (in-scope) [Gemini 3.5 Flash]. The copy skips excluded paths, usually the large ones such as `node_modules`, but a large tree with narrow excludes costs time and temporary space before the diff appears.
- **A per-directory merge filter would hand the filtering to the guest** (future) [Claude Opus 5.5] [Codex GPT 6 Astra]. Round 1 suggested `--filter ':- .limasyncignore'`. On the sync-back the guest is the sender, so its copy of the file would decide what comes back; a single file read on the host avoids that.

### Strengths

- **The ignore-file lookup probes the native path and names the converted one** (in-scope) [Claude Opus 5.5] [Codex GPT 6 Astra] [Gemini 3.5 Flash]. It mirrors the `hostCurrentDirNative`/`hostCurrentDir` split at lines 243-256, so a Cygwin or MSYS rsync gets the same path form as its source argument.
- **`validateSyncFlagValue` checks the command's real flag set** (in-scope) [Claude Opus 5.5] [Gemini 3.1 Pro] [Gemini 3.5 Flash]. At runtime that includes inherited flags (the built binary rejects `--sync -y`), and a directory named `--data` still works.
- **Both trees in the diff view go through the same rsync tool** (in-scope) [Claude Opus 5.5] [Codex GPT 6 Astra] [Gemini 3.1 Pro]. Excluded files drop out of both sides; I2 is about keeping it that way.
- **`StringArray` keeps each pattern intact** (in-scope) [Codex GPT 6 Astra]. Repeated `--sync-exclude` values are never split on commas.

Round 1 credited "the same exclude args throughout the pipeline". All five rsync calls do pass the same exclude arguments, but C1 shows the stats call reading them from a different starting directory, so that credit holds for the arguments only.

## Review Process Notes

### Skill improvements

- When the probe that decides a finding ran on a different implementation of an external tool than the one most users run (Apple's openrsync versus GNU rsync, BSD versus GNU utilities), re-run it on that implementation before recording the severity. Implementations of one tool differ in filter, option and exit-code semantics, and such a difference would reverse the finding.

### Repo context updates

- **[repo] UPDATE "Rsync invocations in `limactl shell --sync`"**: the shell runs rsync from five call sites, not four. The "View the changed contents" branch also copies the host directory into a temporary tree when excludes are set. Matching options across those calls is not enough. rsync matches exclude and filter patterns against paths from the directory where the transfer starts, which the trailing slash on the source decides. A source without the slash starts the transfer in its parent, so an anchored pattern (`/name`) stops matching and an unanchored pattern equal to the directory's own name excludes everything. Flag any call that passes the shared filters with a different source or destination form.
- **[repo]** `copytool.CopyTool.Command(ctx, paths, opts)` replaces the tool's stored `Options` whole when `opts` is non-nil, `AdditionalArgs` included. A per-call override on a tool built with `--delete` or exclude arguments silently drops them for that call; flag one.

###### Design Observations

**Concerns**

- **`.limasyncignore` round-trips through the guest it is meant to restrict** (in-scope). Nothing excludes the file itself, so the guest copy holds it, and `rsyncBack` writes guest edits back to the host with `--delete`. Under `--tty=false`/`--yes` that happens without a prompt (line 591). rsync reads `--exclude-from` when it starts, so the current session stays protected. On the next session, though, a guest that deleted the file, or dropped lines from it, has the previously excluded files synced into it.
  - The docs (line 193) recommend this mechanism for "credentials". A guest that can already rewrite any synced file can do worse to the host, such as editing a Makefile. Confidentiality is, however, the property this feature advertises.
  - Alternative: always add `--exclude /.limasyncignore` when the file is present, so the guest never sees or rewrites it. The anchor is safe once I1 is fixed. Or adopt the author's explicit `--sync-exclude-from FILE` (r3174888608), which reads a file outside the synced tree, and keep it host-only.
- **Per-directory merge filter (R1-S3)** (future). `--filter ':- .limasyncignore'` would honour nested files. On sync-back, however, the sender is the guest, so the guest's copies would control the filtering. That argues for keeping a single host-read file.
  - Round 1 also described a data-loss path when the file is deleted mid-session. It no longer exists: with the file missing, rsync failed before transferring anything (`rsync: open: …nonexistent: No such file or directory`, rc=1, host files intact, measured with openrsync). `cleanupGuestWorkdir` is set only after a successful sync-back or an explicit "No" (lines 576, 600, 653), so the guest copy survives.

**Strengths**

- `buildSyncExcludeArgs` probes the native path and names the converted one. This mirrors the `hostCurrentDirNative`/`hostCurrentDir` split at lines 243-256, so a Cygwin or MSYS rsync gets the same path form as its source argument.
- `validateSyncFlagValue` looks values up in the real flag set, so at runtime it also covers inherited flags. The built binary rejects `--sync -y`, and directories named like non-flags (`--data`) still work.
- The diff view's filtered host copy uses the same `rsync` tool and options as the guest copy, so both sides of the `diff` see identical filters.

###### Design Observations

###### Concerns

1. **Interactive Diff View Clones Full Host Tree** `(in-scope)`: In `askUserForRsyncBack` (lines 634-639, 671-675), when `excludeArgs` is non-empty, the diff view copies the entire host directory into a temporary staging folder (`baseDir/host/<dir>`) using rsync. For large repositories (e.g. multi-gigabyte trees), selecting "View the changed contents" in the interactive TUI incurs substantial I/O latency and disk usage under `os.TempDir()`. While this accurately evaluates rsync filters against local file differences, an in-process diff filter or warning for large directories would improve responsiveness.
2. **Static vs. Dynamic Evaluation of `.limasyncignore`** `(future)`: `buildSyncExcludeArgs` runs once at shell launch (line 467). If a `.limasyncignore` file is created or deleted during the shell session, the changes are not reflected in `askUserForRsyncBack` or `getRsyncStats`. Conversely, using rsync's per-directory merge filter (`--filter ':- /.limasyncignore'`) would allow rsync to dynamically evaluate the file if present without failing if removed mid-session.

###### Strengths

1. **Clean Windows Path Partitioning in `buildSyncExcludeArgs`**: The `nativeDir` vs `rsyncDir` parameter split introduced in the delta properly addresses R1-I1: `os.Stat` probes the native filesystem path while rsync receives the MSYS/Cygwin POSIX path required by the host rsync binary.
2. **Safe Flag Token Disambiguation via `validateSyncFlagValue`**: Inspecting the command's own `pflag.FlagSet` prevents consuming subsequent flag tokens as directory arguments while preserving valid directories that happen to start with dashes (e.g. `./--dir` or non-flag names).
