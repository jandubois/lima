## Executive Summary

One defect dominates. `install_provision.ps1` enumerates four `provision.<mode>` directories that exist on the ISO only when that mode is configured, under `$ErrorActionPreference = "Stop"`. Any config not using all four modes aborts the installer before it registers the scheduled tasks, silently, because no caller checks the exit code.

All four reviewers found that independently. The remaining important findings cluster into three themes: the guest copy of the payload freezes at first logon and never refreshes; the port drops several cross-platform contracts documented in `templates/default.yaml` (env/`PARAM_` delivery, unprivileged `user` mode, continue-on-failure, readiness gating); and unsupported modes are accepted in silence.

## Critical Issues

C1. **`install_provision.ps1` aborts on the first absent `provision.<mode>` directory** — `pkg/cidata/wincidata.TEMPLATE.d/install_provision.ps1:17` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```powershell
foreach ($item in Get-ChildItem -LiteralPath $startupsystemScriptsSrc) {
```

`appendProvisionEntries` emits an ISO entry only for modes actually configured, so a `system`-only config puts `provision.system` on the ISO and nothing else. `$ErrorActionPreference = "Stop"` at line 5 escalates `Get-ChildItem`'s `ItemNotFoundException` into a terminating error, killing the script at line 26, 35, or 44, before `Register-ScheduledTask` at lines 53 and 58. `first_logon.ps1:81` ignores the exit code and still writes the boot-done marker, so the host sees a clean start. Scripts then run once at first logon and never again, with no error anywhere.

The Linux implementation this mirrors guards every equivalent loop with `[ -d ... ]` (`pkg/cidata/cidata.TEMPLATE.d/boot.sh:172`), and the sibling `startup_runner.ps1:11` has the `Test-Path` guard this file lacks. The author's manual test used all four modes, the one configuration that works.

Fix: guard all four enumerations with `Test-Path`, or extract a `Copy-ProvisionDir -Src -Dst -Extension` helper and call it four times.

## Important Issues

I1. **User startup task uses a service-account logon type and runs elevated** — `pkg/cidata/wincidata.TEMPLATE.d/install_provision.ps1:57` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.5 Flash]

```powershell
$startupPrincipalUser = New-ScheduledTaskPrincipal -UserId "{{.User}}" -LogonType ServiceAccount -RunLevel Highest
```

Microsoft documents `TASK_LOGON_SERVICE_ACCOUNT` as valid only for Local System, Local Service, and Network Service, but `{{.User}}` renders to the ordinary lima account created at `autounattend.xml:216`. Under `$ErrorActionPreference = "Stop"` a failing registration kills the script at its last statement, leaving only the SYSTEM task. That matches the PR description, which verifies `LimaProvisionStartupSystem` and says nothing about `LimaProvisionStartupUser`. Separately, `-RunLevel Highest` runs user provisioning elevated, contradicting `templates/default.yaml:220` ("`user` is executed without root privileges").

No reviewer had a PowerShell runtime, so the registration failure is reasoned from documentation, not executed.

Fix: `-LogonType S4U -RunLevel Limited`, then confirm with `Get-ScheduledTaskInfo -TaskName "LimaProvisionStartupUser"` after a reboot.

I2. **Windows ISO carries `boot` and `yq` entries that nothing consumes** — `pkg/cidata/cidata.go:625` [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	layout, err = appendProvisionEntries(layout, instConfig.Provision, true)
```

`includeBoot: true` writes `provision.boot/%08d` into the Windows ISO, and the `yq` arm writes `provision.yq/%08d` unconditionally. But `templates/windows-2025.yaml:29-30` documents both modes as unsupported, and no Windows template reads either directory. A user writing `mode: boot` gets no error, no execution, and no log line. `pkg/limayaml/validate.go` already switches on `p.Mode` and has `y.OS` in hand, so the constraint has an obvious home.

Fix: pass `false` at line 625, and reject `boot` and `yq` in validation when `*y.OS == limatype.WINDOWS`, so the documented limitation is enforced instead of merely stated.

I3. **`first_logon.ps1` captures the provisioning payload once and never refreshes it** — `pkg/cidata/wincidata.TEMPLATE.d/first_logon.ps1:81` [Codex GPT 5.6 Sol, Claude Opus 5]

```powershell
powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -File "$root\install_provision.ps1" -Root "$root\"
```

`first_logon.ps1` runs from `<FirstLogonCommands>` (`autounattend.xml:234`), which fires exactly once. The startup tasks then execute the copies under `C:\ProgramData\Lima\provision`, never the ISO. The hostagent regenerates the ISO on every start (`pkg/hostagent/hostagent.go:192`), but QEMU stops attaching it once the guest is installed.

That skip is at `pkg/driver/qemu/qemu.go:726`. Edited scripts and newly added provisions therefore never reach an existing instance, the opposite of Linux, where `boot.sh` reads the freshly generated ISO each boot. Nothing in the templates or `windows.md` says so.

Fix: attach a provision-only volume on every start and re-sync from it before running the modes, or document that provisioning applies only to newly created instances.

I4. **Provision scripts receive no `env` or `PARAM_` variables** — `pkg/cidata/wincidata.TEMPLATE.d/startup_runner.ps1:30` [Codex GPT 5.6 Sol]

```powershell
$baseDir = "C:\ProgramData\Lima\provision"
foreach ($f in (Get-ProvisionFiles -Root $baseDir -Mode $Mode)) {
    Invoke-ProvisionScriptFile -File $f
}
```

The runner starts each script with no configuration loaded. `templates/default.yaml:588-594` promises that `param` values reach provisioning scripts as `PARAM_<key>` environment variables, and lines 579-586 promise `env` values are loaded into the VM. `templateArgs` populates both maps, but a grep of `wincidata.TEMPLATE.d` finds no reference to `Env` or `Param` in any of the four files. So a script reading `$env:PARAM_Key` or a configured proxy silently gets an empty value.

Fix: serialize `Env` plus prefixed `Param` values into the provision payload and import them before invoking each script, or document the gap alongside the other Windows limitations.

I5. **One failing script skips every remaining script in that mode** — `pkg/cidata/wincidata.TEMPLATE.d/startup_runner.ps1:24` [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```powershell
    if ($LASTEXITCODE -ne 0) {
        throw ("Provision script exited with code {0}: {1}" -f $LASTEXITCODE, $File.FullName)
        exit $LASTEXITCODE
    }
```

The uncaught `throw` unwinds `startup_runner.ps1`, so the loop never reaches later files. Linux runs every entry and only then reports failure: `boot.sh:172-179` logs `WARNING "Failed to execute $f"`, sets `CODE=1`, and continues, and `boot.Linux/30-install-packages.sh:20-28` does the same for dependency scripts. This bites hardest in dependency mode, which runs only at installation, so a skipped entry is skipped permanently. Line 25 is also dead code, since `throw` unwinds before `exit` runs.

Fix: `Write-Error` per failure, record a non-zero status, continue the loop, and `exit` that status once at the end.

I6. **`limactl start` does not wait for startup provisioning on reboots** — `pkg/hostagent/requirements.go:285` [Claude Opus 5]

```go
			script:      `PowerShell.exe -NoProfile -NonInteractive -Command "if (Test-Path -Path 'C:\ProgramData\Lima\lima-boot-done.txt' -PathType Leaf) { exit 0 } else { exit 1 }"`,
```

The Windows readiness check tests only that the marker exists, and `first_logon.ps1:97` writes the constant `'done'`. Linux compares the marker's contents against the current boot's instance ID (`requirements.go:364`) precisely so the host waits for this boot's provisioning, and `finalWinRequirements` (`requirements.go:372`) is empty. Before this PR nothing ran on a Windows reboot, so the weak marker was harmless. Now `limactl start` reports ready while the startup tasks are still running or have already failed. The cited code sits outside the diff, but this PR is what makes it load-bearing.

Fix: have the startup runner write the current IID (shipped on the ISO) to the marker, and add a `finalWinRequirements` entry comparing it to `a.iid`.

S2. **Data files land under opaque index names** — `pkg/cidata/wincidata.TEMPLATE.d/install_provision.ps1:46` [Claude Opus 5, Gemini 3.5 Flash]


S3. **Startup tasks do not preserve the documented system-before-user order** — `pkg/cidata/wincidata.TEMPLATE.d/install_provision.ps1:50` [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.1 Pro]


Filed as a suggestion because I1 currently prevents the user task from registering at all. Fix I1 first, and this becomes reachable.

Fix: register one SYSTEM-triggered coordinator that runs system mode to completion and then starts the user task on demand.

S4. **Windows template tests ignore the two new files** — `pkg/cidata/template_test.go:358` [Codex GPT 5.6 Sol, Claude Opus 5]

The `switch f.Path` matches only `autounattend.xml` and `first_logon.ps1`, and nothing asserts the layout's entry set. So the test still passes if `install_provision.ps1` drops out of the embedded filesystem or stops rendering `{{.User}}`, the one substitution I1 depends on.

Fix: collect entries into a map keyed by path, assert the expected four-path set, and assert `install_provision.ps1` contains `-UserId "windows-user"`.

S5. **Variable casing differs from its declaration** — `pkg/cidata/wincidata.TEMPLATE.d/install_provision.ps1:17` [Claude Opus 5, Gemini 3.1 Pro]


Declared as `$startupSystemScriptsSrc` at line 14. PowerShell variable names are case-insensitive, so this resolves correctly and is cosmetic. But the three sibling loops all match their declarations, and no CI job lints `.ps1` in this repo, so nothing else will catch drift like this.

S6. **Caveat line is ungrammatical and vague** — `website/content/en/docs/usage/guests/windows.md:37` [Claude Opus 5]

## Design Observations

### Concerns

- **Two security contexts for the same script** (in-scope) [Claude Opus 5, Gemini 3.1 Pro]. At first logon, `-Mode system` runs inside `FirstLogonCommands`, as the elevated lima administrator; from the next boot on, the same script runs as `SYSTEM`. `$env:USERPROFILE`, `HKCU`, and mapped drives all differ between the two, so a script that looks idempotent on the first boot can diverge afterwards. Running the first-boot pass through the registered tasks would give one context for both.
- **ISO-as-source versus copy-as-source** (future) [Codex GPT 5.6 Sol, Claude Opus 5]. The design copies provisioning into `C:\ProgramData` once and treats that copy as the source of truth, which is what produces I3's stale scripts and much of C1's per-mode branching. Re-syncing from a per-start volume, then running the modes in order, would collapse C1, I3, and S3 into one path that mirrors Linux's `boot.sh`.
- **`ValidateTemplateArgs` now runs twice per call** (in-scope) [Claude Opus 5]. `executeTemplateWalkDir` validates at `template.go:212` while both callers already validate (`cidata.go:404`, `cidata.go:605`). Harmless, but it is why five test cases needed new `UID`/`Home`/`Shell`/`SSHPubKeys` fields. Worth deciding which layer owns the check.

### Strengths

- Replacing the hand-listed two-file Windows layout with the `WalkDir` helper the Linux path already uses means new files under `wincidata.TEMPLATE.d` ship automatically and get template expansion for free. That is what lets `install_provision.ps1` use `{{.User}}` with no extra wiring. (in-scope) [all four reviewers]
- `%08d` naming in `appendProvisionEntries` plus `Sort-Object Name` in `startup_runner.ps1:14` preserves the declared script order, matching Linux's glob order. (in-scope) [Codex GPT 5.6 Sol, Gemini 3.1 Pro, Claude Opus 5]
- Provisioning runs before the boot-done marker (`first_logon.ps1:93`), so first-boot provisioning is covered by `limactl start`'s wait. (in-scope) [Claude Opus 5]

## Review Process Notes

### Skill improvements

- When a change adds a second platform's implementation of a feature that already exists on another platform, locate the feature's normative documentation (spec file, template comments, user-facing docs) and check the new implementation against each promise it makes, one promise at a time. Ports reproduce the happy path and quietly drop the guards, environment plumbing, ordering guarantees, and error-continuation semantics that the documentation states as cross-platform contracts. Report each unmet promise as a finding, and say whether documenting the divergence would be an acceptable resolution.
- When a change makes new work run during an existing lifecycle phase (boot, startup, first login, shutdown), check whether that phase's completion signal still covers the new work. A readiness marker, probe, or wait condition written before the new work existed will report done while the new work is still running, and the failure is silent because the caller sees a successful start.

### Repo context updates

- The PowerShell scripts under `pkg/cidata/wincidata.TEMPLATE.d/` ship to the Windows guest, and no CI job lints, parses, or executes them. No CI job boots a Windows guest at all: `windows-2025` in `.github/workflows/test.yml` is a runner label, so those jobs run lima on a Windows host with Linux guests. Treat any behavior claim about these scripts as unverified and reason from documented PowerShell semantics.
- `templates/default.yaml` is the normative spec for `provision` semantics. It documents the per-boot execution order (data → yq → system → user), that `user` scripts run without root privileges, and that `param` values reach provisioning scripts as `PARAM_<key>` environment variables. Check any platform-specific provisioning implementation against each of those promises.
- The Windows guest's cidata ISO is attached only until the guest is installed (`pkg/driver/qemu/qemu.go`, gated on `isWindowsBootDone`), while the hostagent regenerates that ISO on every start. Anything the guest needs after installation must be copied into the guest or delivered on a separate volume, so host-side config edits never reach an existing Windows instance.

### Design Observations

**Concerns**

- *Two security contexts for the same script* (in-scope). At first logon, `-Mode system` runs inside `FirstLogonCommands`, i.e. as the elevated lima administrator; from the next boot on, the same script runs as `SYSTEM` (`install_provision.ps1:52`). `$env:USERPROFILE`, `HKCU`, and mapped drives all differ between the two, so a script that appears idempotent on first boot can diverge afterwards.
