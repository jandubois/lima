## Executive Summary

Round 5 answers every round-4 finding, and the privilege boundary still holds under probing. Three defects the round introduced do not. The newly documented sudoers install mode leaves the file unreadable to Lima, breaking `limactl start` and `--check`. The helper-install preflight moved onto a code path `limactl delete` also takes, so an instance with `blockDevices` can no longer be removed. And the same-VM lock reuse now lets one VM attach the same disk twice.

---

## Critical Issues

None.

The trust boundary held everywhere I pushed on it. The socket handoff still authenticates in both directions before the nonce is written, `validateDiskDeviceIdentity` still compares `st_rdev`, and the recursive ownership/symlink/ACL walk over the helper path and its ancestors is unchanged. Nothing below lets a local user reach a device they were not granted; the three Important findings all cost availability, not confinement.

I1. **The newly documented `0440 root:wheel` install mode leaves `/etc/sudoers.d/lima` unreadable to Lima** — `website/content/en/docs/config/disk.md:127` [Claude Opus 5]


## Design Observations

### Concerns

**Block-device grants are per-user inside a file every user rewrites** *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol]. `renderSudoers` emits only the invoking user's grants and `verifySudoersFile` compares the whole file byte-for-byte whenever `--block-device` is passed, so two users on one machine cannot both hold device grants and neither can `--check` the combined file. S3 fixes the documentation; the model itself is the decision. A `--block-device` check that used `ContainsActiveFragment` on the block fragment — the containment the network path already uses at `pkg/networks/sudoers.go:112` — would tolerate other users' grants, at the cost of no longer detecting stale extra device grants.

**The grant names a device slot, not a disk** *(future)* [Claude Opus 5, Codex GPT 5.6 Sol]. Unchanged from round 4 and documented at `disk.md:139-141`. Keying the grant on a `diskutil` UUID resolved at open time remains the durable answer, which the sudoers argv form cannot express.

**Receive-to-dup close-on-exec window** *(future)* [Codex GPT 5.6 Sol]. The pinned `github.com/balajiv113/fd` receives descriptors with `syscall.Recvmsg` and returns them without `FD_CLOEXEC`; Lima sets it on the later duplicate at `pkg/blockdevice/block_device_darwin.go:681`. No competing in-process `exec` exists during that window today. If VM startup ever becomes parallel, the receiver must hold `syscall.ForkLock` across it.

### Strengths

- **The release-archive install recipe is correct end to end** *(in-scope)* [Claude Opus 5]. `make artifact` tars `_output/` wholesale, the GOOS-guarded phony target builds the helper into `_output/libexec/lima/privileged/`, and extracting into `/opt/lima` puts it exactly where `privilegedHelperPathForExecutable` looks. `--no-same-owner` is load-bearing: the archive stores the builder's uid, which `validateSecurePathElement` would reject.
- **All four round-4 strengths survive** *(in-scope)* [Claude Opus 5]. The single argv pin with the `Lstat` → `O_NOFOLLOW` → post-open `Stat` chain, ACL detection on directories as well as files, per-VM retention with `processRetainedFDs` still serving krunkit's exported entry points, and a network fragment byte-identical to the merge-base after the `sudoers.NOPASSWD` extraction.
- **The stopped branch now reaches cleanup** *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol]. This answers round 4's unreachable-defer observation, and the `return` strands no sender: `Code-Hex/vz` delivers state changes over an unbounded channel.
- **`attachDisks` unlocks every additional disk it acquired on the error path** *(in-scope)* [Claude Opus 5]. `vm_darwin.go:623-630` closes a stranded-lock class beyond this PR's own feature.

## Review Process Notes

### Skill improvements

- **When a fix moves a check from a cheap predicate to an expensive one, enumerate every caller of the enclosing function before accepting it.** A stricter check is usually evaluated against the path the fix was written for. Find the other callers — teardown, inspection, listing and repair paths often share a configuration or validation entry point — and ask what the new predicate costs a user on each. A check that is correct for the start path can make an instance impossible to remove.

- **When a round adds a retry, a timeout or another tolerance to a test harness, re-read the failure modes that harness deliberately makes loud.** Tolerance and loudness are added for opposite reasons and frequently land in the same round, each justified on its own. Ask which deliberate failure the new tolerance now absorbs, and whether state from the absorbed attempt is still reachable to the cleanup that runs after it.

- **A documented command is code; check it against every consumer of the artifact it produces.** When a change prescribes ownership, mode or location for a file the program itself reads, find the read sites and check what error the prescribed form produces there. Fallbacks written for "file absent" rarely cover "file present but unreadable", and the two are one octal digit apart.

### Repo context updates

- **[repo] `wheel` contains only `root` on macOS, so a `0440 root:wheel` file is unreadable to the invoking user.** Lima reads `/etc/sudoers.d/lima` unprivileged in `cmd/limactl` and `pkg/networks`, and both fall back only on `os.ErrNotExist`. Any change that prescribes or installs a mode for that file has to keep it readable by the user running `limactl`.

- **[repo] `Configure` is on the teardown path, not just the startup path.** `pkg/instance/delete.go`, `pkg/snapshot` and `cmd/limactl/factory-reset.go` all reach a driver's `validateConfig` through `driverutil.CreateConfiguredDriver`. A refusal added there blocks removing an instance, and `--force` does not bypass it. Checks that describe what a running VM needs belong in the driver's `Validate`, which only start, edit, restart and clone call.

- **[repo] macOS device paths that differ textually can address the same storage.** `/dev/diskN` and `/dev/rdiskN` are aliases, and `/dev/diskNsM` is a slice of `/dev/diskN`. Any check that compares configured device paths for equality — duplicate rejection, lock keying, retention accounting — has to normalize the leading `r` and the partition suffix first, and distinguish "same extent" from "sibling partitions of one disk", which are legal together.

- **[repo] `hack/bats/extras/` is not part of `make bats`.** The `bats` target runs `./hack/bats/tests` only; the `extras/` suites run from explicit workflow steps. When judging who a defect in an `extras/` suite reaches, the primary consumer is an ephemeral CI runner, not a developer machine.

> ## Design Observations
> 
> **Concerns**
> 
> - **`/etc/sudoers.d/lima` is a single-writer file, but block-device grants are per-user (in-scope).** `verifySudoersFile` (`cmd/limactl/sudoers_darwin.go:124`) compares the whole file byte-for-byte whenever `--block-device` is passed, and `renderSudoers` emits only the invoking user's grants. Two users on one machine cannot both hold device grants: whoever runs `limactl sudoers` last wipes the other's, and neither can `--check` the combined file. The docs warn about regenerating within one user's set but not across users. A `--block-device` check that used `ContainsActiveFragment` on the block fragment — the same containment the network path already uses at `pkg/networks/sudoers.go:105` — would tolerate other users' grants and other Lima fragments, at the cost of no longer detecting stale *extra* device grants. > - **`limayaml` → `blockdevice` inverts the layering (future).** See S9. A two-file `pkg/blockdevice/path` (or a constant in `pkg/limatype`) would give `limayaml` the grammar without the sudo-invoking package.

> 
> - The `attachDisks` error path now unlocks every additional disk it acquired (`vm_darwin.go:623-630`), closing the stranded-lock class the qemu `Cmdline` path still has. That is a real improvement beyond the PR's own feature.

> S1. **S3 partly fixed: Symlinked CLI binaries are still misdiagnosed** — `pkg/blockdevice/block_device_darwin.go:244` (suggestion, gap)
> 
> ```go
> func ValidateExecutable(exe string) error {
> 	if filepath.Base(exe) != "limactl" {
> 		return fmt.Errorf("field `blockDevices` requires builtin VZ invoked as limactl, not external VZ drivers or renamed executables (got %q)", exe)
> 	}
> ```
> 
> The error message was improved to acknowledge that "renamed executables" are rejected, but the check still relies on `filepath.Base(exe)`. If a user runs Lima via an actual symlink to the binary named `lima` (e.g., created manually or by a package manager alias), `os.Executable()` on macOS evaluates to the symlink path. This triggers the rejection, frustrating users who are running the correct builtin VZ binary. *(Note: The standard `lima` shell script wrapper is unaffected because it uses `exec`, but direct symlinks fail.)*
> 
> Fix: Use `filepath.EvalSymlinks(exe)` before checking the basename.

> S2. **Goroutine leak when hostagent stops before VM state change** — `pkg/driver/vz/vm_darwin.go:209` (suggestion, regression)
> 
> ```go
> 					// Release descriptors before notifying the hostagent, which may
> 					// exit immediately upon receiving the stopped state.
> 					retainedFDs.CloseAll()
> 					sendErrCh <- errors.New("vz driver state stopped")
> 					return
> ```
> 
> The `startVM` background goroutine sends the stopped state to the unbuffered `sendErrCh`. If the hostagent has already exited its `startRoutinesAndWait` select loop (e.g., because `ctx.Done()` occurred), there is no receiver for this channel. The send blocks forever, leaking the goroutine. Because the `hostagent` process terminates shortly after this shutdown sequence, the leaked goroutine and its stranded resources are reclaimed by the OS, making this practically harmless.
> 
> Fix: Wrap the send in a `select` with `ctx.Done()`, or use a `default` case, or change `sendErrCh` to be buffered (`make(chan error, 1)`).

> #### Suggestions
> 
> S1. **Unbuffered channel send in `startVM` goroutine can block on VM stopped state** — `pkg/driver/vz/vm_darwin.go:208` (suggestion, gap)
> 
> ```go
> 					// Release descriptors before notifying the hostagent, which may
> 					// exit immediately upon receiving the stopped state.
> 					retainedFDs.CloseAll()
> 					sendErrCh <- errors.New("vz driver state stopped")
> 					return
> ```
> 
> `sendErrCh` is initialized as an unbuffered channel (`make(chan error)`). If the hostagent has already exited `startRoutinesAndWait` (for example, due to a signal or context cancellation), there is no active reader on `errCh` (which is `sendErrCh`). Consequently, sending the stopped state to `sendErrCh` will block the background goroutine indefinitely. While this is a pre-existing, benign, self-healing leak since the hostagent process terminates shortly after VM stop anyway, making the channel buffered adds extra resilience.
> 
> Fix: Initialize `sendErrCh` as a buffered channel of size 1.
> 
> ```diff
> -	sendErrCh := make(chan error)
> +	sendErrCh := make(chan error, 1)
> ```
