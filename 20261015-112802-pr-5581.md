A `limactl` without this change reads `networkOpts` as an unknown field. It logs "Non-strict YAML detected" (`pkg/limayaml/marshal.go:81`) and starts the guest with host loopback reachable, so the option fails open for the untrusted guests it targets. Round 2 recorded this as a design concern.

## Design Observations

### Concerns

- (future) An explicit `hostLoopback: null` in a child template overrides a base template's `false`. The merge drops every non-map node of the base that the child also sets, null included (`pkg/limatmpl/embed.go:235-237`). A child copied from `templates/default.yaml`, which now contains `hostLoopback: null`, therefore turns off a base's isolation without a warning. `limactl template copy --embed` gives `hostLoopback: null` for such a child and `false` without the null line. Every field merges this way, so the rule belongs to the template system; a docs note would help users of an isolation option. [Claude Opus 5.5]

## Acknowledged Limitations

- External drivers from the registry ignore the option, and a driver feature flag is deferred. The in-tree external vz build receives the field, because the gRPC client sends the instance as JSON.
- krunkit, `user-v2` and QEMU's `disable_host_loopback` are deferred, and each rejects `false`.
- A host service bound to all interfaces stays reachable through the host's LAN IP. The change does not make that worse.
- With the refusals in `Validate`, `limactl create` on an unsupported driver writes the instance and then fails, because `createAction` runs `instance.Prepare`, which calls the driver's `Validate` (`cmd/limactl/start.go:578`, `pkg/instance/start.go:83`). `limactl start` refuses it too, and `limactl edit` can clear the setting. Round 2 said only `start` refuses.
- Do not re-suggest moving the refusals into `limayaml.Validate`. It runs on every load (`pkg/store/store.go:127`), so every instance that sets the option on an unsupported driver would load with an error. `limactl list` would show it with errors (`pkg/store/instance.go:81-87`), and it could not start. Earlier rounds called such an instance unlistable, which overstates it.
- Do not re-suggest remapping the gateway to `127.0.0.2` or `240.0.0.1`. On macOS both time out instead of failing at once (round 1 measured 75 s and over 5 s).
- Do not re-suggest mapping `127.0.0.1` in `natTable`. gvisor drops guest packets addressed to `127/8`, and this still holds with gvisor-tap-vsock v0.9.0 and gvisor 2026-04.
- Do not re-raise the qemu `Validate` panic on a nil config. `CreateConfiguredDriver` dereferences `inst.Config` (`pkg/driverutil/instance.go:22`) before any driver method runs.
- Do not re-suggest spelling the five refusals one way, through `HostLoopbackEnabled` or a single error format. It is style. `hcs_driver_windows.go`, `wsl_driver_windows.go` and `krunkit_driver_darwin_arm64.go` would each need a new import for no change in behavior, and every message already names the field and the driver or network it conflicts with.

## Review Process Notes

### Skill improvements

- When a probe depends on a package-level variable that tests stub (a resolver, a clock, a hook), run it in a full package run as well as alone. A sibling test that swaps the variable and never restores it can make the probe pass, or fail, for a reason unrelated to the code under test.
- When a change reuses a notation that the file already uses (a version note, a marker, a status tag), check what the notation means at its other uses. A note copied into a new context can state something false while looking consistent.

### Repo context updates

- [repo] UPDATE "gvisor-tap-vsock dials guest destinations from the host": as of gvisor-tap-vsock v0.9.0, the TCP forwarder dials with `net.DialTimeout` (30 s by default, `TCPConnectTimeout`) and admits 128 connection attempts in flight by default (`TCPMaxInFlight`), and a new ICMP forwarder applies the same NAT table to guest pings. gvisor still drops guest packets with a `127/8` source or destination, and the stack still registers only IPv4 and ARP.
- [repo] ADD: In `templates/default.yaml`, a version note after a builtin default, as in "Builtin default: false (since Lima v1.0)", dates a change of default. The version that introduced a field goes on its own comment line, so a reader does not take a new option for a changed default.
- [repo] ADD: `TestSetupEnv` in `pkg/cidata` replaces `netLookupIP` with a stub that returns one loopback address and does not restore it. A later test in the package that depends on name resolution must install its own stub, or its result depends on test order.

###### Design Observations

**Concerns**

- **An older `limactl` ignores the option without failing (in-scope, docs only).** This is round 2's design concern, and the rename does not change it. A `limactl` without the field decodes `networkOpts` non-strictly: `Unmarshal` in `pkg/limayaml/marshal.go:81` logs "Non-strict YAML detected" and starts the guest with host loopback reachable. Most users opt in for untrusted guests, so for them this is the one way the option fails open. `minimumLimaVersion` already provides a fail-closed check: `pkg/limayaml/validate.go:46-48` refuses an instance whose Lima is older. Adding one sentence to `user.md` and the template comment, telling users to set `minimumLimaVersion: 2.3.0` in templates that depend on the option, would close it.
