website/content/en/docs/config/mount.md

The "wsl2" mount type relies on using WSL2's native disk sharing, where the root disk is available by default at `/mnt/$DISK_LETTER` (e.g. `/mnt/c/`).

When using `vmType: wsl2`, entries in `mounts` are supported:
- A drive-letter `location` (e.g. `C:\Users\...`) automatically defaults its `mountPoint` to the corresponding `/mnt/<drive>/...` path.
- Lima mounts only drive-letter locations. The guest skips a location without a drive letter, such as a UNC network path, and logs a warning.
- Custom `mountPoint` paths are bind-mounted to the destination inside the guest at boot.
- When `writable: false` is configured, the mount is remounted read-only to prevent accidental modifications at that path. Note that with a custom `mountPoint`, the underlying host files may still be accessible and writable through WSL2's native drive automounts unless configured otherwise.

The source stays writable under /mnt/<drive>, the user has passwordless sudo, and interop runs Windows programs, so a read-only bind guards against mistakes only.
  • An existing wsl2 instance whose mount point cannot be defaulted becomes unloadable, and deleting it leaves the distro registered (in-scope) Codex GPT 6 Astra Claude Opus 5.5. This corrects round 2, which said such an instance shows as Broken. Even then, Delete skips unregister whenever inst.Errors is non-empty (:27-31), so lima-<name> stays registered with WSL. The commit message does not mention the stricter validation.
  • The script changes mounts while it still reads the mount table for later decisions (in-scope) Codex GPT 6 Astra. S1, S2 and S3 share that cause. Translating every source and checking for overlaps first, then mounting, would address all three.
  • The translator hard-codes /mnt (future) Claude Opus 5.5 Codex GPT 6 Astra. With a custom [automount] root, wslpath and the default mount point disagree. (raised in round 2 by all four agents)
