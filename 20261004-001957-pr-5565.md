## Executive Summary

The PR sends `host_time` ahead by half the smaller of the last two round trips, so steady RPC latency no longer steps the guest clock back each tick. When that estimate, one or two ticks old, exceeds the current request delay (after a slow first sync, when load ends, or when replies run slow), the guest is set ahead of the host and a later tick steps it back. Two small patches fix this, at some cost to the gain.

## Important Issues

I1. **The second sync compensates from a single sample, so a slow first sync steps the guest ahead and then back** — `pkg/hostagent/timesync.go:94-101` [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash, Gemini 3.1 Pro]

```go
func oneWayDelay(prev, last time.Duration) time.Duration {
	if last <= 0 {
		return 0
	}
	if prev > 0 && prev < last {
		return prev / 2
	}
	return last / 2
```

On tick 2 `prev` is still 0, so line 101 returns half the only sample. The doc comment's claim that a single stall cannot aim the next tick ahead holds only from tick 3. The first sync runs while the guest is still booting. After a slow first round trip, tick 2 aims `host_time` ahead and the guest steps forward; with no guest NTP, tick 3 steps it back. An 8 s stall on the first reply gives +3.995 s, then −3.995 s, where the merge-base does not step. Below the threshold the guest stays ahead. Round trips of 220 ms then 40 ms leave it 90 ms ahead, against 110 ms behind at the merge-base and on time with the fix.

			}
			receipt := sentAt.Add(tr.out)
			drift := receipt.Add(offset).Sub(hostTime)

	}
	return steps
}

I2. **A stale estimate sets the guest ahead of the host when load ends or replies run slow, and a later tick steps it back** — `pkg/hostagent/timesync.go:66-69` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```go
	sentAt := now()
	// host_time is the predicted receipt time (issue 5543).
	hostTime := compensatedHostTime(sentAt, oneWayDelay(prev, last))
	resp, err := doSync(ctx, hostTime)
```

The delay comes from round trips 10 and 20 s old. When it exceeds the current request leg by more than 100 ms, the guest (`pkg/guestagent/api/server/server.go:128-130`) sets its clock to a `host_time` ahead of the host's own clock. The merge-base never could, because its `host_time` was never later than the guest's receipt. Load ending triggers this, and so do replies slower than requests, since rtt/2 charges half the reply leg to the request. Without guest NTP, a later tick steps it back. Which model Lima guests follow is open (Design Observations).

## Suggestions

S1. **`Fixes #5543` closes the issue while a single latency spike still steps the guest back by almost its full delay** — `3a5e97c3` [Claude Opus 5.5]

The estimate predicts each RPC from earlier ones, so it cannot see a spike in the current one. In Claude's executed simulation, a 4 s round trip between 10 ms ticks steps the guest back 1.995 s, against 2 s at the merge-base. The issue's largest adjustments (1388, 4102 and 9577 ms) look like that, and the issue proposes two guards for them (persistent same-signed drift, or never stepping back by less than the measured latency) that this PR does not add. Merging with `Fixes #5543` closes the issue on those cases.

Fix: write `Refs #5543` in the commit and the PR body, or keep the issue open for the spike case.

S2. **Several test assertions are arithmetic identities, and no test applies the guest's step rule** — `pkg/hostagent/timesync_test.go:24-26` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]

```go
		assert.Equal(t, hostTime, sentAt.Add(180*time.Millisecond))
		// Receipt at sentAt+180ms has drift 0, inside the guest's 100ms threshold.
		assert.Equal(t, sentAt.Add(180*time.Millisecond).Sub(hostTime), time.Duration(0))
```

Once line 24 passes, line 26 cannot fail. Lines 34-38 build `guestNow` 140 ms behind and then assert the drift is −140 ms, without noting that −140 ms crosses the threshold and makes the guest step. Every `TestSyncGuestClock` subtest is a single call with a hand-set window, so nothing feeds one tick's output into the next or applies `GuestServer.SyncTime`'s threshold-and-set rule. That is why I1 and I2 pass the suite.

Fix: replace the identity assertions with a multi-tick test that models the guest's rule, like the probes in I1 and I2, and assert on the guest's step sequence.

S3. **`syncTimeOnce` assigns its named results only to return them** — `pkg/hostagent/timesync.go:58-59` [Gemini 3.5 Flash]

```go
	prevRTT, lastRTT = syncGuestClock(ctx, client.SyncTime, prev, last, time.Now)
	return prevRTT, lastRTT
```

Fix: `return syncGuestClock(ctx, client.SyncTime, prev, last, time.Now)`.

S4. **The negative-RTT clamp guards a value production cannot produce** — `pkg/hostagent/timesync.go:75-76` [Claude Opus 5.5]

```go

	prev, last = last, max(now().Sub(sentAt), 0)
```

Fix: drop the clamp, the subtest and the commit-body sentence.

## Design Observations

### Concerns

- **(in-scope) Whether the PR reduces backward steps depends on what moves the guest clock between ticks, and nobody has measured that.** [Claude Opus 5.5] Claude ran 2000 simulated ticks per latency distribution with symmetric legs. If the guest is restored to true time before each tick, the PR cuts backward steps from 1343 to 694 (uniform 0 to 600 ms RTT) and from 2000 to 1 (200 to 400 ms). If the guest keeps whatever offset the last step left, the PR raises them, from 439 to 571, 1 to 47, and 313 to 374 for 10 ms RTT with 20% of ticks at 400 ms. With I2's cap the free-running counts are 478, 1 and 313, and the restored ones 894, 1 and 383. The reporter's log, with positive drift on tick after tick, fits the restored model better, but I don't know what restores the guest that fast. A loaded-host VM run counting guest steps before and after the PR would settle it.
- **(future) Measuring the offset inside one exchange would cover spikes, drops and asymmetric legs.** [Claude Opus 5.5, Codex GPT 6 Astra] The guest would report its clock without stepping, and the host would compute `offset = guest_now − (sentAt + rtt/2)` from that same call and order a step only when the offset exceeds the threshold plus rtt/2. That needs a proto field and a guest agent change. The guest agent ships in the cidata that the same `limactl` build generates, so version skew is limited to instances not restarted since an upgrade.
- **(in-scope) The `Info` call before every `SyncTime` is not a clean fresh sample.** [Claude Opus 5.5] Claude suggested timing it, since `getOrCreateClient` calls `client.Info` (`pkg/hostagent/hostagent.go:915`) just before each sync. But the guest's `Info` runs `LocalPorts` (`pkg/guestagent/guestagent_linux.go:205`), so its round trip includes guest work and overstates transport, the direction I2 warns about.

### Strengths

- **(in-scope)** Injecting `doSync` and `now` makes `syncGuestClock` testable without a VM, and both probes in this review depend on it. [Codex GPT 6 Astra, Claude Opus 5.5]
- **(in-scope)** The change stays on the host: no proto field and no guest agent change. [Gemini 3.5 Flash]
- **(in-scope)** The RTT window is a local of the time-sync goroutine, so it does not need locking. [Codex GPT 6 Astra]
- **(in-scope)** In steady state the min-of-two filter does stop one stall from aiming the following tick ahead. [Claude Opus 5.5, Gemini 3.5 Flash]

## Review Process Notes

### Skill improvements

- When a change feeds measurements from earlier iterations into a decision a downstream consumer acts on (a predicted delay, a rate estimate, a backoff), evaluate the consumer's actions over a sequence of iterations that includes the cold start and a regime change in each direction. An estimator that is right in steady state overshoots or undershoots at each transition, and the consumer's action there can be worse than the uncompensated behavior.

### Repo context updates

- [repo] Guest time sync is a closed loop. `GuestServer.SyncTime` steps the guest clock to the request's `host_time` whenever the drift exceeds 100 ms, and the hostagent sends a request every 10 s. Judge any change to a request's `host_time` by the guest's sequence of steps across ticks, including the first ticks and a latency change in each direction. A guest left ahead of the host is corrected by a backward step on a later tick, which is the symptom time sync exists to avoid.

**Concerns**

- **Whether the PR helps depends on what moves the guest clock between ticks (in-scope).** I ran a simulation, not a measurement: 2000 ticks per distribution, symmetric delay, counting backward steps. I compared two guest models.

  - The I1 cap gives 478, 1 and 313 free-running, and 894, 1 and 383 disciplined.

  An alternative design measures the latency in the same exchange instead of predicting it. The guest would report its clock without adjusting it, and the host would compute `offset = guest_now - (sentAt + rtt/2)` from the RTT of that call. The host would then order a step only when `|offset| > threshold + rtt/2`. That needs a proto field. The guest agent ships in the cidata that the same `limactl` build generates, so version skew is limited to instances that have not been restarted.
- **A cheaper current-latency sample already exists (in-scope).** `getOrCreateClient` calls `client.Info` (`hostagent.go:899-901`, `915`) immediately before every `SyncTime`. On a loaded host, the request leg probably waits for the guest vCPU and so carries most of the delay. rtt/2 then under-compensates, which errs in the safe direction. Over-compensation, and the ahead-then-back steps it causes, comes only from a slow response leg or from a falling estimate as in I1.

+				prev, last = last, max(time.Now().Sub(sentAt), 0)

I1. **`oneWayDelay` uses single sample at startup, allowing an initial stall to aim timestamps into the future** — `pkg/hostagent/timesync.go:94-102` (important, regression)

```go
func oneWayDelay(prev, last time.Duration) time.Duration {
	if last <= 0 {
		return 0
	}
	if prev > 0 && prev < last {
		return prev / 2
	}
	return last / 2
}
```

The docstring at lines 91–93 states that "a single stall cannot aim the next tick ahead." However, at startup (`timesync.go:38`), `prev` is initialized to 0. After the first sync, `prev` remains 0 and `last` stores sample 1. On tick 2, line 98 evaluates `prev > 0` as false and falls through to line 101 (`return last / 2`). If the initial RPC stalls during VM boot (e.g., 6s), tick 2 projects `host_time` 3s into the future. The guest adjusts forward by 3s (`server.go:130`) and then steps backward by 3s on tick 3 when latency settles.

### Design Observations

#### Concerns
- **Clock overshooting and backward step on latency collapse `(in-scope)`**:
  Because `syncGuestClock` predicts receipt time unilaterally based on prior RTT samples, a sudden drop in RPC latency after a period of sustained host load (e.g., RTT falling from 1000ms to 20ms) causes the host to send a `host_time` stamp up to 490ms in the future. Because `GuestServer.SyncTime` (`server.go:129`) sets system time whenever `|drift| > 100ms`, the guest steps its clock forward by 490ms. On the subsequent tick 10 seconds later, `oneWayDelay` reflects the lower latency (10ms), but the guest clock remains 490ms ahead, triggering `SetSystemTime` and stepping the guest wall clock *backward* by 490ms. While addressing this fully without a cooperative protocol (e.g., guest-side NTP or slewing via `clock_adjtime`) is challenging within the existing gRPC schema, capping `oneWayDelay` or enforcing two-sample stability helps minimize these overshoot windows.

#### Strengths
- **Zero guest-agent dependency**: Implementing the compensation entirely within `pkg/hostagent/timesync.go` fixes the issue for existing VM instances without requiring guestagent rebuilds, image updates, or cloud-init re-provisioning.
- **Min-filtering in steady state**: Taking the smaller of two recent round-trips prevents isolated latency spikes from inflating `oneWayDelay`.
