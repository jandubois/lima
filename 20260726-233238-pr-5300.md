## Suggestions

S1. **Stock Cygwin with `sftpDriver: builtin` serves a directory that does not exist** — `pkg/hostagent/mount.go:29` [Codex GPT 5.6 Sol]

```go
	resolvedLocation, err = sshutil.PathForSSH(ctx, sshExe, location)
	if err != nil {
		return "", "", err
	}
	if driver == limatype.SFTPDriverBuiltin {
		return resolvedLocation, "", nil
	}
```

`PathForSSH` runs before the builtin short-circuit. Under `builtin` sshocker serves the mount in-process, so Go's `pkg/sftp` on the host is the only consumer. On stock Cygwin the sibling `cygpath` returns `/cygdrive/c/...`, and sshocker's `convertMSYS2Path` rewrites a value only when its third byte is a slash, so this form passes through untouched. `toLocalPath` then maps it to `\cygdrive\c\...`, which resolves against the current drive.

At the merge-base the same configuration already failed whenever `cygpath` sat on PATH, because `fsutil.WindowsSubsystemPath` produced that identical form. The regression is narrower: a stock Cygwin whose `cygpath` is absent from PATH but sits beside the selected `ssh.exe` used to take the in-process `/c/...` fallback, which sshocker rewrote correctly.

Fix: hand the builtin server a native path, which is what it wants on every toolchain.

```diff
+	if driver == limatype.SFTPDriverBuiltin {
+		return filepath.ToSlash(location), "", nil
+	}
 	resolvedLocation, err = sshutil.PathForSSH(ctx, sshExe, location)
```

S2. **Two of the three new Cygwin subtests return the same answer through the native fallback** — `pkg/sshutil/sshutil_windows_test.go:166` [Claude Opus 5]

```go
	t.Run("candidate that resolves to nothing returns empty", func(t *testing.T) {
		sshExe := cygwinToolchain(t)
		t.Setenv(fakeCygpathOutEnv, filepath.Join(filepath.Dir(sshExe), "sftp-server"))

		assert.Equal(t, SftpServerForSSH(ctx, SSHExe{Exe: sshExe}), "",
			"unresolvable candidate -> caller falls back to sshocker auto-detect")
	})
```

`cygwinToolchain` writes `ssh.exe` and `cygpath.exe` into one directory, and every fake answer points back into that same directory. The native fallback at `pkg/sshutil/sshutil.go:267` searches exactly there, so it yields the identical result in all three subtests. Were `cygpathForSSH` to stop reporting the toolchain as Cygwin, all three would still pass. `TestCygpathForSSH` covers branch selection on its own, which keeps this a suggestion.

Fix: make the two answers differ. Put the resolvable `sftp-server.exe` in a second directory the native fallback cannot see, and in the empty-result subtests write an `sftp-server.exe` beside `ssh.exe` so a native fallback would return it. Asserting `""` then proves the Cygwin branch ran.

S3. **The fake cygpath ignores its arguments, so nothing pins the probe path** — `pkg/sshutil/sshutil_windows_test.go:26` [Codex GPT 5.6 Sol]

```go
func TestMain(m *testing.M) {
	if out, ok := os.LookupEnv(fakeCygpathOutEnv); ok {
		if out == fakeCygpathFailure {
			os.Exit(1)
		}
		os.Stdout.WriteString(out + "\n")
		os.Exit(0)
	}
```

The fake reads the environment and never looks at `os.Args`. `SftpServerForSSH` asks for `-w /usr/lib/ssh/sftp-server` (`pkg/sshutil/sshutil.go:246`), and `website/content/en/docs/config/mount.md:62-64` now documents that exact path as the Cygwin location. A change to either argument leaves all three subtests green, so the doc and the code can drift apart silently.

Fix: assert the argv before producing output.

```diff

+		if !slices.Equal(os.Args[1:], []string{"-w", "/usr/lib/ssh/sftp-server"}) {
+			os.Exit(2)
+		}
 		if out == fakeCygpathFailure {
```

S4. **A test comment gives a reason the sibling package now disproves** — `pkg/hostagent/mount_windows_test.go:19` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
// TestMountPathAndSftpServer: the mount path and the sftp-server serving it
// come from one toolchain, and the builtin driver gets no server. Only the
// native branch is covered; the Cygwin branch runs cygpath.exe, which a fake
// toolchain directory cannot provide.
```

A fake toolchain directory can provide `cygpath.exe`. This very round added
`cygwinToolchain` (`pkg/sshutil/sshutil_windows_test.go:214`), which copies the
test binary and lets that package's `TestMain` answer as cygpath. The real
constraint is narrower: the fake lives inside `pkg/sshutil`'s test binary, and
`pkg/hostagent` would need a `TestMain` of its own. As written the comment tells
the next reader that a technique sitting in the same commit does not exist.

Fix: state the constraint that actually holds, for example "the Cygwin branch
needs a fake cygpath.exe, which `pkg/sshutil`'s test binary provides through its
own TestMain and this package lacks."

S5. **The fallback message warns about the outcome that seldom happens** — `pkg/hostagent/mount.go:38` [Claude Opus 5]

```go
	if sftpServerBinary == "" {
		logrus.Infof("reverse-sshfs: no sftp-server in the toolchain of %#q; falling back to a generic search, which may pick one that cannot resolve %#q", sshExe.Exe, resolvedLocation)
	} else {
```

Lima defaults `sftpDriver` to `""` (`pkg/limayaml/defaults.go:791-792`), which
routes sshocker through `DetectDriver`. When the generic search finds nothing,
sshocker returns `DriverBuiltin` and serves the mount in-process, and the mount
works. That is the usual outcome on the host class this PR targets, a plain
Windows box carrying the OpenSSH Client feature and no `sftp-server.exe`. The
line then fires at Info on every `limactl start` and warns about a mismatch that
never arises. Under an explicit `sftpDriver: openssh-sftp-server` with nothing
found, sshocker instead fails the mount with `no openssh sftp-server found`,
which the message also omits. The hedge in "may pick" keeps the sentence
accurate, so this is a question of tone and completeness.

Fix: name both outcomes, or drop the line to `Debugf` and let sshocker's own
result speak.

S6. **The native branch drops its lookup error while the Cygwin branch logs one** — `pkg/sshutil/sshutil.go:267` [Claude Opus 5]


The Cygwin branch records its failure at line 257 (`cannot use the sftp-server at

```diff
+		logrus.WithError(err).Debugf("no sftp-server.exe beside ssh at %#q", path)
```

S8. **The self-exec fake has no guard for a caller that forgets the env var** — `pkg/sshutil/sshutil_windows_test.go:33` [Claude Opus 5]

```go
	}
	os.Exit(m.Run())

```

`cygwinToolchain` copies the test binary to `cygpath.exe`, and only
`fakeCygpathOutEnv` tells that copy to answer as cygpath. A future caller that

## Design Observations

### Concerns

1. **`pkg/sshutil` now documents a dependency it does not import** *(in-scope)*
   [Claude Opus 5]. `pkg/sshutil/sshutil.go:224` asserts that sshocker rewrites a
   `/c/...` form to `C:\...`, and line 251 asserts that sshocker resolves the
   explicit binary through `LookPath`. I verified both against v0.3.11:
   `convertMSYS2Path` fires on `len >= 3 && p[0] == '/' && p[2] == '/'`
   (`reversesshfs.go:337`), and `DetectDriver` calls `exec.LookPath` on a
   non-empty explicit binary (`reversesshfs.go:114-119`). But `pkg/sshutil` does
   not import sshocker, so a version bump falsifies either comment without
   breaking the build. `pkg/hostagent/mount.go` constructs the `ReverseSSHFS`
   and is where a `go.mod` bump review would land.

2. **The single-toolchain invariant stops at the transport** *(future)*
   [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.5 Flash]. sshocker's
   `SSHConfig.Binary()` is still a hardcoded `return "ssh"` in v0.3.11
   (`pkg/ssh/ssh.go:22-24`, re-verified this round), so PATH picks the ssh that
   carries the mount while Lima pins the path form and the sftp-server. Closing
   this needs an upstream field. Carried from rounds 1 and 2.

3. **Three call sites still convert through the PATH-global helper** *(future)*
   [Gemini 3.5 Flash]. `cmd/limactl/shell.go:789`, `pkg/copytool/copytool.go:127`,
   and `pkg/limayaml/defaults.go:732` call `fsutil.WindowsSubsystemPath`, which
   runs a bare `cygpath` off PATH. Flash also named `pkg/hostagent/mount.go` and
   `SSHOpts`, which this commit and earlier work already moved off that helper.

### Strengths

- The `TestMain`-as-fake-cygpath technique closes a branch that previously needed
  a real Cygwin install, and CI confirms it runs *(in-scope)* [all four reviewers]
- `exec.LookPath` matches the resolution sshocker itself performs, so Lima cannot
  hand over a path the library will reject, and the comment at
  `pkg/sshutil/sshutil.go:249-252` states that rationale correctly *(in-scope)*
  [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]
- Extracting `mountPathAndSftpServer` gives the pairing one testable entry point,
  and the four subtests cover the driver cross-product rather than the happy path
  alone *(in-scope)* [Claude Opus 5, Gemini 3.1 Pro]
- Caching `sshExe` on `HostAgent` reuses the value `SSHOpts` and
  `writeSSHConfigFile` already received, so the mount path cannot drift from the
  SSH config *(in-scope)* [all four reviewers]

## Review Process Notes

### Skill improvements

- When a test exercises one branch of a two-way selector (a platform detector, a
  toolchain probe, a driver switch), check whether the same fixture would produce
  a different result through the other branch. A fixture that yields the same
  value either way asserts the function's output rather than the selection, so
  the test stays green after the selector itself regresses. The tell is a fixture
  whose inputs all sit in the one location both branches consult.

- When a test replaces an external command with a fake binary or script, check
  whether the fake asserts the arguments it received. A fake that answers purely
  from configuration pins the return value and not the call, so a change to the
  command name, its flags, or its operand leaves the test passing. Weigh this
  higher when the ignored argument is also documented behavior, because the code
  and the documentation can then drift with nothing to catch it.

### Repo context updates

- [repo] UPDATE the "Windows SSH toolchains: native OpenSSH vs. Cygwin-based
  OpenSSH" and "Native vs converted host paths on Windows" entries. Both name
  `pkg/ioutilx.WindowsSubsystemPath`. That package exports only `ReadAtMaximum`;
  the converter lives in `pkg/fsutil` as `WindowsSubsystemPath` and
  `WindowsSubsystemPathWithCygpath`. Both entries also list
  `pkg/hostagent/mount.go` among the call sites still using the PATH-global
  helper, and the hostagent mount path now converts through the selected
  toolchain instead. The PATH-global callers that remain are
  `cmd/limactl/shell.go`, `pkg/copytool/copytool.go`, and
  `pkg/limayaml/defaults.go`. A stale symbol name misdirects every future review
  that greps for it, and one reviewer repeated it verbatim this round.

- [repo] UPDATE the "sshocker performs a hidden sftp-server path conversion on
  Windows" entry. Its opening premise, that `pkg/hostagent/mount.go` leaves
  `ReverseSSHFS.OpensshSftpServerBinary` unset, no longer holds: the hostagent
  sets it from the selected ssh toolchain, and sshocker's own detection runs only
  when that lookup returns empty. Keep the conclusion, since Lima's conversion is
  still not the last word on what the sftp-server receives. Round 2 raised this
  same entry and it remains unprocessed.

- [repo] ADD: under `sftpDriver: builtin` sshocker serves the mount in-process
  through `github.com/pkg/sftp`, so the host path reaches that library's
  `toLocalPath` rather than any external sftp-server. `toLocalPath` turns a
  leading-slash path that is not a drive-letter path into a rooted path on the
  current drive, so a stock-Cygwin form such as `/cygdrive/c/Users/...` becomes
  `\cygdrive\c\Users\...` and silently misses. sshocker's `convertMSYS2Path`
  rescues only the MSYS2 `/c/...` shape, and only when the third byte is a slash.
  When reviewing a change to host mount-path conversion, check what the builtin
  driver receives separately from what an external sftp-server receives; the two
  want different forms and only one of them appears in Lima's own code.

**Concerns**

- **`pkg/sshutil` now documents a dependency it does not import** *(future)*. `sshutil.go:224` asserts "sshocker rewrites a `/c/...` form to `C:\...` before either sees it" and `sshutil.go:252` asserts "Under the default driver sshocker resolves this path with LookPath as well". ### Executive Summary

This PR enables robust reverse-sshfs file sharing on plain Windows hosts by ensuring that both the `sftp-server` binary and the host paths served are resolved from the exact same SSH toolchain selected at startup. This eliminates toolchain mismatches when both native OpenSSH and Cygwin/MSYS2 are installed. The implementation is clean, and the new mock-driven unit tests provide excellent, high-confidence coverage of the Windows path translation and server lookup logic.

### Design Observations

#### Concerns

* **Latent Issue: Toolchain-Aware vs. PATH-global Path Conversion** `(future)`
  `sshutil.PathForSSH` (defined in `pkg/sshutil/sshutil.go:223`) is a toolchain-aware path converter that pins conversion to the selected `ssh` executable's own `cygpath` tool. However, several other components in the codebase—including `SSHOpts`, `pkg/hostagent/mount.go`, `pkg/copytool`, `cmd/limactl/shell.go`, and `pkg/limayaml/defaults.go`—continue to call the PATH-global `ioutilx.WindowsSubsystemPath`. This can decouple path conversion from the selected SSH binary when the `SSH` environment variable is overridden. In a future iteration, these call sites should be refactored to use `PathForSSH` to maintain toolchain consistency.

#### Strengths

* **Elegant Mocking of `cygpath.exe`:** The use of `TestMain` as a self-reexecuting binary to double as a fake `cygpath.exe` (defined in `pkg/sshutil/sshutil_windows_test.go:21`) is an incredibly clever and lightweight way to test Cygwin path resolution and `sftp-server` lookup without requiring a real Cygwin/MSYS2 toolchain during unit tests.
* **Defensive Toolchain Lookups:** Validating the resolved `sftp-server` path using `exec.LookPath` (defined in `pkg/sshutil/sshutil.go:253` and `pkg/sshutil/sshutil.go:268`) on Windows ensures that if the binary doesn't exist, we immediately fall back to sshocker's auto-detection rather than passing an unresolvable path that would fail the mount.

### Acknowledged Limitations

The following limitations have been acknowledged by the author or established in prior rounds and are confirmed as resolved or out of scope for this PR:

* **UNC/Drive-Relative Path Rejection** (`pkg/sshutil/sshutil.go`): The native branch of `PathForSSH` does not reject UNC or drive-relative paths because UNC mounts succeed under the builtin driver via `filepath.ToSlash` and `toLocalPath` (from `pkg/sftp`). Rejection would remove existing, valid behavior.
* **Plain-Windows End-to-End Validation**: E2E testing with no Cygwin toolchain present is deferred to #5342, as it requires specialized plain-Windows CI runner setup.
* **Guest-side Drive-Letter Stats**: Whether Win32 OpenSSH's sftp-server correctly stats drive-letter paths can only be verified on a plain Windows runner, which is deferred to #5342.
* **Explicit LocalPath Verification**: Restructuring production code to assert that the resolved path reaches `LocalPath` was declined, as it is already validated end-to-end in integration tests.
* **`sftpDriver` Constraints Validation**: The absence of validation for `sftpDriver` in `pkg/limayaml/validate.go` is pre-existing; invalid driver values fail loudly at mount time.
* **Windows Environment Variable Workaround**: `TestMain` uses `fakeCygpathFailure = "exit-non-zero"` because Windows cannot distinguish an empty env var from an unset one. Subsequent tests introduced in Round 3 perfectly align with this workaround.
