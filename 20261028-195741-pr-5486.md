## Executive Summary

The PR enables the Linux `shared`, `host` and `bridged` networks, and its new commit replaces the `pkill -F` stop grant with a `stop` subcommand that checks the target's executable. That closes the root kill. But when a helper killed with SIGKILL leaves its PID file and another process gets the PID, `stop` refuses and keeps the root-owned file, so every `limactl start`, `stop` and `delete` fails until that PID frees. The new experimental warning also fires for `user-v2`.

## Important Issues

I1. **A stale PID file whose PID was reused makes every lifecycle command fail, and no grant can remove it** — `cmd/lima-privileged-net/network_linux.go:166-169` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	exe, err := os.Readlink(fmt.Sprintf("/proc/%d/exe", pid))
	if err != nil || strings.TrimSuffix(exe, " (deleted)") != self {
		return fmt.Errorf("PID file %#q is stale: process %d is not running %#q", pidFile, pid, self)
	}
```

A `start` killed with SIGKILL (the OOM killer, `cgroup.kill`) leaves its PID file behind. Once another process gets that PID, `store.ReadPIDFile` reports the network running, since it counts EPERM as alive (`pkg/store/instance.go:279-283`), and `stopNetwork` calls `stop`, which refuses and keeps the file. `Reconcile` stops every unused network and returns the first error (`pkg/networks/reconcile/reconcile.go:69-81`), which `limactl start` returns (`cmd/limactl/start.go:641-644`). So no instance starts, stops or deletes until the PID frees, and the user cannot remove the root-owned file. `pkill -F` cleared this state by killing the process. The probe's last line, for a free PID, is the control.

## Suggestions

S1. **`stop` signals any process that runs the helper, not only the `start` of the network it names** — `cmd/lima-privileged-net/network_linux.go:166` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	exe, err := os.Readlink(fmt.Sprintf("/proc/%d/exe", pid))
```

If the stale `shared` PID now belongs to the `host` network's `start`, or to a `tap` call, `stop --pidfile=/run/lima/shared_lima-privileged-net.pid` terminates it. The caller gains nothing, because the group already holds every network's `stop` grant, and the PID has to be reused by a helper process. I1's patch leaves this unchanged, since it consults the lock only after the executable check fails.

Fix: also require `/proc/<pid>/cmdline` to name `start` and `--pidfile=<pidFile>`.

S2. **Go ignores SIGXFSZ, so the comment's reason for catching it is wrong** — `cmd/lima-privileged-net/network_linux.go:109-114` [Claude Opus 5.5]

```go
	// Every catchable signal the unprivileged caller can provoke must end in an
	// orderly teardown too: SIGHUP and SIGQUIT come from the caller's terminal,
	// SIGPIPE from logging to a stderr whose read end the caller has closed, and
	// SIGXFSZ from a file size limit the caller set.
	sig := make(chan os.Signal, 1)
	signal.Notify(sig, syscall.SIGINT, syscall.SIGTERM, syscall.SIGHUP, syscall.SIGQUIT, syscall.SIGPIPE, syscall.SIGXFSZ)
```

In a Linux instance, a Go program that sends itself SIGXFSZ, SIGXCPU, SIGUSR1, SIGUSR2 or SIGALRM without `signal.Notify` keeps running, while SIGHUP and SIGQUIT end it (exit 129 and 2). A file-size limit makes the write fail with EFBIG, which `writePIDFile` already handles. Catching SIGXFSZ only adds a teardown when a log write passes the caller's `ulimit -f`.

Fix: drop SIGXFSZ and its clause.

S1. **SIGXFSZ does not kill a Go process, so this comment's premise is false for it** — `cmd/lima-privileged-net/network_linux.go:109-114` (suggestion, regression)

```go
	// SIGPIPE from logging to a stderr whose read end the caller has closed, and
	// SIGXFSZ from a file size limit the caller set.
	sig := make(chan os.Signal, 1)
	signal.Notify(sig, syscall.SIGINT, syscall.SIGTERM, syscall.SIGHUP, syscall.SIGQUIT, syscall.SIGPIPE, syscall.SIGXFSZ)
```

In Go's runtime signal table SIGXFSZ is plain `_SigNotify` (no `_SigKill`, no `_SigThrow`; `runtime/sigtab_linux_generic.go:35` in go1.26.6). Without `Notify`, the runtime ignores the signal, the write returns EFBIG, and the helper keeps running. Adding it to `Notify` means a log write past the user's `ulimit -f` now tears down the network. SIGHUP, SIGQUIT and SIGPIPE do need the handler. A too-small RLIMIT_FSIZE already makes `writePIDFile` fail cleanly.

Fix: drop SIGXFSZ and its clause from the comment.

S2. **`stop` signals any process running the helper, not the `start` of the network it names** — `cmd/lima-privileged-net/network_linux.go:165-170` (suggestion, gap)

```go
	// The suffix is there when the helper was reinstalled while the network was up.
	exe, err := os.Readlink(fmt.Sprintf("/proc/%d/exe", pid))
```

Then `stop --pidfile=…/shared…` terminates that process, and the `host` network goes down under its running instances. The caller gains no privilege, since the group holds every network's stop grant, and the PID has to be reused by exactly a helper process.

Fix: also require `/proc/<pid>/cmdline` to start with `start` and contain `--pidfile=<pidFile>`. Read it under the same pidfd guard.

Under the `pkill -F` grant, which v2.3.0-beta.1 already renders on Linux (`git tag --contains f3d2492a`, plus beta.1's `StopCmd`), a group member could SIGKILL their own `start` and later let `pkill` signal whatever took the PID, as root. What the caller can still reach is S2 (DoS within the job, no privilege gain), and I found no state that leaves a helper running with no grant able to stop it, apart from the reinstall case below. The cost is I1.
- **(future) limactl decides "running" from a PID it cannot verify.** In I1's state, `startNetwork` (`reconcile.go:229-235`) also skips `start` and attaches taps to the leftover bridge, which has no dnsmasq, so the guest gets no DHCP lease. If a reinstall moves the prefix, the exe check fails for good. `linux.md:66-68` already says to reinstall the file. Consider adding "stop all instances before reinstalling Lima".
- **(future)** `os.FindProcess` silently falls back to a plain PID when pidfd is unavailable (pidfd needs Linux ≥5.4, per `checkPidfd`), so the comment at lines 155-156 holds only on such kernels. The remaining window is microseconds, which is impractical to exploit.

**Strengths**

- `writePIDFile` writes through a rename. That also ends a race in which `pidFileWritten` read an empty file mid-write and `waitForDaemon` killed the daemon.

###### Design Observations

**Concerns**

- **Network ownership needs one authoritative lifecycle protocol — in-scope.** PID existence, executable identity, flock ownership, and tap carrier currently answer different questions. A privileged status/recovery operation sharing the start lock would address I1 and S1 without treating arbitrary live PIDs as healthy networks.

- **Caller-controlled logging can still block privileged teardown — inherited, future.** The synchronous log writes before the signal receive and before cleanup remain at `cmd/lima-privileged-net/network_linux.go:130-135`. A harmless Go primitive probe demonstrated that a full stderr pipe keeps a registered SIGTERM pending until the write unblocks. The old code had this problem too; the new stop command does not resolve it. Detach privileged lifecycle logging from caller-controlled blocking streams, or provide bounded shutdown with verified-target escalation.

- **Cross-process reconciliation remains unserialized — in-scope.** A starting VM is counted locally before QEMU opens its tap (`reconcile.go:52-64,255-261`), while another process uses carrier as its sole external-use guard (`reconcile.go:293-295,479-483`). A shared reservation spanning network setup through QEMU attachment would avoid a concurrent last stop removing the starting VM’s network. This race was reasoned, not executed.

- **The macOS cross-`LIMA_HOME` limitation remains inherited.** The external-use guard is Linux-helper-specific (`reconcile.go:479`). Socket_vmnet still lacks equivalent shared ownership accounting.

**Strengths**

- The QEMU and reconcile paths derive the tap from the same UID, instance-directory ID, and network name.
- Keeping the lock inode persistent avoids splitting lock ownership across replacement files.
- Atomic PID publication and removing the PID only after cleanup improve distinct failure windows.
- The stop command now goes through the same digest-pinning renderer as the other helper commands.

**Crash-state audit — reasoned from the reviewed code**

| State | Result |
|---|---|
| PID file absent, lock free | Startup can acquire the lock and publish a PID. |
| Startup owns lock, PID not yet published | A competing start is rejected. Stop has no published target yet. |
| Write fails before rename | Prior PID file remains unchanged; temporary file is removed. Locally reproduced. |
| Crash leaves a temporary file | A later lock owner overwrites that temporary file. |
| Helper dies; PID is free | `ReadPIDFile` reports no running process; startup can replace the record. Unprivileged removal of the root-owned file need not succeed. |
| PID reused by caller-owned non-helper | Startup treats it as running; stop rejects it and retains the record: I1. |
| PID reused by root/another user | Permission denial from signal 0 is explicitly treated as live; same I1 outcome. |
| PID reused by another helper | Executable comparison can pass: S1. |
| Malformed PID file | Initial reconcile reads discard the error; startup polling can subsequently report it. Atomic publication prevents new partial-number records, but is not a general corruption-recovery path. |
| Normal teardown | PID is removed after dnsmasq and network cleanup; the acknowledged five-second caller limit remains. |

###### Executive Summary

The PR implements managed `shared`, `host`, and `bridged` networks on Linux using a privileged helper (`lima-privileged-net`). ###### Critical Issues

C1. **`stop` check allows cross-tenant kill and permanently wedges on other reuses** — `cmd/lima-privileged-net/network_linux.go:167-168`
(critical, regression)

The new `stop` command verifies the PID by checking if `/proc/%d/exe` matches the helper. If a stale PID is reused by another user's `lima-privileged-net` (e.g., from a different `LIMA_HOME`), this check passes and kills the other user's network daemon (a cross-tenant DoS). If the PID is reused by an unrelated process (e.g., `bash`), the check fails and `stop` returns an error, which causes `stopNetwork` to abort `limactl stop`. Because `limactl start` thinks the daemon is running, the network is permanently wedged until an administrator manually removes the root-owned PID file.

Fix: Have `stop` check `/proc/%d/cmdline` for its own `--pidfile=` argument to definitively identify the target daemon. If the check fails, log a warning and remove the stale PID file instead of returning an error, so `stopNetwork` succeeds and the next `start` can recover.

```go
	cmdline, err := os.ReadFile(fmt.Sprintf("/proc/%d/cmdline", pid))
	if err != nil || !bytes.Contains(cmdline, []byte("--pidfile="+pidFile+"\x00")) {
		logrus.Warnf("PID file %#q is stale", pidFile)
		_ = os.Remove(pidFile)
		return nil
	}
```

3. iptables -I FORWARD -o br -j REJECT       -> Chain: [REJECT(out:br), REJECT(in:br), ACCEPT(in:br,out:br)]

###### Design Observations

###### Concerns

- **PID file verification decoupled from lock file** `(in-scope)`: In commit `0b8887b0`, `lima-privileged-net start` holds an exclusive non-blocking `flock` on `<pidfile>.lock`, but `stop` does not consult this lock. Instead, `stop` inspects only `/proc/<pid>/exe`. Coupling `stop` to the lock file would make daemon status detection 100% reliable: if the lock can be acquired, the daemon is dead, and the stale PID file can be cleanly purged without signaling foreign processes or failing `stopNetwork`.
- **Unserialized Reconcile execution** `(future)`: Instances starting concurrently do not hold carrier on their tap devices until QEMU opens the device. A concurrent `limactl stop` on another instance can inspect `bridgeInUse`, observe 0 carrier, and initiate network teardown while a starting instance is mid-flight.

###### Strengths

- **Mitigation of GHSA-78jv-8g3c-frr3**: Replacing bare `pkill -F` with a digest-pinned `lima-privileged-net stop` command and checking `/proc/<pid>/exe` prevents local privilege escalation to kill arbitrary system processes.
- **Exclusive daemon locking**: Employing kernel `flock` on `<pidfile>.lock` prevents accidental duplicate daemon instances from running concurrently over the same bridge.
- **Digest pinning in sudoers**: Generating `sha256:` Digest_Specs in `/etc/sudoers.d/lima` prevents hijacked or replaced helper binaries from executing with root privileges.
