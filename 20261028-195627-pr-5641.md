## Design Observations

### Concerns

- **(in-scope) Rejecting a control character is still an open question for the maintainers.** A raw ESC in `PATH` rendered at the merge-base into a plist that `plutil -lint` accepts and reads back intact. With this PR the render fails and names U+001B, so `limactl autostart enable` fails. Claude and Codex both ran the two sides on macOS this round. XML 1.0 forbids the character even as a reference, and #5645 asks for an error, so I'd keep the rejection, but nobody has ruled on it in the thread. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]
- **(future) The systemd unit still writes `LimaHome` and `Binary` raw** into `Environment=` and `ExecStart=` (`pkg/autostart/systemd/lima-vm@INSTANCE.service:6-7`), where a space splits the value and `%` starts a specifier. Nobody has tried the unit with such a value. Round 1 raised this too. [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

### Strengths

- The rune ranges in `xml` match `encoding/xml`'s unexported `isInCharacterRange` (read in the Go 1.27.3 source), so the function rejects exactly the runes that `EscapeText` would rewrite to U+FFFD. [Claude Opus 5.5]
- Both installers render the plist before they write anything (`pkg/autostart/managers.go:82` and `cmd/limactl/autostart_darwin.go:123`), so a rejected value leaves an existing registration alone. [Codex GPT 6 Astra]
- `plutil -lint` accepts both rendered plists. `plutil -convert json` reads every escaped value back unchanged, including the `&#x9;` and `&#xD;` references (Claude), and so does a `pkg/plist` decode (Codex). [Claude Opus 5.5, Codex GPT 6 Astra]

###### Concerns

- **Rejection of XML 1.0 control characters vs. parser tolerance** `(in-scope)`: In `pkg/textutil/textutil.go:124-133`, control characters outside `\t`, `\n`, and `\r` (such as `\x1b` in a path) return an error during template rendering. Apple's CoreFoundation plist parser accepts raw control characters in string tags without validation errors. However, XML 1.0 forbids these characters even via numeric character references, and issue #5645 specifically requested failing loudly rather than emitting invalid XML or silently rewriting bytes. The explicit error `value contains character U+... not allowed in XML 1.0` makes troubleshooting immediate.
- **Systemd autostart unit escaping** `(future)`: While launchd plists are now protected from XML metacharacter corruption, `pkg/autostart/systemd/lima-vm@INSTANCE.service` interpolates `{{.LimaHome}}` and `{{.Binary}}` raw into `Environment=` and `ExecStart=`. In systemd service units, unquoted spaces split arguments and `%` introduces specifiers. A future PR should consider systemd-specific escaping for autostart service definitions.

###### Strengths

- **Strict UTF-8 pre-validation prevents path corruption**: Checking `!utf8.ValidString(s)` before iterating over runes prevents Go's `for _, r := range s` from silently decoding invalid UTF-8 sequences as `utf8.RuneError` (`U+FFFD`), which would otherwise pass the XML 1.0 rune range check and silently mutate filesystem paths.
- **Type-enforced fail-fast on missing keys**: Declaring the `xml` template function with a concrete `func(string) (string, error)` signature causes Go's `text/template` engine to reject untyped nil/missing map values with an execution error (`invalid value; expected string`) rather than substituting `<no value>`.
