## Suggestions

S1. **The wrapped listener removes the socket path on every `Close` and reports the staging path from `Addr`** — `pkg/portfwd/listener.go:330` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash] (round 2 S6 unaddressed)

```go
func (l *ownerOnlyUnixListener) Close() error {
	err := l.UnixListener.Close()
	if rmErr := osutil.RemoveStaleSocket(l.path); rmErr != nil {
		logrus.WithError(rmErr).Debugf("failed to remove unix socket %s", l.path)
	}
	return err
}
```

`Close` removes whatever socket is at `l.path`, so a second `Close` after a new listener has bound that path deletes the new socket. `Addr` still reports the staging path, which no longer exists. The in-place fallback returns a plain listener, so the two branches of `listenUnixOwnerOnly` now disagree on `Addr`. No caller closes twice or reads `Addr` today.

Fix: guard the removal with `sync.Once`, and return `l.path` from `Addr`.

## Design Observations

### Concerns

- **Socket routing follows the TCP forwarder choice** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]. With `LIMA_SSH_PORT_FORWARDER=true`, every `guestSocket` rule stays on the ControlMaster, and Rancher Desktop and Colima set that variable by default. No maintainer has ruled on this in the PR, so it stays an open question.
- **A client that is still sending when the guest service half-closes can get a reset instead of EOF** (future) [Claude Opus 5.5, Codex GPT 6 Astra]. This is I1's mechanism outside the test. On Linux, a client that reads to EOF gets the whole response and then an error, where a direct connection sees EOF. Windows reports the reset too, but nobody has checked whether it delivers the whole response first. A tunnel that can pass a half-close through would fix it. Draining the client after a failed send would avoid the reset too, at the cost of a goroutine that waits on the client.
- **On QEMU, docker.sock still drops with the ControlMaster, but comes back** (in-scope) [Codex GPT 6 Astra, Gemini 3.1 Pro]. The gRPC tunnel there runs over the SSH-forwarded `ga.sock`, as round 2 noted.

### Strengths

- **The staging name fits for any basename of 4 bytes or more** (in-scope) [Claude Opus 5.5, Gemini 3.1 Pro]. At the length limit only a basename of 1 to 3 bytes binds in place, which answers round 2's review question about a shorter staging name.
- **Each dial looks up the current client** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]. The socket listeners keep working across guest agent reconnects.
- **The forwarder choice is testable without a VM** (in-scope) [Claude Opus 5.5]. `forwardGuestSockets` and `cancelGuestSocketForwards` take it as a parameter.
- **A failed copy to the host still frees an idle connection** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra], while a failed send now half-closes as round 2 asked.

## Acknowledged Limitations

- **The in-place fallback exposes the socket until its chmod** (`pkg/portfwd/listener.go:274-281`). Between bind and chmod the socket has the umask's mode, and a connection made in that gap stays open after the chmod. Only a `hostSocket` basename of 1 to 3 bytes at the length limit takes this path. At 103 bytes on macOS, `s`, `ds` and `abc` bind in place, and `abcd` gets a staging directory. Another user can connect in the gap only when the umask grants group or other write access and the parent directory lets that user through. Round 2 proposed this fallback with that trade-off, and the threat model rates a hardening gap without a demonstrated exploit as low. Do not re-suggest closing it unless such paths become realistic; closing it needs a private staging directory on a shorter path on the same filesystem.
- **A guest half-close ends the whole tunnel** (`pkg/portfwdserver/server.go:126-133`), as in round 2. I1 and the second design concern are where it shows this round.
- **A connection whose guest end never answers and never closes keeps its tunnel and both copy goroutines**, as in round 2. `tcpproxy` behaves the same on the TCP path, so do not re-suggest `tcpproxy` as a fix for it. A failed host read half-closes the tunnel rather than aborting, which round 2 also accepted.
- Round 1's suggestions, unaddressed and undeclined through rounds 1, 2 and 3:
  - `forwardUnix` repeats `forwardTCP`'s accept loop, and no test covers the pseudoloopback `continue`.
  - `Remove` still lists `"tcp6"` (`pkg/portfwd/listener.go:82`).
  - Two tests log an error on every run, and the dedup tests hang or pass when dedup breaks.
  - A Unix listen failure is logged twice, and the gRPC socket forward is never logged at Info.
  - The website still describes the forwarder choice only in terms of ports.
