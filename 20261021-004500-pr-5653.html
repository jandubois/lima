When the guest service closes, GRPCServerRW.CloseWrite ends the tunnel (pkg/portfwdserver/server.go:130), while part of the response can still be waiting in the host's gRPC receive buffer. A host write after that point makes stream.Send return io.EOF, and abort() closes the host connection and cancels the stream before the other goroutine delivers the rest. An HTTP server that answers before reading the whole upload can trigger this, and so can docker exec -i when the process exits while stdin is still streaming. Round 1 half-closed here and delivered every byte, and the TCP path's tcpproxy also only calls CloseSend in this direction. With the abort removed, every case gets the whole response in 3 of 3 runs.

pkg/portfwdserver/server.go

// CloseWrite is called once the guest service closes its side. The tunnel
// protocol cannot signal a half-close towards the host, so this ends the whole
// tunnel; the host then sees the stream end and shuts down the write side of
// its own connection.
func (g *GRPCServerRW) CloseWrite() error {
	logrus.Debugf("closing write GRPCServerRW for id: %s", g.id)
	g.closeOnce.Do(func() { close(g.closeCh) })
	return nil
}

Design Observations ¶

Concerns ¶

  • Socket routing follows the TCP forwarder choice (in-scope), raised in round 1. With LIMA_SSH_PORT_FORWARDER=true every guestSocket stays on the ControlMaster, and colima sets that variable unless its portForwarder is grpc, so colima users keep docker.sock on the master by default. The maintainers should decide whether the socket transport follows the TCP forwarder.
  • On QEMU, docker.sock still drops with the master, but now comes back (in-scope) Claude Opus 5.5. On macOS and Linux hosts, QEMU leaves virtioPort empty (pkg/driver/qemu/qemu_driver.go:70-74), so the gRPC tunnel runs over the SSH-forwarded ga.sock. A master death still breaks docker.sock there, but the socket returns once the guest agent reconnect loop re-forwards ga.sock, which an SSH-forwarded socket never did. The PR description's "decouples non-reverse Unix socket forwarding from the SSH ControlMaster" holds on vz, not on QEMU.

Strengths ¶

  • Each dial looks up the current client (in-scope) Claude Opus 5.5 Codex GPT 6 Astra. DialContextToGRPCTunnel(a.getClient) keeps the socket listeners working across guest agent reconnects.
  • The staging directory gives 0600 without touching the umask (in-scope) Claude Opus 5.5 Gemini 3.1 Pro. No other user can reach the socket between bind and chmod, and prepareUnixSocket refuses to replace a non-socket, so the rename cannot clobber a regular file. I2's fallback gives up the first property only for paths near the length limit.
  • A failed copy to the host now frees an idle connection (in-scope) Claude Opus 5.5. This is the case Copilot described, and I1's patch keeps it.

Acknowledged Limitations ¶

  • GRPCServerRW.CloseWrite cannot pass a guest half-close to the host, so it ends the whole tunnel (pkg/portfwdserver/server.go:126-134). Unix forwards inherit this from the TCP path, and it is what ends the stream in I1.
  • A connection whose guest end never answers and never closes keeps its tunnel and both copy goroutines until it does. tcpproxy.DialProxy.HandleConn waits for both directions the same way, so the TCP path behaves identically. Do not re-suggest tcpproxy as a fix for it. With I1's patch, a failed host read half-closes as at round 1, so this entry describes the patched code too.
