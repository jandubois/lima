## Design Observations

### Concerns

- **The Makefile's `$(shell find …)` is empty on any Windows host without a Unix `find` ahead of System32** *(future)* [Claude Opus 5]. S2 measured CI leaving that state by accident. A developer running `make` on a plain Windows box still gets empty prerequisite lists for `_output/bin/limactl.exe` and every guest agent, so incremental rebuilds skip source changes. Pre-existing and outside this PR's scope, but this PR is what made the divergence visible.

- **`windows_plain_templates` reimplements `make`'s TEMPLATES target in PowerShell** *(future)* [Claude Opus 5]. The two now have to stay in sync by hand. The action's `Copy-Item -Recurse` is a superset of the Makefile rules today, and a future rule that filters, renames, or generates would not reach it.

- **The verified state is not quite the state the smoke test runs under** *(in-scope)* [carried from round 1]. In `windows-plain-qemu` the verify step still precedes `Add QEMU to PATH`. The I2 fix removed the tautology, so Layer 2 now checks the inherited PATH, but a `$GITHUB_PATH` entry registered after the verify step remains uninspected. Nothing does that today.

### Strengths

- **Five layers asserting state rather than steps** *(in-scope)* [Claude Opus 5, Gemini 3.5 Flash]. The action checks what the test depends on, not what produced it, so a runner-image change in either direction fails loudly. Layer 5 earns its place: job `90166439597` shows `sftp-server.exe` genuinely consumed through sshocker's own `exec.LookPath("sftp-server")`.

- **Reading symlink targets from git's object store** *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol]. This sidesteps the whole `core.symlinks` and Developer Mode matrix. Job `90166439597` printed 24 `Resolving symlink:` lines, matching the 24 mode-120000 entries in the tree.

- **Two real toolchains under test** *(in-scope)* [Claude Opus 5]. Adding `openssh` to the pacman list keeps the MSYS2 jobs on a Cygwin-family ssh while the plain jobs use the native one, and it does so without reviving the env var.

## Review Process Notes

### Skill improvements

- Before accepting a documentation change that files an entry under a version heading, check whether that version has shipped. Read the tag, not the heading's formatting: an unlinked or trailing heading looks identical whether it is the next release or the last one. Compare the section's content against the tagged file, and confirm the default branch has not diverged from the tag. A heading that was open when a prior round asked for the entry can close before the entry lands.

- When a finding quotes a log line you cannot find, check the encoding before dropping it. A tool that writes UTF-16 leaves text no plain-text grep will match, and CI log viewers render it as if it were ASCII. Search for a distinctive fragment with the interleaved-NUL form, or decode the region, before concluding the quote was reconstructed.

- A prior round's decline reason is a claim about the world, not a settled fact, and the cheapest way to re-derive it is usually to find the same condition somewhere the change is absent. Prefer a comparison that isolates the single variable in question over one that changes several at once, and say which comparison you ran.

### Repo context updates

- [repo] `website/content/en/docs/releases/breaking.md` uses one `##` heading per release, and entries accumulate under the current heading until that version is tagged. The heading for a shipped release is not closed or marked in any way, so a new entry appended to the bottom section can silently attach to a release that already went out. Check the newest tag against the newest heading before judging where an entry belongs.

- [repo] `Makefile:223` computes prerequisite lists with `$(shell find …)`. On a Windows host without a Unix `find` ahead of `C:\Windows\System32`, this resolves `FIND.EXE`, which prints `File not found - <pattern>` and returns nothing, so `FILES_IN_PKG` and `dependencies_for_cmd` come out empty and incremental rebuilds skip source changes. A change to what is on PATH during a Windows `make` step therefore changes what the Makefile rebuilds.

- [repo] `pkg/sshutil.NewSSHExe` falls back to `exec.LookPath("ssh")` when `pickCompleteSSHOnWindows` returns `""`, and `%SystemRoot%\System32\OpenSSH` stays on PATH under every Windows CI job. A missing `scp.exe` or `ssh-keygen.exe` therefore produces a working `ssh` and a later failure elsewhere, never the `exec: "ssh": executable file not found` that a missing `ssh.exe` produces.

- [repo] The `windows-plain-*` jobs build limactl with a bare `go build`, so `pkg/version.Version` is empty and limactl logs ``treating lima version `<unknown>` … as very latest release``. Any behaviour keyed on the recorded version takes its newest-release arm on those jobs and the compiled-in version on every other Windows job.

## Design Observations

### Concerns

- **The Makefile's `$(shell find …)` is silently empty on any Windows host without a Unix `find` ahead of `C:\Windows\System32`** *(future)*. S2 shows CI was in that state until this PR incidentally moved out of it. A developer running `make` on a plain Windows box still gets empty prerequisite lists for `_output/bin/limactl.exe` (`Makefile:281`) and every guest agent (`Makefile:431`), so incremental rebuilds skip source changes. This is pre-existing and out of scope here, but this PR is the first thing to make the divergence visible. A `find` that goes through Go (`go list -deps`) or a `FILES_IN_PKG` computed with `$(wildcard …)` would remove the shell dependency entirely.
- **`windows_plain_templates` reimplements `make`'s `TEMPLATES`/`TEMPLATE_IMAGES`/`TEMPLATE_DEFAULTS` targets in PowerShell** *(future)*. The two now have to stay in sync by hand; the action's `Copy-Item -Recurse` at line 33 is a superset of `Makefile:442-450` today, but a future `make` rule (a filter, a rename, a generated file) would not reach it. Worth a comment in the Makefile pointing at the action, or a follow-up that has the action shell out to `go run` a tiny installer both paths share.

### Strengths

- The five-layer verification in `windows_plain_host` is the right shape for this job: it asserts the *state* the test depends on rather than the *steps* that produce it, so a runner-image change in either direction fails loudly rather than silently degrading coverage. Layer 5 in particular is load-bearing — I confirmed `sftp-server.exe` is really consumed (job `90166439597`).
- Reading symlink targets from git's object store instead of the working tree (`windows_plain_templates:39-51`) sidesteps the whole `core.symlinks` / Developer Mode matrix, and the escape guard at line 74 is a genuine containment check rather than a comment.
- Keeping the MSYS2 jobs on a Cygwin-family ssh while the plain jobs use the native one gives two real toolchains under test instead of one, and the `openssh` package achieves it without reintroducing the env var.

#### Suggestions

##### S1. Registry expansion loss on persistent scopes — `.github/actions/windows_plain_host/action.yml:79-87`

```yaml
      foreach ($scope in @('Machine','User')) {
        $orig = [Environment]::GetEnvironmentVariable('Path', $scope)
        if (-not $orig) { continue }
        $cleaned = ($orig -split ';' | Where-Object { $_ -and ($_ -notmatch $forbidden) }) -join ';'
        if ($cleaned -ne $orig) {
          Write-Host "Scrubbing $scope PATH"
          [Environment]::SetEnvironmentVariable('Path', $cleaned, $scope)
        }
      }
```

Calling `[Environment]::GetEnvironmentVariable('Path', $scope)` retrieves the registry PATH variable with all embedded environment variables (e.g., `%SystemRoot%` or `%USERPROFILE%`) fully expanded. Calling `[Environment]::SetEnvironmentVariable('Path', $cleaned, $scope)` then writes this expanded string back to the registry, converting the registry entry type from `REG_EXPAND_SZ` to `REG_SZ`. On a persistent, self-hosted runner, this permanently bakes in the expanded paths and breaks dynamic registry PATH behavior for future users or system changes.

Fix: Read and write registry keys directly to preserve `REG_EXPAND_SZ` types and unexpanded variables, or document that the action is strictly intended for disposable virtual environments.

```diff

-        $orig = [Environment]::GetEnvironmentVariable('Path', $scope)
-        if (-not $orig) { continue }
-        $cleaned = ($orig -split ';' | Where-Object { $_ -and ($_ -notmatch $forbidden) }) -join ';'
-        if ($cleaned -ne $orig) {
-          Write-Host "Scrubbing $scope PATH"
-          [Environment]::SetEnvironmentVariable('Path', $cleaned, $scope)
-        }
-      }
```

### Design Observations

#### Concerns

- **Destructive uninstalls on self-hosted runners `(in-scope)`**: The `windows_plain_host` action is designed to be highly aggressive, forcefully terminating processes, running Git's silent uninstaller, and deleting directories (`C:\msys64`, `C:\Program Files\Git`). While ideal for fresh, disposable GitHub-hosted runners, this behavior is extremely destructive for any self-hosted runner sharing the workspace. It would be beneficial to add an explicit check gating execution on a disposable/CI environment flag or adding a disclaimer.

#### Strengths

- **Multi-layered Verification Layer**: The 5-layer verification (filesystem, process/machine/user PATHs, smoking-gun binaries, registry uninstall keys, and OpenSSH presence) is an exceptional, high-signal safeguard that ensures the runner stays in the expected vanilla Windows state.
- **Pure PowerShell Build & Symlink Replication**: Successfully replicating `make` targets and git symlink resolution using pure PowerShell and git commands eliminates MSYS2/make toolchain dependencies cleanly during plain Windows builds.
- **Accurate Inno Setup Wait Loops**: Tracking both the uninstaller parent `unins000` and its temp child copies `_iu*.tmp` ensures directories are only deleted when the uninstaller is completely finished.
