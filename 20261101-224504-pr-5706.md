## Executive Summary

The PR converts both paths to MSYS2 form before calling the ISO generator, which fixes #5704 on an MSYS2 host. But it takes `cygpath` from PATH before it picks a generator, so the path form doesn't follow the tool that reads it. A Windows host without `cygpath` now fails even with a generator installed, and a native generator can receive `/c/...`. The attached patch converts per candidate through `sshutil.PathForTool`.

## Design Observations

### Concerns

- **Lima would have three ways to bind a Windows path conversion** (in-scope) [Claude Opus 5.5, Gemini 3.1 Pro, Gemini 3.5 Flash]: `PathForTool` follows the tool, `pathForRsync` uses the sibling `cygpath` of a tool that is always Cygwin-based, and this change uses whichever `cygpath` PATH finds. Only the third can disagree with the program that reads the path, and I1's patch removes it.
- **`pkg/iso9660util` would import `pkg/sshutil`** (future) [Claude Opus 5.5]: the package name looks odd beside an ISO helper, but `PathForTool`'s doc comment names this use, and `go list -deps ./pkg/sshutil` doesn't list `iso9660util`, so there's no cycle.

### Strengths

- **The conversion stays inside `writeJolietCommand`** (in-scope) [Claude Opus 5.5]: its parameters are by value, so `writeJoliet` keeps the native paths for `os.RemoveAll` and the file writes.
- **The new test runs a real generator** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]: `TestWriteJolietWindows` drives `Write` and reads the image back, which an argv comparison couldn't show. I1's patch keeps it.
- **CI fails when `xorrisofs.exe` is missing** (in-scope) [Claude Opus 5.5, Gemini 3.5 Flash]: the job stops in `windows_msys2_prep`, so the new test can't turn into a silent skip there.

###### Design Observations

###### Concerns

- **Toolchain-coupled path conversion** `(in-scope)`: Translating paths globally using `cygpath` from `PATH` before finding the ISO generator creates tight coupling to PATH ordering and breaks native Windows generators. Moving candidate resolution (`cmdAbs`) ahead of path conversion, inspecting `cmdAbs` for a companion `cygpath.exe` (after evaluating symlinks), and delegating path conversion only when a Cygwin/MSYS2 toolchain is detected cleanly separates native and subsystem toolchains. This follows the architectural precedent established in `pkg/copytool` and `pkg/sshutil`.

###### Strengths

- Leveraging `fsutil.WindowsSubsystemPathWithCygpath` reuses Lima's central path translation helper rather than introducing ad-hoc path manipulation in `pkg/iso9660util`.
- Adding `xorriso` and companion checks to `windows_msys2_prep` ensures Windows CI actively exercises Joliet ISO generation.

###### Testing Assessment

- **I1, I2** (Required under check 3: How would a user see it?): A Windows host with native `mkisofs.exe` or `genisoimage.exe` and no `cygpath` installed sees `limactl start` fail with `exec: "cygpath": executable file not found in %PATH%`. Existing unit testing in `TestWriteJolietWindows` runs only under MSYS2 and does not catch this regression. A test covering tool resolution without `cygpath` on PATH is needed.
- **S1** (Optional under check 2: Does the code run only for us?): Broadening `TestWriteJolietWindows` to accept any available candidate generator prevents skipping on test environments equipped with `mkisofs` or `genisoimage` instead of `xorrisofs`.

###### Documentation Assessment

`writeJolietCommand` lacks an explanatory comment regarding why Windows path translation is performed for Cygwin/MSYS2 tools while native tools retain native drive-letter paths. A brief in-code comment should be added explaining the toolchain distinction.
