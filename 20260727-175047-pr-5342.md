## Executive Summary

Seven composite actions replace the inline Windows setup, and two plain-Windows jobs add native-toolchain coverage. The extraction is careful and the four-layer host verification is well built. But dropping `_LIMA_WINDOWS_EXTRA_PATH` leaves no Cygwin ssh on `limactl`'s PATH. Both pre-existing Windows jobs, green on master, now fail with native `scp.exe`, and the copy test dies before it reaches the rsync backend this PR set out to enable.

All four reviewers ran against `fac4aebb`. Two CI runs settled every disputed finding, the PR's own `30243838085` and master's `30236908109`. In both plain jobs `windows_plain_build` succeeded, so the "Go is dropped from PATH" claim that two reviewers raised as critical is false. Both MSYS2 jobs failed at `limactl copy` with `C:\Windows\System32\OpenSSH\scp.exe`, which confirms the regression three reviewers reached independently. The two plain-Windows jobs fail exactly as the PR description predicts.

## Critical Issues

C1. **Dropping `_LIMA_WINDOWS_EXTRA_PATH` switches the MSYS2 jobs to native OpenSSH** — `.github/workflows/test.yml:170-172` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro]

```yaml
    - name: Integration tests (WSL2, Windows host)
      run: |
        $env:PATH = "$pwd\_output\bin;" + $env:PATH
```

`C:\Program Files\Git\usr\bin` is not on the runner's machine PATH, and the runner's `C:\msys64\usr\bin` ships no `ssh.exe`. The removed variable was the only thing putting a Cygwin ssh ahead of `%SystemRoot%\System32\OpenSSH`, so `limactl` now picks the native client.

In run `30243838085`, jobs `89906470800` (WSL2) and `89906470695` (QEMU) both die at the first `limactl copy` with `C:\Windows\System32\OpenSSH\scp.exe: Connection closed`. Both pass on master run `30236908109`. That pair of runs also contradicts the commit message's "back when Lima required a Cygwin toolchain".

The copy test aborts before `hack/test-templates.sh:284`, so the rsync backend this PR enables never runs either.

Fix: install MSYS2's `openssh`, which puts `ssh.exe`, `scp.exe`, and `ssh-keygen.exe` beside the `cygpath` and `rsync` these jobs already use.

```diff
-      & 'C:\msys64\usr\bin\pacman.exe' -Sy --noconfirm openbsd-netcat diffutils rsync socat w3m
+      & 'C:\msys64\usr\bin\pacman.exe' -Sy --noconfirm openbsd-netcat diffutils openssh rsync socat w3m
```

## Important Issues

I1. **After #5299 lands, the MSYS2 jobs cover the native toolchain, not the Cygwin one** — `.github/actions/windows_msys2_prep/action.yml:20` [Claude Opus 5]

```yaml
      & 'C:\msys64\usr\bin\pacman.exe' -Sy --noconfirm openbsd-netcat diffutils rsync socat w3m
```

This outlives C1. Once #5299 makes native OpenSSH work, these two jobs go green again while running the native path, because no `cygpath.exe` sits beside `C:\Windows\System32\OpenSSH\ssh.exe`. All four Windows jobs would then exercise native OpenSSH, and nothing would drive the Cygwin branch of `PathForSSH`. That is the reverse of the PR's goal, which is plain-Windows coverage *alongside* the existing Cygwin coverage.

The newly added rsync sharpens it: rsync comes from MSYS2 while ssh is native, so the un-skipped rsync block runs a host combination neither of the two code paths targets.

Fix: the same `openssh` addition as C1 puts ssh, scp, cygpath, and rsync all in `C:\msys64\usr\bin`.

I2. **`$GITHUB_PATH` is not suppressed by `$GITHUB_ENV`, so the PATH scrub is bypassable** — `.github/actions/windows_plain_host/action.yml:67-69` [Claude Opus 5, Codex GPT 5.6 Sol]

```yaml
      # via $GITHUB_ENV — registry changes do not reach the running runner
      # process. Later steps adding entries (QEMU) must also write PATH= via
      # $GITHUB_ENV; $GITHUB_PATH is suppressed once $GITHUB_ENV sets PATH.
```

Job `89906470794` refutes the claim. After the scrub, every step env dump lists only the image's `go\1.24.13\x64\bin`, yet `windows_plain_build` compiled a module whose `go.mod` requires `go 1.25.7` under `GOTOOLCHAIN: local`, with no toolchain download logged. Only setup-go's `go 1.26.5`, registered through `$GITHUB_PATH`, explains that. The runner prepends those entries on top of the `$GITHUB_ENV` PATH.

A forbidden directory registered the same way therefore survives the scrub unseen, and lines 92-94 keep the verify step from noticing. They overwrite `$env:PATH` from Machine and User, then Layer 2 checks the `Process` scope it just wrote, so that arm cannot fail. Only Go uses `$GITHUB_PATH` here today, so the hole stays latent. `test.yml:263-264` repeats the same wrong claim.

Fix: check the inherited PATH as-is, and correct both comments.

```diff
-      # This process inherited PATH before the scrub above; refresh it from
-      # the scrubbed Machine + User values so Layer 2 reflects what later
-      # steps inherit.
-      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
-      $user = [Environment]::GetEnvironmentVariable('Path','User')
-      $env:PATH = (@($machine, $user) | Where-Object { $_ }) -join ';'
```

I3. **The 1-minute bound on the WSL2 distro import is gone** — `.github/actions/windows_wsl2_setup/action.yml:29-31` [Claude Opus 5]

```yaml
  - name: Install dummy WSL2 distro
    shell: pwsh
    run: |
```

At the merge-base this same work carried `timeout-minutes: 1`, bounding a `wsl --import` hang. GitHub supports `timeout-minutes` only on job-level steps, never inside a composite action, so the extraction silently drops it. A hang now burns the job's full 30 minutes, and in two jobs rather than one.

Fix: keep the import as a job-level step in both jobs, or bound it in-script with `Start-Job` plus `Wait-Job -Timeout 60`.

S3. **The plain-host action verifies only absence, never that native OpenSSH is present** — `.github/actions/windows_plain_host/action.yml:124-127` [Claude Opus 5]

```powershell
      $forbiddenCmds = @('cygpath','pacman','mintty','git','git-bash','git-cmd')
      foreach ($cmd in $forbiddenCmds) {
        $g = Get-Command $cmd -ErrorAction SilentlyContinue
        if ($g) { $fail += ("binary: {0} -> {1}" -f $cmd, $g.Source) }

```

The job's premise is that Lima falls back to `%SystemRoot%\System32\OpenSSH`. Nothing asserts that directory exists. A runner image that ever ships without the OpenSSH client fails later with an opaque `exec: "ssh": executable file not found`, not the loud prerequisite error the action promises. The same gap let C1 through on the MSYS2 side: no job asserts which ssh it selected.

Fix: add a positive layer asserting `ssh.exe`, `scp.exe`, `ssh-keygen.exe`, and `sftp-server.exe` under `Join-Path $env:SystemRoot 'System32\OpenSSH'`.

S4. **A documented environment variable disappears with no `breaking.md` entry** — `website/content/en/docs/config/environment-variables.md` [Claude Opus 5]

`website/content/en/docs/releases/breaking.md` has an open `## v2.2.0` section. `_LIMA_WINDOWS_EXTRA_PATH` was the only knob for pointing `limactl` at tools outside PATH, and C1 shows it was load-bearing rather than vestigial. `SSH` replaces it for the ssh binary alone; `rsync` and `cygpath` still resolve from the bare PATH.

Fix: add a v2.2.0 bullet naming the removal and the replacement.

S5. **`wsl --list --online` gates the step that calls it informational** — `.github/actions/windows_wsl2_setup/action.yml:22-28` [Claude Opus 5]

```powershell
      # --update reaches a Microsoft update service that returns
      # transient 403s; treat it as informational, like --status /
      # --version / --list --online below.
      wsl --update
      wsl --status
      wsl --version
      wsl --list --online
```

The runner appends `exit $LASTEXITCODE` to every `pwsh` script, so the last command's exit code becomes the step's. `wsl --list --online` queries the same Microsoft service the comment calls flaky, and unlike `--update` it does gate the step. The ordering predates this PR; the new comment is what asserts otherwise.

Fix: append `exit 0`, or move an unchecked command off the end.

S6. **Adding rsync introduces a pacman error that the exit-code guard misses** — `.github/actions/windows_msys2_prep/action.yml:20-21` [Consolidator]

```yaml
      & 'C:\msys64\usr\bin\pacman.exe' -Sy --noconfirm openbsd-netcat diffutils rsync socat w3m
      if ($LASTEXITCODE -ne 0) { throw "pacman failed: $LASTEXITCODE" }
```

In run `30243838085` this prints `error: command failed to execute correctly` from the `Updating the info directory file` post-transaction hook, which the new `rsync` package triggers. Master's run `30236908109` installs the same list without rsync and logs no error. pacman still exits 0, so the guard does not fire and the error rides along in every future Windows job log.

Fix: install `texinfo` alongside, or pass `--noscriptlet`, so the log stays clean.

S7. **A `zizmor: ignore` comment in `test.yml` suppresses nothing** — `.github/workflows/test.yml:269` [Consolidator]

```yaml
      # zizmor: ignore[github-env]
```

zizmor 1.28 reports no `github-env` finding for `test.yml` at any persona, because the workflow triggers on `push` and `pull_request` rather than a dangerous trigger. Removing the line changes nothing. The two inline `run: | # zizmor: ignore[github-env]` comments in the composite actions do carry weight: each suppresses a real finding, since an action has no trigger context. CI pins zizmor through `zizmor-action` v0.6.0, whose version I did not check.

Fix: drop the `test.yml` comment, keep the two in the actions.

S8. **The Git uninstaller wait does not cover the forked worker** — `.github/actions/windows_plain_host/action.yml:21-24` [Gemini 3.5 Flash]

```powershell
        & $uninstaller /VERYSILENT /NORESTART /SUPPRESSMSGBOXES
        # The uninstaller forks and the parent exits immediately; wait for
        # the worker process to finish before we wipe the leftover dir.
        Wait-Process -Name unins000 -Timeout 120 -ErrorAction SilentlyContinue
```

Inno Setup copies itself to a randomly named `_iu*.tmp` in the temp directory, so `-Name unins000` never matches the worker. Job `89906470794` shows the wait returning after 5 seconds with `C:\Program Files\Git` still present, and the `Remove-Item` fallback doing the real work. It succeeded there, but the fallback runs with `-ErrorAction SilentlyContinue`, so a worker still holding a lock would leave remnants and fail Layer 1.

Fix: poll `Get-Process` for any name matching `unins000` or `_iu*` until it clears.

S9. **`wsl --import dummy` is not idempotent, though the action says it is** — `.github/actions/windows_wsl2_setup/action.yml:42` [Gemini 3.5 Flash, Gemini 3.1 Pro, Claude Opus 5]

```powershell
      wsl --import dummy $env:TEMP $tarball
```

A second run fails with "The distribution name is already in use" and line 43 throws. The action's own description claims it "stays idempotent for local re-runs", but only the tarball creation is. Importing into the `$env:TEMP` root rather than a subdirectory also drops an `ext4.vhdx` beside everything else there.

Fix: narrow the idempotency claim, or unregister an existing `dummy` first and import into a dedicated subdirectory.

S10. **An empty round-trip file raises a null-method error instead of the mismatch message** — `.github/actions/windows_plain_smoke_test/action.yml:61-64` [Claude Opus 5]

```powershell
      $back = (Get-Content "$env:LIMA_HOME\rt-back.txt" -Raw).Trim()
      if ($back -ne 'roundtrip') {
        throw "round-trip mismatch: expected 'roundtrip', got '$back'"
      }
```

`Get-Content -Raw` returns `$null` for a zero-byte file, and `$null.Trim()` throws under the `$ErrorActionPreference = 'Stop'` at line 39. A copy defect that creates the file but transfers nothing is exactly the case this check exists for, and it is the case that loses the diagnostic. I did not run this: no PowerShell on the review host.

Fix: `$back = "$(Get-Content "$env:LIMA_HOME\rt-back.txt" -Raw)".Trim()`.

## Review Process Notes

### Skill improvements

- When the target has a completed CI run, read it before rating any finding whose severity depends on runtime behaviour: which binary a step resolved, whether a build or test step passed, what a tool printed. A finished run is primary evidence and outranks reasoning from documented platform semantics. A prediction that a step will fail is refuted by that step passing in the run under review. Compare against the base branch's most recent green run to separate a failure this change introduced from a pre-existing one.

- A diff that deletes a configuration knob (an environment variable, a PATH entry, a wrapper that changes lookup order) shows the deletion but never what the knob was doing at runtime. Before accepting such a removal as inert, work out what the value selected while it was set, and confirm something still selects the same thing. Removals justified as "this had no remaining users" deserve the most scrutiny, because the remaining user is often a runtime lookup rather than a textual reference a grep would find.

- When a change moves steps or settings into a more constrained container (a composite action, a shared template, a helper with a fixed signature), list the attributes the original carried and check each against what the container can express. An attribute the container cannot represent disappears without a syntax error, so the loss shows up only as behaviour missing later.

### Repo context updates

- [repo] GitHub's `windows-2025` runner image ships MSYS2 without the `openssh` package, so `C:\msys64\usr\bin` supplies `cygpath` and (once installed) `rsync`, but no `ssh.exe` or `scp.exe`. A Windows CI job that needs Lima to select a Cygwin/MSYS ssh must put one on PATH deliberately. Otherwise Lima falls back to `%SystemRoot%\System32\OpenSSH` and the job exercises the native path, whatever its name suggests. When reviewing a change to PATH handling in the Windows jobs, work out which `ssh.exe` `limactl` will resolve.

- [repo] `.github/workflows/test.yml` sets `GOTOOLCHAIN: local` at workflow level. Any job whose Go ends up older than `go.mod`'s `go` directive fails outright instead of downloading a matching toolchain, so a successful build is proof that the intended Go was on PATH. Use that when judging a claim that some step lost the `setup-go` entry.

- [repo] Required status checks match a job's check-run name, which comes from its `name:` key, not its YAML job id. Lima's jobs give the two different values, so renaming a job id while leaving `name:` unchanged does not affect branch protection, and a PR doing only that needs no protection edit.

# Deep Review — PR #5342: CI: factor Windows setup into composite actions; add plain-Windows jobs

## Executive Summary

The PR extracts Windows runner setup into seven composite actions and adds two plain-Windows jobs. The extraction is careful and the plain-host verification is well constructed. However, dropping `_LIMA_WINDOWS_EXTRA_PATH` also drops the only thing that put a Cygwin ssh on `limactl`'s PATH in the MSYS2 jobs: both pre-existing Windows jobs, green on master, fail at this SHA with native `scp.exe`.

## Findings

### Critical Issues

**C1. Dropping `_LIMA_WINDOWS_EXTRA_PATH` switches the MSYS2 jobs to native OpenSSH and turns both pre-existing Windows jobs red** — `.github/workflows/test.yml:170-177`, `.github/workflows/test.yml:199-206` (critical, regression)

```yaml
    - name: Integration tests (WSL2, Windows host)
      run: |
        $env:PATH = "$pwd\_output\bin;" + $env:PATH
        $env:MSYS2_ENV_CONV_EXCL = 'HOME_HOST;HOME_GUEST'
        $env:HOME_HOST = $(cygpath.exe "$env:USERPROFILE")
```

`C:\Program Files\Git\usr\bin` is not on the runner's machine PATH; only `Git\cmd` and `Git\bin` are, and neither holds `ssh.exe`. The removed env var was the sole reason `pickCompleteSSHOnWindows` (`pkg/sshutil/sshutil.go:86-102`) found a complete Cygwin install, so it now falls through to `%SystemRoot%\System32\OpenSSH` (lines 99-107) and `pkg/copytool/copytool.go:127` hands it a `/c/...` path.

At `fac4aebb`, jobs `89906470800` and `89906470695` both fail: `C:\Windows\System32\OpenSSH\scp.exe: Connection closed`. On master `7868e712` (run `30236908109`), the same jobs pass. The commit message's "back when Lima required a Cygwin toolchain" is contradicted by that pair of runs — master still requires it.

Fix: make the MSYS2 jobs supply their own complete Cygwin toolchain rather than relying on an in-process PATH injection:

```diff
       # Without rsync the copy test skips its rsync backend instead of failing,
       # so the Windows path conversion for that backend goes unexercised.
-      & 'C:\msys64\usr\bin\pacman.exe' -Sy --noconfirm openbsd-netcat diffutils rsync socat w3m
+      # openssh gives limactl a complete Cygwin ssh/scp/ssh-keygen beside
+      # cygpath, so these jobs cover the Cygwin toolchain rather than the
+      # native one the plain-Windows jobs cover.
+      & 'C:\msys64\usr\bin\pacman.exe' -Sy --noconfirm openbsd-netcat diffutils openssh rsync socat w3m
```

Failing that, state in the PR that this must land after #5299 and that it turns two existing jobs red until then.

### Important Issues

**I1. With native ssh selected, the MSYS2 jobs stop covering the Cygwin toolchain entirely** — `.github/actions/windows_msys2_prep/action.yml:20` (important, regression)


Separate consequence from C1, with a separate lifetime: once #5299 lands, the MSYS2 jobs go green again but running the *native* path, because `cygpathForSSH` (`pkg/sshutil/sshutil.go:169-189`) finds no `cygpath.exe` beside `C:\Windows\System32\OpenSSH\ssh.exe`. **I2. The plain-host verify step overwrites `$env:PATH` on a false premise, making its Process-scope check tautological** — `.github/actions/windows_plain_host/action.yml:89-94` (important, regression)

```powershell

      # the scrubbed Machine + User values so Layer 2 reflects what later
      # steps inherit.
      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
      $user = [Environment]::GetEnvironmentVariable('Path','User')
```

The premise is wrong. `ActionRunner.cs:282` processes the `$GITHUB_ENV` file after every step, including each embedded composite step, and `CompositeActionHandler.cs:259-263` re-reads `Global.EnvironmentVariables` for the next embedded step — so this step already inherits the scrubbed `PATH=` published at line 83. The overwrite then feeds Layer 2 (line 110) the same Machine and User values it goes on to check, so the `Process` arm cannot fail independently, and Layer 3's `Get-Command` lookups (lines 125-135) test a reconstructed PATH instead of the real one.

The related claim at line 69 and `test.yml:263-264` — "`$GITHUB_PATH` is suppressed once `$GITHUB_ENV` sets PATH" — is also wrong: `Handler.cs:224-231` prepends the `PrependPath` list onto the task-env PATH rather than replacing it. Fix:

```diff

-      # the scrubbed Machine + User values so Layer 2 reflects what later
-      # steps inherit.
-      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
-      $user = [Environment]::GetEnvironmentVariable('Path','User')
-      $env:PATH = (@($machine, $user) | Where-Object { $_ }) -join ';'
+      # $GITHUB_ENV from the scrub step applies to this step, so the inherited
+      # PATH is already the scrubbed one plus any $GITHUB_PATH prepends -
+      # exactly what later steps see. Check it as-is.
```

and correct the two comments about `$GITHUB_PATH`. The `PATH=` write in `test.yml:271` still works either way.

**I3. The 1-minute bound on the WSL2 distro import is lost in the extraction** — `.github/actions/windows_wsl2_setup/action.yml:29-44` (important, regression)

### Concerns

### Executive Summary
This PR factors Windows CI setup into reusable composite actions and adds two plain-Windows jobs (WSL2 and QEMU) to test Lima against a vanilla toolchain without MSYS2/Cygwin. The headline findings are two critical regressions: path-scrubbing in the plain-host action drops `setup-go` from the `PATH` (breaking the build), and the removal of the Git OpenSSH path injection without an MSYS2 equivalent forces existing MSYS2 jobs to use Native OpenSSH, breaking their `rsync` tests.

### Findings

#### Critical Issues

C1. **Path scrubbing drops `setup-go` installation** — `.github/actions/windows_plain_host/action.yml:65-68`

```powershell
      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
      $user = [Environment]::GetEnvironmentVariable('Path','User')
      $combined = (@($machine, $user) | Where-Object { $_ }) -join ';'
      Add-Content -Path $env:GITHUB_ENV -Value "PATH=$combined"
```

The action overwrites the `PATH` in `$GITHUB_ENV` using only the `Machine` and `User` registry keys. According to GitHub Actions semantics, setting `PATH` via `$GITHUB_ENV` completely overrides the `$GITHUB_PATH` values set by previous steps. 

Because `setup-go` relies on `$GITHUB_PATH` to expose the Go binary from the runner's tool cache, this scrub silently drops `go` from the `PATH`. The subsequent `windows_plain_build` step will fail with "The term 'go' is not recognized" unless it accidentally hits an older pre-installed version. The Layer 2 PATH verification later in the file also wrongly checks the registry-only `PATH`.

Fix: Scrub the inherited process `PATH` (which already includes `$GITHUB_PATH` contributions) instead of rebuilding it from the registry:
```diff
-      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
-      $user = [Environment]::GetEnvironmentVariable('Path','User')
-      $combined = (@($machine, $user) | Where-Object { $_ }) -join ';'
-      Add-Content -Path $env:GITHUB_ENV -Value "PATH=$combined"
+      $processPath = $env:PATH
+      $cleanedProcess = ($processPath -split ';' | Where-Object { $_ -and ($_ -notmatch $forbidden) }) -join ';'
+      Add-Content -Path $env:GITHUB_ENV -Value "PATH=$cleanedProcess"

...
-      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
-      $user = [Environment]::GetEnvironmentVariable('Path','User')
-      $env:PATH = (@($machine, $user) | Where-Object { $_ }) -join ';'
+      $env:PATH = $cleanedProcess
```
(critical, regression)

C2. **Removal of Git OpenSSH path breaks MSYS2 `rsync`** — `.github/workflows/test.yml:171`

```yaml
-        $env:_LIMA_WINDOWS_EXTRA_PATH = 'C:\Program Files\Git\usr\bin'
         bash.exe -c "./hack/test-templates.sh templates/experimental/wsl2.yaml"
```

### Executive Summary

This PR factors Windows runner setup into reusable composite actions and adds plain-Windows smoke tests to prevent toolchain leakage. While the modularization and multi-layered verification are exceptionally clean, a critical regression exists where rewriting `PATH` completely discards process-level additions like Go, breaking subsequent builds. A race condition also exists when waiting for the Git uninstaller to finish before removing its directory.

### Findings

#### Critical Issues

C1. **Scrubbing `PATH` with registry values discards process-level Go installation** `(critical, regression)` in `.github/actions/windows_plain_host/action.yml:68-81`

```yaml
      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
      $user = [Environment]::GetEnvironmentVariable('Path','User')
      $combined = (@($machine, $user) | Where-Object { $_ }) -join ';'
      Add-Content -Path $env:GITHUB_ENV -Value "PATH=$combined"
```

Rebuilding the `PATH` environment variable solely from raw registry `Machine` and `User` scopes discards process-level prepends established by prior actions, specifically `actions/setup-go`. Consequently, subsequent build steps (e.g. `windows_plain_build`) fail to find the `go` executable, terminating the workflow with a "command not found" error.

Fix: Scrub and publish the active process-level `$env:PATH` to preserve environment-injected tool paths.

```diff
-      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
-      $user = [Environment]::GetEnvironmentVariable('Path','User')
-      $combined = (@($machine, $user) | Where-Object { $_ }) -join ';'
-      Add-Content -Path $env:GITHUB_ENV -Value "PATH=$combined"
+      $cleaned = ($env:PATH -split ';' | Where-Object { $_ -and ($_ -notmatch $forbidden) }) -join ';'
+      Add-Content -Path $env:GITHUB_ENV -Value "PATH=$cleaned"
```

In the verify step (line 94), similarly update to:

```diff
-      $machine = [Environment]::GetEnvironmentVariable('Path','Machine')
-      $user = [Environment]::GetEnvironmentVariable('Path','User')
-      $env:PATH = (@($machine, $user) | Where-Object { $_ }) -join ';'
+      $forbidden = '(?i)(msys|mingw|cygwin|\\Git\\(cmd|bin|usr))'
+      $env:PATH = ($env:PATH -split ';' | Where-Object { $_ -and ($_ -notmatch $forbidden) }) -join ';'
```

#### Important Issues

I1. **Git uninstaller race condition during directory cleanup** `(important, regression)` in `.github/actions/windows_plain_host/action.yml:18-25`

```powershell
        & $uninstaller /VERYSILENT /NORESTART /SUPPRESSMSGBOXES
        # The uninstaller forks and the parent exits immediately; wait for
        # the worker process to finish before we wipe the leftover dir.
        Wait-Process -Name unins000 -Timeout 120 -ErrorAction SilentlyContinue
```

Inno Setup uninstallers immediately spawn a background worker copy of themselves in Temp (typically `_unins000.exe`) and terminate the parent process immediately. `Wait-Process -Name unins000` therefore completes prematurely while the background copy is still running and locking files inside `C:\Program Files\Git`. The subsequent recursive deletion fails, leaving remnants that trigger a loud Layer 1 filesystem verification failure.

Fix: Query and wait for any active processes containing `unins000` to exit.

```diff
-        Wait-Process -Name unins000 -Timeout 120 -ErrorAction SilentlyContinue
+        Start-Sleep -Seconds 2
+        $timeout = [System.Diagnostics.Stopwatch]::StartNew()
+        while ($timeout.Elapsed.TotalSeconds -lt 120 -and (Get-Process | Where-Object { $_.Name -like "*unins000*" })) {
+          Start-Sleep -Seconds 2
+        }
```
