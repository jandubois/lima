## Executive Summary

This PR adds a form to `limactl-menu` for creating an instance, builds its fields from the `limactl create` flags, and offers an Edit button that opens the template YAML first. Two defects need fixing before merge. One mouse click on the column header or footer disables every list shortcut, which the merge-base did not do. And when limactl rejects YAML edited through the Edit button, the edits are lost, because neither limactl nor the menu saves them.

## Important Issues

I1. **A mouse click on the header or footer disables every list shortcut** — `cmd/limactl-menu/main.go:216-218` [Claude Opus 5.5]

```go
	if s.app.GetFocus() != s.list {
		return e
	}
```

The menu enables the mouse, and tview's `TextView` takes the focus on a left click (tview v0.42.0 `textview.go:1395-1396`). So a click on the column header, or on the footer whose `F7 Create` label looks like a button, moves the focus off `s.list`. From then on this guard passes every key through, so F1 to F8, `c`, `q` and the other letter shortcuts all do nothing. Only F10 and Ctrl-C still work, and clicking the list to get the focus back opens the actions menu. Run against the merge-base's `main.go`, the probe below shows the keys still working after the click. The create form, its dialogs and the help view are separate roots, so checking the list view as a whole keeps the PR's protection for typing into the form.

I2. **A YAML edit that limactl rejects is lost** — `cmd/limactl-menu/create.go:676` [Codex GPT 6 Astra, Claude Opus 5.5]

```go
	return s.runLimactl(bytes.NewReader(y), opts.stdinArgs(name)...)
```

The Edit button pipes the edited YAML to `limactl create --name=<name> -`. limactl turns `tty` off when it reads stdin (`cmd/limactl/start.go:268`), and `instance.Create` saves `lima.REJECTED.yaml` only when `tty` is on (`pkg/instance/create.go:57-60`). The editor's temporary file is already deleted (`pkg/editutil/editutil.go:70`), and `editAndCreate` drops its own copy. So one typo or validation error throws away every edit, and the user starts again from the template. limactl's own interactive create keeps the same buffer, as the probe's second case shows.

## Suggestions

S1. **Checkboxes cannot turn off a setting that the template enables** — `cmd/limactl-menu/create.go:310-313` [Codex GPT 6 Astra]

```go
		case *tview.Checkbox:
			if item.IsChecked() {
				flags = append(flags, "--"+f.flag.Name)
			}
```

An unchecked box means "template default" and a checked one passes `--video`, `--rosetta` and so on, so the form cannot pass `--video=false`. With `template:experimental/vnc`, which sets `video.display: "vnc"`, unchecking the `video` box leaves VNC on, and checking it sets the display to `default` (`cmd/limactl/editflags/editflags.go:401-404`). The dropdowns label their default "(template default)", but a user will take an unchecked box to mean "off". The Edit button and the `set` field still work around it.

Fix: show bool flags as a `choiceField` with the choices `true` and `false`, which gives them the same "(template default)" option as the dropdowns, and update the checkbox cases in `create_test.go`.

S2. **A variant chosen for one template carries over to the next** — `cmd/limactl-menu/create.go:446-450` [Claude Opus 5.5]

```go
		for _, f := range details {
			if c, ok := f.item.(*choiceField); ok {
				switch f.flag.Name {
				case "image-variant":
					c.setChoices(variants)
```

`setChoices` keeps the current value and adds it back when the new choices lack it (`create.go:177-183`). That suits the static fields, but `image-variant` and `arch-variant` belong to the template. Pick `server` for one template, switch to a template whose images have no such variant, and the form still sends `--image-variant=server`. limactl then filters `.images` down to nothing (`cmd/limactl/editflags/editflags.go:423`) and fails with "field `images` must be set", which never mentions the variant.

Fix: in `updateTemplateChoices`, clear a value that the new template does not offer before calling `setChoices`.

S3. **limactl's stderr is missing from the error messages** — `cmd/limactl-menu/create.go:354-357` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	y, err := exec.CommandContext(ctx, s.limactl, "template", "copy", "--embed-all", "template:"+name, "-").Output()
	if err != nil {
		return nil, fmt.Errorf("failed to read template %q: %w", name, err)
	}
```

`Cmd.Output` keeps stderr in `*exec.ExitError.Stderr`, but the error string is only `exit status 1`. So a failed template read shows `failed to read template "x": exit status 1`, and `limactlLines` (`create.go:363-366`) reports a failed `--list-templates` the same way.

Fix: when `errors.As(err, &ee)` succeeds, add `strings.TrimSpace(string(ee.Stderr))` to the wrapped error in both helpers.

S4. **The form accepts an instance name that limactl rejects** — `cmd/limactl-menu/create.go:132-136` [Gemini 3.5 Flash]

```go
	if o.Name != "" {
		if err := identifiers.Validate(o.Name); err != nil {
			return fmt.Errorf("invalid name %q: %w", o.Name, err)
		}
	}
```

`identifiers.Validate` allows a name such as `test.yaml`. limactl checks the name with `dirnames.ValidateInstName`, which also rejects a `.yml` or `.yaml` suffix (`pkg/limatype/dirnames/dirnames.go:100-103`). So the form accepts the name, suspends the menu, and only then does limactl fail.

Fix: call `dirnames.ValidateInstName` instead of `identifiers.Validate`.

S5. **Edit rejects a `--param` that only the global base template defines** — `cmd/limactl-menu/create.go:117` [Codex GPT 6 Astra]

```go
	exprs, err := editflags.YQExpressions(flags, true, tmpl.Param)
```

`tmpl` comes from `limactl template copy --embed-all`, which embeds the user's `_config/base.yaml` only with `--fill` (`cmd/limactl/template.go:141-143`). A `--param` defined only in that file therefore fails on the Edit path with "template does not define param". The Create button accepts the same value, because `limactl create` embeds the global base before it checks parameters (`cmd/limactl/start.go:341-350`).

Fix: check the parameters against the template with `_config/base.yaml` embedded, but keep piping the unfilled YAML to limactl, which embeds the base itself and would otherwise merge it twice.

## Design Observations

### Concerns

- **The menu binary grew 4.6 times** (future) [Claude Opus 5.5]: a default `go build` on macOS arm64 gave 6,592,754 bytes at the merge-base and 30,123,586 at the head, and `go list -deps` grew from 189 to 527 packages (both measured for this review). The new imports of `editflags`, `limatmpl`, `limayaml` and `yqutil` pull in much of limactl, and the release archive ships the menu as a plugin (`Makefile:326`). Reading the flags and the template from limactl at run time would avoid that, at the cost of a larger change.
- **The help screen says `h` opens the actions menu** (in-scope) [Claude Opus 5.5, Gemini 3.5 Flash]: `main.go:291` says `Enter / h` opens the actions menu, but `h` opens the help (`main.go:221`), as it already did at the merge-base. The PR edits both places, so the one-line fix fits here.

### Strengths

- **The fields follow `limactl create`** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.5 Flash]: the form builds its fields from `editflags.RegisterCreate` and its completion functions, and the Edit path applies them with `editflags.YQExpressions`, so a new `limactl create` flag appears in the form without menu changes.
- **The key guard fixes an older bug** (in-scope) [Claude Opus 5.5]: at the merge-base, `d`, F2, F3 and F8 acted on the highlighted instance while the help view or the actions menu covered the list, and `q` quit the menu from the help view. The new guard stops that, and the I1 fix keeps it.

## Acknowledged Limitations

- **Entering `Other...` as a custom value** (`create.go:186`): typing the literal text `Other...` into an "Other..." dialog reopens the dialog, because the value then matches `otherChoice`. It does not loop. `promptValue` shows the dialog and returns, and Cancel restores the previous value. Do not re-raise it as a hang.
- **Reading the template on the UI goroutine** (`create.go:444`): `updateTemplateChoices` runs `limactl template copy --embed-all` each time the template changes. Here it took 0.79 s for `default` (first run) and 0.06 to 0.07 s for `k8s` and `docker`, all local reads. No bundled template has a remote `base:`, so only a user template with one would fetch, and `limactl create` fetches the same base. Do not re-suggest an asynchronous read without a template that shows a visible stall.
- **`context.Background()` in `editAndCreate`**: `s.ctx` comes from cobra's `Execute`, which nothing cancels, so the two contexts behave the same.

## Review Process Notes

### Skill improvements

- When a change routes keys or other input by which widget has focus, list every event that moves the focus, including a mouse click on a passive widget such as a label, a header or a status bar, and check the routing after each one. A focus check written for keyboard navigation misses the paths that the mouse opens.

### Repo context updates

- [repo] `limactl-menu` runs tview with the mouse enabled, and tview gives the focus to any `TextView` or `Box` the user clicks, the column header and the footer included. Key handling that tests `app.GetFocus()` against one widget breaks after such a click; test the view as a whole, for example with `Flex.HasFocus`.
- [repo] `limactl create` and `limactl start` turn `tty` off when they read a template from stdin (`-`), and `instance.Create` saves `lima.REJECTED.yaml` only with `tty` on. A caller that pipes user-edited YAML to limactl must keep the buffer itself when limactl rejects it.
- [repo] `limactl template copy --embed-all` leaves out the user's `_config/base.yaml`, which only `--fill` adds, while `limactl create` embeds it before checking `--param`. Code that edits or validates a template outside limactl must decide whether the global base applies.

However, `choiceField.selected` causes infinite recursion and freezes the application if `"Other..."` is entered as a custom choice, and instance name validation allows names ending in `.yaml`/`.yml`, triggering subprocess failures.

###### Findings

###### Critical Issues

None.

###### Important Issues

I1. **Infinite recursion in `choiceField.selected` when custom choice is `"Other..."`** — `cmd/limactl-menu/create.go:185-195` (important, regression)

```go
func (c *choiceField) selected(text string, index int) {
	if text != otherChoice {
		c.prev = index
		return
	}
	if c.promptFunc != nil {
		c.promptFunc(c)
	} else {
		c.restore()
	}
}
```

In `c.selected` (line 185), the check `if text != otherChoice` (line 186) inspects the option's text rather than its index. `c.options()` appends `otherChoice` (`"Other..."`) at index `len(c.choices)+1`. If a user selects `"Other..."` and enters `"Other..."`, `c.setValue("Other...")` (line 205) appends `"Other..."` to `c.choices` and invokes `c.SetCurrentOption(idx)`. In `tview.DropDown`, setting the option synchronously triggers `c.selected("Other...", idx)`. Because `text == otherChoice` evaluates to true, `c.promptFunc(c)` (line 191) fires recursively, re-opening the dialog in an infinite loop and freezing the menu.

-	if text != otherChoice {
+	if index <= len(c.choices) {

 	}

I2. **Instance name validation permits `.yaml` and `.yml` extensions** — `cmd/limactl-menu/create.go:132-136` (important, regression)

```go
	if o.Name != "" {
		if err := identifiers.Validate(o.Name); err != nil {
			return fmt.Errorf("invalid name %q: %w", o.Name, err)
		}
	}
```

In `createOptions.validate` (line 128), `o.Name` is checked against `identifiers.Validate(o.Name)` (line 133). `identifiers.Validate` permits identifiers with dots, including names ending in `.yaml` or `.yml` (such as `"test.yaml"`). However, `limactl` commands interpret trailing arguments ending in `.yaml`/`.yml` as template files rather than instance names, so every other instance validation path in the codebase (`cmd/limactl/start.go:236`, `cmd/limactl/start.go:336`, `pkg/limatype/dirnames/dirnames.go:83`) calls `dirnames.ValidateInstName(name)`. Because `create.go` only calls `identifiers.Validate`, entering `"test.yaml"` passes form validation, suspends the TUI, and fails only when `limactl` runs in `runSuspended` (`instance name "test.yaml" must not end with .yml or .yaml suffix`).

###### Suggestions

S1. **Subprocess failure diagnostics discard `stderr` in `limactlLines` and `readTemplate`** — `cmd/limactl-menu/create.go:356-378` (suggestion, enhancement)

```go
func (s *State) readTemplate(ctx context.Context, name string) ([]byte, error) {
	y, err := exec.CommandContext(ctx, s.limactl, "template", "copy", "--embed-all", "template:"+name, "-").Output()
	if err != nil {
		return nil, fmt.Errorf("failed to read template %q: %w", name, err)
	}
	return y, nil
}
```

Both `readTemplate` (line 356) and `limactlLines` (line 365) execute `exec.CommandContext(...).Output()`. If `limactl` exits non-zero, `err` contains an `*exec.ExitError` whose default string is uninformative (e.g. `exit status 1`), while the actual error message written to stderr is discarded. When `limactlLines` fails during `showCreateForm` (line 420), the user sees `Failed to list templates: limactl create --list-templates failed: exit status 1`.

Fix: Inspect `err` for `*exec.ExitError` and append `string(exitErr.Stderr)` when non-empty to preserve diagnostics.

S2. **Context propagation in `editAndCreate`** — `cmd/limactl-menu/create.go:671-672` (suggestion, enhancement)

```go
func (s *State) editAndCreate(opts *createOptions, name string) error {
	ctx := context.Background()
	y, err := s.editYAML(ctx, opts, name)
```

`editAndCreate` initializes `ctx := context.Background()` (line 671) and passes it to `s.editYAML`, which invokes `readTemplate` and `opts.applyToYAML`. `State` already holds `s.ctx` initialized from `cmd.Context()` in `runMenu` (`cmd/limactl-menu/main.go:87`). Using `s.ctx` ensures template reading and expression evaluation respect context cancellation.

Fix: Pass `s.ctx` instead of allocating a detached `context.Background()`.

###### Strengths

1. **Re-use of core flag and yq mechanics**: `create.go` avoids hand-rolled flag mapping by leveraging `editflags.RegisterCreate` and `editflags.YQExpressions`. Both the CLI command generation (`opts.args()`) and direct YAML modification (`opts.applyToYAML`) share the same validation and translation engine as `limactl create`.
2. **Keyboard and arrow navigation ergonomics**: Translating arrow keystrokes via `formArrowKey` while selectively bypassing open dropdowns and multi-line text areas ensures standard terminal navigation feels natural.
3. **Empty state integration**: Replacing the merge-base's standalone application spawn in `showEmptyState` with modal navigation inside `s.app` provides a clean transition into the create form when no instances exist.
