## Executive Summary

The PR maps Lima `mounts` onto WSL2: it translates a Windows location to its `/mnt/<drive>` path for the default mount point, and a guest boot script bind-mounts each entry, remounts read-only ones, and edits `/etc/wsl.conf`. A location the translator rejects, such as a UNC path, now panics `FillDefault` instead of reaching the new validation error. The boot script also overwrites existing automount options and leaves a writable mount nested under a read-only one read-only.

Step 3 rewrites any `options` line under `[automount]` to `options = "metadata"`, which drops `uid`, `gid`, `umask` and anything else a rootfs or user set. It runs on every boot, so the user cannot restore them. The finch rootfs that `templates/experimental/wsl2.yaml` uses ships only a `[boot]` section, so the stock template appends a new section instead.

Nothing in the mount loop needs `metadata`. WSL reads `wsl.conf` only when the distro starts, so the option first applies after a restart. From then on it changes permission handling for every `/mnt/<drive>` path, whether Lima mounted it or not.

## Suggestions

S1. **The read-only fallback ends writable and still reports success** — `pkg/driver/wsl2/boot.Linux/03-wsl-mounts.sh:74-81` [Gemini 3.5 Flash, Gemini 3.1 Pro, Claude Opus 5.5]

```sh
				if ! mount -o remount,ro,bind "$mountpoint"; then
					WARNING "Failed to remount $mountpoint as read-only. Unmounting for safety."
					umount "$mountpoint"
					# Cleanup leaf directory and create symlink fallback
					# Note: intermediate parent directories created by mkdir -p are left behind (harmless in practice)
					rmdir "$mountpoint" 2>/dev/null || true
					if [ ! -e "$mountpoint" ]; then
						ln -sfn "$wsl_path" "$mountpoint"
```

When `remount,ro,bind` fails, the script unmounts "for safety" and then links the path to the same writable source, so the entry ends up writable either way. Line 86 still logs "Successfully bind-mounted". Two reviewers rated this a broken security boundary, but `writable: false` isolates nothing on WSL2. The source stays writable under `/mnt/c`, the guest user has passwordless sudo, and interop runs Windows programs. So the cost is a misleading log and a pointless unmount.

Fix: keep the read-write bind and warn, or leave the path unmounted, and log success only on the success path.

S2. **The shell fallback passes a location without a drive letter through unchanged** — `pkg/driver/wsl2/boot.Linux/03-wsl-mounts.sh:45-47` [Claude Opus 5.5]

```sh

			wsl_path="$location"
```

When `wslpath` fails, lines 34-48 repeat `TranslateWindowsToWSLPath` with `/mnt` hard-coded. Any other form, such as a UNC location with an explicit `mountPoint` (which `Validate` accepts on Windows), goes to `mount --bind` and then `ln -sfn` unchanged, and the script logs "Successfully symlinked" for a link to a Windows path.

## Design Observations

### Concerns

- **`writable: false` on WSL2 protects one path, usually the one `limactl shell` starts in** (in-scope) [Claude Opus 5.5]. The source stays writable under `/mnt/c`, the guest user has passwordless sudo, and interop runs Windows programs, so the read-only bind guards against mistakes only. An instance with the usual `- location: "~"` (default `writable: false`) now gets a read-only `/mnt/c/Users/<user>`, and on wsl2 `limactl shell` changes into the host's working directory under that path (`cmd/limactl/shell.go:270`), so builds there fail. The maintainers should decide whether wsl2 mounts keep the automount's read-write default; either way, `mount.md` should say what the flag does on wsl2.
- **Host and guest translate paths separately** (in-scope) [Gemini 3.5 Flash]. The Go translator hard-codes `/mnt`, while the guest's `wslpath` follows `[automount] root`. With a custom root the two disagree, and the script bind-mounts the automount path onto a new `/mnt/<drive>/...` directory.

### Strengths

- Host-side translation is a pure string function, so `FillDefault` does not start a WSL distro during load, and the table test covers it directly. [Codex GPT 6 Astra, Claude Opus 5.5]
- The WSL2-only logic is a driver boot script embedded through `BootScripts`, which keeps it out of the shared `cidata.TEMPLATE.d`. [Claude Opus 5.5, Codex GPT 6 Astra]

## Testing Assessment

## Review Process Notes

### Skill improvements

- When code applies a list of entries that each change the state of a path (a mount, a permission, an owner), check the pairs whose paths nest or overlap. An earlier entry's effect can override a later entry's request, and a reviewer reading one entry at a time misses it.
- When the code a finding needs is gated by a platform constant such as `runtime.GOOS`, a probe can patch that one condition in a scratch copy and call the real function. A probe that retypes the gated logic proves only the copy.
- When the PR's base lags the default branch, check every function a finding's mechanism depends on against the default branch, including files the PR does not touch. A finding can hold at the PR's base and vanish with the rebase the PR needs anyway.

### Repo context updates

- [repo] UPDATE "Guest boot scripts: ordering and silent degradation": `04-persistent-data-volume.sh` acts only on Alpine guests whose root is tmpfs, so the rule that `/etc` and `/var/lib` changes sort after it binds those guests only. A driver boot script for another guest family, such as wsl2, may edit `/etc` earlier.
- [repo] `FillDefault` runs inside `limayaml.Load`, before `driverutil.ResolveVMType` fills the platform default, so `y.VMType` is nil there whenever a template omits `vmType`. A `FillDefault` branch keyed on the VM type must resolve the default itself (`limatype.DefaultDriver()`, or `DefaultNonNativeArchDriver()` for a foreign arch).
- [repo] Drivers warn about config they ignore through `reflectutil.UnknownNonEmptyFields` and a list of known field names. `FillDefault` fills `SSHFS` and `NineP` for every mount, so a driver's mount list must name both or it warns on every load. When a change makes a driver honor a field, check that the driver's list names it.
- [repo] The Windows WSL2 CI job runs `templates/experimental/wsl2.yaml`, which does not define any mounts, and its mount-home check reads through WSL's automount. No CI job runs a wsl2 boot script gated on `LIMA_CIDATA_MOUNTS`, so a green run says nothing about wsl2 mount handling.

### Design Observations

#### Concerns

- **Decoupled host and guest path translation** `(in-scope)`: `TranslateWindowsToWSLPath` translates paths on the host, while `03-wsl-mounts.sh` re-translates them via guest `wslpath` or a shell fallback. If host translation in `defaults.go` and guest translation in `03-wsl-mounts.sh` diverge (e.g. customized WSL `root = /` automount prefix in `wsl.conf`), the guest detects an artificial mismatch and creates unnecessary bind mounts.
- **Boot-time vs. pre-boot `wsl.conf` provisioning** `(future)`: WSL2 configuration in `/etc/wsl.conf` is static and read only when the WSL distribution initializes. Writing `/etc/wsl.conf` from inside a guest boot script means the configuration is always one boot behind. Generating `wsl.conf` during distribution import (`tar` generation or cidata injection) would ensure automount options are active on the very first boot.

#### Strengths

- Reusing WSL2's native automount (`/mnt/c`) and bypassing bind mounting when `$wsl_path == $mountpoint` avoids unnecessary VFS overhead and preserves native filesystem performance.
- Passing structured per-mount metadata (`LIMA_CIDATA_MOUNTS_<n>_LOCATION`, `_WRITABLE`) through `lima.env` cleanly integrates WSL2 mounts into Lima's generic cidata mechanism without breaking other drivers.
