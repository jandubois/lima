## Executive Summary

The PR teaches the networks defaults, path validation and sudoers generator about Linux hosts, enables `limactl sudoers` there, and moves shared sudoers code into `pkg/sudoers`. Two defects need fixing. `limactl sudoers --check` now reports a file it cannot read as up-to-date, which the Linux install mode makes the normal case. And `Validate()` rejects the `networks.yaml` that every earlier Lima wrote on Linux, with a socket_vmnet error. Three comments and the help text also contradict the code.

## Suggestions

S1. **`--check` probes `root:wheel` on Linux when the file is missing** — `cmd/limactl/sudoers_action.go:121` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
				if err := sudoers.Run(ctx, "root", "wheel", nil, nil, nil, "", "true"); err == nil {
```

This probe checks the macOS mkdir grant, which Linux does not emit. Where `/etc/sudoers.d` is searchable and the file is missing, a user with blanket passwordless sudo on a distribution without a `wheel` group gets "can't read …: no such file or directory", which names the wrong cause. Only `--check` takes this path. Network start goes through `VerifyFragment`, which does not need `wheel`, and `RegenerateHint` already handles the missing group. Gemini 3.1 Pro and Gemini 3.5 Flash rated this Important. It stays a Suggestion because it affects one diagnostic command and nobody ran it on Linux.

Fix: run the `root:wheel` probe only on darwin.

S2. **`defaultGroup` ignores the user's group membership** — `pkg/networks/config.go:65-70` [Claude Opus 5.5]

```go
	for _, name := range []string{"sudo", "wheel"} {
		if _, err := user.LookupGroup(name); err == nil {
			return name
		}
	}
	return "root"
```

On a host with both groups it picks `sudo` even when the user is only in `wheel`. When neither exists, it silently falls back to `%root`, which grants nothing to an ordinary user.

Fix: prefer the first candidate in `user.Current().GroupIds()`, and log a warning on the fallback.

S3. **The Linux regeneration hint warns about `--block-device` grants** — `pkg/sudoers/verify.go:79-80` [Claude Opus 5.5]

```go

		exe, args, install, file, RegenerateGrantWarning)
```

`RegenerateGrantWarning` describes `--block-device` entries, but on Linux that flag only returns an error.

Fix: append the warning only on darwin.

S4. **Deleting `pkg/networks/sudoers_test.go` dropped the only test of `VerifySudoAccess`** — `pkg/networks/sudoers.go:105-106` [Claude Opus 5.5]

```go

```

The moved tests feed `VerifyFragment` a fixed fragment. Nothing now checks that `VerifySudoAccess` passes `c.Sudoers()` and the hint through. A wrong wiring would fail every network start loudly with "out of sync", so the rubric rates this test optional.

## Design Observations

### Concerns

- (in-scope) Network start cannot see a stale grant on Linux. With the file `0440 root`, `VerifyFragment` returns nil without reading it, and the digest pin makes the file stale after each reinstall of the helper. Users then meet only sudo's "a password is required" in the daemon's stderr log, with no regeneration hint. When the file is unreadable, running `sudo -n -l <rendered start command>` could turn that failure into the hint. Nobody has checked whether `sudo -l` applies a `Digest_Spec` when matching. [Claude Opus 5.5, Gemini 3.1 Pro, Gemini 3.5 Flash]
- (future) Even with I2's fix, an upgraded Linux user must regenerate `networks.yaml`. #5486's Linux page should say so. [Claude Opus 5.5]

### Strengths

- On macOS, `Config.Sudoers()` renders the same text before and after the PR, apart from temporary paths. Claude measured this with a probe at both commits. [Claude Opus 5.5]
- Moving the shared rendering and verification into `pkg/sudoers` leaves each package owning its grants, and one `RegenerateHint` replaces the two hint strings that had diverged between `cmd/limactl` and `pkg/networks`. [Claude Opus 5.5, Codex GPT 6 Astra]
- The `tap` grant pairs a pinned `--` in the renderer with `SetInterspersed(false)` and `ExactArgs(1)` in the helper, so any smuggled word becomes a surplus positional argument. [Claude Opus 5.5, Codex GPT 6 Astra]
- sudo itself enforces the digest pin, which closes the time-of-check race that the helper's ownership checks leave open. [Gemini 3.5 Flash]

## Acknowledged Limitations

- Network start tolerates an unreadable sudoers file. The author chose that trade-off, writing that "a correctly installed file cannot be verified from an unprivileged process, and a wrong one still fails loudly inside sudo". I1 covers `--check` only. A future review should not re-raise the startup tolerance as a defect; the design concern above proposes an alternative.
- `/usr/bin/pkill` stays unpinned on purpose, because it is a system binary that updates independently of Lima. Do not re-suggest pinning it.
- `VerifyFragment` with an empty fragment returns "out of sync", which Gemini 3.5 Flash raised as Important. No caller reaches that case. Network start validates only a non-usernet network, whose block is never empty, and `--check` compares the whole file first, so a regenerated empty file passes. Do not re-raise it without naming a caller.

###### Executive Summary
This PR successfully extracts sudoers file management into a reusable `pkg/sudoers` package, adds support for Linux privileged network daemons, and secures them by pinning their execution via `sudo`'s `Digest_Spec`. However, a regression in how unreadable sudoers files are handled bypasses validation entirely, leading to misleading `--check` reports and lost regeneration hints when the file is out of sync.

###### Critical Issues

###### Important Issues

I1. **`VerifyFragment` ignores unreadable sudoers files, masking the regeneration hint** — `pkg/sudoers/verify.go:56-58`

```go
	if !ok {
		return nil
	}
```
When `sudoers.ReadFile` encounters a permission error (e.g., `/etc/sudoers.d` is `0750 root:root` on Linux), it returns `ok=false` and `err=nil`. `VerifyFragment` immediately returns `nil` (success), completely bypassing validation. 

This introduces two serious regressions:
1. **Misleading `--check` output**: `verifySudoersFile` inherits this bypass, unconditionally reporting `"... is up-to-date"` for an unreadable file, even if it is outdated or missing required block-device entries.
2. **Lost regeneration hint**: During network startup, `VerifySudoAccess` skips verification and proceeds to execute `sudo`. If the file is actually out of sync (or the binary was upgraded, changing its `Digest_Spec`), `sudo` fails non-interactively. The user sees an opaque `sudo: a password is required` or digest mismatch error and never receives the `RegenerateHint`, which is the primary reason this validation layer exists.

Fix: Do not blindly return `nil` on `!ok`. For `--check`, it must report that the file cannot be verified. For network startup, fall back to `VerifyPasswordLess(ctx, runAs...)` to ensure the required commands can actually execute before returning success, or return a wrapped error providing the hint.

I2. **Hardcoded `root:wheel` breaks passwordless `--check` on Linux** — `cmd/limactl/sudoers_action.go:121-123`

```go
			if err := nwCfg.VerifySudoAccess(ctx, ""); err == nil {
				if err := sudoers.Run(ctx, "root", "wheel", nil, nil, nil, "", "true"); err == nil {
					return nil
				}
			}
```
When `--check` is run and the sudoers file does not exist, it verifies if passwordless `sudo` is globally available. After confirming `nwCfg.VerifySudoAccess` works, it runs an additional hardcoded fallback test as `root:wheel`. 

This file is now compiled for Linux, where the `wheel` group often does not exist (e.g., Debian/Ubuntu use `root` or `sudo`). If a Linux user relies on a global `NOPASSWD: ALL` setup without a Lima-specific sudoers file, this check will fail due to the missing group and falsely report that the file needs regeneration.

Fix: Block devices (which require `wheel`) are not supported on Linux. Gate this fallback check on `runtime.GOOS == "darwin"`, or dynamically look up the appropriate group using `defaultGroup()`.

###### Design Observations

###### Concerns

- **Unprivileged sudoers verification on Linux** (in-scope):
  The attempt in `pkg/sudoers/sudoers.go` to inspect `/etc/sudoers.d/lima` via unprivileged `os.ReadFile` conflicts with Linux filesystem permissions where `/etc/sudoers.d` is `0750 root:root` and files are `0440 root:root`. Tolerating `os.ErrPermission` as success neutralizes `--check` and `VerifySudoAccess`. Instead of attempting an unprivileged read, Linux verification should test execution of the specific helper commands via `sudo -n <helper> --version` or inspect rules with `sudo -n -l`, which tests actual privilege escalation rather than file contents.

###### Strengths

- **Digest Pinning via sudo `Digest_Spec`**:
  Using `sudoers.Pin` with `github.com/opencontainers/go-digest` to pin the exact binary digest of `lima-privileged-net` in the sudoers file eliminates TOCTOU races in helper execution by delegating integrity checks to `sudo` itself.
- **Fixed-width Tap device naming**:
  Encoding the caller's UID in clear alongside the instance/network hash in `TapName` ensures non-colliding, deterministic interface names that fit within Linux `IFNAMSIZ-1`.

###### Acknowledged Limitations

- **Unreadable `/etc/sudoers.d` on Linux hosts**:
  - *PR comment*: The author noted in PR review comments that `ReadFile() tolerates an unreadable sudoers file, as /etc/sudoers.d is typically 0750 root:root: a correctly installed file cannot be verified from an unprivileged process, and a wrong one still fails loudly inside sudo.`
  - *Rationale verification*: While the author recognized that `/etc/sudoers.d` is `0750`, swallowing `os.ErrPermission` causes `limactl sudoers --check` to report that absent or corrupt files are up-to-date, and regresses macOS behavior where unreadable `0440` files were previously caught. Promoted to finding I1.
