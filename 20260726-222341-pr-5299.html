Design Observations ¶

Concerns ¶

  • limactl shell --sync still mixes two toolchains' path forms in one rsync argv (future) Claude Opus 5. mountDirFromWindowsDir converts hostCurrentDir through the PATH-global fsutil.WindowsSubsystemPath, and the result reaches copytool as a rooted non-IsAbs path that pathForRsync passes through untouched, while hostTmpDest from askUserForRsyncBack arrives native and is converted by rsync's own sibling cygpath. Both forms agree under this repo's CI, where Git for Windows and MSYS2 both map C:\ to /c/; a stock Cygwin install or a custom fstab would not. This PR narrows the gap, leaving mountDirFromWindowsDir as the last PATH-global converter feeding a toolchain-pinned consumer.
  • CommonOptsForTool's promise about version detection holds only for the first caller (in-scope) Claude Opus 5. The doc says version detection still runs against sshExe, but that probe sits inside sshInfo.Do (pkg/sshutil/sshutil.go:479), a process-wide sync.Once, so after any earlier call the argument is inert. The sync.Once predates this PR; the new doc is the first place that promises anything about it.

Strengths ¶

  • Converting local operands before the trailing-slash pass at pkg/copytool/rsync.go:114 (in-scope) Claude Opus 5 Codex GPT 5.6 Sol. It preserves directory-versus-contents semantics that cygpath output would otherwise scramble, and the comment says why.
  • Keying each path to the binary that consumes it (in-scope) Claude Opus 5 Codex GPT 5.6 Sol Gemini 3.1 Pro Gemini 3.5 Flash. All four reviewers named this as the right split, and it removes pkg/copytool from the PATH-global converter's callers.
  • Resolving symlinks inside pathForRsync rather than in newRsyncTool (in-scope) Claude Opus 5 Codex GPT 5.6 Sol. It keeps exec's target and argv[0] untouched on every platform, and the comment records that constraint.
  • One shared sshOptsForInstance for the availability probe and the transfer (in-scope) Claude Opus 5 Codex GPT 5.6 Sol. It forecloses a probe rejecting an rsync the command would have driven.
  • Classifying Windows absolute paths before the ":" split (in-scope) Gemini 3.5 Flash Claude Opus 5. Single-letter instance names keep working, and TestParseCopyPathsWindowsDriveLetter pins both halves.

Review Process Notes ¶

Skill improvements ¶

  • When a change adds a test or a CI step, confirm the job that would run it actually reaches it. Read the workflow's setup steps for the tools the test's guard requires, and read the most recent job log for a skip message. A guarded block (if command -v X, a platform conditional, a matrix filter) reports success whether it ran or was skipped, so a reviewer who reads only the diff records new coverage where none exists, and a later round inherits that belief as established.
  • When a comment or commit message explains why a change is correct by naming a mechanism in an external tool, verify the mechanism before accepting the conclusion. Run the tool and observe what it does with the input in question. A correct conclusion resting on a wrong mechanism reads as fully verified, and the next reader who checks the mechanism has grounds to revert the change.
  • When a prior round's fix replaced a comment that was wrong, check whether the replacement errs in the opposite direction. A correction written to escape one over-claim commonly lands on its mirror image, and the round that requested the fix is the least likely to re-examine it.

Repo context updates ¶

  • [repo] Neither Windows CI job installs rsync. .github/workflows/test.yml prepends C:\msys64\usr\bin to PATH and runs pacman -Sy --noconfirm openbsd-netcat diffutils socat w3m, which omits rsync, so hack/test-templates.sh logs Skipping rsync backend test (rsync not available on host or guest) on both the QEMU and WSL2 Windows jobs. Any claim that Windows CI exercises the rsync backend, its path conversion, or its -r trailing-slash handling is false. The Linux and macOS jobs do run that block, so a guest-side explanation for the skip is wrong.
  • [repo] Windows unit tests do run: the WSL2 Windows job has a go test -v ./... step on windows-2025 before its integration step. A Windows-only branch guarded by runtime.GOOS == "windows" in a Go test therefore executes in CI, unlike a Windows-only branch reachable only through hack/test-templates.sh.
  • [repo] scp does not interpret the -o options Lima passes it. It forwards them to an ssh subprocess resolved from its own install directory (/usr/bin/ssh compiled in on Unix; beside the running binary under Win32-OpenSSH). Path-valued options must therefore take the form scp's toolchain reads, which is why keying them to the scp binary is right, and any comment saying scp parses them itself is wrong.
  • [repo] pkg/hostagent/requirements.go and pkg/hostagent/mount.go rebuild the hostagent's sshConfig with DisableControlMasterOptsFromSSHArgs on Windows. Combined with the hostagent's own sshConfig keeping the mux options, this means some hostagent invocations multiplex on Windows and some do not. Reject both blanket claims: that Lima strips multiplexing everywhere on Windows, and that every command the hostagent runs multiplexes.
