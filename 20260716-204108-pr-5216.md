## Suggestions

S1. **Integration test asserts the FD release but not the goroutine termination** — `pkg/portfwdserver/server_test.go:144` [Claude Opus 4.8]

```go
	deadline := time.After(5 * time.Second)
	for {
		if _, err := guestConn.Write([]byte("x")); err != nil {
			return
		}
```

Issue #5210 reports two leaks per forwarded connection: one FD and one goroutine. `TestTunnelServerClosesGuestConn` asserts only the FD, and it reaches that assertion through `Start`'s `defer conn.Close()` rather than through `HandleConn` completing. Restore the blocking sends while keeping `defer conn.Close()` and the `HandleConn` goroutine wedges forever in `rw.Close()`, yet this test still passes. `TestGRPCServerRWCloseNeverBlocks` catches that case at the unit level, so the branch as a whole covers it; the gap is that the test whose doc comment claims to reproduce "the teardown sequence of `tcpproxy.DialProxy.HandleConn`" never verifies the sequence finishes.

Fix: assert the proxy goroutine settles after `startDone`, or expose its completion for the test to wait on.

S2. **`fakeTunnelStream.Recv` ignores the stream context, confining the test to one teardown path** — `pkg/portfwdserver/server_test.go:88` [Claude Opus 4.8]

```go
func (s *fakeTunnelStream) Recv() (*api.TunnelMessage, error) {
	msg, ok := <-s.recvCh
	if !ok {
		return nil, io.EOF
	}
	return msg, nil
}
```

A real gRPC server stream unblocks a parked `Recv()` when the handler returns. This fake ignores `s.ctx`, so it unblocks only when the test closes `recvCh`. That confines coverage to the host-half-closes-first path. The two paths that produced the reported leak — the guest service closing first (`CloseWrite`) and the host cancelling the stream (`ctx.Done`, `server.go:50-52`) — cannot be driven through this fake, because `Recv` would park forever. The fake constrains what the suite can test rather than masking a live bug.

Fix: `select` on both `s.recvCh` and `s.ctx.Done()`, returning `s.ctx.Err()` for the latter.

S3. **`chan any` is vestigial now that `closeCh` only ever closes** — `pkg/portfwdserver/server.go:70` [Claude Opus 4.8]

```go
	closeCh chan any
```

`chan any` fit the old design, where each `Close*` sent a `struct{}{}` into a 1-slot buffer. Nothing is sent any more: the channel is only closed and received from once, so the element type misleads a reader into expecting a delivered value. `chan struct{}` is the dominant idiom in `pkg/` (7 `make(chan struct{})` against 4 `make(chan any`, two of which are the sites under review), and the new test already uses `chan struct{}` for its own `done` signal.

Fix: change the field and both construction sites (`server.go:48`, `server_test.go:57`) to `chan struct{}`.

S4. **A `GRPCServerRW` built without `closeCh` now panics where it used to block** — `pkg/portfwdserver/server.go:106` [Claude Opus 4.8]

```go
	g.closeOnce.Do(func() { close(g.closeCh) })
```

`close()` on a nil channel panics; the previous `g.closeCh <- struct{}{}` blocked forever. Nothing reachable panics today: every field is unexported and the type has no constructor, so the only valid construction is the composite literal in `Start` (`server.go:48`). The footgun is live in-package, though — `TestGRPCServerRWReadShortBuffer` (`server_test.go:37`) already builds one without `closeCh`, and adding a `defer rw.Close()` there would crash the test binary. In the guest agent such a panic would land in the `HandleConn` goroutine and take the process down.

Fix: add a `newGRPCServerRW` constructor that owns the invariant, and build from it in `Start` and the tests.

## Design Observations

### Concerns

**Half-close from the host tears down the guest connection before the response is relayed (future)** [Gemini 3.1 Pro, Claude Opus 4.8]

`Start` returns as soon as any `Close*` fires, so a client that calls `shutdown(SHUT_WR)` and waits for a reply loses it. The chain: the host's `io.Copy` finishes, `GrpcClientRW.CloseWrite()` calls `stream.CloseSend()` (`pkg/portfwd/client.go:129`), the guest's `Recv()` returns `io.EOF`, and `closeRead(rw)` closes `closeCh` and ends the tunnel.

This predates the PR. I confirmed it by running the new tests against the merge-base: `TestTunnelServerClosesGuestConn` fails at the write loop (`server_test.go:151`), meaning it passed the `startDone` assertion — the old code also returned from `Start` on the same `CloseRead`, and lost the response to a dead stream. This PR changes only how the guest connection dies: a prompt close instead of a lingering leaked FD, which is strictly better.

Gemini proposed dropping `closeOnce.Do` from `CloseRead`. That enables half-close but changes teardown semantics well beyond a leak fix, and it needs its own tests — the guest→host direction then parks in `conn.Read` until the guest service closes or the host cancels the stream. Treat it as follow-up work, not a change to this PR.

### Strengths

**The root-cause analysis is exact and independently verifiable (in-scope)** [Claude Opus 4.8]

`HandleConn` registers `defer dst.Close()` (`tcpproxy.go:390`) before `defer src.Close()` (`:396`), so LIFO ordering means a blocked `src.Close()` permanently strands `dst.Close()`. `rw` receives exactly three `Close*` calls against one receive and a 1-slot buffer, so the third blocks. The commit message states this correctly.

**`defer conn.Close()` also fixes an unreported UDP leak (in-scope)** [Claude Opus 4.8]

Datagram sockets never EOF, so for `udp` tunnels the guest→host `io.Copy` parks in `conn.Read` forever and `HandleConn`'s second `<-errc` never fires — meaning `sync.Once` alone would not have fixed UDP. Closing `conn` from `Start` is what unblocks that read. The same reasoning applies to a TCP guest service that holds its side open, which is what the code comment at `server.go:43-46` anticipates.

**`sync.Once` + `close()` replaces a caveat with an enforced invariant (in-scope)** [Codex GPT 5.5, Claude Opus 4.8]

The one-shot-signal pattern preserves the single receive in `Start` while making repeated calls safe, and it retires the old "we can't close rw.closeCh" comment.

### Design Observations

#### Concerns

**Half-close from the host tears down the guest connection before the response is relayed (future).** `Start` returns as soon as *any* `Close*` fires (line 61), and `tcpproxy`'s `proxyCopy` calls `closeRead(rw)` when the host→guest direction ends. So a client that does `shutdown(SHUT_WR)` and waits for a reply — HTTP/1.0 clients, `nc -N`, request/response protocols that signal end-of-request with a FIN — triggers this chain: host `io.Copy(grpcRW, hostConn)` ends → `GrpcClientRW.CloseWrite()` → `stream.CloseSend()` (`pkg/portfwd/client.go:129`) → server `stream.Recv()` returns `io.EOF` → `rw.Read` EOF → `closeWrite(conn)` correctly propagates the half-close to the guest service, then `closeRead(rw)` closes `closeCh` and destroys the tunnel. The guest's response is discarded.

This predates the PR — `<-rw.closeCh` (blame: `0c0a78dd3`, 2025-10-20) already returned on the first signal, and the response was lost to the dead stream either way. The PR only changes *how* the guest connection dies (hard `Close`/RST instead of a lingering leaked FD), which is strictly better. Worth flagging because `TestTunnelServerClosesGuestConn` now encodes this path as expected behavior, so a future half-close fix must update the test.

A fix is not simply "wait for `HandleConn`" — that deadlocks, since the guest→host direction parks in `stream.Recv()`, which only unblocks once the handler returns. It would require `Read` to select on `closeCh`, plus distinguishing `CloseRead` (host is done sending; keep relaying the response) from `Close`/`CloseWrite`. That is a materially larger change and does not belong in this PR.

#### Strengths

- The root-cause analysis is exact and independently verifiable: `HandleConn` registers `defer dst.Close()` at `tcpproxy.go:390` before `defer src.Close()` at `:396`, so the LIFO ordering means a blocked `src.Close()` (the third send into a 1-slot buffer drained once) permanently strands `dst.Close()`. The commit message states this correctly.
- `sync.Once` + `close()` is the canonical Go one-shot-signal pattern, and it replaces the awkward "we can't close this channel" comment with an invariant the type enforces.
- `defer conn.Close()` also fixes an unmentioned UDP leak: for `udp` tunnels the guest→host `io.Copy` parks in `conn.Read` forever (datagram sockets never EOF), so `HandleConn`'s second `<-errc` never fires and its `defer dst.Close()` never ran — even with non-blocking `Close*`. Closing `conn` from `Start` is what unblocks that read. The comment at lines 43-46 anticipates exactly this.
- The comments (lines 43-46, 71-76) explain *why* — the tcpproxy call pattern and the FD-leak consequence — rather than restating the code.

### Important Issues
I1. **`CloseRead` breaks host-to-guest TCP half-close** — `pkg/portfwdserver/server.go:114-118` (important, gap)
```go
func (g *GRPCServerRW) CloseRead() error {
	logrus.Debugf("closing read GRPCServerRW for id: %s", g.id)
	g.closeOnce.Do(func() { close(g.closeCh) })
	return nil
}
```
The fix elegantly solves the FD leak by making `Close*` idempotent and executing `defer conn.Close()` in `Start`. However, retaining `closeOnce.Do(...)` inside `CloseRead` breaks TCP half-close from the host to the guest. 

When a host client half-closes its connection (e.g., finishes sending an HTTP request but waits for the response), the host agent sends an EOF via `stream.CloseSend()`. The guest proxy receives this, finishes the copy, and calls `rw.CloseRead()`. This immediately closes `closeCh`, unblocking `Start`. `Start` then returns and executes `defer conn.Close()`, forcefully terminating the connection to the guest service and destroying any pending response data the guest service was still generating.

A full disconnect from the host is already handled safely by gRPC context cancellation, which triggers the `ctx.Done()` goroutine to call `rw.Close()`. `CloseRead` should be a no-op regarding tunnel teardown.

### Design Observations

**Strengths**
- **Fallback Teardown:** Adding `defer conn.Close()` to `Start` is a highly effective fallback. If the gRPC context is cancelled while a proxy goroutine is indefinitely blocked on `conn.Read()` against an idle guest service, the defer forcefully closes the read socket, unblocking the goroutine and preventing the FD leak.
