## Executive Summary

This PR replaces a stale MinGit bullet in `wsl2.md` with a Windows toolchain
section. The prose is clear and the scoping is right, but most of the behavior
it describes is not on master yet. The sftp-server pairing lives in the
still-open PRs #5299 and #5300. The rewrite also drops the PATH instruction that
made the old Git for Windows advice work, and states a Windows build number
Microsoft's own docs contradict.

Three of four reviewers produced output; Gemini 3.1 Pro hit a hard quota wall
before its first tool call. Findings cluster into three groups: the docs run
ahead of the code (I1), the rewrite loses actionable guidance the old bullet
carried (I2, S6), and six factual claims disagree with the code or with
Microsoft's documentation (S1 to S5, and S7).

## Important Issues

I1. **Documented sftp-server pairing has no implementation on master** — `website/content/en/docs/config/vmtype/wsl2.md:96-98` [Claude Opus 5, Codex GPT 5.6 Sol]

```markdown
Lima detects which ssh toolchain is in use on each `limactl start` and
takes both the path form and the `sftp-server` binary from that
toolchain, so the path and the server that reads it match:
```

At the review SHA nothing implements this pairing. `sshutil.SftpServerForSSH` exists but has no caller outside its own test file, and `pkg/hostagent/mount.go:56` still converts the mount path with the PATH-global `fsutil.WindowsSubsystemPath`, never setting `OpensshSftpServerBinary`.

`pkg/copytool/copytool.go:127` does the same for absolute scp operands, so the native `C:/Users/USER` form promised at lines 104-107 never reaches scp either. The code lives in #5299 and #5300, both open.

`.github/workflows/test.yml:7-16` skips the whole workflow for `website/**`, so no CI job would catch the mismatch.

Fix: merge #5299 and #5300 first, or keep only the binary inventory here and move lines 96-111 into #5300.

I2. **Git for Windows advice lost the PATH step, so Lima will not select that toolchain** — `website/content/en/docs/config/vmtype/wsl2.md:90-94` [Claude Opus 5]

```markdown
Installing [Git for Windows](https://gitforwindows.org/)
(`winget install -e --id Git.Git`) remains supported as an alternative
to the native binaries. Use the full Git for Windows installer, not
MinGit. MinGit omits `scp.exe`, `ssh-keygen.exe`, and `cygpath.exe`,
all of which Lima needs.
```

The deleted bullet ended with "add the resulting `C:\Program Files\Git\usr\bin\` directory to your path", and nothing replaces it. The installer's default PATH option adds only `cmd\`, which holds no `scp.exe`.

`pkg/sshutil/sshutil.go:86` scans PATH for the first directory holding `ssh.exe`, `scp.exe`, and `ssh-keygen.exe`, then falls back to `%SystemRoot%\System32\OpenSSH`. A reader who installs Git for Windows and stops there silently keeps the native toolchain.

The remaining lever, `_LIMA_WINDOWS_EXTRA_PATH`, is documented at `website/content/en/docs/config/environment-variables.md:159` with exactly this directory as its example, and #5342 removes it.

Fix: restore the PATH sentence, and state the selection rule so a reader can predict which toolchain wins.

## Suggestions

S1. **"logs a warning" does not match the implementing branch's log level** — `website/content/en/docs/config/vmtype/wsl2.md:109` [Claude Opus 5, Codex GPT 5.6 Sol]

```markdown
When no matching `sftp-server` is found, the hostagent logs a warning at
start and lets `sshocker` auto-detect from `PATH`; a missing
OpenSSH.Server install on a native-only host typically shows up there.
```

On `origin/hostagent-reverse-sshfs-plain-windows` (#5300, tip 2026-07-27 00:11, newer than the integration branch) the message goes out through `logrus.Infof`, and its wording is "falling back to a generic search" rather than a PATH search. A user told to watch for a warning will not see one at the default log level.

Fix: say "logs an info message", or change #5300 to `Warnf` and keep the doc as written. Drop "from `PATH`" in favour of sshocker's own detection.

S2. **OpenSSH Server is preferred for reverse-sshfs, not required** — `website/content/en/docs/config/vmtype/wsl2.md:86` [Codex GPT 5.6 Sol, Claude Opus 5]

```markdown
  Only the QEMU driver's reverse-sshfs mounts need it. Install via
```

Lima's default `sftpDriver` is `""` (`pkg/limayaml/defaults.go:792`). Reading `sshocker@v0.3.11` from the module cache, that empty value sends `Start()` into `DetectDriver`, which returns `DriverBuiltin` when it finds no sftp-server anywhere, and sshocker then serves the mount in-process. The mount still works with OpenSSH Server absent. Setting `sftpDriver: builtin` skips the search outright.

The "only the QEMU driver" scoping is right: the WSL2 driver rejects any `mountType` other than `wsl2` (`pkg/driver/wsl2/wsl_driver_windows.go:102`), so reverse-sshfs never runs under it.

Fix: say the external server is preferred and the built-in driver takes over when none is found, and mention `sftpDriver: builtin` as the way to skip the install.

S3. **`/c/Users/USER` is the MSYS2 form, not what stock Cygwin emits** — `website/content/en/docs/config/vmtype/wsl2.md:100-103` [Codex GPT 5.6 Sol, Claude Opus 5]

```markdown
- **Cygwin-based ssh** (Git for Windows, MSYS2): paths are converted by
  `cygpath` to a POSIX form like `/c/Users/USER`, respecting any custom
  MSYS2 fstab the user has configured. `sftp-server` is resolved from
  the same toolchain.
```

The bullet is headed "Cygwin-based" but gives only the MSYS2 form. Stock Cygwin maps `C:\` to `/cygdrive/c/`, and `cygpathForSSH` accepts it just as readily, since it only looks for a `cygpath.exe` next to `ssh.exe`. Line 114 repeats the same loose "Cygwin's `/c/...`".

Fix: "a POSIX form, `/c/Users/USER` under MSYS2 and Git for Windows, `/cygdrive/c/Users/USER` under stock Cygwin".

S4. **The fstab caveat pins the hazard to create-then-start, but nothing is frozen at create** — `website/content/en/docs/config/vmtype/wsl2.md:115-116` [Claude Opus 5]

```markdown
on disk. On such a host, do not swap toolchains between `limactl create`
and `limactl start` on a QEMU instance with a reverse-sshfs mount,
```

`pkg/instance/create.go:78` writes the raw config bytes it was handed; the filled config goes to a separate variable and is never persisted. So the mount point is re-derived on every load, and `pkg/hostagent/mount.go:56` re-converts the host path on every start.

The divergence therefore recurs between any two starts whose cygpath differs. A user who only avoids swapping across create-then-start is still exposed.

Fix: reword to "do not change ssh toolchains between starts of an existing instance".

S5. **"build 1803" contradicts Microsoft's docs and the page's own requirement** — `website/content/en/docs/config/vmtype/wsl2.md:83-84` [Claude Opus 5, orchestrator]

```markdown
- **OpenSSH Client** (`ssh.exe`, `scp.exe`, `ssh-keygen.exe`) ships by default
  on Windows 10 build 1803 and later, and covers the WSL2 driver.
```

Microsoft's OpenSSH overview says "Beginning with Windows 10 build 1809 and Windows Server 2019, OpenSSH is available as a feature on demand", and its table row reads "Windows 10 build 1809 + | Not installed, install and enable using optional features". The page linked at line 85 is the Server quickstart, whose prerequisites also say 1809; neither supports 1803.

The "ships by default" half holds for the client on Windows 10 and 11, and #5342's runner action assumes it. But the page's own requirement table at line 9 already demands build 19041 or Windows 11, so the build number tells this audience nothing.

Fix: drop the build number and say "ships by default on Windows 10 and Windows 11".

S6. **The deleted bullet also covered decompressors, and nothing replaces that** — `website/content/en/docs/config/vmtype/wsl2.md:44` [Claude Opus 5, orchestrator]

```markdown
- WSL2 requires a `tar` formatted rootfs archive instead of a VM image. Standard VM disk images (like `.qcow2`, `.raw`, etc.) or `.squashfs` images cannot be natively imported by WSL2.
```

The removed line read "Windows doesn't ship with ssh.exe, gzip.exe, etc." Commit `1cce8dc0` gave gzip a pure-Go fallback, so that half is genuinely obsolete, but the same comment at `pkg/downloader/downloader.go:761` says "xz, bzip2, and zstd stay external-only" and the code returns "decompressor %q not found and no built-in fallback".

The WSL2 driver's own error message advertises `.tar.xz` as acceptable (`pkg/driver/wsl2/wsl_driver_windows.go:143`), so a user can pick a rootfs that fails on a plain Windows host with no hint from these docs.

Fix: add a bullet saying `.tar.gz` decompresses in-process while `.xz`, `.bz2`, and `.zst` need the matching binary on PATH.

S7. **`sftp-server.exe` comes from the same directory as `ssh.exe`, not a sibling directory** — `website/content/en/docs/config/vmtype/wsl2.md:106-107` [orchestrator]

```markdown
  this form directly. `sftp-server.exe` is picked from the sibling
  directory of `ssh.exe`.
```

`SftpServerForSSH` builds the candidate as `filepath.Join(filepath.Dir(path), "sftp-server.exe")`, so it looks in `ssh.exe`'s own directory. "Sibling directory" names a different place. The Cygwin branch above genuinely does cross directories, since `cygpath -w /usr/lib/ssh/sftp-server` leaves `usr/bin`, which may be where the phrasing came from.

Fix: "picked from the same directory as `ssh.exe`".

S8. **Host-wide toolchain requirements sit on the WSL2 vmType page** — `website/content/en/docs/config/vmtype/wsl2.md:78` [Gemini 3.5 Flash, Claude Opus 5]

The section covers the QEMU driver's reverse-sshfs needs at lines 85-88 and 113-118, which a QEMU-on-Windows reader has no reason to look for under Config, VM types, WSL2. `website/content/en/docs/installation/_index.md:5-13` already lists supported hosts and the QEMU prerequisite.

Fix: move the toolchain section under `docs/installation/` or a new `docs/config/windows.md`, and leave a one-line pointer in `wsl2.md` and `qemu.md`.

S9. **The `SSH` environment variable overrides everything the section describes** — `website/content/en/docs/config/vmtype/wsl2.md:96` [Claude Opus 5]

`NewSSHExe` reads `SSH` first and returns early (`pkg/sshutil/sshutil.go:50-62`), so a user who sets it never reaches the detection this section documents. `SSH` has no entry in `website/content/en/docs/config/environment-variables.md` either, which leaves a user with both toolchains installed no documented way to pin one.

Fix: mention the override here, and add an `SSH` entry to the environment-variables page.

## Review Process Notes

### Skill improvements

- When the diff is documentation that describes runtime behavior, check each behavioral claim against the code at the review SHA, not only against the branch the author developed it on. Documentation sites usually publish from the default branch, so a docs change that merges ahead of its implementation ships instructions that do nothing. Report any claim whose implementing code is not yet merged, and name the PR or branch that carries it.

- When a change rewrites or replaces existing prose, diff the removed text against the added text claim by claim, and flag guidance the removal drops. A replacement that is accurate about its own subject can still delete the one sentence that made the surrounding advice actionable, and a reviewer reading only the added lines will not notice.

- When documentation describes a detection or selection mechanism, look for overrides that bypass it: an environment variable, a config field, or a flag whose handler returns before the described logic runs. Check that the override is documented somewhere the reader will find it. A mechanism described as automatic reads as exhaustive.

- When a change cites an external source to support a factual claim, open the cited page and confirm it states what the text says it states. Cited sources drift, and a link lends a claim authority the source may not actually give it.

### Repo context updates

- [repo] The website publishes from the default branch, and `.github/workflows/test.yml` skips the whole workflow for `website/**`. Nothing ties a documentation claim to the code implementing it, so a docs PR describing runtime behavior can merge well before that behavior exists. Treat any behavioral claim in a `website/` diff as needing verification against the code at the review SHA.

- [repo] The repo's only hyperlink check is a lychee step in the quick-lints workflow, and it passes `README.md` alone. That workflow runs on every PR including docs-only ones, so its green tick says nothing about links added under `website/` or `docs/`. Verify new external links by hand during review.

- [repo] Lima leaves `sftpDriver` empty by default, and the pinned `sshocker` falls back to its own in-process SFTP server when it finds no `sftp-server` binary. Reverse-sshfs mounts therefore keep working with no external SFTP server installed. Treat any claim that an external `sftp-server` is required for mounts as wrong; it is preferred, not required.

- [repo] `pkg/downloader` decompresses `.gz` in-process when no external `gzip` exists, but `xz`, `bzip2`, and `zstd` stay external-only and fail with "no built-in fallback". On a host that ships none of them, only `.gz` images work. Weigh guidance about host decompressor requirements against this split rather than against a blanket "Lima needs external decompressors".
