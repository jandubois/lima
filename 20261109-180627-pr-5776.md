## Executive Summary

The PR adds `--allow-env` and `--block-env` to `limactl shell`. Each flag appends patterns, for one command, to the `LIMA_SHELLENV_*` lists (or to the default block list) and turns on `--preserve-env`, which is what #4263 and the #4483 review asked for. Two things need fixing: the environment-variables page still says nothing propagates without `--preserve-env`, and no test fails when the `--allow-env` pattern check is deleted. The four suggestions are small.

## Suggestions

S1. **Flag patterns keep the spaces and empty entries that the env vars drop** — `cmd/limactl/shell.go:373-377` [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	allowEnv, err := cmd.Flags().GetStringSlice("allow-env")
	if err != nil {
		return err
	}
	if err := envutil.ValidatePatterns(allowEnv); err != nil {
```

`parseEnvList` trims each entry and drops empty ones, and `hack/bats/tests/preserve-env.bats:89-118` asserts that for both env vars. pflag's CSV parsing does neither. So `--block-env "FOO, BAR"` yields `" BAR"` and fails with ``pattern ` BAR` contains invalid character ` ` at position 0``, while `LIMA_SHELLENV_BLOCK="FOO, BAR"` works. And `--block-env "FOO,,BAR"` keeps an empty pattern, which validation accepts. The error names the space, so nobody is misled, but the per-command form of a variable should accept the variable's syntax.

Fix: run the flag values through `parseEnvList` before validating them. A helper like this one passed a scratch test for trimming, dropping empty entries and rejecting `FOO-BAR`; `shell.go` would call it for both flags.

```go
// ParsePatterns trims the patterns and drops empty ones, like the env var lists.
func ParsePatterns(patterns []string) ([]string, error) {
	patterns = parseEnvList(strings.Join(patterns, ","))
	return patterns, ValidatePatterns(patterns)
}
```

S2. **A bad pattern is rejected only after `--start` boots the VM or `--reconnect` drops the SSH master** — `cmd/limactl/shell.go:384` [Claude Opus 5.5, Gemini 3.5 Flash]

```go
	if err := envutil.ValidatePatterns(blockEnv); err != nil {
		return fmt.Errorf("invalid --block-env pattern: %w", err)
	}
```

`shellAction` reads and validates both flags just before it builds the env prefix, after `instance.Start` (line 178) and `ssh.ExitMaster` (line 202). So, going by the code order, `limactl shell --start --block-env FOO-BAR inst` boots a stopped instance and only then fails. On a vz instance built from the review SHA, `limactl shell --reconnect --block-env FOO-BAR` logged "Exiting ssh session for the instance" before the "invalid --block-env pattern" error. Bad `LIMA_SHELLENV_*` values fail later still (`logrus.Fatalf` at `pkg/envutil/envutil.go:72` and `:97`), but a command-line flag can be checked before anything happens.

Fix: move the two reads, the validation and the `preserveEnv` implication above `store.Inspect` at line 135.

S3. **An empty flag value does not turn on `--preserve-env`** — `cmd/limactl/shell.go:387` [Codex GPT 6 Astra, Gemini 3.1 Pro]

```go
	if len(allowEnv) > 0 || len(blockEnv) > 0 {
		preserveEnv = true
	}
```

The help says either flag implies `--preserve-env`, but `--allow-env ""` parses to an empty slice and leaves propagation off. A script that passes `--allow-env "$EXTRA"` therefore propagates the environment or not depending on whether `EXTRA` is empty.

Fix: check `flags.Changed("allow-env") || flags.Changed("block-env")` to match the help, or keep the length check and say in the help that an empty value does nothing. Decide it together with S1, which turns `","` into the same empty list that `""` gives today.

S4. **`getAllowList`'s empty-variable branch repeats the general path** — `pkg/envutil/envutil.go:86` [Claude Opus 5.5]

```go
	if allowEnv == "" {
		if len(extra) == 0 {
			return nil
		}
		return slices.Clone(extra)
	}
```

With `LIMA_SHELLENV_ALLOW` empty, `parseEnvList` returns an empty slice, and `slices.Concat(patterns, extra)` at line 101 returns nil when `extra` is empty and a copy of `extra` otherwise. That is what this branch returns. With lines 86-91 deleted, `go test ./pkg/envutil/` still passes and `getAllowList(nil)` still returns nil.

Fix: delete lines 86-91.

## Design Observations

### Concerns

- **`--allow-env` exempts a variable from the block list; it does not limit what propagates** (in-scope) [Claude Opus 5.5]. The flag implies `--preserve-env`, so `limactl shell --allow-env GITHUB_TOKEN default gh` forwards every unblocked host variable. `GITHUB_TOKEN` is not on the default block list, so in #4263's own example the flag adds nothing beyond `--preserve-env`. That is the specified behavior, and the flag text is the one suggested on #4483. Still, "patterns to allow" in the flag help (`cmd/limactl/shell.go:81`) invites the reading "only these", while the long help at line 53 says "exempt". The `--block-env '*' --allow-env NAME` example in I1's patch shows how to forward one variable alone.
- **Windows guests ignore both flags** (future) [Claude Opus 5.5]. `cmd/limactl/shell.go:403-406` replaces the script with `windowsQuoteShell(shell)` and drops `envPrefix`, as it already did for `--preserve-env` before this PR.

### Strengths

- The extra patterns reach `FilterEnvironment` as arguments, so the process environment is never modified and the patterns apply to one command only. [Codex GPT 6 Astra]
- `getBlockList` now returns a fresh slice from `slices.Concat`, so no caller can alias `defaultBlockList`. [Claude Opus 5.5, Gemini 3.5 Flash]
- Invalid flag patterns come back as returned errors that name the flag, while invalid env var patterns still exit through `logrus.Fatalf`. [Claude Opus 5.5, Gemini 3.5 Flash]
- The PR makes every change that the #4483 review asked for (`StringSlice` flags, appending to the lists and to the default block list when `LIMA_SHELLENV_BLOCK` is empty, the implied `--preserve-env`, the "to block" wording, and tests). [Claude Opus 5.5, Codex GPT 6 Astra, Gemini 3.1 Pro, Gemini 3.5 Flash]
