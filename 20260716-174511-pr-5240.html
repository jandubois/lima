## Symbolic links

Lima will check if the template file referenced by the `github:` URL is a symlink (or a text file whose content has no spaces, newlines, or colons). In that case it will treat the content as a relative path and return the address of that target file.

For example the `fedora` template is a symlink to `fedora-43.yaml`:

```console
❯ limactl tmpl url github:lima-vm/lima/templates/fedora

The page promises a relative path and stops there. A user who trips the new error has no documentation describing the rule. This section is where the PR's security property belongs.

Fix: state that the target must stay within the repository, and that a target climbing above the repo root is rejected. Line 100 makes the stronger claim that a redirect "must point to the same GitHub org" — I1 shows the code does not enforce it, so fix the code rather than soften the doc.

S2. Absolute symlink targets resolve as repo-relative Claude Gemini¶
pkg/limatmpl/github.go

// symlinkTarget resolves a symlink target relative to the directory of filePath.
// It returns an error if the target escapes the repository root, so a symlink
// cannot redirect the fetch to a different repository via `../` segments.
func symlinkTarget(filePath, target string) (string, error) {
	resolved := path.Join(path.Dir(filePath), target)
	if resolved == ".." || strings.HasPrefix(resolved, "../") {
		return "", fmt.Errorf("symlink target %#q in %#q escapes the repository", target, filePath)
	}
	return resolved, nil
}

path.Join drops the leading slash, so symlinkTarget("dir/config.yaml", "/etc/passwd") returns dir/etc/passwd without error. The result stays inside the repo, so nothing is exploitable, and the behavior predates this PR.

The two agents that raised it disagree on the remedy: reject an absolute target as a hard error, or keep the behavior and pin it with a test. Assessment — rejecting changes behavior beyond the PR's scope, and the doc already calls targets relative. A test documenting the current resolution is the proportionate option, and neither is a merge blocker.

Design Observations ¶

Concerns

  • Containment guards one of the three places filePath is set (in-scope) Claude. filePath reaches githubUserContentURL from user input (github.go:42), redirect re-entry through the TransformCustomURL loop (locator.go:401), and symlink resolution (github.go:172). Only the third is guarded, which is exactly how I1 survives. Asserting the invariant once at the parse boundary covers all three and forecloses the class rather than this instance.
  • The URL builder trusts every component it interpolates (future) Codex. githubUserContentURL formats org, repo, branch, and filePath straight into a URL with no escaping or segment validation. Today the server's own normalization contains the encoded variants, so this is latent rather than live — but it is why a single unguarded producer becomes an escape.

Strengths

  • The check sits after path.Join, not before (in-scope) Claude. Testing the cleaned result rather than pattern-matching .. in the raw target avoids both classic errors: rejecting a legitimate ..foo.yaml and missing a/../../b. Because path.Clean leaves surviving .. only at the front, the ..-or-../-prefix test is complete.
  • path, not filepath (in-scope) Claude. These are URL paths. filepath would treat \ as a separator on Windows and make containment host-OS-dependent.
  • Encoded traversal is genuinely covered, not merely missed (in-scope) Claude. path.Clean does not decode percent-escapes and Go preserves them on the wire, which reads as a bypass on paper. It is not one — see the Reconciliation note.

The syntactic check therefore matches the server's grammar exactly. Claude reached the same conclusion independently.

Review Process Notes ¶

Skill improvements ¶

  • When a finding's evidence is an observed behavior — an HTTP status, an exit code, a log line — confirm the observation demonstrates the consequence you claim rather than a precondition of it. A probe showing that a system decodes, parses, or accepts hostile input proves only that much; it does not prove the input crosses a trust boundary. Name the boundary in the finding and test an input that crosses it. If the crossing test does not reproduce, there is no finding. Systems routinely contain hostile input at a layer the probe never reached, so the gap between "it parsed my input" and "it acted on my input" is where false positives live.
  • When a change adds a containment or validation check and its rationale credits an adjacent code path with already enforcing the same property, test that credit against the adjacent path before accepting it. A reviewer inherits the author's framing, and an unexamined premise in the rationale is where the remaining instance of the bug class usually survives. Where sibling paths enforce one property by different mechanisms — a prefix or substring test in one, a canonicalizing check in the other — treat the weaker mechanism as the finding.

Repo context updates ¶

  • [repo] github: template locators build raw.githubusercontent.com URLs by interpolating org, repo, branch, and path into a format string with no escaping. raw.githubusercontent.com normalizes literal ../ before routing and answers with a 307 to the collapsed path, so a ../ climbing above the repo root reaches an unrelated repository. It does not treat percent-encoded traversal (%2e%2e, ..%2f) as a routing separator: those requests reach the original repo and 404. Containment checks on these paths need only reject literal .. segments. Treat a claim that percent-encoding defeats such a check as a false positive unless it comes with a request that demonstrably leaves the repository.
  • [repo] TransformCustomURL re-feeds each transformed locator through the transform loop until it stops changing, so any github: URL a resolver returns is re-parsed from scratch. Validation applied to one producer of the path does not bind the others, and the loop's re-entry point is the choke point that does.
