Executive Summary ¶

This round fixes round 2's four Importants. The response now reaches the client after a failed send, near-limit host sockets bind, the template comment matches the code, and a test pins the forwarder choice. But on a Linux host, piped docker run -i and exec -i often exit 1 through the gRPC forwarder, because the proxy closes the connection with the client's input unread. Reading that input until the client closes fixes it, as 901cd02e now does.

When the send to the tunnel fails, this goroutine stops reading the host connection, and handleUnixConnection then closes it while the client's latest input is still unread. Linux and Windows report that close as a reset, where a direct connection or the merge-base's SSH forward gives EOF. Acknowledged Limitations ¶

  • The in-place fallback exposes the socket until its chmod (pkg/portfwd/listener.go:274-281). Between bind and chmod the socket has the umask's mode, and a connection made in that gap stays open after the chmod. Only a hostSocket basename of 1 to 3 bytes at the length limit takes this path. At 103 bytes on macOS, s, ds and abc bind in place, and abcd gets a staging directory. Another user can connect in the gap only when the umask grants group or other write access and the parent directory lets that user through. Round 2 proposed this fallback with that trade-off, and the threat model rates a hardening gap without a demonstrated exploit as low. Do not re-suggest closing it unless such paths become realistic; closing it needs a private staging directory on a shorter path on the same filesystem.
  • A guest half-close ends the whole tunnel (pkg/portfwdserver/server.go:126-133), as in round 2. A client still sending when the tunnel ends sees I1's reset, and I1's patch keeps reading that input, so the client gets EOF.
  • A connection whose guest end never answers and never closes keeps its tunnel and both copy goroutines, as in round 2. tcpproxy behaves the same on the TCP path, so do not re-suggest tcpproxy as a fix for it. A failed host read half-closes the tunnel rather than aborting, which round 2 also accepted. With I1's patch, the host-to-guest goroutine also waits for the client to close after a failed send, as it already did while blocked on a read.
  • Round 1's suggestions, unaddressed and undeclined through rounds 1, 2 and 3:
  • forwardUnix repeats forwardTCP's accept loop, and no test covers the pseudoloopback continue.
  • Remove still lists "tcp6" (pkg/portfwd/listener.go:82).
  • Two tests log an error on every run, and the dedup tests hang or pass when dedup breaks.
  • A Unix listen failure is logged twice, and the gRPC socket forward is never logged at Info.
  • The website still describes the forwarder choice only in terms of ports.

Review Process Notes ¶

Skill improvements ¶

  • Before consolidating a PR review, compare the PR's current head with the reviewed SHA. When the author pushed during the review, diff each new head against the reviewed tree, judge every finding against it, and read CI on each new head, including a re-push of the same tree, whose jobs rerun flaky tests on other runners.
  • When a test fails on some platforms only, decide whether its expectation or the code is wrong by running the code's real client on a platform where the test fails and comparing it with the path that the change replaced. Relax the assertion only when that client behaves the same both ways.

Repo context updates ¶

  • [repo] When a host-side Unix socket closes while it still holds unread input from the client, Linux and Windows report a reset to the client, and macOS reports EOF. So a forwarder that closes this way looks fine on a macOS host but can make piped docker run -i exit 1 on a Linux host. It must keep reading the client's input until the client closes. Go's syscall.ECONNRESET does not match Windows' WSAECONNRESET, so a test that accepts it hides the bug on Linux and still fails the WSL2 unit-test job.
