## Important Issues

I1. **Local path is formatted for ssh but consumed by rsync** — `pkg/copytool/copytool.go:148-152` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
				path, err = sshutil.PathForSSH(ctx, sshExe, path)
				if err != nil {
					return nil, err
				}
				cp.Path = path
```

`parseCopyPaths` feeds both backends but formats for `sshExe` alone. With native OpenSSH selected, `PathForSSH` returns `C:/foo`, and `rsyncTool.Command` appends it verbatim (`pkg/copytool/rsync.go:189`). Measured here: `rsync -n C:/foo C:/bar` gives `both source and destination cannot be remote files`, while `/c/foo` reaches `stat` (openrsync, "rsync 2.6.9 compatible", darwin). Windows has no native rsync, so the colon always triggers hostspec parsing.

The initial `limactl shell --sync` transfer escapes this: shell.go pre-converts `hostCurrentDir` to `/c/…`, which `filepath.IsAbs` rejects on Windows. The diff view does not, because `hostTmpDest` (`cmd/limactl/shell.go:581`) is a native temp path handed straight to rsync.

Round 1 called this a regression. At the merge-base, `SSHOpts` already gave native ssh `ControlMaster=auto` plus a ControlPath it cannot use (`pkg/sshutil/sshutil.go:591`), so rsync failed on those hosts too. This change replaces one blocker with another.

Fix: keep `Path.Path` native and convert per backend, `PathForSSH` in `scp.go` and the rsync toolchain's own `cygpath` in `rsync.go`.

**Resolved:** fixed in `20d168aa`. `parseCopyPaths` keeps the native path, `scp.go` converts with `PathForSSH`, and `rsync.go` converts through the cygpath beside its own `rsync.exe`.

I2. **`scp` is resolved from PATH independently of the selected ssh** — `pkg/copytool/scp.go:26` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	path, err := exec.LookPath("scp")
```

The local-path format is now a function of the `sshExe` that `NewSSHExe` picks, while the binary consuming it comes from a bare PATH lookup. `$SSH` returns early with no sibling check, and `pickCompleteSSHOnWindows` can fall back to `%SystemRoot%\System32\OpenSSH`, off PATH entirely. Codex demonstrated the split with `$SSH` pointing outside PATH while `scp` resolved to `/usr/bin/scp`.

The default case stays consistent because `pickCompleteSSHOnWindows` requires `scp.exe` beside the `ssh.exe` it selects and walks PATH in `LookPath` order, which is why this is Important and not Critical. Gemini 3.1 Pro again filed it Critical; that overstates the reach.

`exec.LookPath("scp")` predates this PR, so this is a gap the change made load-bearing, not a regression.

Fix: export `companionForSSH` (`pkg/sshutil/sshutil.go:176`, already used for `ssh-keygen` at `:320`) and resolve scp from the selected toolchain.

**Resolved:** fixed in `20d168aa`. `CompanionForSSH` is exported, and `scpTool` stores the ssh it resolved scp from, which also drives the path form and the version probe.

I3. **The new Warn cannot fire on the default `auto` backend** — `pkg/copytool/rsync.go:40-42` [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
		// Warn, not Debug: New()'s fallback then reports "scp not found on
		// host", masking the real cause, often a missing ssh.exe on Windows.
		logrus.Warnf("rsync availability check skipped: %v", err)
```

The comment names the exact failure this line exists to expose, and `limactl copy` defaults to `auto`. On that path `New` calls `hasRemoteSourceAndDestination` first, which runs the same `parseCopyPaths`, discards the identical error, and returns `true` (`pkg/copytool/copytool.go:100-103`). `true` means "both ends remote", so `New` skips the whole rsync branch, including `IsAvailableOnGuest` and this Warn, and reaches `newSCPTool`, which emits the very message the comment set out to avoid. The Warn fires only under an explicit `--backend rsync`.

Codex filed this as a suggestion, arguing the failure is loud even when misdescribed. The line still cannot do the job its own comment claims, on the only backend most users invoke, so Important is the right severity.

Fix: report the parse error where it is swallowed, in `hasRemoteSourceAndDestination` or in `New`.

**Resolved:** fixed in `1775db7b` on a separate branch, so it is absent from this PR's diff. `hasRemoteSourceAndDestination` returns its parse error and `New` reports it; the unreachable `Warn` was never introduced.

The strip at lines 125-129 removes exactly the options this comment says are kept, so on Windows the single-instance branch re-authenticates like the multi-host branch. Confirmed that the strip is a no-op in the `else` branch: `CommonOpts` never adds the mux triple.

S5. **`ensureSSHExe` caches the cheap half of the per-path cost** — `pkg/copytool/copytool.go:129-135` [Claude Opus 5, Gemini 3.5 Flash] (round 1 S5 unaddressed)

```go
	ensureSSHExe := func() (sshutil.SSHExe, error) {
		if !sshExeLoaded {
			sshExe, sshExeErr = sshutil.NewSSHExe()
			sshExeLoaded = true
		}
		return sshExe, sshExeErr
	}
```

Codex defends the closure: it does what its comment says, collapsing `NewSSHExe` to one call when a single parse sees several absolute paths. That is correct, and it is also the smaller cost. A single `limactl copy` calls `parseCopyPaths` three times and `NewSSHExe` four more times unconditionally (`rsync.go:64`, `:130`; `scp.go:72`, `:105`), while the `cygpath` subprocess inside `PathForSSH` runs once per absolute path per call and is never cached; only the Cygwin detection is (`pkg/sshutil/sshutil.go:205-220`).

Fix: memoize in `sshutil` beside `cygwinDetectCache`, or let I1's restructure delete the closure outright.

**Resolved:** fixed in `20d168aa`. I1's restructure deleted the closure; the residual `NewSSHExe` and `cygpath` cost is deliberately left alone.

S6. **`SSHOpts` computes, and can fail on, a `ControlPath` the caller strips two lines later** — `pkg/copytool/scp.go:109` [Claude Opus 5]

```go
			sshOpts, err = sshutil.SSHOpts(ctx, sshExe, inst.Dir, *inst.Config.User.Name, false, false, false, false)
```

All three Windows copy paths (`scp.go:109`, `rsync.go:69`, `rsync.go:134`) build the mux options and then discard them. On Windows `SSHOpts` first rejects a socket path at or above `UnixPathMax`, 108 (`pkg/sshutil/sshutil.go:582-584`, `pkg/osutil/osutil_windows.go:18`), then spawns `cygpath` to convert it (`:591`). So a long `$LIMA_HOME` plus a long instance name fails `limactl copy` with "socket path … is too long" for a control socket the command never opens, and every copy pays a subprocess for a discarded value.

Fix: add a `sshutil` helper composing `CommonOpts` plus `User=` without the mux triple, and call it from the three Windows branches instead of building and stripping.

**Resolved:** fixed in `20d168aa` as `sshutil.SSHOptsWithoutMultiplexing`, which the scp path, the rsync probe, and the rsync command all reach through one `copytool` helper.

S7. **Debug line announces a strip that can remove nothing** — `pkg/copytool/scp.go:128` [Claude Opus 5]

```go
		logrus.Debug("scp: stripping ControlMaster/ControlPath/ControlPersist (Windows)")
```

The strip sits after both branches, so on the multi-instance path it logs a strip against `CommonOpts` output that never held those options. The resulting argv is already visible through `logrus.Debugf` in `cmd/limactl/copy.go`.

Fix: drop the line, or move the strip into the `len(instances) == 1` branch where it can act, which also settles S4.

**Resolved:** fixed in `20d168aa`. Both Debug lines are gone, and the mux-free helper replaced the strip they described.

## Design Observations

### Concerns

- **`Path.Path` conflates what the user typed with what one tool wants** *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]. After `copytool.go:152` the native host path is unrecoverable, so a second consumer with different rules has no correct value to read. This is the structural cause of I1 and it will recur for any future backend. Round 1 raised the same concern; all four reviewers reached it independently again, which is the strongest signal in this round. Storing the native path and adding one formatter per backend puts each conversion beside the `exec.Command` that consumes it.

- **Windows mux stripping is now five copy-pasted sites with three different justifications** *(future)* [Claude Opus 5, Codex GPT 5.6 Sol]. `cmd/limactl/shell.go:390`, `pkg/hostagent/hostagent.go:317`, `pkg/copytool/scp.go:129`, `pkg/copytool/rsync.go:77` and `:142`, plus three `DisableControlMasterOptsFromSSHArgs` sites in `pkg/hostagent/requirements.go:148`, `:181` and `pkg/hostagent/mount.go:87`. The stated reasons range over "Cygwin does not support multiplexing when executing commands", "Cygwin ssh's mux is unreliable for sftp", and "native Windows OpenSSH has no multiplexing", which are three claims about two toolchains. One `sshutil` entry point would hold the rationale once and could gate on `cygpathForSSH`, the distinction this PR already detects, rather than on `runtime.GOOS`.

### Strengths

- The `continue` short-circuit at `copytool.go:152-155` is the right call [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro]. Once `PathForSSH` can return a colon-bearing `C:/foo`, falling through to `strings.SplitN(path, ":", 2)` would re-misclassify it as instance `C`. Round 1 credited this and it still holds; `filepath.IsAbs` rejecting drive-relative `C:foo` is what keeps single-letter instance names working.

- Applying the same strip to the probe (`rsync.go:74-78`) as to the command it predicts is a correctness fix [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]. A probe with different options answers a different question, and the comment's stated failure mode, falsely rejecting a working rsync, is real.

- Binding conversion to the selected toolchain rather than to PATH is the correct principle [Claude Opus 5]. I1 asks only that rsync get the same treatment.

## Review Process Notes

### Skill improvements

- Before accepting a "regression" label, name a configuration in which the merge-base produced a working outcome and the change breaks it. A diff that replaces one failure mode with another on the same hosts is a gap, not a regression, even though the cited lines did change. Check the other inputs the same code path receives (options, environment variables, sibling arguments) for one that already failed under the affected configuration, because a reviewer reading only the changed lines sees the new failure and assumes the old path worked.

- When judging how a formatting or conversion defect reaches users, inspect each caller for a pre-conversion of the same value. A caller that already normalizes its argument escapes the defect entirely, so naming it as an affected path overstates the reach; a caller that mixes normalized and raw values inside one invocation is the real reproducer. Enumerate the arguments individually rather than treating the call site as uniform.

- When a change makes a comment stale, grep the repo for a distinctive clause from that comment before proposing the fix. Comments that enumerate where a policy applies get copy-pasted alongside the code they describe, so a fix that touches one copy leaves the others asserting the same false claim.

- On a round after the first, treat the prior round's retro as claims to re-verify, not as settled findings. A retro that rejected a proposed fix, or credited one, rests on a helper's behavior that the retro may have read wrong, and the judgment carries forward unchallenged because it sits outside the findings list. Read the helper the fix calls before repeating either verdict.

### Repo context updates

- [repo] UPDATE the "Windows SSH toolchains" entry: it names `pkg/ioutilx.WindowsSubsystemPath` as the path-translation helper and lists `SSHOpts` and `pkg/copytool` among the call sites that still use a PATH-global converter. The helper lives in `pkg/fsutil` (`pkg/ioutilx` exports only `ReadAtMaximum`), and both named call sites now convert through the toolchain-aware `sshutil.PathForSSH`. The remaining PATH-global callers are `pkg/hostagent/mount.go`, `pkg/limayaml/defaults.go`, and `cmd/limactl/shell.go`'s `mountDirFromWindowsDir`.

- [repo] `fsutil.WindowsSubsystemPathWithCygpath` falls back to an in-process `/c/...` conversion when the cygpath binary is absent, and returns an error only when cygpath runs and fails, or when the input is not an absolute drive-letter path (UNC, device, extended-length, drive-relative). - [repo] `sshutil.SSHOpts` always builds the `ControlMaster`/`ControlPath`/`ControlPersist` triple and, on Windows, both validates the control socket against `osutil.UnixPathMax` and spawns cygpath to convert it. Flag a build-then-strip pattern on Windows and prefer composing `CommonOpts` without the triple.

- [repo] `cmd/limactl/shell.go` hands `pkg/copytool` a mix of path forms on Windows: `mountDirFromWindowsDir` pre-converts the synced host directory to the MSYS form, while the temporary directory it creates for the sync-back diff view stays a native drive-letter path. A defect in copytool's Windows absolute-path branch therefore reaches `limactl shell --sync` only through the native argument. When judging the reach of such a defect, check each argument the caller passes rather than the call site as a whole.
