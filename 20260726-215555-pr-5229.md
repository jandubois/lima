## Executive Summary

The design is sound. Every resume is gated on an expected digest, and the per-URL directory lock makes the stable `data.part` safe. But the status-code switch derives its state from the response alone, and that costs two remote-triggerable defects. A 416 answered to a range-less request recurses until the stack overflows. An unsolicited 206 appends to a stale partial and caches the result unverified. I reproduced both.

All four reviewers found C1 independently. C2, and the mutation proof behind I5, came from one reviewer each and I confirmed both by running them. The remaining important findings all concern validator handling, where a weak ETag silently disables the feature and a missing validator lets two representations splice. `go test`, `go test -race`, `go vet`, `gofmt`, and `golangci-lint` are all clean at the review SHA.

## Critical Issues

C1. **416 restart has no base case, so the process crashes** — `pkg/downloader/downloader.go:1114-1116` [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro, Gemini 3.5 Flash]

```go
	case resp.StatusCode == http.StatusRequestedRangeNotSatisfiable:
		resp.Body.Close()
		return finalizeOrRestartPartial(ctx, t, partial, offset, url, description, expectedDigest)
```

The branch keys on the response alone. `finalizeOrRestartPartial` removes the partial and re-enters `downloadHTTP`, so the next request carries no `Range` header, but a server that answers 416 anyway re-enters the same branch forever.

I ran this against a handler that always returns 416. The process died with `fatal error: stack overflow` after exceeding the 1 GB goroutine stack limit, with `downloadHTTP` and `finalizeOrRestartPartial` alternating down the whole trace (`pkg/downloader/downloader.go:1078` is the recursive call). Before this change a 416 returned a clean `HTTPStatusError` from `httpclientutil.Get`.

Fix: enter the branch only when a `Range` header was actually sent, letting the rest fall through to `default:` at line 1123.

```diff
-	case resp.StatusCode == http.StatusRequestedRangeNotSatisfiable:
+	case resp.StatusCode == http.StatusRequestedRangeNotSatisfiable && offset > 0:
```

C2. **An unsolicited 206 caches a corrupt file with no error** — `pkg/downloader/downloader.go:1111-1113` [Claude Opus 5]

```go
	case resp.StatusCode == http.StatusPartialContent:
		logrus.Debugf("server returned 206 Partial Content; resuming %#q from offset %d", url, offset)
		resuming = true
```

`resuming` comes from the status code, never from `offset`. On a digest-less target `resumeOffset` returns 0 and no `Range` goes out, yet a 206 still sets `resuming`, so `openPartialFile` takes the `O_APPEND` branch over a stale `data.part`. The digester is nil, `verifyDownloadedDigest` is a no-op, and the concatenation is renamed to `data`.

I reproduced it. With `data.part` holding `STALE-JUNK` and the server returning `FRESH-BODY` as a 206, the cached `data` came out as `STALE-JUNKFRESH-BODY`, and `Download` returned `StatusDownloaded` with a nil error. The corrupt entry then persists until someone prunes it.

Fix: derive the state from the request, and reject a 206 whose `Content-Range` does not start at `offset`.

```diff
-		resuming = true
+		resuming = offset > 0
```

## Important Issues

I1. **A weak ETag silently disables resume** — `pkg/downloader/downloader.go:911` [Codex GPT 5.6 Sol, Claude Opus 5]

```go
	if etag := readFile(etagPath); etag != "" {
		return etag
	}
	return readFile(timePath)
```

RFC 9110 §13.1.5 forbids a client from sending a weak entity tag in `If-Range`, and servers compare strongly. Preferring a cached `W/`-prefixed tag over a usable `Last-Modified` therefore turns every resume into a full re-download.

I confirmed the behavior against `http.ServeContent`. With `W/"abc123"` the server answered 200; with `"abc123"` it answered 206. The feature goes quietly inert on any host that emits weak tags, which compressing CDNs commonly do.

Fix: skip a weak tag and fall through to `Last-Modified`.

```diff
-	if etag := readFile(etagPath); etag != "" {
+	if etag := readFile(etagPath); etag != "" && !strings.HasPrefix(etag, "W/") {
```

I2. **`Range` goes out even when no validator exists** — `pkg/downloader/downloader.go:945-950` [Codex GPT 5.6 Sol]

```go
	if offset > 0 {
		req.Header.Set("Range", fmt.Sprintf("bytes=%d-", offset))
		if ir := ifRangeValidator(t.etagPath, t.timePath); ir != "" {
			req.Header.Set("If-Range", ir)
		}
	}
```

When neither validator is cached the request still asks for a range, so a server that changed the resource splices the new tail onto the old partial. I seeded a partial with no `time` and no `etag` file and watched the request go out as `Range: bytes=12-` with `If-Range: ""`.

The digest catches the result, so the cost is one wasted transfer of a multi-gigabyte image plus an `expected digest %q, got %q` error that reads like corruption instead of a changed remote.

Fix: send `Range` only when `ifRangeValidator` returns a value; otherwise start fresh.

I3. **Response metadata overwrites cached validators with empty strings** — `pkg/downloader/downloader.go:957-962` [Gemini 3.5 Flash, Claude Opus 5]

```go
	write := func(path, value string) error {
		if path == "" {
			return nil
		}
		return os.WriteFile(path, []byte(value), 0o644)
	}
```

A 206 answering an `If-Range` request need not repeat the representation headers, so an absent header truncates a good cached value to nothing. I checked what `http.ServeContent` sends on a 206. `Last-Modified` is present, `ETag` is empty. Every resume therefore erases a previously cached ETag and demotes the next attempt to the `Last-Modified` fallback, or to the unvalidated request of I2 when neither header comes back.

The `time` file also feeds `matchLastModified` at line 287, the sole freshness marker for digest-less images, where an empty value forces a full re-download.

Fix: leave the file alone when the header is absent.

```diff
-		if path == "" {
+		if path == "" || value == "" {
```

I4. **`internals.md` contradicts what `prune --keep-referred` does** — `website/content/en/docs/dev/internals.md:150` [Claude Opus 5, Codex GPT 5.6 Sol]

> A leftover partial is only removed together with its cache entry: `limactl prune` deletes the entire cache, and when `limactl prune --keep-referred` deletes an unused cache entry, any `data.part` in that entry is removed with it.

`cmd/limactl/prune.go:71` calls `RemoveStaleTempFiles` after the deletion loop, and `removeStaleTempFilesInDir` globs `data.part` out of every *surviving* entry. So `--keep-referred` destroys resume progress for exactly the images it keeps, which is the opposite of the promise. That sweep predates this branch, so the doc is the regression here, but the two features still need one agreed policy.

Fix: state that `--keep-referred` also sweeps partials from retained entries, or stop sweeping kept entries.

I5. **Nothing tests that a failed download keeps `data.part`** — `pkg/downloader/downloader_test.go:242-250` [Claude Opus 5]

```go
func seedPartial(t *testing.T, cacheDir, url string, partial []byte, lastModified string) {
	t.Helper()
	shad := cacheDirectoryPath(cacheDir, url)
	assert.NilError(t, os.MkdirAll(shad, 0o700))
	assert.NilError(t, os.WriteFile(filepath.Join(shad, "data.part"), partial, 0o644))
```

Every resume subtest hand-seeds the partial, so nothing exercises the write side of the feature, where an interrupted transfer must leave its bytes behind.

I verified this by mutation. Replacing the `if !t.resume` guard at `pkg/downloader/downloader.go:1136-1138` with an unconditional `defer os.RemoveAll(partial)`, which disables resume completely, leaves the entire package suite green.

Fix: cancel the context mid-body against a slow handler, assert `data.part` survives with the expected prefix, then assert a second `Download` finishes it with one `Range` request.

## Suggestions

S1. **The ETag branch of `ifRangeValidator` is never exercised** — `pkg/downloader/downloader_test.go:246-249` [Claude Opus 5, Codex GPT 5.6 Sol]

```go

	if lastModified != "" {
		assert.NilError(t, os.WriteFile(filepath.Join(shad, "time"), []byte(lastModified), 0o644))
	}
```

ETag is the preferred validator and the one the commit message leads with, yet `seedPartial` writes only `time` and `ServeContent` emits no ETag, so all seven subtests take the `Last-Modified` fallback. I1 and I3 both live in code this suite cannot reach.

Fix: give `seedPartial` an `etag` parameter, and assert the exact `Range` and `If-Range` request headers for a strong tag, a weak tag, and no validator at all.

S2. **New validators are persisted before the stale partial is discarded** — `pkg/downloader/downloader.go:1127-1131` [Claude Opus 5]

```go
	if err := writeResponseMetadata(t, resp); err != nil {
		return err
	}

	fileWriter, err := openPartialFile(partial, resuming)
```

On the 200-restart path the `etag` and `time` files describe the new representation before line 1131 truncates the old bytes. A crash in that window leaves the next attempt resuming stale bytes under a validator that matches. The digest catches it, so the cost is one wasted download.

Fix: truncate the partial first, then write the metadata.

S3. **Hash the existing bytes before opening the file for writing** — `pkg/downloader/downloader.go:1131-1140` [Gemini 3.5 Flash]

```go
	fileWriter, err := openPartialFile(partial, resuming)
	if err != nil {
		return err
	}
	defer fileWriter.Close()
```

`resumeDigester` opens the same path for reading immediately afterwards. Two handles on one file work on every platform Lima targets, but reading first and then opening for append is easier to follow and removes the question.

S4. **The in-code cache layout comment omits the two new files** — `pkg/downloader/downloader.go:608-612` [Claude Opus 5, Codex GPT 5.6 Sol]

```go
// cacheDirectoryPath returns the cache subdirectory path.
//   - "url" file contains the url
//   - "data" file contains the data
//   - "time" file contains the time (Last-Modified header)
//   - "type" file contains the type (Content-Type header)
```

`internals.md` gained `data.part` and `etag`; this enumeration of the same directory did not.

Separately, the comment on `httpTarget.etagPath` at line 903 reads `// "" or shadETag (ETag)`, but `shadETag` appears nowhere else in the tree. Its siblings `shadTime` and `shadType` are real locals in `fetch`, which inlines `filepath.Join(shad, "etag")` at line 416 instead.

Fix: add the two entries, and declare `shadETag` in `fetch` so the comment names something real.

S5. **`perProcessTempfile` runs on the resume path only to be discarded** — `pkg/downloader/downloader.go:1090-1094` [Claude Opus 5]

```go
	partial := perProcessTempfile(t.localPath)
	if t.resume {
		partial = partialFilePath(t.localPath)

```

Every resumable download bumps the package-global `tempfileCount` for a value it throws away. Harmless, but the counter exists so tests can reason about temp-file names.

Fix: invert the condition so only the uncached path calls it.

S6. **A `resumeDigester` failure leaves the partial in place** — `pkg/downloader/downloader.go:1140-1143` [Gemini 3.5 Flash]

```go
	digester, err := resumeDigester(expectedDigest, partial, offset)

		return err

```

Removing a resumable partial on this error path would match what `verifyDownloadedDigest` already does on a digest mismatch. The directory lock and the immediately preceding `os.Stat` make a real failure here hard to reach, so this is symmetry rather than a live bug.

## Design Observations

### Concerns

**Download state is derived from the response, not the request** *(in-scope)* [Codex GPT 5.6 Sol, Gemini 3.5 Flash] — C1 and C2 share one root. The switch at `downloader.go:1109-1125` reads only `resp.StatusCode`, so it cannot tell a 416 that answers a `Range` request from one that does not, or a solicited 206 from an unsolicited one. Modelling the operation as at most two attempts, one optional resume and one fresh retry, would close both by construction and remove the recursion.

**Transparent gzip covers the first request but not the resume** *(future)* [Claude Opus 5] — Go's transport adds `Accept-Encoding: gzip` and auto-decodes only when the request carries no `Range` header (`net/http/transport.go:2854-2858`, go1.26.5, citing golang/go#8923). So a first fetch from a gzipping server writes *decoded* bytes into `data.part`, while the follow-up `Range: bytes=N-` addresses the *encoded* representation and arrives undecoded. The digest catches the mismatch and clears the partial, so it self-heals after one wasted round trip. A sentence in `resumeOffset`'s comment would save the next reader the trace.

**Resume and prune pull in opposite directions** *(future)* [Claude Opus 5] — `limactl prune --keep-referred` deletes the file this PR exists to preserve (I4). Prune is a reclaim-space verb, so that is defensible, but the two features shipped in adjacent PRs with no stated policy. Someone should decide whether `--keep-referred` keeps partials for referred images and sweeps only orphans.

### Strengths

**Resume requires an expected digest** *(in-scope)* [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.1 Pro] — `resumeOffset` (lines 928-934) refuses to resume without one. That single invariant turns every stitching failure, mirror skew, an ignored `If-Range`, power-loss tail garbage, `Content-Range` drift, into one wasted download instead of a corrupt cached image. C2 is exactly the case where the invariant does not apply, which shows how much work it does everywhere else.

**The stable name rests on a real lock** *(in-scope)* [Gemini 3.5 Flash, Codex GPT 5.6 Sol] — `Download` wraps `getCached` and `fetch` in `lockutil.WithDirLock(shad, ...)` at line 253, so one writer per URL is guaranteed without serializing unrelated URLs.

**The 416 already-complete path recovers a real interruption** *(in-scope)* [Claude Opus 5] — `finalizeOrRestartPartial` (lines 1069-1073) finalizes a download killed between the last byte and the rename, and its test pins `requests == 1` so the no-re-download property cannot silently regress.

**The uncached path keeps per-process temp files** *(in-scope)* [Claude Opus 5, Codex GPT 5.6 Sol, Gemini 3.1 Pro] — extending a single-writer assumption to a path with no lock would have broken the parallel-download property from issue 2722.

## Review Process Notes

### Skill improvements

- When a handler sets internal state from a field of a peer's response (an HTTP status, a reply code, a protocol flag), check whether the local request ever asked for that state. A response-derived flag the request cannot corroborate lets a non-conforming or hostile peer drive a code path the client never requested, and the resulting behavior is usually unreachable through a conforming test server. Flag any state variable assigned from a response field alone when the matching request condition is in scope.

- Prove a test-coverage claim by mutation rather than by reading. Before reporting that a behavior is untested, break that behavior in the code and run the suite; report the gap only if the suite still passes, and name the mutation you applied. A gap argued from inspection alone is often wrong, because coverage frequently arrives through an assertion in a test that looks unrelated.

- When an error path recovers by re-entering the function that called it, identify the state change that makes the next entry differ, then confirm the re-entry condition actually depends on that state. A retry keyed on a peer's response rather than on local state has no base case and recurses until the stack is exhausted. Report the crash rather than the missing retry limit.

### Repo context updates

- [repo] **Cache downloads hold an exclusive per-URL directory lock.** `downloader.Download` wraps both `getCached` and `fetch` in `lockutil.WithDirLock` on the cache entry directory, and `Cached` and the stale-partial sweep take the same lock. One Lima process writes a given cache entry at a time, so a TOCTOU finding premised on two Lima processes racing over files inside one entry directory is a false positive. Name the non-Lima writer explicitly if the race needs one.

- [repo] **`limactl prune --keep-referred` sweeps partial downloads out of the entries it keeps.** After deleting unreferenced cache entries, `pruneAction` calls `downloader.RemoveStaleTempFiles`, which globs `data.part` and `data.tmp.*` from every surviving entry. Any claim that a partial download survives a prune of a still-referenced image is wrong, and any doc that says so contradicts the code. Check the deletion loop and the sweep that follows it as one unit.

If the server continues returning `416` (due to local firewall filters, proxies, or server misconfiguration), this recursive chain never terminates, crashing the CLI with a stack overflow or timing out.

#### Important Issues

I1. **Corrupt or truncated partial files cause permanent resume failure** — `pkg/downloader/downloader.go:1138-1141` (important, regression)

```go

	if err != nil {
		return err
	}
```

When resuming a download, `resumeDigester` (line 1138) is called to hash the existing `data.part` file up to `offset` bytes. If `resumeDigester` fails (e.g., due to an I/O read error or a truncated/unreadable file), `downloadHTTP` returns the error immediately (line 1140) without deleting the corrupt `data.part` file. On subsequent runs, `resumeOffset` sees the file, sends another Range request, fails at `resumeDigester` again, and permanently blocks downloads for that URL unless the user manually deletes the partial file.

Fix: Discard the partial file on `resumeDigester` failure when `t.resume` is enabled.

```diff

 	if err != nil {
+		if t.resume {
+			_ = os.Remove(partial)
+		}
 		return err
 	}
```

### Design Observations

#### Concerns
- **Recursive design for download HTTP fallback (in-scope)**: The recursion between `downloadHTTP` and `finalizeOrRestartPartial` on `416` responses is delicate. While we have capped the depth of recursion to 1 with the `offset > 0` check, recursive architectures are generally more complex to reason about and are prone to stack exhaustion bugs. A state-machine or iterative retry loop would be a cleaner alternative.

#### Strengths
- **Safe single URL downloads**: Using the exclusive directory lock (`lockutil.WithDirLock`) on the cache path makes the stable `data.part` filename completely safe across concurrent processes and caps leftover junk files to at most one per URL.
