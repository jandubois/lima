## Executive Summary

The PR cleanly consolidates external-driver config-filling into `Configure` and makes the gRPC server persistent per-instance. Two regressions block merge: moving default-filling out of `ResolveVMType` leaves `MountType` nil for `store.Inspect` consumers, so `limactl factory-reset` panics on the default instance after deleting its files (C1); and a `create` failure orphans the spawned driver server (I1). The rest are robustness and UX suggestions.

All three reviewers agreed the refactor is sound and builds/tests green. Codex alone caught the crash-class C1; Gemini alone caught the Windows signal regression (I2); Claude gave the sharpest account of I1. The three findings barely overlap, so each reviewer carried real weight.

## Critical Issues

C1. **`limactl factory-reset` panics on nil `MountType`** — `pkg/cidata/cidata.go:196` [Codex GPT 5.5]

```go
switch *instConfig.MountType {   // nil-pointer dereference
```

`factory-reset.go:73` passes the `store.Inspect` config straight to `GenerateCloudConfig` without running `Configure`. `store.Inspect` → `LoadYAMLByFilePath` now fills only `VMType`; `FillDefault` leaves `MountType` nil because the built-in default is `mountType: null` (`pkg/limayaml/default.yaml:108`). The old `ResolveVMType` filled it via the driver's `FillConfig` (vz→virtiofs, qemu→9p), so this is a regression. factory-reset first stops the instance and deletes its files (`factory-reset.go:52-71`), *then* panics — leaving a half-reset instance. Triggers on the default instance, whose persisted YAML sets no `mountType`.

Fix: fill driver defaults before non-`Configure` consumers use the config (a side-effect-free fill/validate step), or nil-guard the `MountType` derefs at `cidata.go:196` and `:247`.

## Important Issues

I1. **`create` failure orphans the external-driver server** — `pkg/instance/create.go:69-99` [Claude Opus 4.8, Gemini 3.1 Pro]

```go
defer func() {
    if !createSucceeded {
        _ = os.RemoveAll(instDir)   // deletes the PID + socket files
    }
}()
```

For an external driver, `CreateConfiguredDriver` (line 88) spawns a server via `server.Start`. limactl runs on `context.Background()` (`cmd/limactl/main.go:51`), so the child is not ctx-cancelled, and the CLI now calls only `server.Disconnect()` at exit, not `StopAllExternalDrivers()`. If a later step (Validate/GenerateCloudConfig/Create) fails, the rollback deletes `instDir` including `lima-driver-*.pid`/`.sock`, which `server.Stop` globs — so the process can never be reaped. With the 60s self-shutdown timer removed, it leaks permanently.

Fix: call `server.Stop(instDir, true)` before `os.RemoveAll` in the rollback.

I2. **`server.Stop` never kills processes on Windows** — `pkg/driver/external/server/server.go:291` [Gemini 3.1 Pro]

```go
if err := proc.Signal(syscall.Signal(0)); err != nil {
    _ = os.Remove(pidFile)
    continue   // Windows: always taken
}
```

On Windows, `os.Process.Signal` supports only `os.Kill`; every other signal — including `Signal(0)` and `SIGTERM` — returns an error. The liveness pre-check therefore always fails, the loop removes the PID file and `continue`s, and neither the graceful `SIGTERM` nor the force `SIGKILL` branch runs. External-driver processes are never stopped, and their PID files vanish. `StopForcibly` previously used the cross-platform `osutil.SysKill`, so this regresses Windows cleanup for external drivers.

Fix: signal and probe liveness through `osutil.SysKill` / a Windows-aware helper instead of raw `proc.Signal`.

## Suggestions

S1. **`ResolveVMType` failure is now fatal in prune/template scans** — `cmd/limactl/prune.go:108`, `cmd/limactl/template.go:95` [Claude Opus 4.8]

Previously these logged a warning and continued; now they return the error. `ResolveVMType` (`pkg/driverutil/vm.go:25`) errors only when `VMType` names a driver absent from both `limatype.VMTypes` and the registry. So one template pinning an uninstalled external driver aborts the whole `limactl prune` or template-validation scan. Built-in types are unaffected. Keep the non-fatal behavior for multi-item scans, or confirm the stricter behavior is intended.

S2. **Duplicate "experimental" warnings during `create`** — `pkg/instance/create.go:56` and `:92` [Claude Opus 4.8, Gemini 3.1 Pro]

`limayaml.Validate(_, true)` runs before and after driver fill, so `warnExperimental` fires twice and users see doubled `os`/`video`/`audio` warnings. Pass `warn=false` to the pre-fill call. (Gemini flagged the same double-validation as a rejection risk, but `Validate` guards its driver-filled derefs, so it does not wrongly reject — only the duplicate warning is real.)

S3. **Dead nil guard for `Arch` in `warnExperimental`** — `pkg/limayaml/validate.go:617` [Claude Opus 4.8]

`Validate` already dereferences `*y.Arch` unconditionally at line 63 (`FillDefault` always sets `Arch`), so the added `if y.Arch != nil` wrapper is unreachable-guarded. The sibling `MountType` guard *is* necessary, since the driver fills `MountType`. Drop the `Arch` wrapper for consistency.

S4. **Registry singleton mutation leaks clients across instances** — `pkg/driverutil/instance.go:34` [Gemini 3.1 Pro]

`CreateConfiguredDriver` overwrites `extDriver.Client` on the shared `registry.ExternalDriver`. A command that processes several instances leaves earlier clients unclosed; `Disconnect` then closes only the last. Return an instance-scoped client instead of mutating the global.

S5. **`Stop` can signal a reused PID or orphan a socket** — `pkg/driver/external/server/server.go:280-319` [Codex GPT 5.5]

A stale PID file can outlive its process; the SIGTERM→SIGKILL escalation (10s window) may then hit a recycled PID. Conversely, a live socket with no PID file is unlinked without stopping its server. Verify process identity before signaling, and unlink a socket only once its process has exited. Low likelihood on a single host, and the stale-PID pattern predates this PR.

S6. **`create` rollback can delete a concurrently created instance** — `pkg/instance/create.go:43-72` [Codex GPT 5.5]

The existence check (line 43) and `MkdirAll` (line 66) do not atomically claim `instDir`. Two concurrent `create` calls for the same name can both pass the check; if the second fails, its `os.RemoveAll` deletes the first's instance. Claim the directory with `os.Mkdir` and install the rollback only after a successful claim.

## Design Observations

**Concerns**

- **No reaper for short-lived CLI callers** (in-scope) [Claude Opus 4.8, Codex GPT 5.5] — the root of C1 and I1. Removing the idle timer means any CLI command that spawns a server but never calls `server.Stop` (`create` on success, `snapshot` on a stopped instance) leaves an idle server running until a later `start`/`stop`/`delete`. Consider a bounded idle backstop, or have non-hostagent callers stop the server they spawn.
- **Keep config normalization side-effect-free** (in-scope) [Codex GPT 5.5] — C1 stems from merging default-filling into runtime `Configure`. A pure "fill defaults + validate" layer, shared by `store.Inspect`, template validation, factory-reset, and startup, would let every consumer normalize without spawning a server or mutating driver state.
- **`isServerRunning` infers health from a successful dial** (in-scope) [Gemini 3.1 Pro] — a shutting-down or hung server whose socket still accepts connections is treated as ready.

**Strengths**

- The `Configure` gRPC round-trip — the server marshals the filled instance back (`server/methods.go:82-89`) and the client unmarshals it (`client/methods.go:309`) — cleanly propagates driver defaults and keeps in-tree and external drivers symmetric. [Claude Opus 4.8, Codex GPT 5.5]
- Socket-file polling with a `procExit` channel (`server.go:223-262`) replaces the fragile stdout handshake and distinguishes "died early" from "timed out." [Claude Opus 4.8]
- Splitting `Disconnect` from `Stop`, moving the socket into the instance directory, and rejecting non-positive PIDs before signaling (`server.go:281`) are all sound. [Claude Opus 4.8, Codex GPT 5.5]

## Review Process Notes

**Skill improvements**

- When a diff changes what a shared load, resolve, or normalization function fills into a config or struct — for example moving default-population out of a load/resolve path into a later runtime step — enumerate every consumer of the earlier path and check each pointer-field dereference. A field a consumer previously received filled may now be nil, turning a `*field` deref into a panic. Flag any consumer that dereferences a pointer field the function no longer populates, paying special attention to consumers outside the diff, because the failing deref and the changed fill often live in different files.

- In cross-platform Go, flag `os.Process.Signal` (or `proc.Signal`) called with any signal other than `os.Kill`. On Windows only `os.Kill` is delivered; a `Signal(0)` liveness probe and `SIGTERM`/`SIGINT` return an error, so signal-based liveness checks and graceful-termination loops silently no-op there. Require a cross-platform kill/liveness helper for any process-management code that must run on Windows, and treat a swap away from such a helper toward raw `syscall` signals as a portability regression.

**Repo context updates**

- [repo] Driver-specific config defaults (`MountType`, and other fields the driver selects) are filled only inside `Driver.Configure` (formerly `FillConfig`). `LoadYAMLByFilePath` / `store.Inspect` fill general defaults via `limayaml.FillDefault` but not driver-specific ones, and the built-in default (`pkg/limayaml/default.yaml`) sets `mountType: null`. Any consumer of a `store.Inspect` config that dereferences `MountType` — or another driver-defaulted pointer field — must nil-guard it or run `Configure` first. When reviewing a change that moves or removes driver default-filling, check `cidata.GenerateCloudConfig` callers and other `store.Inspect` consumers for unguarded derefs.

### Important Issues

**I1. `create` rollback orphans a spawned external-driver server — `pkg/instance/create.go:69-99`** (important, regression)

```go
var createSucceeded bool
defer func() {
    if !createSucceeded {
        _ = os.RemoveAll(instDir)   // deletes the PID + socket files
    }
}()
...
limaDriver, err := driverutil.CreateConfiguredDriver(ctx, inst, 0) // may spawn a server (line 88)

```

For an external driver, `CreateConfiguredDriver` (line 88) calls `server.Start`, which spawns the server via `exec.CommandContext(ctx, …)`. Fix:
```diff
 defer func() {
     if !createSucceeded {
+        server.Stop(instDir, true) // reap any spawned external-driver server before the files vanish
         _ = os.RemoveAll(instDir)
     }
 }()
```
Apply the same state-enumeration rigor: `server.Stop` before `RemoveAll` still works because the PID/socket files exist at that point.

### Design Observations

**Concerns**

- **External-driver server lifecycle has no reaper for short-lived CLI callers (in-scope).** The removed 60s self-shutdown timer means a server is now stopped only by `server.Stop` (hostagent shutdown, `stop -f`, `delete`) or by ctx cancellation. But CLI commands that spawn a server yet never call `server.Stop` — `create` on success (`create.go:103` sets `createSucceeded` and returns, server left running), and `snapshot` on a stopped external-driver instance (`pkg/snapshot/snapshot.go` never stops) — leave an idle server running under `init` until a later `start`/`stop`/`delete`. Sketch: have `CreateConfiguredDriver` callers that are not the hostagent stop the server they spawned, or reintroduce a bounded idle timeout as a backstop. This is the same root cause as I1.

- **PID-reuse across the SIGTERM wait in `Stop` (future).** `server.go:299-311` sends SIGTERM, then polls `Signal(0)` for up to 10s, then SIGKILLs if `Signal(0)` still succeeds. If the original process exits and its PID is recycled during the wait, the final SIGKILL (line 310) hits an unrelated process. Low likelihood on a single host; noting for completeness. A re-read of the PID file before the escalation, or matching the process start-time, would close it.

**Strengths**

- `Stop` rejects non-positive PIDs before signaling (`server.go:281`, `pid <= 0`), avoiding the `kill(0)`/`kill(-1)` process-group broadcast hazard.
- The `Configure` round-trip (`server/methods.go:82-89` marshals the filled instance back; `client/methods.go:309` unmarshals it) is a clean mechanism for remote default-filling and keeps in-tree and external drivers symmetric.
- Replacing the fragile stdout `{"socketPath":…}` handshake with socket-file polling plus a `procExit` channel (`server.go:223-262`) is more robust and correctly distinguishes "process died early" from "timed out."

I1. **Driver defaults no longer reach non-configuring inspect callers** — `pkg/store/store.go:123-128` (important, regression)

I2. **PID/socket cleanup can kill reused PIDs or orphan live servers** — `pkg/driver/external/server/server.go:272-319` (important, regression)


### [Gemini 3.1 Pro]

### Executive Summary
This PR successfully simplifies the external driver lifecycle by merging `FillConfig` into `Configure` and making the gRPC server persistent. However, it introduces critical regressions in server startup (stale sockets prevent restart) and shutdown (silent failures on Windows), along with a resource leak where `limactl create` leaves the driver running indefinitely.

### Findings

#### Critical Issues

C1. **Stale sockets permanently break instance startup** — `pkg/driver/external/server/server.go:80-84`

```go
	socketPath := driverSocketPath(*instDir, driverName)
	defer func() {
		// ...
	}()

	listener, err := net.Listen("unix", socketPath)
```

If the external driver crashes, is force-killed, or the host reboots, the `.sock` file is left behind in the instance directory. On the next startup, `isServerRunning` correctly returns `false` (connection refused) and spawns a new server. However, `net.Listen("unix", ...)` fails with `bind: address already in use` because the stale file exists. The server fatally exits, and `limactl start` permanently fails for that instance.

Fix: Unlink the socket file before calling `net.Listen`.

```diff
 	socketPath := driverSocketPath(*instDir, driverName)
+	_ = os.Remove(socketPath)
 	defer func() {
```

C2. **Graceful shutdown fails silently on Windows** — `pkg/driver/external/server/server.go:277-285`

```go
			_ = proc.Signal(syscall.SIGTERM)
			deadline := time.Now().Add(10 * time.Second)
			for time.Now().Before(deadline) {
				if err := proc.Signal(syscall.Signal(0)); err != nil {
					break
				}
				time.Sleep(200 * time.Millisecond)
			}
```

On Windows, `os.Process.Signal` only supports `os.Kill` and `os.Interrupt`. Passing `syscall.SIGTERM` or `syscall.Signal(0)` immediately returns an "unsupported signal type" error. Consequently, the graceful stop fails silently, the polling loop breaks immediately on the `err != nil`, and the fallback `SIGKILL` is never reached. This leaves a zombie external driver process while prematurely deleting its PID file.

Fix: Use Lima's cross-platform helper `osutil.SysKill` for both signaling and liveness checks instead of raw `proc.Signal`.

#### Important Issues

I1. **`limactl create` orphans the driver server indefinitely** — `pkg/driver/external/server/server.go:107-123`

The PR removes the server's 60-second idle self-shutdown timer, assuming it will "remain alive with the hostagent." However, commands like `limactl create` invoke `instance.Create`, which calls `CreateConfiguredDriver` and spawns the driver server to execute `limaDriver.Create(ctx)`. Since `create` exits without starting the hostagent or explicitly stopping the driver, the server process is left running indefinitely in the background for a VM that is not active.

Fix: Explicitly call `server.Stop(instDir, false)` at the end of `instance.Create`, or restore a mechanism where the server cleanly shuts down if a client connection closes and no hostagent claims it.

I2. **Premature `limayaml.Validate` aborts instance creation** — `pkg/instance/create.go:53-59`

```go
	if err := driverutil.ResolveVMType(loadedInstConfig); err != nil {
		return nil, err
	}
	if err := limayaml.Validate(loadedInstConfig, true); err != nil {
		if !saveBrokenYAML {
```

Because `FillConfig` was merged into `Configure()`, `ResolveVMType` no longer populates driver-specific defaults. This means the first `limayaml.Validate(..., true)` checks the configuration *before* the driver can fill its mandatory defaults. If an external driver relies on `Configure` to supply required fields, this early validation will incorrectly reject the valid YAML and abort before the driver is ever spawned.

Fix: Remove the early `limayaml.Validate` call. Perform the strict `requireAll=true` validation and the "save broken YAML" logic only after `CreateConfiguredDriver` returns the fully populated configuration.

#### Suggestions

S1. **Global singleton mutation causes connection leaks for multi-instance commands** — `pkg/driverutil/instance.go:34-35`

```go
		extDriver.Client, err = client.NewDriverClient(socketPath, extDriver.Logger)
```

`CreateConfiguredDriver` mutates the global registry singleton (`extDriver.Client = ...` and `extDriver.InstanceName = ...`). If a CLI command processes multiple instances sequentially, the global `Client` reference is repeatedly overwritten. Later, `server.Disconnect()` iterates `registry.ExternalDrivers` and only closes the connection for the last configured instance, leaking the previous gRPC client connections until the CLI process exits.

Fix: Avoid storing instance-specific state (`Client`, `InstanceName`) in the global `registry.ExternalDriver` struct. Return a new instance-specific struct or wrapper.

### Design Observations

**Concerns**
- **State Inference via Proxy:** `isServerRunning` infers server health by successfully dialing the socket. If the server is shutting down or hung but the socket is still accepting connections, this check falsely assumes the server is fully ready. (in-scope)

### Testing Assessment
1. **Server crash recovery:** No test verifies that an instance can start after its external driver server crashes (leaving a stale socket file).
2. **Resource leaks on `create`:** Ensure tests verify that no external driver processes are left running after `limactl create` completes.
