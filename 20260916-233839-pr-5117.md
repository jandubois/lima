## Executive Summary

The privilege boundary holds. Probes against the sudo helper (metacharacters, extended ACLs, argv pinning, peer credentials, TOCTOU) all failed to break it. The external-VZ rejection added for a prior round compiles into no binary the Makefile produces, so that finding is still open. The root helper follows a symlink at the socket path. Three paths that regenerate or verify the sudoers file each narrow or over-accept a grant silently.

---

## Critical Issues

None.

I probed the trust boundary this PR exists to close from several directions, and it held. The negative results are the point of this round, so here they are. The sudoers metacharacter blocklist admits no character that changes how `visudo` parses a command path; `pathHasExtendedSecurityACL` correctly reports ACLs on both files and directories, and `validateSecurePath` recurses to `/`, so an ACL on an ancestor disqualifies the helper; `SUDO_UID` is authoritative under `NOSETENV`, and forging it only narrows which socket directory the helper accepts; argv pinning means sudo's own command matching is the allowlist; and the device grant cannot be widened from `/dev/disk4` to another node through the stdin request.

I2. **The root helper follows a symlink at the socket path, so it can be made to connect to a socket outside the private directory** — `pkg/blockdevice/block_device_darwin.go:315` [Gemini 3.1 Pro]

```go

	if err != nil {
		return fmt.Errorf("failed to lstat socket directory %q: %w", parent, err)
```

`validatePrivateSocketPath` lstats the *parent* and rejects a symlinked or group-readable directory, but never lstats the socket path itself. `net.DialUnix` follows symlinks. A user holding a block-device grant can put a symlink inside their own `0700` directory and make the root helper connect to any Unix socket on the host, write 64 attacker-chosen hex bytes (the nonce is echoed from the request), and offer a raw-disk descriptor over `SCM_RIGHTS`. The attacker already holds the device fd, so the gain is the root connection itself, reaching sockets their own uid cannot open.

I6. **The new BATS suite overwrites `/etc/sudoers.d/lima` and never restores it** — `hack/bats/extras/vz-block-device.bats:64` [Claude Opus 5, Codex GPT 5.6 Sol]

`teardown()` (`:18-34`) deletes the instance and detaches the RAM disk but never touches the sudoers file. ## Suggestions

S1. **Duplicate device paths come through the layer merge and validation accepts them** — `pkg/limayaml/defaults.go:312` [Claude Opus 5]

```go

```

A device listed in both `_config/override.yaml` and the instance YAML arrives twice: `FillDefault` produces `[/dev/disk4 /dev/disk4]` and `validateBlockDevices` returns nil (measured). The privileged helper then runs twice for one device, and both attachments receive the same identifier from `guestBlockDeviceIdentifier`. The `--block-device` yq expression applies `unique` (`cmd/limactl/editflags/editflags.go:381`); the merge does not.

Fix: reject duplicates in `validateBlockDevices`, where the field index is available for the message.

S2. **`osutil.SysStat` dereferences before returning `ok`, so both new `!ok` guards are unreachable** — `pkg/osutil/osutil_others.go:22-25` [Claude Opus 5]

```go
func SysStat(fi fs.FileInfo) (Stat, bool) {
	stat, ok := fi.Sys().(*syscall.Stat_t)
	return Stat{Uid: stat.Uid, Gid: stat.Gid}, ok
}
```

A failed type assertion nil-derefs before the caller sees `ok`. A probe against a `FileInfo` whose `Sys()` returns something else panics with `invalid memory address or nil pointer dereference`. The helper (same shape in `osutil_linux.go:20`) predates this PR and nothing triggers it in production, but this PR adds two call sites, `pkg/blockdevice/block_device_darwin.go:326` and `:407`, whose error text asserts a behavior the helper does not have. The new `fakeFileInfo` in `block_device_darwin_test.go` takes `stat any`, which is exactly the shape that panics.

Fix: return early inside `SysStat` when the assertion fails.

S3. **`os.Executable()` does not resolve symlinks on macOS, so a symlinked install derives the wrong helper path** — `pkg/blockdevice/block_device_darwin.go:218` [orchestrator]

Measured on macOS 25.6: a binary invoked through a symlink reports the symlink's own path, not the target's. `privilegedHelperPathForExecutable` takes the grandparent of that, so a distributor who installs into `/opt/lima` and symlinks `/usr/local/bin/limactl` gets `/usr/local/libexec/lima/privileged/...`, a path that need not exist, even though a valid root-owned helper is installed. The same measurement shows `/usr/local/libexec` is already user-owned on an ordinary Apple Silicon host, so the default `sudo make install` prefix can fail the check too. Both fail closed.

Fix: say in `disk.md` that the helper is located relative to the `limactl` path as invoked, so a symlinked `limactl` must have the helper beside *it*.

S4. **Helper-path rejection errors do not name the install requirement** — `pkg/blockdevice/block_device_darwin.go:365` [Claude Opus 5]

`validateSecureHelperPath` surfaces raw element errors: `dir "/usr/local/libexec" is not owned by root uid 0, but by uid 501` (measured on this host), or `... is a symlink` for a Homebrew layout. Accurate, but they do not point at the remedy `disk.md:109-112` already documents.

Fix: wrap the error in `sudoOpenBlockDeviceHelperArgs`, as in "the block-device helper must be installed in a root-owned, non-user-writable path (e.g. `sudo make PREFIX=/opt/lima install`)".

## Design Observations

### Concerns

**Verification now has three owners instead of two** *(future)* [Claude Opus 5]. `pkg/networks` verifies its own fragment, `pkg/blockdevice` renders another, and `pkg/sudoers` owns the shared rendering and the matcher, but nothing validates the composed file. `cmd/limactl` is the only place that knows the full expected content, and only under `--check`. This round widens the prior round's split by a package. A single `sudoers.Verify(file, fragments...)` called by both the network start path and `--check` would give one answer to "is this file what Lima rendered", and I3 and I5 both reduce to it. @unsuman has signaled a follow-up refactor here, so this is the moment to agree on that interface.

**The grant is neither time-bounded nor tied to the device it was issued for** *(future)* [Claude Opus 5, Gemini 3.1 Pro]. Unchanged from the prior round: `/dev/diskN` is assigned by attach order, the helper always opens `O_RDWR`, and nothing revokes an entry. The regex deliberately permits `/dev/disk0`, where `O_RDWR` on the whole device is root-equivalent. I6 makes this concrete, because the BATS suite leaves exactly such a grant behind. Two mitigations to weigh: refuse to grant a device that is currently the boot disk or a mounted system volume, and record the `diskutil` UUID beside the entry so `--check` can warn when the slot has been reassigned.

**Revalidating the received descriptor cannot establish which device arrived** *(in-scope)* [Claude Opus 5]. `validateDiskDeviceFile` checks `os.ModeDevice` and the raw/block match, never comparing `st_rdev` with the device requested. The receiver verifies the kind of the descriptor, not its identity. With the sender authenticated as root and nonce-checked this is defense in depth, but it is one `Rdev` comparison from being meaningful.

### Strengths

- **Every property the prior round credited came through the move into the new helper binary intact, and none was duplicated** *(in-scope)* [Claude Opus 5, Gemini 3.1 Pro]. The helper is a 29-line `main` that calls straight into `pkg/blockdevice`, so there is exactly one copy of the argv pin, the `Lstat` → symlink → `O_NOFOLLOW` → post-open `Stat` → block/char chain, the `F_DUPFD_CLOEXEC` dup, and the `SUDO_UID` plus socket-directory ownership check.
- **The macOS ACL rejection answers the reviewer question it was written for** *(in-scope)* [Gemini 3.1 Pro, Claude Opus 5]. `pathHasExtendedSecurityACL` detects ACLs on directories as well as files, verified by adding one with `chmod +a` to a temp directory. The shipped test runs for real; it does not skip.
- **Prior C1 is fixed, and better than the merge-base** *(in-scope)* [Claude Opus 5, Gemini 3.1 Pro]. `PassFDToUnix` and `DialQemu` route through a package-level retainer that is never closed, while each VM gets a fresh one that only its own teardown closes, so the vz teardown no longer closes krunkit's descriptors, which the merge-base did. Both halves have tests.
- **The metacharacter blocklist holds up under test** *(in-scope)* [Claude Opus 5]. I fed unlisted characters into a command path and ran `visudo -c`. None of them changes how the entry parses, while each blocked character does.

## Review Process Notes

### Skill improvements

- **Ask which binary a build-tag guard is compiled into.** When a change gates behavior on a build-tag constant, do not stop at confirming the constant flips under the tag. Identify every binary the build system produces, and for each one determine whether the package holding the constant is in its dependency graph and which value it takes there. `go list -deps -tags <tag> ./cmd/<binary>` answers this in one command. A tag applied to one binary's build line while the guarded code runs inside a different binary produces a guard that is simultaneously well-tested and never executed, and both the diff and a tagged unit test look correct.

- **A test whose build constraints no CI job satisfies is not coverage.** When a change adds a test under a build tag, a platform constraint, or an environment gate, check whether any CI job sets that condition before crediting the test. Report a test that cannot run in CI as a coverage gap at the severity of the behavior it was meant to protect, not as a style note.

- **When a check is loosened, find the input the old check rejected and the new one accepts.** Reading the new code will not tell you what a relaxation from exact comparison to containment, prefix matching, or normalization permits. Build the value that now passes, run it through both versions, and state what it permits. Where the check guards a privilege boundary, the constructed value should be the one an attacker would want.

### Repo context updates

- **[repo] Build tags for external drivers reach only the limactl build line.** `ADDITIONAL_DRIVERS=vz` sets `external_vz` in `GO_BUILDTAGS_LIMACTL`, which is applied when building `./cmd/limactl` and nowhere else. The `additional-drivers` target builds `./cmd/lima-driver-<name>` with no extra tags, so any `external_<driver>` constant is false inside the external driver binary, and under the tag the driver package leaves limactl's dependency graph entirely. A guard written as `if externalVZ` therefore executes in neither binary. When reviewing a change that branches on one of these constants, run `go list -deps` against both binaries before accepting it.

- **[repo] No CI job sets `ADDITIONAL_DRIVERS`.** Tests guarded by `external_vz`, `external_qemu` or `external_wsl2` never execute in CI. Treat them as documentation rather than coverage.

- **[repo] The `vz` integration job installs no socket_vmnet.** The `vmnet` job does; the `vz` job does not. Code paths that branch on `networks.Config.Validate()` succeeding therefore take the failure branch in the `vz` job, and any BATS test running there exercises the degraded path. When a change adds a branch for "network config unavailable", the `vz` job is where it runs.

- **[repo] `osutil.SysStat` panics instead of returning `ok=false`.** Both the `_others` and `_linux` variants dereference the type-assertion result before returning it, so a `fs.FileInfo` whose `Sys()` is not `*syscall.Stat_t` nil-derefs. Callers that write an error message for the `!ok` branch are writing unreachable code. Do not credit such a guard as defensive handling.

- **[repo] `os.Executable()` does not resolve symlinks on macOS.** It returns the path as invoked. Any Lima code that derives a sibling path from the running executable resolves relative to the symlink's directory, not the real install prefix, so a symlinked entry point finds nothing. The privileged helpers under `libexec/lima/privileged` are the case in point.
