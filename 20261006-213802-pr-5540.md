## Executive Summary

The PR adds the MCP `replace` tool. It replaces `old_string` only when it occurs exactly `expected_replacements` times, holds a lock shared with `write_file` from read to write, refuses files and results over 32 MiB, writes in place, and tries to restore the original on failure. The code is correct, and the tree bears out each reply to Copilot's review. One required test is missing. Nothing exercises the refusal of an oversized file, so a regression there would silently truncate it.

## Important Issues

I1. **No test reaches `Replace`'s refusal of files over the read limit** — `pkg/mcp/toolset/filesystem.go:141-149` [Codex GPT 6 Astra, Claude Opus 5.5]


## Suggestions

S1. **Three new comments claim more than the code does** — `pkg/mcp/toolset/filesystem.go:134` [Claude Opus 5.5]

```go
	// Hold the lock from the read to the write, so that concurrent calls cannot undo each other.
```

The lock serializes `write_file` and `replace` only. A `run_shell_command` call such as `sed -i` can still run between the read on line 137 and the truncating open on line 158, and `replace` then writes stale content over that edit. The author's reply to Copilot excludes writers outside this server, but `run_shell_command` runs inside it.

The field comment at `pkg/mcp/toolset/toolset.go:42-44` makes the same claim, since `run_shell_command` is also "another call".

The comment at `pkg/mcp/toolset/filesystem.go:22` calls `readLimitBytes` "the maximum size of a file that ReadFile and Replace read". But `ReadFile` reads a file of any size and returns its first 32 MiB, and `Replace` also uses the constant to limit the size of its result.

Fix: Say in both lock comments that the lock covers `write_file` and `replace`, and that `run_shell_command` and writers outside the server can still interleave. Say what `readLimitBytes` limits for each caller.

## Design Observations

### Concerns

- (future) **Opening a FIFO stalls every SFTP-backed tool for the rest of the session** [Gemini 3.1 Pro]. The guest serves every SFTP-backed tool from one OpenSSH `sftp-server`, which handles one request at a time and opens files without `O_NONBLOCK`. Against `/usr/libexec/sftp-server` (OpenSSH 10.3p1), both `read_file` and `replace` on a FIFO left a later `read_file` of a regular file still blocked after 2 s. `read_file` behaved the same before this PR, so the new lock adds nothing to the stall. The fix belongs in every SFTP-backed tool: `Stat` the path and refuse anything but a regular file. Gemini proposed `Lstat`, which would also refuse the symlinks that `replace` writes through.
- (in-scope) **`write_file` still drops its `Close` error** [Gemini 3.1 Pro, Claude Opus 5.5]. `WriteFile` defers `f.Close()` and ignores the result (`pkg/mcp/toolset/filesystem.go:106`), as it did before this PR, so a failed close still reports success. The PR's new `writeAndClose` would report it. Not reproduced, since a stock SFTP server cannot be made to fail a close on demand.
- (future) **`read_file` can see `replace`'s truncate-then-write window** [Claude Opus 5.5]. `read_file` does not take the lock, so a parallel read of the same file can return empty or partial content. `write_file` already had the same window. A `sync.RWMutex`, with readers taking `RLock`, would give in-server readers a consistent view.

### Strengths

- (in-scope) The result-size check divides instead of multiplying, so it cannot overflow, and its tests sit on both sides of the boundary [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash].
- (in-scope) Writing in place keeps the file's mode, owner and hard links, and leaving out `O_CREATE` makes "never creates a file" a property of the open call [Claude Opus 5.5, Gemini 3.5 Flash].
- (in-scope) `TestReplaceConcurrent` can fail. With the lock lines removed from `Replace`, it failed in 3 of 3 runs. One lock for every path also covers symlinks and hard links, which a per-path lock would miss [Claude Opus 5.5, Codex GPT 6 Astra].

### [Gemini 3.1 Pro]

##### Executive Summary

This PR implements the `Replace` MCP tool for targeted file edits, addressing the token overhead and stale-read risks of rewriting entire files. The implementation is robust, featuring excellent fallback logic for disk-full scenarios and appropriate memory bounds. However, two important gaps remain in the filesystem toolset: operations on named pipes block the SFTP connection and permanently deadlock the MCP server's write mutex, and the pre-existing `WriteFile` tool silently drops close errors, masking delayed write failures.

##### Findings

###### Critical Issues

None.

###### Important Issues

I1. **`Replace` and `WriteFile` permanently deadlock the MCP server on named pipes** — `pkg/mcp/toolset/filesystem.go:135-137` (important, gap)

```go
	// Hold the lock from the read to the write, so that concurrent calls cannot undo each other.
	ts.writeMu.Lock()
	defer ts.writeMu.Unlock()
	f, err := ts.sftp.Open(guestPath)
```

`Replace` and `WriteFile` hold `ts.writeMu` across their entire execution to serialize edits. However, SFTP servers (including `sftp-server` and `pkg/sftp`) block indefinitely in `open()` when opening a FIFO (named pipe) without `O_NONBLOCK`. If an AI agent attempts to read, replace, or write to a named pipe, `sftp.Open` or `sftp.Create` will hang. Because the `context.Context` is ignored during these SFTP calls and `writeMu` is held, this permanently deadlocks all future `Replace` and `WriteFile` calls for the entire MCP session.

```go repro
// Save as .scratch/repro_main.go and run: go run .scratch/repro_main.go

import (
	"fmt"
	"net"
	"os"
	"path/filepath"
	"syscall"
	"time"

	"github.com/pkg/sftp"
)

func main() {
	serverConn, clientConn := net.Pipe()
	server, _ := sftp.NewServer(serverConn)
	go func() { _ = server.Serve() }()
	client, _ := sftp.NewClientPipe(clientConn, clientConn)

	tmpDir, _ := os.MkdirTemp("", "pipe_test")
	defer os.RemoveAll(tmpDir)

	pipePath := filepath.Join(tmpDir, "mypipe")
	syscall.Mkfifo(pipePath, 0600)

	done := make(chan struct{})
	go func() {
		client.Open(pipePath)
		close(done)
	}()

	select {
	case <-done:
		fmt.Println("Opened")
	case <-time.After(100 * time.Millisecond):
		fmt.Println("client.Open hung on named pipe")
	}
}
```

```text repro-output

```

Fix: Before acquiring `writeMu`, call `ts.sftp.Lstat(guestPath)` and return an error if the path exists but `!info.Mode().IsRegular()`. (Also apply this check to `ReadFile` to prevent it from hanging its own goroutine).

I2. **`WriteFile` drops the `Close` error, silently masking write failures** — `pkg/mcp/toolset/filesystem.go:106-110` (important, gap)

```go
	defer f.Close()
	_, err = f.Write([]byte(args.Content))
	if err != nil {
		return nil, nil, err
	}
```

In `WriteFile`, `f.Close()` is deferred and its error is ignored. If `f.Write()` succeeds but the subsequent `Close()` fails—which commonly happens when a delayed flush encounters a full disk or an NFS error—the error is dropped and the tool silently reports success to the MCP client. The new `Replace` tool avoids this by using the `writeAndClose` helper, but `WriteFile` was modified in this PR to add locking without fixing its error handling.

Unproven: requires a custom SFTP server that simulates a delayed flush failure by returning an error on `SSH_FXP_CLOSE`, which the standard `pkg/sftp` test server does not trivially support.

Fix: Remove `defer f.Close()` and use the new helper: `err = writeAndClose(f, []byte(args.Content))`. Return this error instead of falling through to success.

- **Robust disk-full recovery:** If `Replace` hits a disk space limit while writing, it effectively recovers by using `O_TRUNC` to free the just-written space before restoring the original, smaller content.

##### Design Observations

###### Strengths

- **Exact match count invariant**: Enforcing exact equality between actual match counts and `expected_replacements` prevents silent partial updates or unintended multi-site replacements when modifying code files.
- **Pre-allocation memory bounds checking**: Checking `growth := len(newString) - len(oldString)` with overflow-safe integer division against `readLimitBytes` before running `strings.Replace` prevents allocation amplification attacks and host process memory exhaustion.
- **Metadata and link preservation**: Opting for in-place writing rather than write-and-rename ensures that file ownership, permissions, and hard links remain intact without requiring write permissions on parent directories.

###### Concerns

- **Coarse ToolSet write synchronization** `(future)`: `ts.writeMu` serializes all `WriteFile` and `Replace` operations across the entire `ToolSet` instance. While sufficient for typical single-agent MCP sessions, parallel tool execution targeting different files on the same VM instance will contend on this single lock. If multi-agent or high-concurrency workloads emerge, migrating to a keyed per-path lock will allow concurrent writes to distinct files.
