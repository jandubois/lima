## Executive Summary

The hcs driver now converts qcow2 and raw images to VHDX through go-qcow2reader instead of qemu-img. The writer itself is sound: a converted image round-trips byte-identically through qemu-img, and the disk finally honors the configured `disk:` size. But the switch narrows what hcs accepts. A zstd-compressed qcow2 that qemu-img read now fails outright, an ISO instance image produces an empty boot disk, and `disk:` is honored for a converted image while a `.vhdx` one keeps its own size.

## Important Issues

I1. **A zstd-compressed qcow2 image now fails where `qemu-img` read it** — `pkg/driver/hcs/hcs_driver_windows.go:359` [Codex GPT 5.6 Sol]

```go
		// HCS natively uses VHDX only, RAW and QCOW2 are added here to avoid the default conversion to RAW.
		SupportedImageFormats: []string{string(raw.Type), string(qcow2.Type), string(vhdx.Type)},
```

Listing `qcow2` stops the downloader from normalizing the image to raw (`pkg/downloader/downloader.go:426-437`), so the qcow2 reaches `convertTo` unchanged. go-qcow2reader registers no zstd decompressor, and `srcImg.Readable()` rejects the image before any byte is copied. At the merge-base the downloader converted every qcow2 to raw through `proxyimgutil`, which tries `qemu-img` first (`pkg/imgutil/proxyimgutil/proxyimgutil.go:61-67`) — and hcs required `qemu-img` anyway, so zstd worked. zlib, which the shipped Ubuntu image uses, still converts natively.

I2. **An ISO instance image now yields an empty boot disk** — `pkg/driver/hcs/hcs_driver_windows.go:382` [Codex GPT 5.6 Sol]

```go
	if err := driverutil.EnsureDisk(ctx, l.Instance.Dir, *l.Instance.Config.Disk, vhdx.Type); err != nil {
		return err
	}
```

`EnsureDisk` renames an ISO image to `iso` and creates an empty disk (`pkg/driverutil/disk.go:78-95`). That split only works for a driver that attaches `filenames.ISO`, which vz (`pkg/driver/vz/vm_darwin.go:549`) and qemu do and hcs does not: `buildVMConfig` gets `filenames.CIDataISO` alone (`pkg/driver/hcs/hcs_driver_windows.go:230`). The removed `mayConvertQcow2ToVHDX` saw `DetectFormat` report an ISO as `raw` and converted its bytes into the boot disk, so a hybrid ISO booted. `validateConfig` rejects no ISO image, so the instance starts against 100 GiB of zeros.

I4. **`disk:` reaches a converted image and passes a `.vhdx` one by, under a comment promising otherwise** — `pkg/driverutil/disk.go:104` [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]

This PR makes hcs the first caller to pass `vhdx.Type`, and the comment stops being true for it: `prepareDisk` returns early for a VHDX disk (`pkg/instance/start.go:541-544`), so the rename branch never gets its resize. I5. **The `SupportedImageFormats` godoc says "can boot"; hcs lists two formats it cannot** — `pkg/driver/driver.go:158` [Claude Opus 5, Codex GPT 5.6 Sol]

## Suggestions

S1. **The "Skip resizing" warning now fires on a disk that is already the right size** — `pkg/instance/start.go:541` [Claude Opus 5]

```go
	if img.Type() == vhdx.Type {
		logrus.Warn("Skip resizing the instance because go-qcow2reader cannot read vhdx type image")
		return nil
	}
```

Before this PR the warning told the user something true: the hcs disk had the image's virtual size and `disk:` had been ignored. Now the converted path sets the size at creation, so a correctly sized instance prints a warning about a skipped resize on every start. The PR description's own boot log shows it. The wording is off besides, since go-qcow2reader does open the image; it reports `Size() == -1` for the VHDX stub.

Fix: make it `logrus.Debug` and say what actually happened, e.g. "Skipping the disk size check: a VHDX records its virtual size when the disk is created."

S2. **A converted disk keeps mode 0600 while every sibling path sets 0644** — `pkg/imgutil/nativeimgutil/nativeimgutil.go:195` [Gemini 3.1 Pro]

```go
	return os.Rename(destTmp, dest)
```

`destTmp` comes from `os.CreateTemp`, which creates with 0600, and nothing widens it. `convertRawToRaw` and `EnsureDisk`'s rename branch both chmod to 0644. I measured the difference on the two paths: `convertTo(vhdx)` produces `-rw-------`, `convertTo(raw)` from a raw source produces `-rw-r--r--`. Go maps only the 0200 bit to `FILE_ATTRIBUTE_READONLY` on Windows (`syscall_windows.go:401`), so hcs is unaffected and this is consistency rather than a defect on the platform this PR touches.

Fix: chmod `dest` to 0644 after the rename, matching the neighboring paths.

S3. **An image larger than `disk:` now aborts `limactl start`** — `pkg/imgutil/nativeimgutil/nativeimgutil.go:60` [Claude Opus 5]

```go
	if size != nil && *size < srcImg.Size() {
		return fmt.Errorf("specified size %d is smaller than the original image size (%d) of %#q", *size, srcImg.Size(), source)
	}
```

`EnsureDisk` passes `disk:` into the conversion, so an image whose virtual size exceeds it fails the start. `qemu-img convert -O vhdx` ignored the size and always succeeded. The failure is loud and names both numbers, and qemu, vz and krunkit already behave this way, so this is hcs catching up with the other drivers.

Fix: mention it in the hcs "Disk images" docs so the error is expected.

S4. **The `// Copy` comment now labels the writer selection** — `pkg/imgutil/nativeimgutil/nativeimgutil.go:126` [Claude Opus 5]

```go

	var (
		wa     io.WriterAt = destTmpF

```

The block under the comment chooses a destination writer; the copy is 30 lines further down at the `convert.Convert` call.

Fix: move `// Copy` down to sit above the progress bar and `convert.Convert`, and label this block for what it does.

S5. **`convertTo` cannot honor its own "NOP if source == dest" contract for VHDX** — `pkg/imgutil/nativeimgutil/nativeimgutil.go:47` [Codex GPT 5.6 Sol]

```go
// convertTo converts a source disk into a raw, ASIF, or VHDX disk.
// source and dest may be same.
// convertTo is a NOP if source == dest, and no resizing is needed.
```

The doc comment was widened to cover VHDX, but a VHDX source reaches the `default` branch and fails `srcImg.Readable()`, because go-qcow2reader exposes VHDX as a stub. I confirmed the shape: `convertTo(vhdx.Type, disk, disk, nil, false)` returns `unimplemented type: "vhdx"` and leaves the disk untouched. `EnsureDisk` renames a matching format before reaching here, so only a direct caller can hit it.

Fix: return early when `source == dest`, `size == nil`, and `srcImg.Type() == destType`.

S6. **A failed `execFsutil` is never retried** — `pkg/driver/hcs/hcs_driver_windows.go:385` [Claude Opus 5]

```go
	if !diskExisted {
		if err := execFsutil(ctx, disk); err != nil {
			return fmt.Errorf("failed to clear the sparse flag on %#q: %w", disk, err)
		}
	}
```

If `fsutil` fails because the shell is not elevated, `CreateDisk` returns an error with `disk` already written. The next start sees the disk exist, skips the clear, and boots against a disk the previous run called unusable. The merge-base had the same shape, so nothing regressed. Separately, `diskExisted` works only because `EnsureDisk` happens to no-op on an existing disk; if that changes, hcs stops clearing the flag with no compile error.

Fix: have `EnsureDisk` report whether it created the disk and drive `execFsutil` off that.

S7. **The hcs "Disk images" docs no longer describe what conversion does** — `website/content/en/docs/config/vmtype/hcs.md:47` [Claude Opus 5, Codex GPT 5.6 Sol]

```markdown
- If the image is not a `.vhdx` (for example `.qcow2`), Lima automatically converts it to `.vhdx` natively.
```

Removing the `qemu-img` sentences was right, but the replacement now understates and overstates at once. It omits that the converted disk takes the configured `disk:` size while a `.vhdx` image does not (I4), and it promises native conversion for formats the native reader rejects: zstd qcow2 (I1) and VMDK, which still needs `qemu-img` normalization.

Fix: name the formats the native path reads, say that anything else still goes through `qemu-img`, and state the `disk:` behavior for each case.

## Design Observations

### Concerns

- **`EnsureDisk` assumes its caller attaches the ISO** *(in-scope)* [Codex GPT 5.6 Sol] — the ISO branch splits the image into `iso` plus an empty disk for every caller, with nothing checking that the driver consumes `filenames.ISO`. Making ISO handling an explicit driver capability, or keeping it in the drivers whose VM config reads that file, forecloses I2 rather than patching it.
- **`SupportedImageFormats` carries two meanings** *(future)* [Claude Opus 5, Codex GPT 5.6 Sol] — boot capability and download-normalization hint. Splitting them, or letting a driver declare the format it wants the image normalized to, removes the coupling behind both I1 and I5.
- **`convertTo` branches on `destType` in three places** *(future)* [Claude Opus 5] — temp-file creation, writer selection, and the resize skip, with nothing tying them together. A fourth format has to touch all three and nothing catches a missed one.

## Review Process Notes

**Skill improvements**

- When the prompt directs agents to read a dependency's source in the module cache or any path outside their worktree, state that a sandboxed agent may be refused there and tell it to say so rather than proceed without the source. An agent that silently loses its reference material reviews the calling code against an assumed API.
- Before accepting a reviewer's reproducer, check that the assertion in its `repro` block and the failure in its `repro-output` block describe the same outcome. A block asserting the value the code actually produces, paired with output claiming that assertion failed, is fabricated output, and the mismatch is visible without running anything.
- When a finding rests on a file permission, a mode bit, or a similar POSIX attribute, check what the attribute means on the platform the changed code runs on before assigning severity. Go's Windows layer maps only the owner-write bit, so a mode difference that matters on Linux can be inert in a Windows-only driver.

**Repo context updates**

- `[repo]` `pkg/driver.DriverFeatures.SupportedImageFormats` has exactly one consumer: `pkg/instance/start.go` passes it to the downloader, which converts a downloaded image to raw in the cache when its format is absent from the list. A driver therefore lists a format both to declare it bootable and to suppress that conversion. When reviewing a change to this field, check which of the two the author intends.
- `[repo]` `proxyimgutil.Convert` tries `qemu-img` first only for a raw target; every other target goes straight to the native converter with no fallback. A change that makes a driver request a non-raw format therefore removes `qemu-img` as a safety net for every image feature the native reader does not implement, such as zstd-compressed qcow2 and VMDK.
- `[repo]` `driverutil.EnsureDisk` renames an ISO instance image to `iso` and creates an empty data disk. That split is correct only for a driver whose VM configuration attaches `filenames.ISO`. When a driver adopts `EnsureDisk`, check its VM config for that attachment.
- `[repo]` `go-qcow2reader` exposes VHDX through a stub: `qcow2reader.Open` detects the type and `Size()` returns -1, so any code that reads a size or converts from a VHDX source fails with `unimplemented type`. Treat a VHDX disk as write-only from Lima's side.
