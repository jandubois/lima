Executive Summary ¶

The privilege boundary holds: no agent found a path from the sudo helper to an arbitrary root-readable file, and the layered defenses around the open are sound. The blocking problem sits outside that boundary. Making VZ file-descriptor retention per-VM dropped retention for the exported PassFDToUnix, whose only caller is krunkit — reintroducing the garbage-collector-closes-live-fd bug the deleted package global existed to prevent. Seven integration gaps follow, none of them challenging the design.

Three reviewers ran one pass each. The findings below group into three themes: the fd-retention regression (C1), sudoers verification and setup (I2, I3, I4, S1), and configuration reach — which builds, install locations, and YAML layers the feature actually works from (I1, I5, I6). Every finding was verified against the worktree at the review SHA before it was kept; two agent claims survived as findings but needed their reasoning corrected, and both corrections are recorded inline.

Design Observations ¶

Concerns ¶

Device-number grants are neither stable nor time-bounded (future) Claude

macOSDiskDevicePathRE pins the sudoers grant to a path like /dev/disk4, and openDiskDeviceNoFollow opens it O_RDWR. macOS assigns diskN by attach order, so a grant issued for a USB stick becomes a standing root read-write grant for whatever device lands on that slot after the next reboot or replug. Nothing in the sudoers file, the docs, or the code re-confirms the binding. The grant names a slot, not a device.

Worth evaluating: record the disk's UUID at grant time and have the helper verify it after opening, rejecting a mismatch. That also forecloses a --block-device=/dev/disk0 grant surviving as a permanent boot-disk handle. Relatedly, the helper always opens O_RDWR, so a read-only attachment cannot be expressed even though the VZ attachment constructor takes a readOnly argument.

Verification is split across two packages that each own half the file (in-scope) Claude

I2 and I4 are one problem seen from two sides: pkg/networks verifies its fragment, pkg/blockdevice renders another, and neither checks the whole. The composition already lives in cmd/limactl via renderSudoers. Moving verification there — one function that renders the expected file and compares it exactly, called by both --check and network startup — collapses both findings.

Strengths ¶

  • Argv pinning is the right primitive (in-scope) Claude Codex. The allowed device arrives as argv, so sudo's own command matching becomes the allowlist and the policy lives in the file the admin reviewed. validateForAllowedDevice is a second check, not the gate.
  • The open path closes its TOCTOU window rather than papering over it (in-scope) Claude Gemini. Lstat and symlink rejection, then O_NOFOLLOW, then a post-open Stat, then a block/char cross-check — each layer is independently justified.
  • F_DUPFD_CLOEXEC on the root-opened fd (in-scope) Claude keeps the descriptor out of later child processes. Most implementations miss this.
  • Requiring SUDO_UID and validating the socket directory against it (in-scope) Claude Gemini means the helper cannot be coaxed into delivering the fd into a directory the sudo-invoking user does not own.
  • Per-VM fd retention removes a real cross-VM hazard (in-scope) Codex Gemini. The direction is right; C1 is a gap in its execution, not an argument against it.

Testing Assessment ¶

Coverage is unusually strong for a security change: 23 new Go tests plus a real end-to-end BATS roundtrip. hack/bats/extras/vz-block-device.bats is the highlight — a real ramdisk, real GPT/exFAT, and a real guest-to-host-to-guest write across a stop/start, with no mocks anywhere in the suite. The regression tests the author added in response to earlier review (real yq evaluation for missing/null blockDevices, the sudoers hint parenthesis assertion, context-cancellation, close-on-exec) each pin a bug that previously escaped.

The gaps cluster where the tests assert the new property but not the one it replaced:

  1. Exported-wrapper fd retention (C1). TestRetainedFileDescriptorsArePerVM proves the new per-VM property; nothing asserts that PassFDToUnix still retains, which is exactly what regressed. A test that calls the exported wrapper, forces a GC, and checks the fd is still valid would have caught it.
  2. validateSecurePath recursion (I6). The element check is tested in isolation; the recursion refusing a user-owned ancestor or a symlinked exe is not — the two cases every Homebrew user hits.
  3. blockDevices layer merging (I1). No test covers override or default inheritance, which is why the missing FillDefault line went unnoticed.
  4. sudoers --check against a file installed with --block-device (I2). The hint's formatting is asserted; that following the hint preserves the grant is not.
  5. VerifySudoAccess containment (I4). A test asserts the new permissiveness; nothing pins what it must still reject.
  6. Full Open() handoff. Request rejection and peer checks are covered separately, but no test drives listener to dial to nonce to SCM_RIGHTS to validateDiskDeviceFile as one unit.

Acknowledged Limitations ¶

  • Documented data-corruption risk. disk.md:144 warns that mounting a shared block-device filesystem on host and guest simultaneously can corrupt data, and the BATS test encodes the stop/remount handoff it requires. The feature exposes this by design; the limitation is documented and tested.
  • Deliberate non-blocking drain. The comment at pkg/blockdevice/block_device_darwin.go:556-557 explains why the code does not wait for a helper response after sudo fails. The handling is correct, though S1 makes this path the common one.
  • Guest device naming. The comment at pkg/driver/vz/block_device_darwin.go:69-71 correctly notes the identifier does not pin a guest /dev node; the 20-character truncation is a VZ API limit.

Review Process Notes ¶

Skill improvements ¶

  • Treat a deleted comment as a claim. When a diff removes a comment documenting a non-obvious invariant — why a reference is held, why an order is fixed, why a check exists — treat the deletion as an implicit assertion that the invariant no longer applies, and verify that assertion against the code the comment guarded. Comments of this kind are often the only record of a constraint the type system does not encode, so their removal alongside a refactor signals that the refactor may have dropped the constraint rather than obviated it.
  • Check what each call site passes when a behavior becomes conditional. When a change converts an unconditional behavior into a conditional one — adding a nil guard, an opt-in parameter, or a feature flag — enumerate every call site and confirm what each one now supplies. Refactors commonly thread the new parameter through the call sites inside the diff while leaving exported wrappers passing a zero value, which silently removes the behavior for every caller outside it. The wrapper looks innocuous in review because its body is one line; the behavior change lives in the argument.

Repo context updates ¶

  • [repo] The vz driver exports helpers that krunkit calls. pkg/driver/vz exports PassFDToUnix and DialQemu, which pkg/driver/krunkit calls. A change to vz internals can therefore break krunkit without any krunkit file appearing in the diff. When reviewing changes to exported functions in pkg/driver/vz, enumerate callers under pkg/driver/krunkit and confirm each still receives the prior behavior.
  • [repo] The vz driver has an external-binary build mode. ADDITIONAL_DRIVERS=vz sets the external_vz build tag, which excludes pkg/driver/vz/register.go from limactl and runs the driver inside lima-driver-vz instead. Any vz code that depends on os.Executable(), or on a command registered only under cmd/limactl, behaves differently in that build. Features added to the vz driver should state whether they support it, and the other backends' explicit rejection stubs are the convention to follow when they do not.
  • [repo] Instance directories are created with mode 0700. pkg/instance/create.go creates inst.Dir with 0o700. Code requiring a private directory beneath inst.Dir — for example a Unix socket whose parent must not be group- or world-accessible — is satisfied by construction. Do not flag such a requirement as a setup step the user must perform.
