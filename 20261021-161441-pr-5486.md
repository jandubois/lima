## Suggestions

S1. **`limactl stop -f` and `delete -f` can leave the network up and blame another `LIMA_HOME`** — `pkg/networks/reconcile/reconcile.go:293-296` [Claude Opus 5.5, Codex GPT 6 Astra]

```go
		b, err := os.ReadFile(filepath.Join("/sys/class/net", e.Name(), "carrier"))
		if err == nil && strings.TrimSpace(string(b)) == "1" {
			return true
		}
```

`StopForcibly` (`pkg/instance/stop.go:110-166`) sends SIGKILL, deletes the instance's PID files and returns without waiting, and both commands then reconcile immediately. The kernel frees a dying process's memory before it closes its files (`exit_mm` before `exit_files` in `do_exit`), so with a large guest the tap can still report carrier 1 here. The helper then keeps running as root, with its NAT rules and dnsmasq, until the next lifecycle command, and the log says an instance outside this `LIMA_HOME` holds the network. ## Design Observations

### Concerns

- **A starting instance's tap is not in use until QEMU opens it** (future) [Gemini 3.1 Pro, Claude Opus 5.5, Codex GPT 6 Astra]: `ensureTaps` creates the tap before the hostagent starts QEMU, and a new tap has no carrier. A concurrent last stop in another `LIMA_HOME`, or in this one before the starting instance counts as running, tears the network down and deletes the tap, and QEMU then fails to open it. The failure is loud, and it is round 1's unserialized-`Reconcile` concern; a host-wide lock in `varRun` around start and stop would close both. Counting every tap as in use would keep a network up forever, because taps outlive their instances.
- **`stopNetwork` still waits only 5 s** (future) [Claude Opus 5.5, Codex GPT 6 Astra]: with the PID file removed last, a teardown whose `firewall-cmd` calls run past 5 s still overlaps a following start. CI exercises only the iptables branch, so nothing has measured it.
- **macOS keeps the cross-`LIMA_HOME` stop** (future) [Claude Opus 5.5]: the guard covers `lima-privileged-net` only, so on macOS one `LIMA_HOME` stopping its last instance still stops socket_vmnet under another's.

### Strengths

- **Tap identity agrees across processes** (in-scope) [Claude Opus 5.5, Codex GPT 6 Astra]: limactl and the hostagent both take the directory from `store.Inspect`, `LimaDir` resolves symlinks for both, and 100,000 generated IDs all pass `identifiers.Validate`.
- **The guard does not need sudo** (in-scope) [Claude Opus 5.5]: it runs before `validateConfig`, so a `LIMA_HOME` that leaves a network alone never calls sudo.
- **The PID file goes last** (in-scope) [Codex GPT 6 Astra, Claude Opus 5.5]: `stopNetwork` now waits for the teardown, and an error from `down()` does not stop the removal.

### Repo context updates

- [repo] On GitHub's hosted Ubuntu runners, Docker sets the iptables FORWARD policy to DROP, and the cloud network drops a reply addressed to an unmasqueraded private source. A negative connectivity test there ("guest X cannot reach Y") therefore passes whatever the firewall rules under test say. Flag such a check unless it excludes the reconciling `LIMA_HOME`'s own instances.

##### Design Observations

**Concerns**

- **(future) Start-up window across `LIMA_HOME`s and users.** `bridgeInUse` treats a tap as in use only once QEMU holds it open. ###### Executive Summary

The implementation correctly isolates the network lifecycle and handles daemon supervision cleanly. However, the condition used to determine if a bridge is idle (`carrier == 1`) introduces a TOCTOU race that aborts concurrent instance startups. ###### Critical Issues

None.

###### Important Issues

**I1. TOCTOU race in bridgeInUse aborts concurrent instance startups** — `pkg/networks/reconcile/reconcile.go:293-295`

```go
		b, err := os.ReadFile(filepath.Join("/sys/class/net", e.Name(), "carrier"))
		if err == nil && strings.TrimSpace(string(b)) == "1" {
			return true
		}
```

`bridgeInUse` relies on `carrier == 1` to prevent `stopNetwork` from tearing down a network that is currently in use. However, a newly created tap has a carrier of `0` until QEMU opens it. If an instance is stopped concurrently (either in the same `LIMA_HOME` or a different one) while a new instance is still starting, `Reconcile` will evaluate `bridgeInUse` as `false` and tear down the network. The `lima-privileged-net` daemon shuts down and deletes all taps, causing the starting instance's QEMU to crash with a missing tap device.

Fix: The race is inherent to using carrier as a proxy for "in use". If distinguishing leaked taps from new ones is impossible without breaking this, consider making `bridgeInUse` return true if *any* tap exists (accepting that leaked taps delay network teardown until the host reboots), or retry tap creation in the hostagent.

**I2. Masked failure in BATS host network isolation tests** — `hack/bats/extras/network-shared-host.bats:86-92`

```bash
@test 'the host network cannot reach the outside world through the host' {
    local ip
    ip=$(limactl shell "$HOST" getent ahostsv4 github.com | awk 'NR==1 {print $1}')
    # The host network advertises no router, so route explicitly; the running shared network has enabled ip_forward.
    limactl shell "$HOST" sudo ip route replace "${ip}/32" via 192.168.106.1 dev lima0
    run ! limactl shell "$HOST" curl -sSf --max-time 10 --interface lima0 --resolve "github.com:443:${ip}" -o /dev/null https://github.com
}
```

The BATS tests verify `lima-host` network isolation by checking that `ping` and `curl` fail to reach the outside network. However, on the CI runner (`ubuntu-24.04`), Docker is installed and sets the host's `FORWARD` policy to `DROP`. Because `host` networks only insert `REJECT` rules and no `ACCEPT` rules, the traffic simply falls through to the `DROP` policy. Consequently, the tests will pass and hide the regression even if the `REJECT` rules are broken or accidentally removed.

Fix: Add a positive check to ensure the `REJECT` rules are actually present during the test, similar to how the teardown explicitly verifies their removal.
```diff
     limactl shell "$HOST" sudo ip route replace "${ip}/32" via 192.168.106.1 dev lima0
+    sudo iptables -C FORWARD -i lima-host -j REJECT
     run ! limactl shell "$HOST" curl -sSf --max-time 10 --interface lima0 --resolve "github.com:443:${ip}" -o /dev/null https://github.com
```

###### Concerns

- **Single daemon shared across multiple `LIMA_HOME`s without start serialization** `(future)`:
  The bridge `lima-<network>` and PID file `/run/lima/<network>_lima-privileged-net.pid` are host-global. While `bridgeInUse` successfully prevents one `LIMA_HOME` from terminating a bridge actively used by another, concurrent `limactl start` commands in separate `LIMA_HOME`s could simultaneously attempt to launch the daemon or create the bridge. Introducing a filesystem lock in `/run/lima/` during startup could eliminate potential start races.
- **`test-templates.sh` in the `vmnet` matrix does not execute network tests** `(in-scope)`:
  In `.github/workflows/test.yml:578`, the step "Test shared network with templates/default.yaml" passes `--network=lima:shared` via `LIMACTL_CREATE_ARGS`. However, `test-templates.sh` parses `.networks[].lima` exclusively from the template file itself, skipping `CHECKS["vmnet"]`. While it functions as a boot smoke test, creating a small test template that defines `networks: [{lima: shared}]` would allow `test-templates.sh` to actually execute its iperf3 and network assertions.

###### Strengths

- **Unprivileged QEMU attachment via persistent TAP devices**: Delegating device creation to `lima-privileged-net tap`, which assigns device ownership to the invoking `SUDO_UID` and attaches it to the bridge, allows QEMU to run completely unprivileged (`script=no,downscript=no`).
- **Reliable bridge protection with `bridgeInUse`**: Using sysfs `/sys/class/net/<bridge>/brif` and inspecting the carrier status of Lima-owned tap devices provides a kernel-backed check that prevents stopping network daemons while any guest holds an open tap descriptor.
- **Hardened sudoers rules with Digest_Spec**: Using sha256 digests in sudoers rules prevents execution of modified binaries, and strict argument pinning with `--` prevents flag injection through the instance identifier wildcard.
