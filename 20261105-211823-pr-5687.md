## Executive Summary

All ten round-1 findings are fixed, and the fixes hold. Real OpenSSH 10.3 refuses a key of another type under every option set, so dropping `HostKeyAlgorithms` did not open a downgrade. Two new failures remain. A guest pinned on RSA fails to start once it gains an ed25519 key, because the scan prefers ed25519 over the pinned type; a patch below fixes that. ## Important Issues

I1. **A guest pinned on RSA or ECDSA fails to start once it gains an ed25519 key** — `pkg/sshutil/hostkey.go:104-111` [Codex GPT 6 Astra, Claude Opus 5.5]

```go

	if err != nil {
		return fmt.Errorf("failed to get the SSH host key of the guest: %w", err)
	}
	pinned, err := ReadPinnedHostKey(instDir)
	if err != nil {
		return err
	}
```

`PinHostKey` scans before it reads the pin, and `ScanHostKey` offers ed25519 first (lines 145-149). Round 1's I2 fix lets a guest without an ed25519 key pin its RSA or ECDSA key. If that guest later generates an ed25519 key, as an image leaving FIPS mode can, the scan returns the new key, and line 116 reports `ErrHostKeyMismatch`. But the guest still has the pinned key, and `ssh` with `HostKeyOpts` accepts it, since OpenSSH offers the pinned type first. The start retries for ten minutes and fails, with a warning that calls the key changed. Round 1's I2 fix accepted this failure and pointed to the documented recovery, but no key changed.

```go

			ErrHostKeyMismatch, ssh.FingerprintSHA256(hostKey), filepath.Join(instDir, filenames.SSHKnownHosts), ssh.FingerprintSHA256(pinned))
```

Lima changes the instance-id on every boot (`pkg/cidata/cidata.go:210`), and cloud-init regenerates the host keys for each new one unless `99_lima_ssh_keep_host_keys.cfg` is already on the guest's disk. A snapshot taken under an older Lima lacks that file. So after `limactl snapshot apply`, the next boot regenerates the keys, and the start fails against the key pinned since the upgrade. The warning tells the user to remove the file if the key "was changed intentionally", which a snapshot user may not take as their case. `limactl snapshot` is experimental, and only qemu and krunkit implement apply.

## Design Observations

### Concerns

- **Two round-1 design questions are still open** (in-scope) [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]: the author deferred an opt-out for guests that change their key on every boot ("not added for now"), and keeps pinning over `ip_unprivileged_port_start` because pinning also covers macOS and Windows guests and stale endpoints. No other maintainer has ruled on either.
- **`limactl snapshot apply` could re-pin** (future) [Claude Opus 5.5]: removing `ssh.known_hosts` on apply would avoid I2 for every snapshot, but Lima would then trust the next boot's key after any apply. That choice belongs to the maintainers.

### Strengths

- **A key of another type is refused under every option set** (in-scope) [Codex GPT 6 Astra, Claude Opus 5.5, Gemini 3.5 Flash]: real OpenSSH 10.3p1 refused an RSA impostor at an ed25519-pinned address under `StrictHostKeyChecking=yes`, and under `accept-new` with `/dev/null` first, as a changed key. A server holding the pinned key connected under both. Win32-OpenSSH was not measured.
- **The persistence script's new position leaves other guests alone** (in-scope) [Codex GPT 6 Astra, Claude Opus 5.5]: it exits at once unless the root is a tmpfs on Alpine, and the `boot.Linux/00-*` scripts that now run after it do not write under `/etc` on Alpine.

## Acknowledged Limitations

- **First boot trusts the guest.** The author chose this after moving key generation into the guest, because the ISO is readable by non-root users in some guests.
- **Localhost is verified on purpose.** A PR comment proposed checking only other hosts, and the author declined.
- **A mismatch retries by design.** `pkg/hostagent/requirements.go:173-174` states why, and the warning prints once.
- **A non-plain `alpine-iso` restart keeps its key.** Do not re-suggest restarting `sshd` in the persistence script.
- **`ssh.md`'s example does not need more options.** Do not re-suggest `HostKeyAlgorithms` or `StrictHostKeyChecking` there.

## Review Process Notes

### Skill improvements

- When a change makes the host keep a record of guest state (a pinned key, a cached digest, a recorded identifier), ask agents to walk every operation that rewinds or replaces that state from outside the guest: snapshot apply, clone, factory reset, disk replacement and downgrade. A diff review checks the record against the guest's normal lifecycle, and the operations that restore older guest state sit in files the diff never touches.

### Repo context updates

- Lima changes the cloud-init instance-id on every boot (`pkg/cidata/cidata.go`), so cloud-init's per-instance modules run on every boot, and guest state they would regenerate survives only if the guest's own disk opts out before the boot starts. `limactl snapshot apply` (qemu and krunkit) restores the whole disk, opt-out files included. Check any host-side record of guest state against snapshot apply, clone and factory reset. Factory reset deletes every instance file except the YAML, `lima-version`, `protected` and the vz identifier, and clone copies everything except `protected` and the TPM state.
