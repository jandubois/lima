## Suggestions

S1. **The new docstring lines describe a path form sshocker rewrites before either consumer sees it** — `pkg/sshutil/sshutil.go:222-223` [Claude Opus 5]

```go
// Tools outside that family read the result too: a locally spawned sftp-server
// chdirs into it, and the guest's sshfs prefixes it to every request.
```

sshocker v0.3.11 (`go.mod:10`, bumped from v0.3.9 on master between rounds) added `convertMSYS2Path`, which `reversesshfs.Start` applies to any `path.IsAbs` `LocalPath`. So on the Cygwin branch `/c/Users/jan` becomes `C:\Users\jan` before the sftp-server's `-d` and the guest's sshfs argument. The Windows QEMU job for this SHA logs both halves: `Accepting "/c/Users/runneradmin" Unix path` then `Converted path for native Windows OpenSSH: "C:\\Users\\runneradmin"`. The native branch is untouched, since `C:/Users/jan` fails `path.IsAbs`.

`mountPathAndSftpServer`'s comment at `pkg/hostagent/mount.go:24-27` claims the same agreement and needs the same qualification.

Fix: say that on Windows sshocker rewrites a `/c/...` result to `C:\...` before handing it on.

S2. **The Infof names sshocker, the mention the reviewer asked to drop** — `pkg/hostagent/mount.go:38` [Claude Opus 5]

```go
		logrus.Infof("reverse-sshfs: no sftp-server in the toolchain of %#q; leaving detection to sshocker, which may pick one that cannot resolve %#q", sshExe.Exe, resolvedLocation)
```

At `78b9ab7a` the mention lived in a code comment and the log read "falling back to auto-detection". The comment is gone, but the mention moved into output users see, which is more visible than the place @AkihiroSuda flagged. The Windows CI log for this SHA carries the full line. The message also overstates the risk on its commonest trigger, a plain host with the OpenSSH Client feature only, where sshocker finds nothing and falls back to the builtin driver, which handles `C:/...` correctly.

Fix: name the remedy instead of the dependency, for example "falling back to a generic search for one that can serve `%#q`".

S3. **The mount.md paragraph presents the same-toolchain guarantee unconditionally** — `website/content/en/docs/config/mount.md:65-66` [Codex GPT 5.6 Sol]

```markdown
This keeps the server and the host paths it serves on one toolchain, which matters when a Cygwin-based OpenSSH
(Git for Windows, MSYS2) and the native Windows OpenSSH are both installed.
```

Two conditions narrow that sentence. `mountPathAndSftpServer` returns early for `sftpDriver: builtin` (`pkg/hostagent/mount.go:33-35`), skipping the lookup entirely. And when the lookup finds nothing, `pkg/hostagent/mount.go:37-38` hands the choice back to the generic search, which may pick another toolchain. The preceding sentence does document the fallback, so only this sentence reads as an unconditional promise.

Fix: qualify it, for example "When the lookup finds one, the server and the host path it serves stay on one toolchain."

S4. **The Cygwin branch of `SftpServerForSSH` is the only branch CI runs, and it has no unit test** — `pkg/sshutil/sshutil.go:253-258` [Claude Opus 5]

```go
		candidate := strings.TrimSpace(string(out))
		sftpServer, err := exec.LookPath(candidate)
		if err != nil {
			logrus.WithError(err).Debugf("cannot use the sftp-server at %#q that cygpath resolved", candidate)
			return ""
		}
```

The `os.Stat` pair to `exec.LookPath` migration narrows what this branch accepts. Go's `findExecutable` skips the direct stat when the path has no extension (`lp_windows.go`), so an extension-less `sftp-server` that exists is now rejected, where the old loop returned it. Git for Windows ships `sftp-server.exe`, so the layout hides this today.

`mount_windows_test.go:20-21` says a fake directory cannot provide `cygpath.exe`. But the helper-process pattern can: copy `os.Executable()` to `<dir>\cygpath.exe` and have `TestMain` short-circuit on an env var.

Fix: add a Cygwin subtest to `TestSftpServerForSSH` covering an extension-less candidate and a missing one.

S5. **No test asserts that the resolved path reaches `LocalPath`** — `pkg/hostagent/mount.go:93` [Claude Opus 5]

```go
		LocalPath:               resolvedLocation,
```

`TestMountPathAndSftpServer` covers the computation, not the delivery. I checked whether a mis-wiring here compiles: replacing `resolvedLocation` with `m.Location` builds clean for `GOOS=windows`, because `resolvedLocation` still has readers at lines 112 through 127. The sibling field `OpensshSftpServerBinary` is safe by accident, since deleting it fails the build with `declared and not used: sftpServerBinary`.

The Windows QEMU integration job would probably catch a `LocalPath` mis-wiring, because `addQuotes` runs `strconv.Quote` and a backslash path reaches the guest with doubled separators.

Fix: extract the struct construction so a Windows test can assert both fields together.

S6. **`nativeToolchain` repeats `resolvedTempDir` without its rationale** — `pkg/hostagent/mount_windows_test.go:36` [Claude Opus 5]

```go
		dir := t.TempDir()
		resolved, err := filepath.EvalSymlinks(dir)
		assert.NilError(t, err)
```

`pkg/sshutil/sshutil_windows_test.go:155-159` carries the same three lines under a comment explaining why: on GitHub Windows runners `t.TempDir()` returns an 8.3 short path (`C:\Users\RUNNER~1\...`) that the production helpers expand, so a raw compare fails. The packages differ, so the helper cannot be shared. Without the comment, a future reader may take the `EvalSymlinks` call for ceremony and drop it, and the test then fails only on CI.

Fix: carry the one-line reason across, or point at `resolvedTempDir`.

## Design Observations

### Concerns

1. **The sshocker bump weakened the premise this PR argues from** *(in-scope)* [Claude Opus 5]. `convertMSYS2Path` maps `/c/...` to `C:\...`, so for the MSYS2 form any sftp-server now receives a native path, and the mismatch the pairing prevents cannot arise. The pairing still earns its place in two cases. Stock Cygwin's `cygpath` returns `/cygdrive/c/...`, which `convertMSYS2Path` leaves alone because its third byte is not a slash, so only a Cygwin sftp-server resolves it. And the native branch never reaches the conversion. So the change is still right, on narrower grounds than the commit message gives. See S1.

2. **The single-toolchain invariant stops short of the transport** *(future)* [Codex GPT 5.6 Sol, Claude Opus 5, Gemini 3.5 Flash]. sshocker's `SSHConfig.Binary()` is still a hardcoded `return "ssh"` in v0.3.11 (`pkg/ssh/ssh.go:22-24`), so PATH picks the ssh that carries the mount while Lima pins the path form and the sftp-server. Closing this needs an upstream field. Carried from round 1, re-verified against the new version.

3. **A pre-existing zero-value bug in the mount-point default** *(future)* [Claude Opus 5]. At `pkg/limayaml/defaults.go:732` the multi-assign leaves `mountLocation` empty when the conversion fails, and the code only warns, so `MountPoint` becomes `""` and sshocker's `Prepare` then rejects it as relative. A UNC location on a Windows host without `cygpath` reaches it. Outside this PR's files, and distinct from the known rule that this call site must keep the POSIX form.

4. **The Cygwin sftp-server probe is one hardcoded path** *(future)* [Claude Opus 5]. `pkg/sshutil/sshutil.go:245` asks cygpath for `/usr/lib/ssh/sftp-server`, and `mount.md:63` now names that as the Cygwin location. CI proves it for Git for Windows: the Windows QEMU job logged no "no sftp-server in the toolchain" line. Stock Cygwin's `libexecdir` is unverified.

### Strengths

- The native branch's forward-slash form avoids an sshocker quirk. `addQuotes` runs `strconv.Quote`, so `C:\Users\lima\shared` would reach the guest as `':C:\\Users\\lima\\shared'` with doubled separators, while `C:/Users/lima/shared` passes through clean *(in-scope)* [Claude Opus 5]
- Returning `""` rather than a candidate sshocker would reject turns a fatal mount failure into a fallback. `DetectDriver` runs `exec.LookPath` on an explicit binary and errors out, and the comment at `sshutil.go:249-252` states this correctly, including its scope to the default driver *(in-scope)* [Claude Opus 5, Gemini 3.1 Pro, Gemini 3.5 Flash]
- `mountPathAndSftpServer` handles every reachable driver value. Only `builtin` returns early; `""`, `openssh-sftp-server`, and any unrecognized string take the lookup path, which matches sshocker's own switch *(in-scope)* [Codex GPT 5.6 Sol, Claude Opus 5]
- Caching `sshExe` on `HostAgent` reuses the value `SSHOpts` and `writeSSHConfigFile` already received, so the mount path cannot drift from the SSH config *(in-scope)* [all four reviewers]

## Review Process Notes

### Skill improvements

- When a finding argues from a counterfactual edit ("deleting this line leaves the suite green", "this field could be removed and nothing would fail"), apply the edit in the lead worktree and run the build and the tests before accepting the finding. Compilers reject a large share of proposed silent regressions, and the experiment costs one build. Keep the finding only for the edits that compile, and say in the finding which edit you ran.

- When a round follows a rebase, diff the dependency manifest between the prior round's base and the current merge-base, then re-verify every prior-round conclusion that rested on a third-party library's behavior. A version bump on the base branch changes what a library does without touching a line of the diff, so a fact one round verified against the old version can be false in the next while the reviewed files look untouched. State the bumped dependencies in the prompt so agents re-read the new source instead of the version a prior round cited.

### Repo context updates

- [repo] UPDATE the "sshocker performs a hidden sftp-server path conversion on Windows" entry. Its description of the conversion is out of date. Since v0.3.11 sshocker does more than accept a Unix-form `LocalPath` with an "assuming Cygwin/msys2 OpenSSH" log line: `reversesshfs.Start` calls `convertMSYS2Path`, which rewrites `/c/Users/...` to `C:\Users\...` before both the local sftp-server's `-d` argument and the guest's sshfs base path. The rewrite fires only when the third byte is a slash, so stock Cygwin's `/cygdrive/c/...` and native `C:/...` forms pass through unchanged. The entry's conclusion still holds and should be kept: Lima's own conversion is not the last word on what the sftp-server receives. Check the entry's opening premise against master when applying, since it asserts that `pkg/hostagent/mount.go` leaves `ReverseSSHFS.OpensshSftpServerBinary` unset.
